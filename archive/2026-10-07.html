EvoOntology: A Self-Evolving Ontology Layer for Data Agents

2026-09-14 · arXiv (人民大学 ruc-datalab)
针对 data agent 的"agent-data gap"（异构数据在 agent 之外、agent 仅能通过通用工具访问列名/路径），提出 EvoOntology——一个自进化本体 MCP server，含 schema 层、content 层、tool 层，使 agent 能在运行时主动查询与交互本体。引入 builder agent 自主构建本体，以及一个自演化循环：通过 attribution-guided 类型编辑提案，仅在 backbone-conditional 配对评估通过后才接受。在三个主流 data-agent benchmark、四个 LLM 上持续超越强基线与现有 semantic-layer 方案。代码开源于 ruc-datalab/EvoOntology。
🔍 技术视角：这是本周最贴合用户课题的论文。它直接回应"语义层 vs 企业知识图谱"两条路线之争，给出第三条：可演化的本体层。关键洞察有三：(1) 手写语义层不 scale、直接探索原始数据不可靠——本体必须是 agent 可查询的活跃层而非静态注入 prompt；(2) 自演化用 attribution-guided edit + paired eval，本质是"每个本体变更都要证明自己比旧版本好才接受"，这正是用户业务术语频繁变更场景需要的可控演化；(3) MCP server 形态意味着本体层是独立服务，可被多 agent/多场景复用。对用户"上百字段宽表 API"场景：本体层可封装宽表字段语义+取值约束+调用顺序，builder agent 可从 API 调用日志自动归纳字段语义，避免人工逐字段标注。

📊 架构示意

🎯 为什么值得关注

用户转型"AI for 业务"的核心难题就是让 AI 懂业务语义。EvoOntology 把"业务语义"从静态文档变成 agent 可查询、可演化的活跃层，且用 MCP 标准化——这是从"知识库"走向"知识服务"的关键一步。它同时是用户"语义层 vs 知识图谱"双路线研究的第三选项。

⚙️ 核心机制

三层 MCP server：schema 层（列名/路径/类型/约束）、content 层（值域/枚举/示例）、tool 层（查询/编辑/验证接口）。Builder agent 自主探索数据源构建初始本体。自演化循环：agent 调用失败时 attribution 引擎定位归因→提议类型化编辑（加约束/改描述/补示例）→在两个 backbone 上配对评估（同一任务两版本对比）→通过才接受。这保证编辑不破坏既有能力。

🧠 深度解读

核心创新在于"自演化的可控性"。很多系统怕自动修改知识库会引入错误，EvoOntology 的解法是 backbone-conditional paired evaluation——用不同模型交叉验证一个本体编辑是否真有改善，相当于"本体编辑的回归测试"。这与 9/5 记录的 EvoSafeHarness（fresh-context 对抗审查拒绝过拟合）思路同源：变更必须经对抗验证。对用户业务场景，这意味着业务术语/字段语义的演化可以安全自动化，不必每次人工评审。注意它仍是 benchmark 验证，生产环境的"本体演化失控"风险（漂移、冲突、死代码）需额外治理。

💼 商业启示

把业务语义维护从"DBA/数据团队手工写文档"变成"agent 使用中自动沉淀+可控演化"，直接降低 AI for 业务的运营成本，是让业务团队而非技术团队成为语义owner的产品化路径。

🛠️ 落地建议

立即可借鉴：(1) 用 MCP server 形态封装业务 API 的字段语义+取值约束+调用契约，而非写进 prompt；(2) 实现 attribution-guided 编辑——agent 调用失败时自动归因到缺失/错误的字段语义并提议修正；(3) 配对评估用两个不同模型交叉验证本体编辑有效性。先在 1-2 个高频宽表 API 上试点 builder agent 自动归纳字段语义，人工抽检接受率。

⚠️ 局限与风险

benchmark 验证非生产验证；自演化在长周期可能积累冲突/冗余本体项，需配 garbage collection；backbone-conditional eval 假设有≥2 个可用 backbone，对小团队有成本；宽表 API 字段间隐式依赖（如字段A取值依赖字段B）当前本体模型未必能表达。

EIO-Agents: The Missing Semantic Layer for AI Agent Evaluation

2026-10-06 · arXiv
指出 AI agent 评估缺乏共享语义标准：分数/trace/judge 输出被用来证明 readiness，却不说明证据支持什么声明、能确立什么、如何导向决策。提出 EIO-Agents 开放规范，两层：Evaluation Intelligence Ontology (EIO) 提供 typed evidence、versioned behavioral predicates、evidence contracts、claims、witness rules、proof status、可计算 metrics/findings/controls + PASS/REVIEW/BLOCK 决策；Portable Evaluation Record (PER) 是 content-addressed 的可重导出/可解释/可验证评估记录系统。
🔍 技术视角：这篇把"语义层"概念从"数据查询"扩展到"评估可信度"，对用户业务 agent 的"业务数据可信度验证"方向是范式补充。核心论点：分数只是摘要、jury 只是解释、trace 只是记录——都不定义证据的含义与证明力。EIO 用 ontology 给评估证据本身一个语义契约。对用户"上百字段宽表 API 查数后做分析"场景：agent 返回的数据对不对、能不能据此做业务决策，需要一个可审计的证据-决策链，而非一个置信度分数。

📊 架构示意

🎯 为什么值得关注

用户课题第三方向明确含"业务数据可信度验证"。当前普遍做法是看 agent 自报置信度或 LLM-as-Judge，但二者都无法回答"这个结论基于哪些证据、证据能证明什么、 limitations 是什么"。EIO 提供缺失的语义契约层。

⚙️ 核心机制

EIO 层：typed evidence（证据有类型）+ versioned behavioral predicates（行为谓词可版本化）+ evidence contracts（证据契约：声明证据能/不能支持什么）+ claims + witness rules（证人规则：何种证据组合可作证一 claim）+ proof status + recurrence + 可计算 metrics/findings/controls + PASS/REVIEW/BLOCK 决策。PER 层：content-addressed（内容寻址，防篡改）+ 可重导出 + 可解释 + 可验证。

🧠 深度解读

关键创新是"证据契约"与"proof status"。传统评估默认"分数高=可信"，EIO 强制声明"这份证据只能证明X不能证明Y"，并用 proof status 显式标注已证/未证/矛盾。这对业务 agent 的高杠杆决策（如封号、调价、放款）是必要的：必须能说"我们基于这N条证据得出了这个决策，证据的边界是这些"。content-addressed PER 让评估本身可被独立第三方重算验证。局限：规范尚新，缺乏生产采用数据；实施成本在于要为每个业务域定义 behavioral predicates 与 witness rules。

💼 商业启示

让"AI 辅助业务决策"从黑箱分数走向可审计证据链，是合规/风控/审计部门接受 AI 进业务流程的前提——这块标准化谁先做，谁就在"可信业务 agent"赛道占位。

🛠️ 落地建议

不必全套采用，可借鉴两件：(1) 给业务 agent 的每次数据查询结果附"证据契约"——声明数据来源API+字段+时间窗+已知局限；(2) 关键决策用 PASS/REVIEW/BLOCK 三态而非连续分数，REVIEW 自动升级人工。先在 1 个高风险业务流程试点。

⚠️ 局限与风险

开放规范非已落地产品；predicate/witness rule 设计高度领域化，初期工作量大；content-addressed PER 对现有 trace 系统是重构；引用待核实（Semantic Scholar 限流，10/6 新文预期0）。

Semantic Layer Induction from Raw Telemetry via Hierarchical LLM and RAG Abstraction

2026-09-17 · arXiv
端到端自动化从应用原始日志构建业务语义层。两阶段语义抽象：阶段一用 LLM 推理+行业特定知识识别高层业务特征；阶段二结构化管线（数据精炼+混合检索+多级过滤+语义聚类+canonical naming）导出细粒度业务节点。生产规模遥测评估：人工语义质量 50→80+/100，维护工作量降80%，过滤74%噪声，LLM-as-Judge Cohen's kappa 0.87。无需标注训练数据或人工规则工程。
🔍 技术视角：这是"业务语义层自动化构建"的直接解。用户课题第二方向（业务语义理解：语义层/指标平台/业务术语表）的核心痛点是语义层要人工维护、不 scale。此文证明可从原始数据自动诱导出业务语义层且质量可观（50→80）。对用户"不直连数据库、通过 API 查数"场景：API 返回的原始字段（尤其上百字段宽表）可视为"原始遥测"，同样适用此诱导管线产出字段语义+业务节点+canonical name。

📊 架构示意

🎯 为什么值得关注

语义层/指标平台的最大成本是人工维护字段语义与指标定义。此文给出无标注、无人工规则的自动诱导路径，且生产规模验证质量可达80分+维护降80%，直接对应用户"业务术语表自动化"诉求。

⚙️ 核心机制

两阶段：(1) LLM 推理+行业知识库识别高层业务特征（如"这是订单事件""这是支付事件"）；(2) 结构化管线——数据精炼清洗噪声→混合检索（稠密+稀疏）召回相关历史语义→多级过滤→语义聚类把同义字段归簇→canonical naming 产出规范名。LLM-as-Judge 做质量评估闭环。

🧠 深度解读

创新在"分层"与"无监督"。高层特征用 LLM 的领域知识（行业 ontology）做弱监督，细粒度节点用检索+聚类做无监督归纳，两者衔接避免纯 LLM 幻觉也避免纯统计无语义。canonical naming 解决"同义不同名"——这正是宽表 API 字段命名的典型混乱。Cohen's kappa 0.87 表明 LLM-as-Judge 在此任务上足够可靠做质量闭环。局限：评估是生产规模但单一遥测域，跨域泛化未证；canonical naming 对跨语言/跨业务线同名字段未必鲁棒。

💼 商业启示

把语义层/指标平台的构建从"数月人工"压缩到"自动化管线+少量人工复核"，是让语义层从"大企业专属"走向"中小团队可用"的成本拐点。

🛠️ 落地建议

直接迁移：把宽表 API 返回字段当"原始遥测"，跑两阶段管线——LLM+行业知识识别业务实体类型，检索+聚类把上百字段归并为canonical字段组并命名。先用 LLM-as-Judge 抽样评估质量再全量。维护降80%的数据可作 ROI 论证。

⚠️ 局限与风险

单一遥测域验证；LLM-as-Judge 自偏好风险（9/5 记录的 self-preference 共振）；canonical naming 对业务术语歧义（如"客户"在不同业务线含义不同）需人工复核；引用待核实（限流，9/17 新文预期0）。

From Benchmarks to Production: A Text-to-SQL System for Complex Financial Data (FLINT)

2026-10-02 · arXiv
通用 text-to-SQL 在 Spider/BIRD（浅 schema、人读列值）上强，但在生产金融库（概念存为不透明整数键而非人读字符串）跌至<50%，因简单查询也需多 join + 谓词引用不透明 ID。提出 FLINT：lookup agent 动态把自然语言概念解析为 reference table 约束、embedding 检索结构相似查询模板、FK 链遍历剪枝大 schema。在两个生产金融 schema 共359问上超越多个 SOTA（同 LLM）。已生产部署于金融数据检索服务。
🔍 技术视角：这是"benchmark→production"落差的硬数据。用户课题第三方向是"业务系统精确查询"，FLINT 证明通用方法在生产金融库直接腰斩，必须领域特化。三组件都直击用户痛点：lookup agent 解析业务术语→ID（宽表 API 字段值常是编码）；模板检索复用历史查询（API 调用模式重复性高）；FK 链 schema linking 剪枝上百字段。已生产部署意味着方案经得起真实流量。

📊 架构示意

🎯 为什么值得关注

Argo-Bench: Evaluating Data Agents on Enterprise-Scale Workflows

2026-10-01 · arXiv
210 个数据科学/分析任务，基于纽约市外卖平台模拟（8100万2024订单、真实经济/欺诈/激励模式）导出 ERP 仓库（235表/75亿行，Oracle E-Business Suite schema）。任务不止 text-to-SQL——agent 要封欺诈号、分配骑手激励预算、发补薪等后果型动作，grader 按模拟器后果评分。每任务有可执行参考解。14 个前沿/开源模型中，最强仅 34.8% 任务≥95分、均分59.5。

💼 商业启示

🛠️ 落地建议

(1) 用作自评标尺——把自己 agent 在 Argo-Bench 上跑分作为"企业级数据 agent"成熟度基线；(2) 借鉴后果型评分思想：业务 agent 的评测不应只看查数对错，要看下游业务后果；(3) 模拟器+ground-truth隔离模式可迁移到用户自己的业务域做内部 eval。

⚠️ 局限与风险

单一外卖域；Oracle E-Business Suite schema 特定；34.8% 可能随模型迭代改善；模拟器构建成本高；引用待核实（限流，10/1新文预期0）。
