Sentinel: Trajectory-Derived Confidence for Reliable, Resource-Aware Clinical Text-to-SQL Agents

2026-10-02 · arXiv 2610.04156
LLM agent 在临床 text-to-SQL 多步推理中无法自评可信度，高风险场景错误代价高昂且浪费计算。Sentinel 引入 trajectory-derived 分类器，在 agent 推理链三个点决策是否停止：运行前拒绝不可答问题(refuse)、运行中中止 doomed trajectory(halt)、交付时保留不可信答案(withhold)。基于 Chow's rule 在 EHRSQL Reliability Score（对错误答案按 utility 加权惩罚）下优化，低 stakes 下 +0.08→+0.24（vs 全拒 +0.03），交付准确率 54%→69% 覆盖率 84%→55%；高 stakes 下主动 abstain 到 +0.03 vs 未监控 -3.02。同时砍 13-28% 计算。
🔍 技术视角：对用户"业务数据可信度验证"方向直接可迁移——Sentinel 的三停止点(refuse/halt/withhold)为 agent 调宽表 API 查数提供了置信度治理模板：运行前判断问题是否可答(避免 agent 在不充分信息上瞎跑)、运行中识别 doomed trajectory(及早中止省计算)、交付时 withhold 不可信结果(防 agent 把低置信答案当事实返回)。高 stakes 下 abstain 到 +0.03 vs 未监控 -3.02 是最硬警示——agent 自评不可靠时必须 abstain 而非硬给答案。

📊 架构示意

🎯 为什么值得关注

agent 多步推理的可靠性瓶颈不在单步精度而在"知道自己什么时候不可靠"。临床场景的错误代价=业务场景的决策代价，Sentinel 把"何时停"从模型自报告升级为分类器决策层。

⚙️ 核心机制

trajectory-derived classifier 分析 agent 的 reasoning + code + database outputs 三个维度→在三个点决策：refuse(question 层)→halt(trajectory 层)→withhold(delivery 层)→Chow's rule 在 Reliability Score 下优化 stop/continue 决策→低 stakes 下保留交付+砍计算，高 stakes 下主动 abstain

🧠 深度解读

Sentinel 的核心洞察是"reliability failure = resource failure"——错误推理轨迹不仅产错答案还浪费计算预算。分类器不依赖 agent 自报告置信度（已有研究证明 agent 自评不可靠），而是从轨迹特征(推理步骤+生成代码+数据库输出)外部评估。Chow's rule 的 utility 加权设计让停止决策与业务 stakes 对齐：低 stakes 下多答少 abstain（utility 高），高 stakes 下少答多 abstain（utility 低）。EHRSQL +0.03 vs -3.02 的 100x 差距是"不监控 vs 监控"的量化对比。

💼 商业启示

Sentinel 为"业务 Agent 可信度验证"提供了可量化的 ROI 论据：低 stakes 下 Reliability Score 3x 提升(+0.08→+0.24)+13-28% 计算节省=同时提升可靠性和降本。高 stakes 下 abstain 到 +0.03 vs -3.02 的 100x 差距是"不监控的代价"量化——任何把 agent 放入高风险业务决策(金融/医疗/合规)的系统都须有停止层。

🛠️ 落地建议

在 agent 调宽表 API 的管线中：(1)在 API 调用前加 refuse 层——判断用户问题是否在 API schema 可答范围内；(2)在多步 API 调用中加 halt 层——分类器监控中间 trajectory 是否 doomed；(3)在返回结果前加 withhold 层——置信度低于阈值时返回"无法确认"而非可能错误的值。分类器训练用历史 query 轨迹+对错标注。

⚠️ 局限与风险

EHRSQL 是临床特定 benchmark，迁移到通用业务 API 需重训分类器。覆盖率从 84%→55% 意味着 29% 问题被 refuse/halt/withhold——业务场景需权衡覆盖 vs 可靠。高 stakes 下几乎不答(+0.03≈全拒)说明当前 agent 在高风险临床场景可靠性不足，需 HITL 兜底。

Text2Dashboard: Governed Agent Architecture with Deterministic Hooks for Dashboard Generation

2026-10-02 · arXiv 2610.06914
Text2Dashboard 是 DataBrain 特定原型，将自然语言分析请求转化为可检视的 dashboard。架构核心是"模型提议+确定性软件控制执行"：schema-constrained 模型决策+typed tools+persistent state+deterministic Hooks(approval/audit/checkpoint/recovery/failure handling)。管线包括 entity resolution→metadata discovery→read-only SQL enforcement→dashboard composition→static checks+dynamic preflight+browser inspection。8/8 metadata+SQL 任务通过(4/4 metadata selection+4/4 SQL 语义正确+2/4 exact column contract)，4/4 单 panel dashboard+1/4 双 panel+1/4 existing refinement 通过，10/10 故障场景达指定结果无未授权副作用。模型推理占 >97% runtime。
🔍 技术视角：Text2Dashboard 是"governed agent"架构范本——模型负责提议(propose)，确定性软件负责控制(control)和记录(record)。deterministic Hooks(approval/audit/checkpoint/recovery)把 agent 行为从黑盒变为可审计可恢复的白盒。对用户"业务系统精确查询"方向直接可迁移：agent 调宽表 API 的每一步都应有 deterministic Hook——entity resolution 后校验、API 调用前 read-only enforcement、结果后 static checks+dynamic preflight。

📊 架构示意

🎯 为什么值得关注

agent 生成 dashboard/SQL 的黑盒性是企业落地的核心障碍——没有 approval/audit/checkpoint 机制，agent 错误无法追溯、无法恢复、无法合规。Text2Dashboard 把治理直接编进管线而非外挂。

⚙️ 核心机制

schema-constrained 模型决策(模型只能在 schema 允许范围内提议)→typed tools(工具调用有类型约束)→persistent state(每步状态可追溯)→deterministic Hooks(approval 审批门/audit 审计日志/checkpoint 检查点/recovery 恢复/failure handling 失败处理)→static checks(SQL 语法/权限)+dynamic preflight(实际执行前预检)+browser inspection(最终渲染检视)

🧠 深度解读

Text2Dashboard 的核心架构原则是"propose-control-record"分离——模型 propose(提议动作)，确定性软件 control(控制执行：是否批准、是否执行、是否记录)和 record(记录状态转换)。这与 Sentinel 的"分类器决策何时停"互补：Sentinel 管"停不停"，Text2Dashboard 管"执行过程可不可审可不可恢复"。模型推理占 >97% runtime 说明确定性 Hook 的性能开销可忽略——治理层不是性能瓶颈。10/10 故障场景无副作用证明 Hook 的 recovery 机制有效。

💼 商业启示

governed agent 架构是受监管行业(金融/医疗/合规)落地 agent 的前提——没有 approval/audit/checkpoint 就无法通过合规审计。Text2Dashboard 的"模型提议+确定性控制"分工为"AI for 业务"提供了合规框架：agent 做决策但确定性软件做执行控制+审计记录，满足"可解释可审计可恢复"的合规要求。

🛠️ 落地建议

在 agent 调宽表 API 管线中嵌入 deterministic Hooks：(1)approval——agent 提议调用某 API 前，确定性代码校验参数是否在 schema 允许范围+权限是否足够；(2)audit——每次 API 调用记日志(参数/返回/时间/agent 推理步骤)；(3)checkpoint——多步调用中间结果可保存可回退；(4)recovery——某步失败时从最近 checkpoint 恢复而非从头重来；(5)failure handling——失败时降级策略(重试/换 API/返回部分结果/HITL)。

⚠️ 局限与风险

DataBrain 特定原型，8 个任务+10 个故障场景规模小，不证明生产就绪或通用 text-to-SQL 准确率。strict success 6/8 意味 2/8 未完全通过(2/4 SQL 未达 exact column contract)。2/4 双 panel dashboard 未完全通过说明复杂组合仍是瓶颈。

PlanPool: Beyond Correctness — Resolving Underspecification in Agentic Text-to-SQL

2026-10-02 · arXiv 2610.02739
Agentic text-to-SQL 系统可与用户交互澄清 underspecified query，但正确执行结果≠充分消歧义——agent 可能静默做未验证假设恰好匹配预期答案。此行为部分由"过早终止澄清"驱动：强制多问可提升执行准确率，但歧义集中在前序交互使暴力提问低效。更关键：即使明确提示规划澄清流程，agent 也频繁放弃已识别为相关的问题。PlanPool 将澄清计划外化为可变 question pool——每个计划问题必须显式 ask 或 drop 后才能提交，新发现歧义可交互中添加。BIRD-Interact+Spider 三 benchmark 一致提升 ambiguity coverage 降 silent failure，维持竞争性执行准确率。
🔍 技术视角：PlanPool 揭示了 agentic text-to-SQL 的隐藏失败模式："正确答案≠充分消歧"——agent 可能静默弃问、做假设恰好猜对，执行准确率看起来 OK 但用户意图未被充分澄清。这对用户"业务系统精确查询"是核心警示——agent 调宽表 API 时可能跳过必要的字段语义确认，靠假设猜对一次但不可复现。PlanPool 的"外化澄清计划为可变 pool+必须 ask 或 drop"机制可迁移到 API 字段语义确认。

📊 架构示意

🎯 为什么值得关注

传统 text-to-SQL 评估只看执行正确性，但 agentic 场景下"正确答案"可能来自未验证假设的运气——agent 识别了需要澄清的问题但放弃提问，假设恰好匹配。这种 silent failure 在生产中不可复现、不可审计。

⚙️ 核心机制

agent 生成澄清计划(plan)→PlanPool 外化为可变 question pool→每个计划问题必须显式 ask(向用户提问)或 drop(显式放弃并记录原因)→交互中新发现歧义可 add 到 pool→提交 SQL 前所有 pool 问题必须 resolved→防止"静默弃问"

🧠 深度解读

PlanPool 的核心洞察是"identifying missing information is not sufficient"——agent 识别了需要澄清的问题不够，还必须可靠地维护和解决它们再提交答案。这与 9/12 TDS Intent Continuity(验证>召回)共振：识别到≠问了，问了≠解决了。强制 ask-or-drop 把"静默弃问"从隐式行为变为显式决策——即使 drop 也要记录原因，为审计留下痕迹。歧义集中在前序交互说明暴力多问低效——PlanPool 的条件性池化机制比"强制多问"更精准。

💼 商业启示

PlanPool 对"业务系统精确查询"的商业价值在于可复现性——agent 每次查同一业务问题的 API 字段语义假设必须显式记录(ask 确认 or drop 带原因)，而非静默猜。合规审计时可追溯"为什么这个 API 字段被解释为 X 而非 Y"。silent failure 的代价是"看起来对了但下次换个 agent/换个 prompt 就错了"——PlanPool 把一次性运气变可复现流程。

🛠️ 落地建议

在 agent 调宽表 API 时：(1)agent 识别 API 字段语义模糊(如"status"字段是订单状态还是支付状态)→加入 PlanPool；(2)每个模糊字段必须 ask 用户确认或 drop 并记录假设；(3)API 调用前所有 pool 中字段语义问题必须 resolved；(4)新发现的歧义(如 API 返回后发现字段含义不符预期)可交互添加到 pool。

⚠️ 局限与风险

BIRD-Interact+Spider 衍生 benchmark 规模未报告。维持"竞争性执行准确率"说明 PlanPool 主要提升 coverage 降 silent failure 而非提升准确率——消除 silent failure 的价值在可复现性可审计性而非单次正确率。

Closing the Cross-Dialect Gap: Query Plans as a Portable Interface in Text-to-SQL

2026-09-27 · arXiv 2609.33670
Text-to-SQL 系统通常在单一方言(SQLite)训练评估，但生产部署跨 PostgreSQL/MySQL/ClickHouse 等。单方言假设导致所有测试模型跨方言精度骤降，降幅跨 scale/architecture/甚至 purpose-built text-to-SQL 系统持续存在。解决方案：改生成目标——不让 LLM 输出方言特定 SQL，而是输出 dialect-agnostic 关系代数 query plan，确定性编译器再渲染为任意方言 SQL。13 模型 3B→frontier 几乎一致恢复跨方言可移植性，capable prompted 模型在 home dialect有小幅峰值精度代价，fine-tune on plans 后无代价；matched fine-tuning 下 plan supervision 比 SQL supervision 更强。引入 MetricName(question-aware result-set comparator)公平跨方言评估。
🔍 技术视角：Cross-Dialect 为用户"不直连数据库而通过 API 查数"场景提供了深层架构启示——把 LLM 生成目标从"方言特定 SQL"改为"方言无关关系代数 plan 再确定性编译"，本质是"模型负责语义意图、确定性编译器负责执行细节"分工。这与 Text2Dashboard 的"propose-control"分离同构。对用户多业务 API 场景：agent 应输出"语义意图描述"而非"特定 API 调用参数"，由确定性层翻译为各 API 的实际调用。

📊 架构示意

🎯 为什么值得关注

生产环境跨多种 SQL 方言(PostgreSQL/MySQL/ClickHouse)，但 text-to-SQL 在 SQLite 训练导致跨方言精度骤降——这不是模型能力问题而是生成目标选择问题。

⚙️ 核心机制

LLM 输出 dialect-agnostic 关系代数 query plan(非方言特定 SQL)→确定性编译器把 plan 渲染为任意目标方言 SQL→plan 是 portability 层→MetricName(question-aware result-set comparator)跨方言公平评估(现有 metric 混淆语义错误与良性跨方言差异)

🧠 深度解读

Cross-Dialect 的核心洞察是"generation target chosen for execution is not necessarily the one that maximizes generation quality"——为执行选择的生成目标不一定最大化生成质量。关系代数 plan 作为中间表示(intermediate representation)解耦了"语义意图表达"与"方言特定执行"。这与编译器设计的 IR(中间表示)思想完全一致——LLM 生成 IR，确定性编译器后端渲染为目标代码(各方言 SQL)。plan supervision > SQL supervision 说明在 IR 上训练比直接在目标代码上训练更有效——模型学习的是语义结构而非方言语法。

💼 商业启示

Cross-Dialect 的商业价值在于"一次语义意图，多 API 可移植"——业务系统对接多个 API 时，agent 不需为每个 API 单独训练/fine-tune，而是输出统一语义意图由确定性层翻译。这降低 API 接入成本(新 API 只需加编译规则非重训模型)并提升一致性(同一意图不同 API 产同语义结果)。

🛠️ 落地建议

在多业务 API 场景中：(1)agent 输出"语义意图描述"(如"查客户 X 的近 30 天订单总额")而非直接输出某 API 的调用参数；(2)确定性翻译层把语义意图映射为各业务 API 的实际调用(API A 需 customer_id+date_range+amount_field，API B 需 cust_no+start_date+end_date+total_amt)；(3)跨 API 可移植——同一语义意图可编译为不同 API 调用，类似 plan 编译为不同方言 SQL。

⚠️ 局限与风险

capable prompted 模型在 home dialect 有小幅峰值精度代价(plan 不如直接 SQL 在最熟悉方言上精准)。需要确定性编译器支持所有目标方言/API——编译器本身是工程投入。MetricName 是新评估方法需验证。

Agent in a Bottle: Can LLM Agents Turn Capabilities Into Cheap, Scalable Artifacts? (BOTTLED Benchmark)

2026-10-06 · arXiv 2610.08775
LLM 可解很多窄任务但百万实例分别查询太贵。能否让 agent 自主创建更便宜方案？作者称此能力为"bottling"——把通用能力转化为平衡质量与 amortised cost 的任务特定方案。BOTTLED benchmark 中 agent 收到完整未标注工作负载，在固定时间/计算/LLM API 预算下完成，自选方法(训小模型/写可重用程序)。10 模型×3 任务发现：强 zero-shot 不可靠转化为强 bottling 能力；相似 zero-shot 得分模型 bottling 后差异大；60 runs 中 48 低于零分 95% CI 下界；31 不如 distillation baseline。但 bottling 可大省：Opus 5 在 query-product 分类保留 82% F1 at ~657x 更低成本，recover Jev "system one" 模型 94% F1 at 1/4 成本。
🔍 技术视角：Agent in a Bottle 量化了一个反直觉发现："强 zero-shot 性能≠强 bottling 能力"——能做好单次任务的模型不一定能把能力蒸馏成可重用廉价方案。这对用户"上百字段宽表 API"场景有直接启示：agent 能一次查对 API 不够，还需能"bottling"出可重用查询程序/小模型降 amortised cost。但 48/60 低于零分 CI 下界说明当前 agent 的 bottling 能力普遍不足，需人工设计蒸馏管线而非依赖 agent 自主。

📊 架构示意

🎯 为什么值得关注

百万实例分别调 LLM 太贵——agent 需能把通用能力转化为可重用廉价方案(bottling)，但当前 agent 的 bottling 能力未被系统评估。

⚙️ 核心机制

agent 收到完整未标注工作负载+固定预算(时间/计算/LLM API)→自选方法(训小模型/写程序/混合)→评估 answer quality vs amortised cost→BOTTLED benchmark 跨 10 模型 3 任务→发现 strong zero-shot ≠ strong bottling

🧠 深度解读

BOTTLED 的核心发现有三层：(1)能力≠蒸馏——强 zero-shot 不可靠转化为强 bottling，模型间 bottling 后差异大于 zero-shot 差异；(2)自主蒸馏<人工蒸馏——31/60 runs 不如 distillation baseline，说明当前 agent 自主创建可重用方案能力不如人工设计蒸馏管线；(3)但 bottling 价值实在——Opus 5 保留 82% F1 at 657x 降本+recover Jev 94% F1 at 1/4 成本，说明 bottling 路径可行但需更好的 agent 自主能力或人工辅助。这与 9/5 Compile-by-Training(教师生成样本训小适配器)共振——都指向"把反复 LLM 调用蒸馏为可重用资产"。

💼 商业启示

BOTTLED 的商业价值在于为"AI for 业务"提供了 amortised cost 评估框架——不是看单次查询成本而是看百万次重复查询的 amortised cost。657x 降本是"bottling 路径可行"的硬数据，但 48/60 低于 CI 下界是"当前 agent 自主能力不足"的硬警示——投入应向人工辅助蒸馏管线倾斜而非盲信 agent 自主。这与 dbt token 压缩(8/17 20x 降本)和 Compile-by-Training(9/5 规范编译本地函数)形成"能力蒸馏降本"三联。

🛠️ 落地建议

在宽表 API 查询场景：(1)识别高频重复查询模式(如"查客户 X 的订单总额"每天调 1000 次)；(2)不让 agent 每次重新推理，而是让 agent(或人工)设计可重用查询程序/小模型；(3)评估 bottling ROI——保留质量 vs amortised cost；(4)当前 agent 自主 bottling 能力不足(48/60 低于 CI 下界)，需人工设计蒸馏管线辅助。

⚠️ 局限与风险

10 模型×3 任务规模有限。48/60 低于零分 CI 下界+31 不如 distillation baseline 说明当前 agent bottling 能力普遍不足——不应盲目信任 agent 自主蒸馏。657x 降本是 Opus 5 单任务单次结果，实际 ROI 需验证。

业务 Agent 精确查数护城河从"模型选型"走向"执行层治理六维"

2026-10-08 · 综合研判
本次五篇论文+三开源项目+一博客串成"业务 Agent 精确查数护城河从模型选型走向执行层治理六维"完整链路。六维：(1)何时停(Sentinel 三停止点置信度层)；(2)如何审(Text2Dashboard deterministic Hooks propose-control-record)；(3)问什么(PlanPool 澄清计划外化防静默弃问)；(4)跨什么(Cross-Dialect 方言无关 plan 编译可移植)；(5)如何省(Agent in a Bottle bottling 能力蒸馏 amortised cost)；(6)基础可靠性(Cube PK/FK 自动检测+OpenMetadata 静默错误消除+tokensave 条件读引导式重定向)。六维共同指向"agent 精确查数护城河不在模型而在执行层治理"。
🔍 技术视角：最核心战略研判：业务 Agent 精确查数的护城河正从"选最强模型"转向"执行层治理六维"——Sentinel 管"何时停"(置信度停止点)+Text2Dashboard 管"如何审"(deterministic Hooks)+PlanPool 管"问什么"(澄清外化)+Cross-Dialect 管"跨什么"(方言无关编译)+Agent in a Bottle 管"如何省"(能力蒸馏)+Cube/OpenMetadata/tokensave 管"基础可靠性"(自动发现/静默消除/条件读)。投入应向六维倾斜而非模型选型。

📊 架构示意

🎯 为什么值得关注

五篇论文+三开源项目共同证明"单点模型能力≠系统可靠"——Sentinel 证 agent 自评不可靠需外部停止层，Text2Dashboard 证黑盒 agent 不可审需 deterministic Hooks，PlanPool 证正确执行≠充分消歧需外化澄清，Cross-Dialect 证单方言训练≠跨方言可移植需中间表示，Agent in a Bottle 证强 zero-shot≠强 bottling 需蒸馏管线。

⚙️ 核心机制

Sentinel(何时停:refuse/halt/withhold)→Text2Dashboard(如何审:approval/audit/checkpoint/recovery)→PlanPool(问什么:ask-or-drop 外化)→Cross-Dialect(跨什么:dialect-agnostic plan 编译)→Agent in a Bottle(如何省:bottling amortised cost)→Cube+OpenMetadata+tokensave(基础可靠性:PK/FK 自动检测+静默错误消除+条件读引导式重定向)

🧠 深度解读

六维分工有层次结构：(1)Sentinel 是"决策层"——在执行前/中/后决策停不停；(2)Text2Dashboard 是"执行层"——控制执行过程可审可恢复；(3)PlanPool 是"交互层"——管理 agent 与用户的澄清交互；(4)Cross-Dialect 是"抽象层"——解耦语义意图与执行方言；(5)Agent in a Bottle 是"经济层"——优化百万次重复的 amortised cost；(6)Cube/OpenMetadata/tokensave 是"基础设施层"——提供 schema 自动发现/元数据治理/代码智能的基础可靠性。六维从决策到执行到交互到抽象到经济到基础，覆盖 agent 精确查数的全生命周期。TDS MMM 的"缺变体信息"为六维补充了"数据可识别性"第七维——agent 须评估数据变体充分性。

💼 商业启示

六维护城河的商业启示："AI for 业务"的投入不应集中在"选最强模型"而应分散到六维执行层治理——Sentinel(可靠性 ROI: +0.08→+0.24+砍 13-28% 计算)+Text2Dashboard(合规前提:可审可恢复)+PlanPool(可复现性:silent failure 消除)+Cross-Dialect(接入成本:新 API 加规则非重训)+Agent in a Bottle(amortised cost: 657x 降本潜力)+Cube/OpenMetadata/tokensave(基础可靠性:自动发现+静默消除+条件读)。六维 ROI 可量化但需各自验证。

🛠️ 落地建议

对用户"AI for 业务"三大方向的映射：(1)业务知识库构建→Cube PK/FK 自动检测+OpenMetadata 元数据治理(基础设施层)；(2)业务语义理解→Cross-Dialect 语义意图抽象+PlanPool 字段语义澄清(抽象层+交互层)；(3)业务系统精确查询→Sentinel 置信度停止+Text2Dashboard deterministic Hooks+Agent in a Bottle 能力蒸馏(决策层+执行层+经济层)。六维投入优先级：先基础(Cube/OpenMetadata)再决策(Sentinel)再执行(Text2Dashboard)再交互(PlanPool)再抽象(Cross-Dialect)最后经济(Agent in a Bottle)。

⚠️ 局限与风险

How Wrong Is Your Marketing Mix Model (MMM)? — Spend 缺变体信息致估计高方差

2026-10-07 · Towards Data Science
Ryan O'Sullivan (10/7, 25 min) 指出 well-built MMM 仍可错——spend 缺三种变体信息导致高方差估计：(1)Multi-collinearity——营销渠道同期规划同涨同跌，缺"每渠道独立移动"信息；(2)Selection bias——spend 随 demand 峰期增长，缺"非 demand 驱动的 spend 变动"；(3)Non-identifiable adstock/saturation——shape 参数不可从普通 spend 数据分离。Google 2017 Challenges 论文+2024 'Your MMM is Broken'+2026 Recast 地理测试 14-30% false lift。三问题同修：spend 需在模型需要的维度上变动，预算分期算法(budget phasing)可构建三维度变体。
🔍 技术视角：MMM 的三问题(多共线性/选择偏差/不可识别 adstock)本质都是"数据缺变体信息"——不是模型不够好而是 spend 数据从未在模型需要的维度上变动过。这对用户"业务数据可信度验证"方向有深层启示：agent 从宽表 API 查回的数据可信度不只取决于 API 本身，还取决于数据中是否包含足够的"变体信息"让分析结论可识别。缺变体=高方差=不可信结论。

📊 架构示意

🎯 为什么值得关注

MMM 回归估计的高方差根因不在模型而在数据——spend 从未在模型需要的维度上独立变动过，导致参数不可识别。

⚙️ 核心机制

Multi-collinearity(渠道同期涨跌→缺独立移动)→Selection bias(spend 随 demand→缺非 demand 驱动变动)→Non-identifiable adstock/saturation(shape 参数不可分离→缺不同 level spend)→三问题同修：budget phasing 算法构建三维变体

🧠 深度解读

MMM 三问题的共同结构是"信息缺失"——不是数据量不够而是数据中缺少特定维度的变体(variation)。这与 Sentinel 的"reliability failure"和 PlanPool 的"underspecification"形成跨域共振：Sentinel 说 agent 推理缺可信度评估，PlanPool 说 agent 澄清缺充分性，MMM 说数据缺变体信息——三者都指向"缺什么信息比多什么数据更重要"。Google 2017 Challenges 论文至今是最清晰表述，说明这个问题十年未解。2026 Recost 地理测试 14-30% false lift 说明现有 incrementally testing 也不可靠。

💼 商业启示

MMM 的商业启示是"可信数据≠完整数据"——数据完整但缺变体信息时估计仍高方差不可信。对"AI for 业务"的启示：agent 查数后须评估数据变体充分性，缺变体时标注"不可识别"而非强行给结论。这为"业务数据可信度验证"提供了"变体信息充分性"这个新的验证维度——不 only 验证数据正确性还验证数据可识别性。

🛠️ 落地建议

在 agent 调宽表 API 查数时：(1)评估返回数据是否含足够变体信息支撑分析结论——如所有订单 status 都是"已完成"则无法分析 status 对金额的影响(缺变体)；(2)设计数据收集策略主动注入变体——如 A/B 测试不同 API 参数组合；(3)标注"不可识别"结论——当数据缺变体时 agent 应返回"此维度不可识别"而非强行给高方差估计。

⚠️ 局限与风险

MMM 特定于营销领域，但"缺变体信息致高方差"原理通用。budget phasing 算法是模拟研究，实际 spend 变动受业务约束。Google 2017 论文+2024+2026 三引用说明问题持久未解。
