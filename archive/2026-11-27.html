Agent 补丁真的「过度编辑」吗？DRA 逐块回放：多余代码 89% 会改变行为，但代码必要性不低于人类

2026-11-25 · arXiv
论文指出「agent 补丁比开发者大」被直接解读为过度编辑，但补丁大小并不能说明多出来的编辑是否必要。作者提出 Delta Residue Attribution（DRA）：回放 agent 轨迹，把最终补丁的每个代码块追溯到写下它的那一步，逐块回滚并重跑任务测试，判定该块是否必要。在 18 个前沿模型的 7,660 条 GitHub Copilot CLI 轨迹（SWE-bench Verified 6,728、DeepSWE 932）上，SWE-bench 的多余编辑 61% 是测试、13% 是文档，DeepSWE 上 58% 是代码；两套基准上 agent 代码的平均必要性都不低于开发者（0.887 vs 0.864、0.797 vs 0.785），SWE-bench 上 18 个模型有 11 个比人类留下更少无用代码。SWE-bench 上仍有 11% 代码单元多余，其中 89% 会改变行为；用 agent 可见测试做 DRA 剪枝可去掉大部分多余代码（召回 67%、精确 46%），89% 被剪补丁仍能通过任务，而让 agent 自审 diff 更精确（66%）但召回只有 36%。
🔍 技术视角：这是本期最重要的一条方法论纠正：diff 行数不是质量信号，「必要性」才是。对架构师的直接含义是，代码评审与质量门禁应当以「行为变更单元」为单位，而不是以文件/行数规模为单位；同时 DRA 提供了一个可落地的 CI 手段——对高风险 PR 做单元回滚 + 测试重跑，产出「这个 hunk 到底有没有被测到」的证据，而不是让模型再猜一遍。注意 46% 的精确率意味着自动删除不可接受，只能做提示与人工确认。

📊 架构示意

🎯 为什么值得关注

「agent 写得多」是团队最直观的体感，也是最容易被误用的指标。这篇论文第一次用可复现的归因方法把「多」拆成「测试多、文档多、代码多」，并给出与人类开发者的对照基线，直接推翻了「agent 代码质量差所以补丁大」的常见叙事。

⚙️ 核心机制

DRA 四步：轨迹回放 → 单元归因（每个 patch block 对应哪一步写入）→ 单元回滚 → 重跑任务测试判定必要性。NP（necessity proportion）按代码/测试/文档分别统计；剪枝实验只用 agent 可见的测试（自身测试 + 仓库测试），并对比「让 agent 自审 diff」两种策略的召回/精确。

🧠 深度解读

两个反直觉发现值得记住：其一，调试步骤几乎不产生多余代码，多余代码主要来自「顺手补测试/补文档」与模型对上下文过度补全；其二，代码必要性与 resolve rate 在 SWE-bench 上无关，在 DeepSWE 上负相关（Spearman -0.59，p=0.01）——越爱「多写点保险代码」的模型在长程任务上反而更容易失败。这暗示「多做一点」不是稳健性，而是掩盖不确定性。

💼 商业启示

代码评审/质量门禁类产品若以「diff 规模/复杂度」作为核心风险分，会系统性误判：大补丁可能只是补了测试。更有商业价值的能力是「行为变更覆盖率」——哪些行为改动没有被任何测试锚定。这也是 AI 评审工具从「读 diff」升级到「跑验证」的差异点。

🛠️ 落地建议

在 CI 里对高风险 PR 做 dry-run 归因：对每个 hunk 回滚后跑相关测试，标记「无测试覆盖的行为变更」；把 89% 仍可 resolve 作为保守上界，先只输出建议不自动改。评审模板增加一栏：本 PR 的行为变更点是否都有对应测试。团队周报可用 NP_code 与 NP_test 两个指标替代 diff 行数。

⚠️ 局限与风险

必要性判定依赖测试可见性，测试没覆盖到的必要代码会被误判为多余；46% 精确率意味着近一半被剪的是有用代码；样本仅 GitHub Copilot CLI 轨迹，harness 差异（上下文策略、工具集）可能改变结论；SWE-bench 类基准本身偏「修 bug」，不代表新功能开发。

AI 代码评审该花多少力气？三档 effort 实测：任何档位都放过 ≥45% 的错误补丁

2026-11-25 · arXiv
研究问的是一个工程问题：reasoning 模型的 effort 档位能否让 AI reviewer 抓住「能过基准测试、但过不了更强测试」的似是而非补丁。Claude Opus 5.5（预注册）、Sonnet 5.5、Haiku 5.5（探索性）分别以 low/medium/high effort 评审同一批 90 个 agent 写的 Django 补丁；用强化后的 SWE-ABS 测试判定，其中 55 个是错的、35 个是对的。三个模型 high 档都比 low 档少放过错误补丁（false success：Opus .45 vs .67、Sonnet .49 vs .65、Haiku .51 vs .78），Opus 与 Haiku 的差异达到显著。Opus 的 medium 在 15pp 内非劣于 high（差值 .018，95% CI [-.065, .108]）且成本低 20%（未达到预注册的 30%）；Sonnet/Haiku 的 medium 分别便宜 39%/51%，但未能证明非劣。Haiku high 的单次评审成本约为 Opus medium 的 8%。关键结论：没有任何档位是强门禁——每个设置至少接受 45% 的错误补丁。
🔍 技术视角：把 AI reviewer 当「合并许可」是当前最危险的做法。数据说明它更像一个召回率有限、且提升 effort 主要增加「能点名被测缺陷」的筛子：effort 提高减少的是「明明看到了问题却放过」，而不是「看不到问题」。正确架构是三层：确定性门禁（测试/静态扫描/类型检查）→ AI 评审做解释与风险提示 → 高风险改动人工签核；并且要用 false success 抽样持续校准，而不是相信 approve。

📊 架构示意

🎯 为什么值得关注

团队普遍在 CI 里加 AI review 并要求「必须通过」，但缺少对「它到底能拦住多少错」的量化。这篇给出了同一批补丁、同一套强化测试下的跨模型/跨 effort 对照，且做了预注册，可信度高于产品博客。

⚙️ 核心机制

固定 90 个 SWE-bench Verified 的 Django agent 补丁，用更强的 SWE-ABS 测试重判标签（55 错 / 35 对）；三个模型 × 三档 effort 全交叉评审；统计 false success（把错补丁判为通过）与 false reject；成本用实际 token/价格折算；Opus 走预注册的非劣性检验（margin 15pp）。

🧠 深度解读

两个细节决定解读方式：其一，多数拒绝都点名了「被测的那个缺陷」，说明 effort 提升的是「表达与定位」而非「发现」；其二，55 个错补丁中有 32 个的问题可能并不需要失败测试所检查的内容——把这 32 个剔除后，所有模型的精度假设都不成立。也就是说，基准标签本身的效度限制了这类评测的天花板。

💼 商业启示

AI review 产品的定价与定位需要重设：按「每 PR 固定价」卖会鼓励客户把它当门禁，最终因漏放事故失去信任；更合理的是按「风险分层 + 人工兜底」卖，把 false success 作为可审计的服务指标写进 SLA。对自建团队，这意味着预算应更多投在测试强化上，而不是把 reviewer 的 effort 拉满。

🛠️ 落地建议

分层用模型：日常 PR 用 Opus medium（性价比拐点），安全/资金/权限相关改动强制 high + 人工；把 AI review 的 approve 降级为 comment，禁止作为 merge 条件；每周抽样 20 个 approve 的 PR 跑强化测试，统计 false success 作为 reviewer 的 SLO。

⚠️ 局限与风险

单一语言（Python/Django）与单一基准；「强化测试」的构造方式会直接影响标签；32/55 的标签存在争议；成本按 API 价格折算，未计延迟与工程维护；Haiku 的精度差异在统计上未分辨。

并行 subagent 什么时候有效？+1-5pp 通过率、最高 3.8 倍成本，大部分收益可被单 agent 的「先探测参考实现」复现

2026-11-25 · arXiv
论文在 NL2Repo 与 ProgramBench（后者带可执行参考程序）的仓库构建任务上，对比「单 agent」与「主 agent 委派并行 subagent」，并在等时间、等成本两种口径下评分。随机抽样的任务上，并行 subagent 只把隐藏测试通过率提高约 1-5pp，成本最高是单 agent 的 3.8 倍；难度高的任务收益更大。作者识别出三种机制：自检（用 GPT-5.6 Sol 时，只需一句话让单 agent「先探测参考程序」就能以极小成本复现大部分收益；从 GPT-5.6 到 GPT-6.1，单 agent 自检变强后收益缩小）、fresh context（长跑中定期开空会话的单 agent 在每次对比里早期进展都更快）、模块化（多 agent 产出更多文件、更短函数，更接近上游源码）。在 Claude Code + Opus 5.5 的较小规模复现中观察到相同模式。
🔍 技术视角：对架构师而言，这条情报的价值是「先做便宜的干预」：并行 subagent 本质是在用钱买三件事——强制自检、上下文重置、模块化。前两件在单 agent harness 里几乎零成本（加一句探测参考实现的提示、每 N 步重开 context），第三件可通过「先出文件骨架再填实现」的流程约束获得。只有在长程、单 agent 已停止自检、或任务确实需要模块化时，才值得付 3.8 倍成本。

📊 架构示意

🎯 为什么值得关注

Codex、Claude Code 都在推「主 agent + 并行 subagent」，但缺少等成本口径的对照，团队很容易把「多花 4 倍钱换 2 个点」当成能力提升。这篇用等时间/等成本两种口径拆开了收益来源。

⚙️ 核心机制

任务来自 NL2Repo 与 ProgramBench（带可执行参考程序，可做行为对照）；对比单 agent 与 orchestrator+subagents；干预实验分别加入「先探测参考程序」提示、定期 fresh session、模块化约束；细粒度行为分析统计自检频率、会话长度、文件/函数粒度。

🧠 深度解读

「fresh context 更快」是一个反直觉但重要的发现：长会话里模型会不断在既有实现上打补丁，早期进展反而变慢；空会话迫使它重新规划。这与本期 DRA 的发现互相呼应——长会话的「继续改」往往产生不必要编辑。模块化收益则提示：多 agent 的优势可能只是「被迫分文件」，而不是并行本身。

💼 商业启示

多 agent 产品的定价必须按 token 成本分层，否则「并行」会成为亏损功能。反过来，如果能把「自检 + 上下文重置」做成默认 harness 行为，就能用单 agent 的成本提供接近多 agent 的效果——这是产品差异化的真实来源，而不是并发数。

🛠️ 落地建议

在自建 coding agent 里加三条 harness 规则：任务开始先读/运行参考实现或验收测试；每 30-50 步或连续两次测试无提升时重开 context 并带上摘要；强制先产出文件骨架。仅对预估 >2 小时的长程任务开启 subagent，并按「每解决一个额外任务」核算成本。

⚠️ 局限与风险

指标静默翻倍的根因是「度量粒度」：grain-aware 约束把 fan-out 错误从 18.4% 降到约 13%

2026-11-21 · arXiv
论文把 text-to-SQL 里最隐蔽的错误——一对多/多对多 join 后 SUM/COUNT 重复计数（fan-out）——形式化为「聚合所读关系上的一个条件」，而这个条件依赖两个 schema 不显示的事实：每个度量的 grain（一行代表什么实体）和每个 key 上 join 重复的行数。在数据上执行该条件的审计发现，BIRD dev 集有 4.2% 的 gold 答案本身被 fan-out 扭曲；BIRD 后来的独立修订改掉了 44% 被标记为「确定 fan-out」的答案，而未标记的只改了 16%。作者发布 BIRD-FanOut（486 条经人工复核的 BIRD 问题）与 GrainTraps（合成陷阱题）。在 8 个 LLM agent 上，从数据计算的普通函数依赖并不比列统计更有用，但「grain-aware FD」（额外声明度量粒度与每 key 重复度）把 BIRD 上的 fan-out 错误从 18.4% 降到约 13%，且在 held-out 问题上同样有效、无需 LLM judge。准确率提升较小，因为剩余错误大多不是 fan-out，且 BIRD 的 hint 常常正好 prescribing 了过度计数。
🔍 技术视角：这条直接命中「宽表 API + 高业务含义」的架构：宽表的每一行代表什么、一个度量在 join 后会不会被放大，是 schema 里没有、但业务语义里必须有的元数据。正确做法不是在 prompt 里提醒模型「小心 join」，而是在语义层/mertic store 里为每个度量声明 grain 与关系基数，并在查询编译期做静态检查——一旦聚合跨越 1:N 关系且没有预聚合，就改写或拒绝。

📊 架构示意

🎯 为什么值得关注

业务 agent 最危险的输出不是报错，而是「跑得通、数字看起来合理」的错数。fan-out 正是这类错误的典型：SQL 合法、执行成功、结果量级可信，但数值被放大数倍。而基准本身的 gold 也有 4.2% 中招，说明这不是模型能力问题，是数据模型语义缺失。

⚙️ 核心机制

把 fan-out 表述为「聚合读的关系上存在重复实体」这一条件；该条件需要 measure.grain 与 join key 的重复行数两个事实。审计：在真实数据上执行条件，标记被扭曲的 gold。方法：给 LLM 提供 grain-aware FD（度量粒度 + 每 key 重复度），与普通 FD、列统计做对照。

🧠 深度解读

普通函数依赖之所以无效，是因为它只描述「列之间谁决定谁」，不描述「聚合的语义单位」。grain-aware FD 补上了「这个 SUM 是在什么实体粒度上求和」以及「join 会不会把这个实体复制多份」。剩余 ~13% 的错误说明还有别的陷阱（如时间窗口、去重口径），但 grain 是最容易形式化、也最容易在语义层落地的一层。

💼 商业启示

对自建业务 agent，这是「可信度」的直接抓手：把 grain 作为指标契约的一部分，可以让「数字对不对」从人工抽查变成编译期可验证。对做 ChatBI/语义层的产品，grain 感知是差异化能力——大多数产品只做 schema linking，没有度量粒度这一层。

🛠️ 落地建议

在指标定义中增加三个字段：grain（如 order_id / user_id / day）、relationships（1:1、1:N、N:M 及 join key）、allowed_aggregations；在查询编译期检测「聚合跨越 1:N 且未先做子查询预聚合」，自动改写为 `SELECT ... FROM (SELECT DISTINCT grain_key, ...)` 或直接拒绝并提示。对宽表 API，把 grain 写进字段注释与 OpenAPI description，让 function calling 的 schema 自带语义。

⚠️ 局限与风险

需要数据分布统计（每 key 重复度）才能判定，纯 schema 不够；BIRD 的 hint 本身会诱导过度计数，说明评测集有偏；准确率提升有限，grain 不能解决所有口径问题；对 API 场景，grain 需要 API 提供方声明，agent 侧只能推断。

Value Semantics Layer：把「值语义」做成 planner 可见的基础设施，而不只是 catalog 和 lineage

2026-11-17 · arXiv
论文指出，现有元数据系统（schema、catalog、lineage、governance）主要提供描述性信息，对「操作性语义」支持有限，而自主 agent 需要后者才能正确选择算子、验证操作。作者提出 Value Semantics Layer（VSL）：把值语义外化为持久、planner 可见的基础设施，核心是 Value Semantic Types（VST）——可复用的操作性语义断言，覆盖五类：分布（distributional）、关系（relational）、过程（process）、定量（quantitative）、政策（policy-grounded）。与描述性元数据不同，VST 让 planner 在执行前验证分析操作是否合法、选择合适的算子并引导工作流。论文给出动机、形式化、架构与原型实现，并列出面向 AI 原生分析系统的研究议程。
🔍 技术视角：这是「语义层 vs 企业知识图谱」路线之争里一个有用的第三条轴：不是「指标定义在哪」，而是「值的语义以什么形式被机器消费」。VST 的五类划分可以直接映射到宽表 API 的字段契约：枚举/值域（distributional）、外键与基数（relational）、状态机与生命周期（process）、单位与量纲（quantitative）、PII 与访问策略（policy）。把这些写进 function calling 的 schema description，比在 prompt 里堆业务术语更可验证。

📊 架构示意

🎯 为什么值得关注

业务 agent 的失败大多不是「不会写 SQL」，而是「不知道这个字段的值意味着什么」——0 是「无」还是「未知」、金额是分还是元、状态 3 是已取消还是已退款。VSL 把这类知识从文档/prompt 提升为可被 planner 查询和验证的基础设施。

⚙️ 核心机制

VST 作为一等对象注册在 VSL 中，按五类语义组织；planner 在生成计划时查询 VST，做三类动作：验证操作合法性（如对 policy-grounded 字段的聚合是否允许）、选择算子（如对 distributional 语义选择分位数而非均值）、引导工作流（如 process 语义要求先校验状态机）。

🧠 深度解读

与知识图谱路线相比，VSL 更「窄而深」：不追求实体关系的全域建模，而是聚焦「值在分析操作中的行为约束」。这恰好补上了 metric store 的短板——metric store 定义「指标怎么算」，VSL 定义「算的时候值能怎么用」。两者组合，才构成 agent 可安全使用的语义层。

💼 商业启示

语义层产品的下一个竞争点可能不是「指标数量」，而是「值语义的覆盖度与可验证性」。对企业客户，VST 是可以写进数据契约的资产；对 agent 产品，它是降低幻觉、提升可审计性的基础设施。

🛠️ 落地建议

先给 3-5 张核心宽表建立 VST：枚举字段列出全部取值及含义、金额字段声明币种与单位、状态字段给出状态机、PII 字段标注访问策略、时间字段声明时区与粒度。以 JSON Schema + description 暴露给 function calling，并在查询校验层强制检查。

⚠️ 局限与风险

position paper，原型规模有限，缺少大规模评测；VST 的维护成本高且容易与真实数据漂移；五类语义的边界在实际建模中会模糊；对 API 场景，VST 需要 API 提供方配合，agent 侧难以独立获得。

论文指出，大量可用于分析的数据散落在开放数据门户、数据湖与独立发布的表集合中，data agent 每回答一个问题都要走完整流程（数据集检索、join 发现与评估、定制程序合成），而这些知识在下一个任务到来时几乎全部丢弃。作者主张把这些知识持久化为不断演进的 semantic atlas：离线描述每个数据集（topic、semantic type、profile），使 agent 能找到任务所需数据集；数据集之间的关系与集成视图需要比较，因此按用户声明的分析域按需构建。每个条目都带 provenance 与产出方法的 confidence，让 agent 决定信任程度或弃答；数据变化时自动检测并修正不一致，人类裁定数据本身无法决定的部分。论文给出愿景与挑战（大规模多域构建、保持正确与最新、服务用户与 agent、评估是否提升答案），并在 DAB 上做概念验证：只用部分 atlas，coding agent 读取的 token 减少 1/5 到 1/3，准确率与不用时相同。

🧠 深度解读

「按需构建关系」是成本控制的关键：join 发现的组合空间随数据集数量爆炸，全量预计算不现实；而用户的分析域通常集中在少数主题，按需构建能把算力花在真实查询上。provenance + confidence 则让 agent 能对低置信关系弃答，而不是硬 join 出一个错数。

💼 商业启示

🛠️ 落地建议

第一步做离线画像（列语义、值域、空值率、主键候选），覆盖核心宽表；第二步按业务域（如履约、结算、增长）逐步补 join 关系与集成视图，每条记录来源与置信度；第三步在 agent 检索层加「置信度阈值 + 弃答」。用 token 消耗与首答准确率做验收指标。

⚠️ 局限与风险

⚠️ 局限与风险

需要可生成/可重放的数据环境，纯 API 接入难以获得；副本与真实分布差异过大会产生假阳性；训练收益不稳，不宜直接作为 RL 目标；「全部一致」对含随机/时间函数的查询不适用。

「兼容」的工具升级会悄悄扩权：604 个 MCP release 中 412 个变更扩大了能力坐标

2026-11-23 · arXiv
论文研究一个被忽视的供应链问题：用户批准过的工具，其 JSON input schema 会持续变化。调查的 8 个 MCP 客户端/扫描器中，没有一个被观察到或文档记载会对「schema 变宽」的工具重新审批（另有 2 个无法判定）。作者定义「非扩权」（non-amplification）：在 schema 可见的坐标上（声明参数与未声明字段，按有效值判定），并用 subschema inclusion 决定是否需要重新绑定，默认不信任任何字段标签。证据包括：组合性的 Coq 证明、48 个回归测试、一个精确参考基准（被评审版本的规则曾静默重绑 27 个扩权变更，已修复），以及 39 个公开 MCP server 的 604 个 release 试点。试点中 580 个「兼容」schema 变更里有 412 个扩大了某个坐标，但兼容性检查把它们静默重绑；双人裁决标注发现至少 76 个新增或放宽了带权限的参数（按名字的标注器发现 66 个、漏 10 个）。在既有工具上，该规则需要 645 次再审批，锁死 input schema 需要 1,197 次（含描述 2,004 次），而按兼容性只需 617 次。schema 不变但行为改变仍无法覆盖。
🔍 技术视角：这条对「宽表 API + function calling」是直接警告：新增一个可选参数、把枚举放宽、增加未声明字段，都可能在语义上给 agent 开了一个新能力（比如新增 `scope=all`、新增 `include_archived=true`）。API 版本号与「向后兼容」标签不足以保证权限不扩张，必须做「能力 diff」——比较新旧 schema 的可接受值集合，任何放宽都触发再审批。645 vs 1,197 的对比也给出了成本更优的折中：按能力重绑定，而不是每次锁死整个 schema。

📊 架构示意

🎯 为什么值得关注

agent 的权限边界实际上由工具 schema 定义。只要 schema 能变，审批就是一次性的、会过期的。现有 MCP 生态没有任何客户端做「变宽再审」，这是一个系统性缺口。

⚙️ 核心机制

把 schema 视为坐标集合（参数名、类型、枚举值、是否可选、未声明字段策略），定义 non-amplification 为「新 schema 的可接受调用集合是旧的子集」；用 subschema inclusion 判定；对扩权变更要求 re-binding（重新审批/重新绑定权限）。用 Coq 证明组合性，用 48 个回归测试与精确基准验证实现。

🧠 深度解读

「默认不信任字段标签」是重要的工程选择：不能靠参数名叫 `admin` 或 `dry_run` 来判断权限，因为攻击者/粗心作者可以随便命名；必须看结构上的可接受值集合。76 vs 66 的差距说明基于名字的启发式会漏掉约 13% 的扩权参数。而「schema 不变、行为变」仍是开放问题，意味着能力 diff 只能覆盖一部分风险。

💼 商业启示

工具/插件市场的信任基础需要从「审核一次」变成「持续能力监控」。这对做 agent 平台或 MCP gateway 的团队是一个明确的产品点：能力 diff + 审批账本 + 高风险工具 pinning。对企业内部，API 契约变更评审应把「是否扩权」列为必检项。

🛠️ 落地建议

为每个工具/API 保存 schema 快照并计算 capability diff：新增参数、枚举扩张、可选→必选放宽、additionalProperties 打开，任一命中即阻断并要求重新审批；把「能力坐标」写入审批记录，审批绑定坐标而非版本号；对高风险工具（写操作、资金、外部收件人）默认锁死 schema。

⚠️ 局限与风险

无法检测 schema 不变的行为变化；判定依赖 JSON Schema 子集包含的可判定性，复杂组合（oneOf/anyOf/$ref）可能退化；试点是 MCP 生态，企业内部 API 的变更流程不同；再审批会增加运维负担。

⚠️ 局限与风险

合成目录与两套引擎，真实环境的策略语言更丰富；开放数据流假设较强（很多企业场景 sink 受限）；有效独立决策数的估计依赖作者分组；未覆盖「策略正确但被绕过」的实现漏洞。

OpenAI + Cisco 开源 Shirudo：让 agent 用 eBPF 写「临时护盾」，Codex 生成的补丁在运行中的 Elasticsearch 上挡住 Java4Shell

2026-11-23 · OpenAI Blog
OpenAI 与 Cisco 发布开源项目 Shirudo（日语「盾」，BSD 2-Clause，BPF 程序 BSD/GPL 双许可）：一个帮助运维在补丁窗口期保护运行中 Linux 系统的运行时。核心矛盾是漏洞利用与合法请求可能依赖同一个 Linux 操作，直接封禁会让服务下线。Shirudo 让团队先测试一个临时护盾（shield）是否能挡住暴露漏洞的行为、同时放行合法请求，批准后在服务不重启的情况下部署。实现基于 eBPF，可在系统调用层观测并施加定向保护；护盾在加载前经过加密签名与 eBPF verifier 的内核安全检查，并由内核安全控制限制未授权变更；TPM 提供护盾加载/卸载的可验证记录。受控测试中，Codex 生成的护盾给 Java Base64 解码器加了输入检查并挂到运行中的 Elasticsearch 进程上，无需重启即挡住了 Java4Shell 利用尝试。项目提供 VM quickstart、Isovalent 实验环境与 12 月 15 日技术深潜。

补丁从披露到部署常常要几天到几周，这段时间系统是裸奔的。Shirudo 把「临时缓解」做成可测试、可签名、可回滚的工程对象，并让 agent 参与生成，这是 agent 进入生产基础设施的关键一步。

eBPF 程序挂载到内核观测点，按规则拦截特定调用路径；护盾先以 monitor 模式运行，观察对真实负载的影响，再切换 enforce；加载前签名校验 + eBPF verifier 安全性检查 + 内核权限控制；TPM 记录加载/卸载形成可验证证据链。

「同一操作既被利用也被合法使用」是所有运行时缓解的共同难题，Shirudo 的解法是把「验证」前置到部署前，用真实工作负载做对照，而不是靠规则作者的经验。Codex 生成的是「给 Base64 解码器加输入检查」这种细粒度修改，说明 agent 的价值在于快速产出针对性 shield，而不是通用策略。
