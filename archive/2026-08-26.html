Beyond the Harness: 企业 Text-to-SQL 的瓶颈在 Context 工件而非模型

2026-08-24 · arXiv 2608.22830
本文论证企业 Text-to-SQL 部署瓶颈不在模型而在送达模型的 knowledge-base context。作者用 query-DAG 分解（与 BEAVER benchmark 同族中间表示，从生产 SQL 恢复）对比 oracle query graph 与检索 context 价值。在 5176 条大型在线零售商生产查询上，优化 context 工件（蒸馏历史查询画像为可复用 SQL reference cards）比优化检索 harness 增益更大（12-25% AST similarity vs 3-12%）。在公开 BEAVER benchmark 上效果更混合（缺乏生产信号），table cards 单独≈原始 SQL，最佳组合 9.00% vs 6.33%（p=0.12）。引用数待核实（Semantic Scholar 限流，8/24 新文预期 0）。
🔍 技术视角：本文对用户课题最直接相关：证明企业 text-to-SQL 的 ROI 重心应从'选更强模型/调检索参数'转向'蒸馏历史查询为可复用 context 工件'。用户团队有大量真实 API 调用历史，可蒸馏为'API reference cards'——把高频查询模式固化为可检索的结构化参考，而非每次让 LLM 从零推理。这与 8/17 Bounded Semantic Planning（确定性 kernel 编译）同向：context 工件本质是把确定性逻辑从 LLM 推理前移到离线蒸馏阶段。

📊 架构示意

🎯 为什么值得关注

首次用生产规模数据（5176 查询）量化 context 工件 vs 检索调参的 ROI 差距（2-3x），为企业 text-to-SQL 投资提供硬数据决策依据

⚙️ 核心机制

query-DAG 分解从生产 SQL 恢复 → 蒸馏历史查询画像为 SQL reference cards（可复用结构化参考）→ 检索时 cards+raw SQL 组合送达模型。cards 是从使用模式蒸馏的，非人为编写

🧠 深度解读

BEAVER 上效果更混合揭示关键边界：有生产信号时 context 工件价值大，无生产信号时退化为 table cards≈raw SQL。这说明 context 工件的护城河来自企业独有的使用历史而非通用知识——对用户'上百字段宽表 API'场景，历史调用模式是独有资产。query-DAG 作为中间表示与 BEAVER benchmark 同族，说明 DAG 化查询分解正成为领域共识

💼 商业启示

核心商业启示：拥有大量真实 API 调用历史的企业有独有数据护城河——蒸馏为 context 工件的 ROI 是继续堆模型参数的 2-3x。这改变了'AI for 业务'立项逻辑：不是先买最强模型，而是先建历史查询蒸馏管道。对 dbt/Cube 等语义层厂商，reference cards 概念可产品化为'查询画像层'，成为语义层的新功能维度

🛠️ 落地建议

1) 建立历史 API 调用日志的 query-DAG 分解管道，蒸馏高频模式为 reference cards；2) reference cards 应含字段语义标注+典型约束+常见聚合粒度，非纯 SQL 模板；3) 检索时 cards+raw 示例组合优于任一单独；4) 公开 benchmark 无法替代内部生产数据评估

⚠️ 局限与风险

BEAVER 公开 benchmark 上 p=0.12 不显著，说明无生产信号时方法优势衰减。5176 查询来自单一零售商，跨行业泛化未验证。AST similarity 是代理指标非执行正确率。Semantic Scholar 引用数未核实（限流）

SPOC-SQL: 四阶段分解 + Stage-wise 偏好优化可控 Text-to-SQL

2026-08-24 · arXiv 2608.22772
现有 text-to-SQL 方法把任务当单步生成，对整条 SQL 序列优化而缺乏关键决策点的针对性反馈与中间过程控制。SPOC-SQL 按 SQL 执行逻辑把 text-to-SQL 拆为四个顺序子任务，对每个阶段设计特定优化策略，在关键决策点做细粒度偏好优化。结构化分解策略通过显式中间表示支持 stage-wise 干预与纠错，实现更可控可靠的 SQL 生成。实验证明 stage-wise 人类知识一致提升性能。引用数待核实（Semantic Scholar 限流，8/24 新文预期 0）。
🔍 技术视角：SPOC-SQL 的四阶段分解与 8/17 Bounded Semantic Planning 的'把 LLM 的随机性放在语义理解而非 SQL 编译'同向——都主张把 text-to-SQL 拆为结构化中间步骤而非端到端生成。stage-wise 偏好优化可迁移到用户'API 调用'场景：把 API 调用拆为意图理解→参数填充→调用→结果解读四阶段，每阶段独立优化与纠错。

📊 架构示意

🎯 为什么值得关注

单步生成无法在关键决策点提供针对性反馈，错误归因困难。四阶段分解使每步可独立评估、干预、纠错，提升可控性与可靠性

⚙️ 核心机制

SQL 执行逻辑拆四阶段 → 每阶段特定优化策略 → 关键决策点细粒度偏好优化 → 显式中间表示支持 stage-wise 干预纠错

🧠 深度解读

与 ReAct-SQL（同日批次）互补：SPOC-SQL 从训练侧（偏好优化）做阶段分解，ReAct-SQL 从推理侧（DSL+迭代）做阶段分解。两者共同指向'端到端 text-to-SQL → 结构化多阶段'范式转移。SPOC-SQL 的'阶段间中间表示'与 Bounded Semantic Planning 的'语义请求→确定性 kernel 编译'本质同构

💼 商业启示

stage-wise 优化降低了对'一个超级模型端到端'的依赖——每阶段可用不同模型/策略，降低单点失败风险。对企业 API 调用场景，分阶段优化使每阶段可独立监控和改进，降低整体运维复杂度

🛠️ 落地建议

1) API 调用拆四阶段：意图理解→参数映射→API 调用→结果解读，每阶段独立评估；2) 收集各阶段偏好数据做 stage-wise DPO；3) 显式中间表示便于人审与纠错

⚠️ 局限与风险

四阶段划分是否对复杂 JOIN/子查询/窗口函数普遍有效未验证。stage-wise 偏好数据收集成本高。引用数未核实

ReAct-SQL: 15 算子 DSL + 迭代推理替代复杂 text-to-SQL 管线

2026-08-23 · arXiv 2608.22651
现代 text-to-SQL 系统过度复杂——schema-linking 模块+RAG 提示+候选生成+多阶段精修管线，引入大量延迟与工程开销。本文提出 ReAct-SQL：零样本 ReAct 框架，用 15 关系算子的 typed DSL 替代自由 SQL 生成。模型增量发 DSL 调用，观察编译 SQL 执行反馈，修正推理。在 BIRD mini-dev 84.5%/EHR-SQL 73.9% 准确率匹配复杂基线且快 8x。消融显示迭代改善 grounding，DSL 改善组合可靠性。引用数待核实（Semantic Scholar 限流，8/23 新文预期 0）。
🔍 技术视角：ReAct-SQL 的 15 算子 DSL 对用户'上百字段宽表 API'场景直接可迁移：与其让 LLM 生成完整 API 调用参数（上百字段），不如定义一组 typed API 操作算子（过滤/聚合/分组/排序/限制），让 LLM 增量组合。DSL 约束降低组合不可靠性，迭代改善字段 grounding。快 8x 对实时业务查询是硬优势。

📊 架构示意

🎯 为什么值得关注

复杂管线（schema-linking+RAG+候选+精修）延迟高、工程重。15 算子 DSL+迭代用更简结构达同等精度且快 8x，证明'复杂管线非必要'

⚙️ 核心机制

15 关系算子 typed DSL（非自由 SQL）→ 增量发 DSL 调用 → 编译为 SQL → 观察执行反馈 → 修正推理。迭代改善 grounding（字段对齐），DSL 改善组合可靠性（算子组合不会产生语法错误的 SQL）

🧠 深度解读

三个层次改善：(1) DSL 把自由生成约束为有限算子组合空间，降低组合爆炸；(2) 编译反馈提供确定性验证信号（执行成功/失败/行数）；(3) 迭代让模型从执行反馈中修正 grounding 错误。与 8/14 Never the Number 的 trusted kernel+generative shell 同构——DSL 是 trusted kernel，ReAct 循环是 generative shell。与 8/24 SPOC-SQL 互补：ReAct 推理侧分解，SPOC 训练侧分解

💼 商业启示

快 8x 是实时业务查询的硬 ROI——用户通过 API 查数时延迟敏感。15 算子 DSL 可标准化为'业务查询算子库'，成为语义层的新产品形态（Cube/MetricFlow 可集成）。降低管线复杂度=降低运维成本与故障面

🛠️ 落地建议

1) 为业务 API 定义 typed 操作算子集（filter/group/aggregate/sort/limit/join）；2) 让 LLM 增量组合算子而非生成完整参数；3) 每步编译为 API 调用并观察执行反馈；4) 快 8x 适合实时业务查询场景

⚠️ 局限与风险

15 算子是否覆盖所有业务查询模式（窗口函数/CTE/递归）未明确。BIRD mini-dev/EHR-SQL 是简化 benchmark，生产复杂度更高。零样本可能在高复杂度查询上不如有样本方法。引用数未核实

RAD: 关系库异常检测拒绝扁平化，保留多表 schema 与多跳依赖

2026-08-24 · arXiv 2608.23468
现有异常检测方法需把多表扁平化为单特征矩阵，这遮蔽了 entity identity、schema 结构、多跳依赖，限制了依赖关系上下文而非孤立特征值的异常检测。RAD（Rule-Augmented Relational Anomaly Detector）结合异构图表示学习与符号规则信号：从 random-forest 路径提取候选规则→精炼为紧凑可解释谓词→注入图模型。在 LANL 网安事件检测+Amazon/H&M 用户流失三场景上，AUROC/AUPRC 平均排名最佳。消融显示直接规则注入+ranking-based 监督是关键，edge reconstruction 非一致有益。引用数待核实（Semantic Scholar 限流，8/24 新文预期 0）。
🔍 技术视角：RAD 对用户'业务知识图谱'路线直接相关：证明保留关系结构（不扁平化）+符号规则注入图模型优于传统扁平化方法。对用户'上百字段宽表 API'，宽表本身是多表 join 的扁平化结果——RAD 启示应在 join 前的源表上做异常检测，保留 entity identity 与多跳依赖。规则注入图模型与 8/19 Policy Algebra 的 path property 约束注入同向。

📊 架构示意

🎯 为什么值得关注

扁平化丢失 entity identity/schema 结构/多跳依赖——而这些正是业务异常（如跨表关联的欺诈模式）的关键信号。RAD 证明保留关系结构+规则注入优于扁平化

⚙️ 核心机制

多表关系库 → 异构图表示学习（保留 entity identity+schema+多跳） → random-forest 路径提取候选规则 → 精炼为可解释谓词 → 规则特征注入图模型 → reconstruction-based+pairwise-ranking 监督

🧠 深度解读

三个创新点：(1) 不扁平化——直接在多表上建异构图，保留关系上下文；(2) 规则从 random-forest 路径提取（非人写），自动发现 + 精炼为可解释谓词；(3) 规则注入图模型（非替代），学习+符号混合。与 8/17 VDGR-RAG 的'目录即图谱骨架+四路统一'共振：两者都在关系结构上建图而非扁平化。edge reconstruction 非一致有益是个重要负面发现——并非所有图结构信号都有用

💼 商业启示

保留关系结构做异常检测对反欺诈/风控/客户流失有直接商业价值——跨表关联的异常模式（如同一实体在不同表的矛盾属性）是扁平化方法会漏检的。规则注入使检测结果可解释，满足合规审计需求。对业务知识图谱路线，RAD 提供了'图+规则'混合架构的实证依据
