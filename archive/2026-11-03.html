修 bug 失败后把记录喂回去有用吗？181 次重试全不显著，唯独完整 transcript 比一句「你失败了」多解 12.2 个点

2026-10-30 · arXiv
研究在 75 个 BugsInPy 真实 Python bug 上，对 gpt-5.4-mini 的 181 次失败尝试做五种条件下的重试：原始 transcript、模型自写 lesson、抽取的测试信号、仅通知失败、朴素重试。所有记忆条件相对朴素重试的点估计提升为 +5.5~9.9pp（基线 29.8%），但没有一个达到显著。模型自写的 lesson 相比它总结的 transcript 没有优势（-1.7pp，95% CI [-8.7,+4.9]；gpt-5.4 上 -3.5pp），却多花一次模型调用。仅「通知失败」不产生显著变化，而完整 transcript 比通知多解决 12.2pp（CI [+4.2,+20.0]），这是 12 个预注册对比中唯一显著的。全量测试复核还发现：看过上次测试结果的记忆重试，更常弄坏参考修复能通过的其他测试。
🔍 技术视角：这可能是本期对研发知识库最有杀伤力的一条：我们习惯把失败「蒸馏」成经验卡/lesson，但实验显示蒸馏反而丢掉了有效信号——真正起作用的是原始轨迹里的报错、堆栈、被改文件与测试输出。对架构师的直接含义是：失败记忆应该存「可重放的证据包」，而不是「模型写的总结」；经验库的检索粒度应是失败现场，而非抽象教训。同时要注意，收益在统计上并不稳，说明失败记忆不是银弹，样本间方差远大于条件间差异。

📊 架构示意

🎯 为什么值得关注

coding agent 的重试策略几乎都默认「给它失败记录会更好」，但此前缺少在真实 bug 上、带预注册分析与显著性检验的量化。这篇把「记忆到底改变了什么」拆开：是知道失败了、是看到细节、还是看到测试信号。

⚙️ 核心机制

实验对每个失败尝试在五种条件下重试：plain retry、完整 transcript、模型自写 lesson、抽取的测试信号、仅 notice。两个预注册跟进用更大的 gpt-5.4 重复 plain/transcript/lesson 并加入 notice-only 对照。度量用 bug-revealing tests，另做全量测试套件复核，检查是否引入回归。

🧠 深度解读

结果结构很清晰：第一，记忆的「存在」几乎无价值（notice-only 不显著）；第二，记忆的「信息密度」有价值（transcript 比 notice 多 12.2pp）；第三，记忆的「再加工」是负价值（lesson 更差还更贵）。作者还观察到记忆重试更少出现「一行 Python 都没改」的空转，说明 transcript 主要修复的是「没进入状态」而不是「推理不对」。但全量测试显示，带测试结果的记忆会把 agent 推向「只让当前失败测试通过」的过拟合，弄坏别的测试——这正是 SWE 基准长期被诟病的 reward hacking 微缩版。

💼 商业启示

商业上，这支持「卖证据、不卖结论」的产品方向：失败诊断/修复产品的差异化不在生成多漂亮的复盘，而在能否保存并重放原始现场。对企业内部平台，失败经验库若只存一段自然语言总结，复用价值接近于零，还会误导后续 agent。

🛠️ 落地建议

① 研发知识库把失败案例存成 evidence bundle：命令、报错原文、diff、相关测试输出、环境指纹，检索时整包注入，不做 LLM 摘要；② 重试时只注入「失败现场」，不注入「上次测试通过情况」，避免过拟合当前测试；③ 把「重试是否引入其他测试回归」作为重试策略的在线指标，而不是只看目标测试。

⚠️ 局限与风险

样本是 75 个 Python bug、单一模型家族，181 次失败尝试，作者自己标注为 exploratory 并给出确认性研究所需样本量；12 个预注册对比只有 1 个显著，不能据此宣称 transcript 普遍有效；全量测试复核是 post hoc。

CodeSpecWeave：4,670 个互相打架的规格任务——长程编码的难点不是规格数量，是规格之间的耦合

2026-10-29 · arXiv
论文指出当前 coding agent 的训练/评测任务规格既少又单一，只强调主目标而忽略接口兼容、错误处理等约束。CodeSpecWeave 用「合成 agent 迭代生成耦合需求 + 可执行测试、review agent 多模型审计轨迹」的流水线，造出 4,670 个训练任务（覆盖 2,865 个仓库），并在其上做 RL，在 DeepSWE-v1.1 上大幅超过基线。作者另建 CodeSpecWeave-Bench：100 个任务、1,044 条规格，能清晰拉开前沿模型差距，说明「处理相互依赖的工程约束」仍有显著 headroom。
🔍 技术视角：「多加几条要求」不会让任务变难，只会让它变成打勾清单；真正难的是约束之间互相牵制（改接口就破坏错误处理，修错误处理又违反兼容性）。这对研发知识库的设计有直接启发：知识条目不应是孤立规范，而应显式记录规范之间的依赖与冲突，让 agent 在改动前看到「这条约束和那条约束会打架」。

📊 架构示意

🎯 为什么值得关注

长程编码 agent 的 benchmark 长期被批评为「单文件、单目标、测试即真理」。这篇把「多规格交互」作为一等公民，并给出可训练的合成方法与可区分的评测集。

⚙️ 核心机制

以真实开发者 seed 为起点，synthesis agent 迭代生成成对的耦合需求与可执行测试；review agent 审计多个模型的解题轨迹，过滤掉测试不可靠或存在隐藏缺陷的样本。产出 4,670 个任务用于 RL；另人工策展 100 个任务、1,044 条规格作为 bench。

🧠 深度解读

关键在于「耦合」而不是「数量」：作者明确说朴素增加规格会把任务退化成 trivial checklist，因为模型可以逐条满足而不用联合推理。评测显示前沿模型在耦合约束下差距被放大，说明现有模型擅长局部满足、不擅长全局一致。这与此前 PACE 的「组件产出≠完整交付」是同一问题的两个侧面：一个是交付完整性，一个是约束一致性。

💼 商业启示

如果团队要把「AI 写代码」变成可交付能力，验收标准应从「功能通过」升级为「多维约束同时满足」。这也是企业采购 coding agent 时最该问的问题：它在接口兼容、错误处理、可观测性这些非主目标上的通过率是多少？

🛠️ 落地建议

① 研发知识库为每条规范记录 depends-on / conflicts-with 关系，形成「规范图」而非规范列表；② CI 里加「约束交互测试」：不仅测新功能，还测旧约束是否被破坏；③ 训练/评测内部 agent 时，用真实 PR 的 review 意见反向合成耦合规格，而不是堆自然语言要求。

⚠️ 局限与风险

合成任务与真实仓库仍有分布差异；bench 只有 100 个任务，统计功效有限；RL 提升依赖基座模型与训练配方，论文未证明可无条件迁移到闭源 agent。

Soei 审计 45 个真实编码会话：23.4% 的改码片段最后没有任何独立检查，57.8% 的「已完成」待办中间没有证据

2026-10-29 · arXiv
作者先核对开源可观测工具 Agenttrail 的源码（commit e4ba2da）：九项机制成立，但两条事件流水线从未合并、Map 服务存在未认证的本地写入面。随后在 45 个真实 coding agent 会话（102,233 条记录、20,577 次工具执行、2,336 个人机回合）上跑原型，用盲审分类器（precision 83.3%/96.7%）估计：23.4%（95% CI 17.1-35.7）的改码片段在最后一次编辑后没有任何独立检查；57.8% 被 agent 标记完成的待办，中间没有证据。另有 42% 会话超过 24 小时、48.1% 的 transcript 字节超出 2MiB 重放边界、16 个会话含 1,326 条疑似凭证。Soei 用 acknowledgement-aware 事件 schema、哈希链本地账本、W3C PROV 图与「声明/证据分离」的验证层来替代原始 transcript：账本只有原始体积 20%，约 126k events/s 校验，可检测篡改并确定性重放。
🔍 技术视角：这是「agent 可观测性」从日志采集走向证据学的标志。它给出的两个数字——23.4% 无独立检查、57.8% 完成无证据——足以否定「agent 说完成就是完成」的验收方式。对研发知识库的启示：知识库不只要存「怎么改」，还要存「谁验证了、验证了什么、证据在哪」，否则只是另一种不可信的记忆。

📊 架构示意

🎯 为什么值得关注

coding agent 已经能连续工作数小时甚至跨天，但人类回来时面对的是一大段 transcript。「说了什么」与「做了什么、谁确认、是否完成」是四个不同问题，现有工具把它们混在一个不可重放的日志里。

⚙️ 核心机制

Soei 定义 acknowledgement-aware 事件 schema（区分 agent 声明、工具回执、人类确认），用哈希链把事件串成本地账本，并映射到 W3C PROV 图做归因与血缘；验证层把「完成声明」与「完成证明」分开，只有存在独立检查证据时才允许标记完成。

🧠 深度解读

论文的价值一半在测量、一半在数据结构。测量上，它把「无检查改码」变成可估计的比例，并暴露 transcript 作为审计载体的三个硬伤：太长（48.1% 超出重放边界）、含敏感信息（1,326 条凭证样字符串）、不可验证（可被改写）。结构上，账本只保留事件与哈希、不存内容与凭证，体积降到 20%，却仍能确定性重放——这给出了「可审计」与「数据最小化」兼得的工程答案。

💼 商业启示

对企业来说，「AI 完成了多少」不能再用 agent 自报。可售卖的是一套证据账本：谁改的、改了什么、谁验的、证据哈希。它同时满足审计与合规，也能把「AI 产出」折算成可结算的交付。

🛠️ 落地建议

① 在 CI/agent 框架里为「完成」增加证据门：最后一次编辑后必须有测试、lint、review 或人工确认之一，否则状态只能是「待验证」；② 用哈希链账本替代全量 transcript 归档，正文留在原系统，账本只存事件指针与摘要；③ 对跨会话交接做内容血缘，而不是靠 10 分钟时间窗猜测。

⚠️ 局限与风险

45 个会话、单一原型，比例估计的置信区间较宽；分类器虽盲审但仍有误判；Agenttrail 的安全问题针对特定 commit，不代表所有工具；账本方案需要 agent 框架配合埋点，改造成本不低。

Claude Code 迁移 14 万行 Fortran：35,000 行 C++/Kokkos，100 成员系综统计一致，GH200 1.71×

2026-10-30 · arXiv
日本团队用 Claude Code 在人工 review 下，把 legacy 气候模式 NICAM（OpenACC 加速的 Fortran）迁移到 C++/Kokkos：分析约 140,000 行 Fortran，产出 35,000 行 C++/Kokkos，覆盖动力核心与七个物理包。验收不是「能编译」，而是 100 成员系综与原始 Fortran 模型比对，结果统计一致；性能在 GH200 上应用加速 1.71×、MI300A 上 1.54×，CUDA kernel 1.38×，HIP 按峰值带宽归一化后为 Fortran/OpenACC 的 0.96×。
🔍 技术视角：这篇给出了「AI 做大规模重构」最可信的验收模板：等价性用系综统计而非单次输出，性能用峰值带宽归一化而非裸 speedup。对研发团队，真正可复用的不是「Claude Code 能写 Kokkos」，而是这套「迁移可接受性」的度量设计——它把「AI 改的代码对不对」变成了可证伪的科学问题。

📊 架构示意

🎯 为什么值得关注

legacy HPC 代码迁移成本极高、风险极大，此前 AI 迁移多为小规模演示。NICAM 是真实业务级科学软件，14 万行、含 GPU offload，迁移后还要在两种加速器上保持性能。

⚙️ 核心机制

agent 逐段把 Fortran 翻译为 C++/Kokkos，人类负责 review 与架构决策；迁移覆盖动力核心与七个物理包。验证用 100 成员系综跑同一初值，比较统计分布；性能在 NVIDIA GH200 与 AMD MI300A 两套集群上测应用时间与 kernel 时间，并按峰值内存带宽归一化。

🧠 深度解读

值得注意的两个细节：第一，代码量从 14 万行降到 3.5 万行，说明迁移同时发生了抽象重构（Kokkos 的并行抽象替代了手写 OpenACC 指令），这既是收益也是风险——等价性验证必须覆盖重构引入的语义变化。第二，HIP 归一化后 0.96× 而非更高，作者没有掩饰「跨厂商仍有损耗」，这种报告方式比单一 speedup 更可信。

💼 商业启示

企业遗留系统现代化（COBOL/旧 ERP/自研 DSL）可以照搬这套验收：AI 负责翻译，人类负责语义决策，验收靠「业务金标准 + 性能基线」。这也是把「AI 重构」从 demo 变成可签合同交付的关键。

🛠️ 落地建议

① 大规模迁移项目把验收写成三层：编译/单测、系综或金标准数值一致、目标硬件性能归一化；② 让 agent 做「翻译 + 局部重构」，人类保留并行模型与数值方法决策；③ 迁移前先冻结一套金标准输入与统计口径，否则无法证明等价。

⚠️ 局限与风险

单一应用、单一时段，Claude Code 的具体版本与提示未完全披露；系综一致不等于所有边界条件一致；性能对比依赖编译器与 Kokkos 版本，跨平台结论需复现。

Caper：先沙箱跑一遍再审批——有害命令率 6.7% vs 14.8%，把「命令文本」换成「实际后果」

2026-10-29 · arXiv
现有 coding agent 的自动审批器（规则、guardrail 模型、权限分类器）都基于请求与命令文本做判断，但一条命令的行为取决于它调用的代码与工作区状态。Caper 改为：在快照沙箱中预执行每条命令，把观测到的有界后果报告给独立审批器，允许则提交、拒绝则回滚并给出 agent 可操作的理由。在 SABER 上有害结果率 6.7%（六个对比系统至少 14.8%）；在作者新建的 YoloFS-Ext（有害行为藏在被调工具里）上 7.8%（对比至少 35.3%），同时只误拦 1.0% 的安全孪生任务。
🔍 技术视角：审批的粒度应该是「后果」而不是「意图表达」。这对所有 agent 权限系统都适用：模型可以写出一行看起来无害的 shell，但真正的风险在它调用的脚本、环境和文件状态里。Caper 的「预执行 + 有界报告 + 可回滚」是把权限系统从静态规则升级为动态后果验证，且不需要理解命令语义。

📊 架构示意

🎯 为什么值得关注

coding agent 越来越常执行 shell；现有审批器看文本，容易放过「无害命令调用有害工具」，也容易误杀正常操作。安全与可用性在这类系统里长期是跷跷板。

⚙️ 核心机制

每条待执行命令先在快照沙箱中跑一遍，收集文件系统、网络、进程等有界后果，形成报告交给独立审批器；批准则在真实工作区提交，拒绝则回滚并返回原因。YoloFS-Ext 专门构造「有害行为隐藏在 invoked tool 内」的样本，用来打现有文本审批器的盲区。

🧠 深度解读

66.7% 到 6.7% 的差距说明：文本信号与真实后果之间的相关性远比我们以为的弱。更值得注意的是 1.0% 的误拦率——安全机制如果误杀太多，开发者会直接关掉它，所以这个数字和召回同样重要。Caper 的代价是每条命令都要预执行，延迟与沙箱成本是真实的，但在高风险写操作上可以按风险分级启用。

💼 商业启示

企业 agent 的「写操作审批」可以照搬这个模式：先在影子环境调用业务 API 看影响面，再决定是否提交。它也能把合规从「制度约束」变成「技术闸门」，减少对人工审批的依赖。

🛠️ 落地建议

① 对写操作/网络操作/删除操作做分级：高风险命令走沙箱预执行 + 后果报告，低风险命令保留快速规则；② 审批器与执行器解耦，审批器只看结构化后果报告，不看 agent 的自述；③ 回滚必须带可操作理由，否则 agent 会重复尝试同一条被拒命令。

⚠️ 局限与风险

预执行会改变外部世界（网络请求、第三方副作用），快照只能覆盖本地文件与部分环境；沙箱成本高；YoloFS-Ext 是作者自建基准，需第三方复现；对长时间运行的命令不适用。

Post-SQLFix：把 SQL 修复当程序修复——解掉 77.8% 执行反馈修不了的错，绝对准确率 +11.6pp

2026-10-30 · arXiv
论文指出 text-to-SQL 修复的「仲裁悖论」：系统用同一个未经验证的 LLM 既提出修复、又判断修复是否满足属性要求。Post-SQLFix 把修复重构为属性引导的程序修复：先把 SQL 规范化成方言感知的 Canonical Query Structure（CQS），再用三层静态分析器（语法、上下文无关结构、上下文相关语义）产出精确的 schema-aware 违规诊断，最后用 Verify-Before-Apply 时序监视器只接受「违规数下降、不重新引入已解决违规、满足算子契约」的补丁。在 BIRD/Spider/Mini-Dev 三个基准、3,000+ 实例、三种方言、六种模型配置上，解决了 77.8% 执行反馈修不了的错误，迭代次数不到一半、token 少 30%，绝对准确率最高 +11.6pp，且被接受的补丁没有引入静态可检测的结构回归。
🔍 技术视角：这是「LLM 提议、符号验证」在数据查询上的漂亮落地：把「修得对不对」从模型自评变成可判定的属性单调性。对用户「不直连数据库、走宽表 API」的场景，等价思路是把 API 查询语言也规范化成结构（字段、过滤、聚合、时间口径、权限），用静态检查器给诊断，并要求每次修复单调减少违规——这样即使没有数据库执行反馈，也能做可信修复。

📊 架构示意

🎯 为什么值得关注

生产 text-to-SQL 的错误大量来自 schema 绑定、作用域、类型与方言差异，而执行反馈只给症状级、方言相关的报错，模型只能猜根因；更糟的是让同一个模型当裁判，等于没有裁判。

⚙️ 核心机制

CQS 把 SQL 归一化为方言感知的规范结构；三层静态分析分别检查语法、结构（如 CTE/子查询作用域）、语义（类型、schema 绑定、算子契约），输出带位置的违规列表。修复循环只接受满足三条不变式的补丁：违规总数下降、不重新引入已解决项、满足算子契约；重试预算有限保证停机。

🧠 深度解读

关键设计是「单调性」而非「正确性」：系统不声称能证明补丁正确，只保证每次接受的修改都在可检测维度上前进。这把一个开放-ended 的生成问题变成了有偏搜索，并且天然防止「修好 A 弄坏 B」的振荡。77.8% 是相对执行反馈修不了的剩余错误，说明执行反馈的召回有明显天花板；+11.6pp 的绝对提升则证明修复质量能传导到最终准确率。

💼 商业启示

这为「可信查询」提供了产品化路径：卖的不是「一次生成正确」，而是「每次修复都可验证地更好」。对语义层厂商，内置属性检查器可以显著降低 agent 查询的运维成本；对企业，它把数据查询的可靠性从模型能力问题变成工程质量问题。

🛠️ 落地建议

① 为业务查询/宽表 API 定义 3 层属性：字段存在与类型、过滤/聚合结构合法、业务口径与权限契约；② 让 LLM 只产出候选补丁，由确定性检查器决定是否接受，且要求违规数严格下降；③ 记录每次修复的违规前后快照，作为审计与回归样本。

⚠️ 局限与风险

属性层由规则族与算子契约界定，覆盖不到语义正确性（查询是否回答了用户真正的问题）；基准以学术数据集为主，企业宽表/API 场景的 schema 更脏；静态分析器需要为每种查询方言/API 维护规则，工程成本真实存在。

🛠️ 落地建议

① 语义层/指标平台为每个指标存 revision（生效日期、知识截止、变更原因），查询时锁定 revision；② 维护一小套「合法反例」数据（边界日期、税率切换点、退款归属边界），作为口径回归测试；③ 口径变更时做影响面扫描：哪些已保存查询/报表在新 revision 下会变，输出差异清单而不是等用户发现。

⚠️ 局限与风险

反例与修订族是作者撰写的，覆盖面受限于其 schema 与本地模型；一致不等于证明正确，只说明在记录的套件内未发现反例；12 个单元未决，说明方法仍有盲区；企业真实口径变更往往没有清晰的修订记录。

📊 架构示意

🎯 为什么值得关注

数据 agent 的很多失败不是模型推理错，而是它信了错误的工具输出。现有评测多测最终答案，缺少对「检查行为」与「采纳行为」的分离测量。

ToxicBench 对同一份源数据生成干净与投毒两版观测，比较任务成功率；记录 agent 是否进行了检查、检查后是否仍采纳错误证据。四类错误分别针对数值、标签、schema 和检索结果；评分器冻结后与人工标注对齐。

🧠 深度解读

最有价值的发现是「检查后采纳」：agent 可能确实调用了校验工具、看到了冲突，但仍然选择相信更早或更自信的那个数字。这解释了为什么很多「加个验证步骤」的补丁无效——验证产生了证据，却没有改变决策规则。作者因此把可靠性拆成证据可得性与答案选择两个维度，后者需要显式的冲突解决策略，而不是更多的工具调用。

💼 商业启示

🛠️ 落地建议

① 对关键数字做双来源对账（如汇总接口 vs 明细接口），冲突时拒答或标注不确定；② 在工具返回中携带 provenance（接口、时间、口径版本），让 agent 能判断证据新旧；③ 把「检查后是否改变答案」作为评测指标，而不只测最终准确率。

⚠️ 局限与风险

🔍 技术视角：两个改动分别对应 agent 时代的两个真问题：列式响应降低了大结果集的序列化与传输开销，利于 agent/程序消费；granularity origin 修复则说明语义层的护城河在「口径边界」——财年、财季、自定义起点这些细节，恰恰是 LLM 最容易想当然算错的地方。对用户，宽表 API 也应提供列式/字段投影，并把 origin 显式建模，而不是让调用方拼 SQL。

📊 架构示意

🎯 为什么值得关注

语义层过去主要服务 BI 工具与人类分析师；agent 成为新消费者后，响应格式、上下文体积、口径精确性都成了瓶颈。Cube 这两个改动是产品层面对新消费模式的适配。

⚙️ 核心机制

responseFormat=columnar 时，每个 data chunk 按 schema 列存放，ArrowColumn 直接从 RecordBatch 的 Arrow 数组序列化，避免 DataFrame 转换，并用 parity 测试覆盖所有 Arrow 类型、与行式结果字节一致；另一个修复让滚动窗口的基准粒度取「窗口单位、查询粒度 min_granularity（含 origin/offset）、to_date 周期粒度」三者中最细的，保证每个基准桶落在单一查询桶内。

🧠 深度解读

财年 origin 的 bug 很典型：按 interval 单位（year）分组会让桶跨越财年边界，滚动窗口于是把「财年内的日历年」加总，结果看起来合理但口径错误。这类错误 LLM 几乎无法自查，因为它需要知道 origin 的语义。语义层的价值正在于此——把口径的复杂性收进模型，让上层（人或 agent）不用重复推导。列式响应则是另一个方向的优化：减少序列化与 token 开销，让 agent 能处理更宽的结果。

💼 商业启示

语义层厂商的竞争点正在从「支持多少数据源」转向「口径是否可信、是否适合 agent 消费」。对企业，选型时应重点测试财年/财季/自定义周期这些边界，而不是只看 demo 的简单聚合。

🛠️ 落地建议

① 宽表 API 增加 fields 投影与 columnar 选项，减少无效字段传输；② 语义层为所有时间指标显式记录 origin/offset/财年规则，并提供口径回归用例；③ 让 agent 通过语义层查询而非拼 SQL，把口径正确性下沉到平台。

⚠️ 局限与风险

Cube 是产品 release，非学术评估；columnar 主要优化传输/序列化，不改变查询正确性；财年修复只覆盖 tesseract 引擎的特定路径；版本迭代快，需锁定版本并做回归。
