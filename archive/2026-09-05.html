From Data Querying to Data Investigations：重新定义 NL 数据接口范式

2026-09-03 · arXiv (cs.DB)
Wenz/Chen/Binnig（TU Darmstadt）论证 text-to-SQL 优化了错误问题：主导范式假设用户问的是"单条 SQL 可答"的问题，但真实用户要的是解决数据问题——需用多条 SQL 序列搜索数据库、在中间结果上推理、收集证据。提出 data investigations 新范式，呈现 D² 原型自主搜索/推理/收集以解决数据问题，基于 Murder Mystery 数据集构造新基准，展示证据支撑决策、超越单查询问答的能力。
🔍 技术视角：对用户"业务系统精确查询分析"方向是范式级信号：用户不直连数据库而是调业务 API，单次 API 调用类比单查询——但业务分析真实需求是多步调查（先查 A 再据结果查 B）。D² 的"中间结果推理+证据收集"恰好是 agent 调多 API 的正确心智模型。用户上百字段宽表 API 场景下，单次返回可能信息过载，需 agent 在中间结果上做选择与再查询——这正是 data investigations 的定义。建议把内部 text-to-SQL/API 调用评测从"单查询精度"升级为"多步调查证据链完整度"。

📊 架构示意

🎯 为什么值得关注

当前 text-to-SQL 基准（Spider/BIRD）几乎都评单查询执行精度，但真实业务系统用户行为是多轮探索；评测与真实任务之间的鸿沟是 enterprise text-to-SQL 部署失败的主因之一，与 8/24 Beyond the Harness 的"context artifacts ROI"共振。

⚙️ 核心机制

D² 把任务建模为自主搜索循环：序列化 SQL 查询 + 中间结果推理 + 证据收集 + 决策。证据支撑决策是关键——不是返回一个数，而是返回"为什么是这个数"的证据链。Murder Mystery 基准天然需要多步推理（凶手=多线索交集）。

🧠 深度解读

这篇与 8/29 BIRD-History（历史 SQL 日志承载业务逻辑）、8/30 TIDE-Bench（对话 chain ambiguity+intent drift）形成 text-to-SQL 范式转移三联：BIRD-History 说"用户查询隐含领域知识"，TIDE-Bench 说"对话有意图漂移"，本文说"任务本质是多步调查"。三者共同指向"单查询精度≠业务系统效果"。data investigations 范式把 agent 从"SQL 生成器"升级为"数据调查员"，要求对话状态管理+中间结果记忆+证据溯源——这与 MaP-SQL（9/1，可复用结构化记忆）+Zeta-Lite（9/1，agent 记忆数据库）同日出现的记忆主题共振。

💼 商业启示

对业务/产品的启示：业务 BI 从"问一个问题得一个数"升级为"启动一个调查"。这改变产品形态——不是 chatbot 返回数字，而是调查报告含证据+推理路径+可信度。对受监管行业（金融/保险）尤其有价值：审计要求证据链而非单值。

🛠️ 落地建议

内部评测套件应增加"多步调查"类任务：给定一个业务问题（如"上月华东区哪个产品线退货率异常"），agent 需调多个 API + 在中间结果上推理 + 返回证据链。用 Murder Mystery 式基准设计（答案=多线索交集）而非单值 QA。

⚠️ 局限与风险

D² 是原型+小基准，Murder Mystery 是合成数据集，真实业务 API 的多步调查复杂度远高（上百字段宽表 API 的中间结果可能极宽）。证据链完整度评测本身需治理（什么算"充分证据"）。

Zeta-Lite：浏览器内并发可分支 SQL 数据库做 Agent 记忆

2026-09-01 · arXiv (cs.DB, cs.AI)
Gene Zhang 提出 zeta-lite——Zeta 数据库引擎的浏览器形态：WebAssembly 构建 2.87MB gzip，保留 log-centric 异步 MVCC 核心，提供两个其他浏览器 SQL 引擎没有的能力：(1) 单线程上重叠快照隔离事务（多事务持不同读/提交时间戳交错，带快照隔离冲突检测）；(2) copy-on-write 整库分支（fork/merge/rebase，浏览器 SQL 库独有）。完整 PostgreSQL 表面含 joins/CTE/窗口函数/JSONB+GIN/全文检索/HNSW 向量检索/SQL/PGQ 图查询/多库/OPFS 持久化。Chrome/Firefox/原生运行时 268k-315k 点读/s，混合读写百万操作保持平稳。
🔍 技术视角：对用户"业务知识库构建"+"业务系统精确查询"方向是基础设施级新选项：agent 记忆不再只是向量库+KV，而是"带事务语义的浏览器内 SQL 库"。copy-on-write 分支能力对"业务数据可信度验证"极有价值——agent 可 fork 一份数据快照做假设性推理（what-if）而不污染主记忆，merge/rebase 支持把验证结论归并。SQL/PGQ 图查询+HNSW 向量在一个库内意味着"语义层 vs 知识图谱"双路线在 agent 记忆层可统一承载。

📊 架构示意

🎯 为什么值得关注

浏览器已成数据库一等宿主：隐私、离线、本地优先协作，以及最近——in-browser AI agent 的持久记忆。PGlite（PostgreSQL 编译到 WASM）继承单连接串行阻塞模型，无法表达并发事务，图查询/分支能力受限于编译进来的服务。zeta-lite 填补并发+分支缺口。

⚙️ 核心机制

log-centric 异步 MVCC：多事务持不同读/提交时间戳交错，快照隔离冲突检测。copy-on-write 分支：整库 fork/merge/rebase，类似 git 语义但作用于数据库状态。SQL/PGQ 图查询内嵌意味着关系+图查询统一在 SQL 表面。OPFS（Origin Private File System）做快照持久化。

🧠 深度解读

这与 8/25 microsoft/typeagent-py（Structured RAG ingest/index/query）+9/1 MaP-SQL（可复用结构化记忆）形成"agent 记忆基础设施"主题周。Zeta-Lite 的关键差异是"事务+分支"——向量库是检索语义，KV 是存取语义，zeta-lite 是"推理语义"（可 fork 做假设推理再 merge）。对用户上百字段宽表 API：agent 可把多次 API 调用结果存入 zeta-lite，用 SQL 在结果集上做 join/聚合/假设推理，分支做"如果按客户分群会怎样"的 what-if 而不污染主调查记忆。SQL/PGQ 图查询让"业务知识图谱"在记忆层与关系层统一，为双路线提供载体。

💼 商业启示

对产品形态启示：业务 agent 可"本地优先"——敏感业务数据在浏览器内 agent 记忆中推理，只把结论/证据上云。这对金融/医疗等受监管行业是隐私架构卖点。分支能力可产品化为"假设分析"功能。

🛠️ 落地建议

评估 zeta-lite 作为业务 agent 的本地记忆层：API 返回结构化数据入库，agent 用 SQL 在库内推理而非把所有数据塞 prompt。对隐私敏感业务（数据不出浏览器）尤其合适。分支能力用于 A/B 假设验证。

⚠️ 局限与风险

浏览器内数据库受单线程+内存限制，大数据量分析仍需服务端。MVCC+分支的复杂度对 agent 正确使用是门槛（需理解事务/分支语义）。生产成熟度需验证。

Reflect-SQL：自反思 text-to-SQL 框架直面 schema 模糊与检索失效

2026-09-01 · arXiv (cs.IR, cs.AI) — Semantic Scholar 已核实 citationCount=0
Jain/Shrivastava（IIIT Hyderabad）指出 text-to-SQL 实践落地的三大真实复杂度：(1) 数据库 schema 模糊庞大；(2) 结构化数据导致相关表/列检索失效；(3) 多步推理错误累积。提出 Reflect-SQL 自反思框架，在生成候选查询后进行反思修正，针对真实企业 schema 复杂度而非干净基准。Semantic Scholar 核实 citationCount=0 / influentialCitationCount=0（9/1 新文符合预期）。
🔍 技术视角：对用户"业务系统精确查询"方向直接相关：用户不直连数据库但调业务 API，API schema 同样面临"字段语义模糊+上百字段宽表检索失效+多步调用错误累积"三大问题。Reflect-SQL 的自反思机制可迁移到 API 调用场景——agent 生成 API 调用计划后反思"字段选择是否正确+参数是否合理"再执行。schema 模糊问题是业务 API 语义标注（用户核心课题）的直接动因。

📊 架构示意

🎯 为什么值得关注

企业 text-to-SQL 精度差距的主因不是模型而是 context——8/24 Beyond the Harness 已论证。Reflect-SQL 把"自反思"作为补救：生成后批判修正。与 8/28 ReToolSQL（强化学习从执行反馈）形成互补——ReToolSQL 训练时学习反馈，Reflect-SQL 推理时反思。

⚙️ 核心机制

生成候选 SQL → 反思模块批判（字段选择/JOIN 正确性/语义对齐）→ 修正 → 输出。反思针对三大失效模式分别设计。重点是"结构化数据检索失效"——向量检索对列名/表名语义模糊（business_term vs db_column）召回差。

🧠 深度解读

schema 模糊+检索失效与 8/24 Beyond the Harness（context artifacts 是 ROI 杠杆）、8/29 BIRD-History（历史 SQL 日志承载业务逻辑解决隐含知识缺口）、9/1 MaP-SQL（结构化记忆替代 listwise selector 微调）形成 text-to-SQL 系统工程链。Reflect-SQL 补"推理时自反思"维度。对用户宽表 API：上百字段中 agent 需反思"我选的字段是否回答了业务问题+是否有更精确字段+参数值是否合理"——这正是业务 API 语义理解+精准调用的核心。

💼 商业启示

企业落地启示：text-to-SQL/API 调用不应止于"生成即执行"，自反思是成本较低的精度提升手段（vs 微调）。对受监管行业，反思链可作审计证据（为什么选这个字段/参数）。

🛠️ 落地建议

在 API 调用 pipeline 中加反思环节：生成调用计划→反思模块检查（字段语义对齐/参数合理性/是否需补查）→修正→执行。反思模块可基于业务术语表（用户指标平台方向）做字段语义校验。

⚠️ 局限与风险

自反思增加延迟与 token 成本；反思模块本身可能误判（反思幻觉）。citationCount=0 因 9/1 新文，需持续跟踪。论文细节待全文核实（基于摘要）。

Compile by Training：把自然语言规范编译成可版本化的本地神经函数

2026-09-03 · arXiv (cs.CL, cs.AI, cs.LG)
Deng/Nie/Shieber（Harvard）提出 compile by training：把自然语言规范"编译"成可存储、可版本化、可组合的本地神经函数。编译时教师模型生成任务特定样本训练小适配器给紧凑解释器，结果函数运行不依赖教师模型，像普通软件一样存储/版本化/组合。FuzzyBench-Hard（Program-as-Weights 快编译 0 精确匹配子集）上语义准确率 83.6%，编译成本约一分钟（vs 快编译秒级）。已部署公开交互服务，演示多站点网站助手/语言控制 3D 头像/双向英-Claudish 翻译。
🔍 技术视角：对用户"业务语义理解"+"业务系统精确查询"方向是降本减依赖路径：反复出现的文本函数（如业务术语归一化、字段语义判断、API 响应分类）当前要么写规则（难）要么调大模型（贵+延迟+依赖供应商）。compile by training 提供第三条路——把规范编译成本地小函数，运行零远端调用。对上百字段宽表 API 的字段语义标注（如判断某字段是金额/日期/枚举）可编译成确定性本地函数。

📊 架构示意

🎯 为什么值得关注

反复文本函数：规则难写、调大模型贵且延迟+供应商依赖。compile by training 把"描述"变成"可执行资产"，介于规则与大模型之间。

⚙️ 核心机制

编译时：教师模型对自然语言规范生成任务样本→训练小适配器（adapter）给紧凑解释器（compact interpreter）。运行时：适配器+解释器本地执行，不调教师。函数可版本化（规范变则重编译）+可组合（函数调用函数）。FuzzyBench-Hard 83.6% 语义准确率。

🧠 深度解读

这与 8/26 Beyond the Harness（context artifacts）+9/1 MaP-SQL（结构化记忆替代微调）形成"把隐式能力外化为可治理资产"主题。MaP-SQL 把选择准则外化为记忆，compile-by-training 把文本函数外化为编译产物——都是"减少运行时对大模型的隐式依赖"。对用户业务术语表/字段语义标注：可把"判断这个 API 字段是否表示活跃客户"的规范编译成函数，agent 调用时不需每次问大模型。与 Cube 移除 cube.ts（配置代码化）共振——都是把语义从配置/隐式走向代码/显式。

💼 商业启示

商业启示：降低 agent 运行成本+减少供应商锁定。把高频业务判断从"每次调 API"变为"编译一次本地跑"。对大规模部署（数百 agent 并发调宽表 API）是显著成本优化。版本化使业务逻辑变更可追踪。

🛠️ 落地建议

识别业务系统中反复出现的文本判断函数（术语归一化/字段分类/响应路由），用 compile-by-training 编译成本地函数，纳入版本化资产库。降低 agent 运行时 token 成本与供应商依赖。

⚠️ 局限与风险

编译成本约一分钟（非秒级），适合反复函数非一次性。适配器质量依赖教师模型样本质量。复杂推理任务可能仍需大模型。FuzzyBench-Hard 是模糊匹配基准，业务任务效果需验证。

TDS：PDF 表格不展平——RAG 在表格上静默幻觉数字的根因与四层表示

2026-09-03 · Towards Data Science (Enterprise Document Intelligence Vol.1 #B4)
Kezhan Shi 指出表格是"被放进布局格式的数据"——生产者已知是数据，展平为文本即破坏已有行列结构。标准 RAG 管线（读PDF→chunk→embed→检索）在表格上静默幻觉数字，往往审计打开源文档才发现。提出四层表示：(A)行作行 line_df 默认 Markdown 行；(B)独立 table_df 保留 2D；(C)命名类型列式提取；(D)列式存储索引。配五种可组合操作的诊断（非决策树），配套 doc-intel/notebooks-vol1 GitHub。
🔍 技术视角：对用户"业务知识库构建"方向是表格处理工程模板：业务文档（合同/报表/费率表）含大量表格，naive RAG 在表格上失败。四层表示的核心洞察是"按表格形态分治"——稳定 schema 的费率表应列式提取（C/D），混合内容文档的表格行作行即可（A）。这与 8/25 TDS Enterprise RAG 十大纲领"结构优先检索"+8/21 RAG 语料三形态"形态决定架构"共振。

🎯 为什么值得关注

表格单元格的答案在行列交叉点，展平后标签与值分离，模型猜哪个数属哪行。三大失效同时发生：行列结构丢失/多页表头仅首页/行级引用失灵（无法指向"第47行"因为从未重建为行）。

⚙️ 核心机制

四层：(A)行作行 line_df，_type=table，Markdown 管道行，保留 bounding box 供引用，Azure Doc Intelligence 默认输出；(B)独立 table_df，列头作 DataFrame 列，line_df 留占位行指向 table id，需跨页拼接/列投影/行过滤时用；(C)命名类型列式提取，稳定 schema 的重复表（保险费率表/财务报表）提取为列式存储按 doc_id+table_id 索引；(D)列式存储，恢复生产者原有列与类型。五种操作可组合（诊断式非决策树）。

🧠 深度解读

💼 商业启示

对受监管行业（保险/金融）的审计价值：表格答案可引用到行列交叉点而非模糊段落，满足审计证据精度要求。列式提取使费率表可按字段查询而非全文检索。

🛠️ 落地建议

业务文档表格处理：按形态分治——稳定 schema 表（费率/报表）走(C)/(D)列式提取入仓做字段语义标注；混合内容表走(A)/(B)。配套 doc-intel/notebooks-vol1 可直接参考。
