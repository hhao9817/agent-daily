Rosetta：从数据值反推列语义——无文档生产仓库的元数据重建

2026-08-12 · arXiv (cs.DB, cs.AI)
Text-to-SQL 基准的 schema 列名自带语义，但生产仓库是反面：乱码标识符、部分或缺失文档。Rosetta 把 LM 放进验证 harness：确定性 profiler 提取值指纹 + 26 模式库 + checksum 判定，LM 基于证据提议语义，每条事实带 provenance 与按证据类限定的置信度。在 680 列 BIRD 数据上，identifier 被破坏后，harness 在承诺的 42% 列上达 0.475 准确率，对比直接用同模型在 94% 列上的 0.223。在 283 列有基准的子集上表现更优。核心理念：从值本身反推列含义，而非依赖列名。
🔍 技术视角：这是本周最贴合用户'上百字段宽表 API 字段语义标注'痛点的论文。用户场景里 API 返回的宽表往往只有技术字段名（如 col_a01），业务含义丢失。Rosetta 的'deterministic profiler + LM 提议 + provenance + 置信度'三层架构可迁移到 API 响应字段的语义反推：profiler 提取字段值的统计指纹/枚举分布/格式模式，LM 提议业务语义，每条标注带证据来源与置信度——这正是用户业务语义层(semantic layer)自动化建层的可行路径。其'commit only when confident'策略（42% 列承诺但高准确）比盲目全标更可信，适合需要人审核的业务关键字段。

📊 架构示意

🎯 为什么值得关注

直接把 LM 丢给无文档列名做语义标注，幻觉率高且无来源可追溯；Rosetta 用确定性证据把 LM 锚定到可验证事实上，是生产级字段语义标注的范式升级。

⚙️ 核心机制

三层：(1) 确定性 profiler——值指纹（min/max/基数/格式正则）、26 模式库（邮箱/UUID/ISO 日期等）、checksum 判定（如校验和匹配可证 ID 类型）；(2) LM 条件提议——基于证据提议列语义；(3) provenance + 置信度——每条事实标注证据类来源并据此限定置信度，'commit only when confident'。

🧠 深度解读

关键创新在'deterministic profiler 先行'：先用 26 模式库做硬规则匹配（零幻觉），再让 LM 在已锚定证据上做语义命名，最后用 confidence class 控制是否对外承诺。这把'列语义标注'从纯生成任务降为'检索+验证+生成'的复合任务，与 Semantic Scholar 核实引用同理——先用可验证事实缩面，再让模型在缩面内提议。对用户宽表 API，可先 profiler 跑历史样本值，再 LM 提议业务术语，最后人工审核高置信承诺项。

💼 商业启示

商业启示：无文档遗留系统的字段语义重建一直是企业数据治理最贵的人工环节。Rosetta 把成本从'人逐字段标注'降到'LM+证据提议+人审核高价值项'，可直接压缩 semantic layer 的立项成本与上线周期。对从'AI for 研发'转'AI for 业务'的用户，这是把遗留业务 API 快速纳入 Agent 可查数据资产的关键工具。

🛠️ 落地建议

落地建议：(1) 对每个宽表 API，先采历史调用样本（100-1000 条），对每个字段跑 profiler 提取值指纹/枚举分布/格式模式；(2) 用 LM 基于证据提议业务语义候选；(3) 按置信度分层——高置信直接入 semantic layer，中置信入候选表待人工审核，低置信标'语义待定'；(4) provenance 字段写入 semantic layer 元数据，供下游 Agent 查询时回溯'这个字段语义基于什么证据'。

⚠️ 局限与风险

局限：(1) 680 列 BIRD 评测仍偏学术，生产仓库脏数据/动态列可能更难；(2) 0.475 准确率虽优于 0.223 但仍意味着过半承诺可能错，业务关键字段必须人工复核；(3) 26 模式库可能不覆盖业务特定格式（如自定义编号规则），需扩展；(4) Semantic Scholar 引用数因限流未核实，标注信息待核实；论文 2026-08-08 新发，引用为 0 符合预期。

MDB-Link：多库 Schema Linking——从单库假设到跨库路由

2026-08-12 · arXiv (cs.CL)
传统 Text-to-SQL 假设已知目标库，MDB-Link 研究多库场景：查询必须先在大而异的库集合中路由定位。框架三层：(1) 从全局索引检索问题相关列；(2) 聚合检索证据候选库；(3) 预算感知 LLM 做 DB reranking + 选表 + 选列。用 Qwen2.5-14B，在 MMQA、Spider2-Snow、BIRD-dev 的库定位与列选择上超越 LinkAlign，schema 子集接近 gold 大小，exact match 从 16.88 提升。
🔍 技术视角：这是用户'多业务 API/多数据源'场景的关键突破。用户不直连单库，而是面对多个带业务含义的 API，每个 API 背后可能对应不同业务域数据。MDB-Link 的'全局列索引→候选库聚合→预算感知 LLM rerank'流程可直接迁移到'多 API 路由'：先建全局 API 字段索引，用户自然语言问题检索到候选 API 字段，聚合定位候选 API，再用 LLM 做 API reranking + 选字段。它超越了此前收录的 LinkAlign（千字段选列，单库），把问题从'选列'升级到'选库/选 API'。

📊 架构示意

🎯 为什么值得关注

单库 Text-to-SQL 已有大量研究，但真实企业 Agent 面对的是几十上百个业务 API/库，'先选对数据源再查'是更上游、更高价值的未解问题。

⚙️ 核心机制

三层分层：(1) 全局列索引检索——把所有库的列建成全局索引，按问题检索 top-k 相关列；(2) 聚合证据候选库——按检索命中的列归属聚合出候选库列表；(3) 预算感知 LLM rerank——在 token 预算内让 LLM 对候选库重排、选表、选列，产出紧凑 SQL 相关 schema。

🧠 深度解读

创新点在'分层 + 预算感知'：先用检索（便宜）做粗筛，再用 LLM（贵）在缩面内做精排，并用预算控制 LLM 调用成本。这与 Carnot 的'管理 API 成本与执行延迟'理念、ReFoRCE 的'consensus+self-refine'理念交叉呼应——都不信任单次 LLM 生成，而是用检索/预算/共识缩面。对用户，关键是把'选 API'从一次性 LLM 决策变成'索引粗筛→证据聚合→预算精排'的可控流程，降低选错 API 的风险。

💼 商业启示

商业启示：企业数据资产正从'单库 BI'走向'多源 Agent 查询'，谁先建好跨源路由层，谁就能让 Agent 在不直连底库的前提下高效选对源。MDB-Link 为'多 API 路由'提供了可复用的三段式架构，是用户从'单 API 查数'升级到'多 API 智能路由'的技术蓝图。

🛠️ 落地建议

落地建议：(1) 把所有业务 API 的响应 schema（字段名+样本值+业务描述）建成全局向量索引；(2) 用户问题先检索 top-k 相关字段；(3) 按字段归属的 API 聚合候选 API；(4) 用 LLM 在预算内 rerank 候选 API 并选出需调用的字段子集；(5) 只对选定 API 做实际调用，避免全量调用上百 API 的成本。

⚠️ 局限与风险

局限：(1) MMQA/Spider2-Snow/BIRD-dev 仍是学术多库基准，真实企业 API schema 异构性可能更高；(2) Semantic Scholar 引用数因限流未核实，标注信息待核实；论文 2026-08-10 新发，引用为 0 符合预期；(3) 'budget-aware'需企业自定预算策略，过紧会漏选库过松会超成本。

SafeQL：让 DBMS 从被动报错者升级为主动修复向导

2026-08-12 · arXiv (cs.DB, cs.AI)
LLM 生成的 SQL 常引用不存在的表/属性/函数/值，现有系统失败后只靠 DBMS 错误消息被动重生成整条查询。SafeQL 重定义 DBMS 角色：失败后不整体重生成，而是解读 DBMS 反馈增量修复错误片段，每步 refinement 当成 DBMS 引导的受限搜索。把不可靠的 LLM SQL 生成变为有 DBMS 主动护航的搜索修复过程。
🔍 技术视角：与 Carnot 的'可拦截可校验执行图'、ADORE 的'orchestrator+Memory Bank'一脉相承——都不信任单次 LLM 生成，而是把执行环境（DBMS）拉进闭环做主动验证修复。对用户业务 API 场景，启示是：API 网关/后端不应只做被动报错，而应返回结构化、可被 Agent 增量修复的反馈（如'字段 X 不存在，相似字段有 Y/Z'），让 Agent 做局部修补而非整条重调，降低上百字段宽表 API 的重试成本。

📊 架构示意

🎯 为什么值得关注

LLM 生成 SQL 的 schema 违反率高，整条重生成既贵又易再错；DBMS 本身掌握 schema 真相，却被浪费在被动报错上——SafeQL 把这层闲置智能激活。

⚙️ 核心机制

核心：把 refinement 当成 DBMS 引导的受限搜索——(1) 执行 LLM 生成 SQL；(2) 失败时 DBMS 返回结构化反馈定位错误片段；(3) Agent 在错误片段邻域做受限搜索修复（而非重写整条）；(4) 逐步推进直到通过或预算耗尽。

🧠 深度解读

创新在'增量 vs 整体重生成'的选择：传统 Text-to-SQL 失败就整体重生成，token 浪费且易引入新错；SafeQL 只动错误片段，保留已验证部分。这与 Rosetta 的'先缩面再生成'、MDB-Link 的'预算感知'理念同构——都在压缩 LLM 作用面以降本降错。对用户，可把宽表 API 调用失败也设计成'局部修复'：API 网关返回'哪个参数错了+相似参数建议'，Agent 只改该参数重试，而非重新组装上百字段的整条请求。

💼 商业启示

商业启示：API 调用失败的重试成本（尤其上百字段宽表）是企业 Agent 不可忽视的延迟与 token 成本。SafeQL 的'局部修复'理念可把重试从'整条重发'降到'字段级修补'，直接压缩 Agent 的平均调用次数与延迟，提升业务查询响应速度。

🛠️ 落地建议

落地建议：(1) 业务 API 网关返回结构化错误（错误字段+错误类型+相似字段建议+约束范围）；(2) Agent 失败时只针对错误字段做局部重写/参数替换，保留其余已验证参数；(3) 设 refinement 步数预算，避免无限修复循环；(4) 把成功修复路径存入 Memory Bank（呼应 MIRA/ADORE），供下次类似错误复用。

⚠️ 局限与风险

局限：(1) '增量修复'依赖 DBMS/网关返回高质量结构化反馈，现网 API 多只返回模糊错误文本；(2) 受限搜索空间设计是关键，过宽退化为整体重生成，过窄可能修不好；(3) Semantic Scholar 引用数已核实为 0（2026 新文符合预期）；(4) 论文聚焦 SQL，迁移到 API 调用需适配 API 网关反馈协议。

Carnot：把黑盒 Deep Research Agent 拆成可拦截可校验的执行图

2026-08-12 · arXiv (cs.DB, cs.AI)
企业越来越想用自然语言查数据湖，但 deep research agent 是黑盒——隐藏中间推理与数据检索步，无法控 API 成本与延迟，分析师无法拦截幻觉前提/校验中间结果/纠正轨迹；而 semantic operator 在企业级数据湖上又太贵。Carnot 是交互式执行引擎：把自然语言请求编译为物理执行图并在交互 notebook 暴露，用户可批判计划/增量执行/拦截幻觉前提/校验中间结果/纠正轨迹，而非盲等最终输出。Semantic Scholar 引用数已核实为 0（2026 新文符合预期）。
🔍 技术视角：Carnot 直击用户'业务数据可信度验证'核心诉求。用户通过 API 查数做业务决策，最怕 Agent 黑盒给出一个数字却不知怎么来的。Carnot 的'编译为执行图+notebook 暴露+人可介入每步'是可审计 Agent 的蓝图。它把'Agent 查数'从一次性黑盒升级为'人机协同的渐进式验证调查'，与 ADORE 的 Memory Bank、SafeQL 的增量修复同属'不信任单次生成'范式，但 Carnot 更强调'人可在环中拦截'。

📊 架构示意

🎯 为什么值得关注

Deep research agent 黑盒不可控（成本/延迟/幻觉前提无法拦截），semantic operator 太贵——两端都有痛点，Carnot 用'交互式执行图'在中间找到可控且可负担的路径。

⚙️ 核心机制

(1) 把自然语言请求编译为物理执行图（节点=检索/计算/推理步，边=数据流）；(2) 在交互 notebook 暴露图；(3) 用户可批判计划、增量执行部分节点、拦截幻觉前提、校验中间结果、纠正后续轨迹。

🧠 深度解读

创新在'编译+暴露+人介入'三段：编译让 Agent 决策显式化为图（可审计），暴露让人能在环中（不盲等），人介入让错误可在早期纠正（不累积到终值）。这与 Agentic Harnesses for Robot Autonomy（同期论文）的'LLM-driven verification layer'理念呼应——都在给 Agent 套验证层。对用户，Carnot 提供了'业务 API 调用链可审计'的架构：把多步 API 调用编译成执行图，业务方可拦截某步前提（如'你假设这个客户是高价值，依据是什么'），校验中间结果，再决定是否继续。

💼 商业启示

商业启示：业务决策型 Agent（如投资决策、风控判定）的'可审计性'是合规与信任的底线。Carnot 的执行图+人介入模式让 Agent 从'黑盒给数'变为'透明可追溯的决策伙伴'，是用户在业务关键场景让业务方敢用 Agent 的关键架构。

🛠️ 落地建议

落地建议：(1) Agent 多步 API 调用不要黑盒串到底，编译成执行图显式化每步（调哪个 API、取哪些字段、做什么推理）；(2) 关键决策点（如业务规则判定、阈值比较）暴露给业务方审核；(3) 中间结果可校验（如'这个 API 返回的金额对不对得上账单'）才继续；(4) 支持'纠正轨迹'——业务方否定某步后 Agent 重规划后续路径。

⚠️ 局限与风险

局限：(1) '交互式'意味着人需在环，对全自动高频场景不适用，更适合低频高价值业务决策；(2) 编译为执行图对复杂 Agent 有工程成本；(3) 评测细节需看正文（本次仅取摘要核实）；(4) 对纯 API 查数（非多步推理）场景，Carnot 可能过重。

VDGR-RAG：向量+目录+图+反思统一企业知识推理（层级异构知识图）

2026-08-12 · arXiv (cs.AI, cs.IR)
企业知识 QA（尤其电信等复杂产品文档领域）现有 RAG 忽视多样检索手段整体集成，导致域路由不准、层级文档结构利用差、推理受限。VDGR-RAG 是 agentic GraphRAG 系统：先从文档块构建层级异构知识图 H²KG 保留层级目录结构与语义关系，再集成向量检索 + 目录驱动推理 + 图遍历 + 迭代反思做统一框架，实现精准域路由与层级推理。
🔍 技术视角：VDGR-RAG 为用户'业务知识图谱路线'在企业级复杂文档场景的可行性提供证据。它同时回答了两个关键问题：(1) 知识图谱怎么建——从文档块自动构建 H²KG，保留目录层级（这恰是企业文档的自然结构）；(2) 图怎么用——不是单一图遍历，而是向量+目录+图+反思四路统一。与此前收录的 ACE-GraphRAG（推理时上下文策略层）形成互补：ACE-GraphRAG 管'何时取什么上下文'，VDGR-RAG 管'多种检索如何统一协同'。

📊 架构示意

🎯 为什么值得关注

单一检索手段（纯向量/纯图）在复杂企业文档上各有盲区：向量漏层级结构，图遍历漏语义相似，目录推理漏跨文档关系——VDGR-RAG 用四路统一补齐。

⚙️ 核心机制

(1) 从文档块构建 H²KG——层级异构知识图，节点保留目录层级与文档内语义关系；(2) 四路统一检索——向量（语义相似）+目录（层级定位）+图遍历（跨文档关系）+迭代反思（纠错补全）；(3) agentic 域路由——先判问题属哪个业务域再选检索策略。

🧠 深度解读

创新在'H²KG 保留层级 + 四路统一'：企业文档天然有目录层级（章/节/小节），传统 chunk+embed 把这层结构压平了（呼应 Beyond Top-K 的论点），VDGR-RAG 用 H²KG 把目录层级显式建模进图，再用目录驱动推理做粗定位，图遍历做细关联，向量做语义补，反思做纠错。对用户业务知识库构建，这是'目录结构即图谱骨架'的可行路径——不需要从零造本体，而是把现有文档目录升级为知识图。

💼 商业启示

商业启示：企业业务知识库的最大成本是'把散落文档结构化为可推理资产'。VDGR-RAG 的'目录即图谱骨架'大幅降低建图门槛——不必先请领域专家造本体，而是复用现有文档目录。这让业务知识图谱路线的立项成本逼近 semantic layer 路线，为用户双路线选择提供新依据。

🛠️ 落地建议

落地建议：(1) 把企业业务文档（产品手册/SOP/政策）的目录结构作为 H²KG 骨架；(2) 文档块作为节点，目录层级为边，跨文档语义关系补边；(3) Agent 查询时先做业务域路由（问题属哪个文档域），再四路统一检索；(4) 迭代反思环节让 Agent 自检'检索结果是否充分回答问题'，不充分则补检。

⚠️ 局限与风险

局限：(1) H²KG 构建依赖文档目录质量，乱序/无目录文档需先整理；(2) 四路统一增加系统复杂度与延迟，需按场景裁剪；(3) 论文聚焦电信等复杂产品文档，通用业务文档场景需验证；(4) Semantic Scholar 引用数因限流未核实，标注信息待核实；论文 2026-08-08 新发。

关键洞察在'context 预算 × 模型大小'的联合效应：16K context 下 30B 模型 25% 工具调用畸形，说明工具描述把 context 吃满后模型在'截断处'生成破损语法；256K + 122B 下 0 畸形，说明足够 context 容纳全部工具 schema 后大模型能稳定产出。这对用户的启示是：上百字段宽表 API 的 schema 描述极长，若用本地小模型+短 context，工具调用破损率会高；要么上大 context 大模型（贵但稳），要么用 semantic layer 把宽表 API 的 schema 压缩成业务语义层短描述（降 context 压力）。
