MERIT：因果情景记忆驱动的 Text-to-SQL 修复 Agent

2026-08-06 · arXiv
LLM Agent 修复失败时常丢弃成功修正，迫使后续 episode 重新发现类似解。MERIT 提出训练免费的 Text-to-SQL 修复 Agent，维护「双极性在线记忆」：oracle 验证的修正存为正例（可检索复用）、观察到的失败方向存为负例（避免重蹈）。确定性分类器分配粗粒度失败类型，条件化混合词法-密集检索器，再用冻结模型生成修订。仅允许早期已终结 episode 的记忆被检索。用 Qwen2.5-7B-Instruct 在相同初始预测与修复预算下，Spider 执行准确率从无状态迭代修复的 66.34% 提升至 69.79%，BIRD 从 47.35% 提升至 48.44%。
🔍 技术视角：MERIT 的核心贡献在于把「修复」从无状态重试升级为带记忆的增量学习——不靠参数更新，靠经验积累。这与用户「业务查询可信度验证」需求高度契合：业务系统查询失败时，Agent 应记住「上次这个 API 参数组合为何失败、怎么修对的」，形成组织级查询知识库。双极性记忆（正例+负例）的设计尤其值得借鉴——不仅要记成功路径，更要记失败方向避免重复踩坑。

📊 架构示意

🎯 为什么值得关注

用户核心课题之一是「业务系统精确查询分析」，必然面临查询失败与修复。MERIT 提供了不重训模型、靠情景记忆让 Agent 越用越准的范式，且在 Spider/BIRD 两大基准上有可量化提升，是业务查询可信度验证的直接技术抓手。

⚙️ 核心机制

①双极性在线记忆：oracle-verified corrections（正例）+ observed unsuccessful directions（负例）。②确定性失败类型分类器：粗粒度分类条件化检索策略。③混合词法-密集检索器：兼顾精确匹配与语义相似。④冻结模型生成修订：不更新参数，靠 in-context 记忆。⑤仅允许早期已终结 episode 记忆被检索，避免信息泄漏。

🧠 深度解读

MERIT 的深层洞察是「修复经验的可复用性」。传统 Text-to-SQL 修复是 episode 级的——每次失败独立处理，成功经验随 episode 结束而丢弃。MERIT 引入跨 episode 的记忆持久化，把组织级的查询修复经验沉淀为可检索资产。这对企业场景意义重大：业务团队的查询失败模式是有限的（schema 理解错误、字段语义混淆、聚合逻辑错误等），记忆这些模式比反复让 LLM 从零推理更高效可靠。双极性设计的精妙处在于负例记忆——传统 RAG 只存正例，但「知道什么不能做」在业务查询中同样重要。

💼 商业启示

MERIT 对业务的启示是「AI Agent 的可信度可以随使用积累而提升，而非一锤定音」。企业部署业务查询 Agent 时，应把查询失败与修复经验视为组织资产而非临时数据——记忆库即查询知识库。这降低了 Agent 的初始准确率门槛（不必一次到位），改为关注「是否有有效的记忆与修复回路」。

🛠️ 落地建议

①在业务 API 查询失败时，记录失败类型（如字段语义混淆、参数组合无效）与修正方案到记忆库。②按失败类型条件化检索，让 Agent 优先参考同类历史修正。③负例记忆用于前置过滤——生成查询前先排除已知失败方向。④记忆库定期审计，淘汰过时条目（schema 变更后）。

⚠️ 局限与风险

①依赖 oracle-assisted benchmark feedback，实际业务中 oracle（正确答案）可能不可得，需用执行结果验证或人工审核替代。②记忆库质量依赖失败分类器的准确性，分类错误会污染检索。③Spider/BIRD 提升幅度有限（3.45%/1.09%），企业级复杂查询的收益待验证。④引用数 0（2026-08-06 新文，符合预期，信息经 Semantic Scholar 核实）。

NeSy-RAG：神经符号 RAG 实现可归因可验证的问答

2026-08-06 · arXiv
NeSy-RAG 提出模块化神经符号 RAG 框架，把检索到的文本块合成为编码布尔声明的 Prolog 谓词模块。对每个 chunk，系统生成语义谓词（可能依赖用户事实），用自然语言-代码联合嵌入检索并组合成 Prolog 查询执行推理。针对用户上下文缺失问题，引入符号化知识缺口检测机制——系统主动识别缺失信息而非默认臆测输出。推理链每步可归因到具体证据 chunk，实现可验证、可追溯的问答。
🔍 技术视角：NeSy-RAG 把 RAG 的「检索-生成」黑盒拆解为「检索-符号化-推理」可审计链路。对用户业务场景的价值在于：业务数据查询不能只给答案，还要给「答案从哪来、依据哪个证据、缺了什么信息」——这正是业务可信度的核心。Prolog 谓词化让推理逻辑可执行、可验证，知识缺口检测避免 LLM 在信息不足时「幻觉补全」。

📊 架构示意

🎯 为什么值得关注

用户要求业务数据可信度验证，而传统 RAG 推理不可追溯、无法归因、不检测上下文缺失——NeSy-RAG 直接解决这三个痛点，是业务级 RAG 可信化的范式参考。

⚙️ 核心机制

①chunk→Prolog 谓词模块：每个检索块合成为编码布尔声明的谓词。②联合嵌入：自然语言-代码联合嵌入检索谓词。③Prolog 查询组合：谓词组合成可执行逻辑查询。④符号化知识缺口检测：识别缺失用户上下文，主动提示而非默认输出。⑤证据归因：推理链每步可追溯到具体 chunk。

🧠 深度解读

NeSy-RAG 的核心突破在于把「语义检索」与「符号推理」分层——检索层负责找到相关知识块，符号层负责把知识块转化为可执行逻辑并推理。这种分层让每一步都可审计：检索是否找对了块？谓词是否正确编码了声明？推理是否逻辑自洽？是否遗漏了必要前提？对于业务数据查询，这意味着 Agent 不仅能回答「这个指标是多少」，还能回答「这个数字基于哪些数据源、用了什么计算逻辑、是否有缺失字段需要补充」——这是从「能答」到「可信答」的跃迁。

💼 商业启示

NeSy-RAG 对业务的启示是「可信 AI 不是给对答案，而是能证明答案怎么来的」。在业务决策场景，管理层不只关心结果，更关心「这个数据基于什么、逻辑是什么、是否有遗漏」——可归因可验证的推理链是 AI 进入核心业务决策的前提。

🛠️ 落地建议

①业务术语表/指标定义可编码为 Prolog 谓词，查询时组合推理。②宽表 API 字段语义标注后符号化，支持跨字段逻辑验证。③知识缺口检测用于前置校验——查询前检查是否具备所有必需上下文，缺失则提示补充而非生成错误结果。④证据归因链用于审计报告，每条业务结论可追溯到源数据。

⚠️ 局限与风险

①Prolog 合成依赖 LLM 代码生成质量，错误谓词会导致推理失败。②Prolog 推理对非布尔/连续值场景需扩展（业务指标多为数值聚合）。③知识缺口检测的完备性依赖谓词覆盖度。④引用数 0（2026-08-06 新文，Semantic Scholar 核实）。

Schema-Guided 分层信息抽取：schema 先行的业务术语表构建范式

2026-08-06 · arXiv
提出基于 schema 的框架，用生成式 AI 从非结构化文本中抽取复杂分层结构信息，并进行自动化语义评估。schema 作为信息模型编码领域知识，提供统一系统一致的框架，处理分层嵌套、变基数属性的信息抽取——单次零样调用完成。评估阶段引入基于路径的语义匹配算法对齐嵌套属性，再用生成式 AI 对属性值做语义比较。
🔍 技术视角：Schema-Guided IE 的核心主张是「schema 先行」——先定义业务语义结构（哪些字段、如何嵌套、基数如何），再驱动抽取与评估。这与用户「业务知识库构建」方向高度契合：业务术语表/字段语义标注本质上就是先建 schema（业务信息模型），再让 AI 按此 schema 从文档/API 描述中抽取并验证字段语义。单次零样调用降低了工程成本。

📊 架构示意

🎯 为什么值得关注

用户三大方向之首是「业务知识库构建」，核心是 schema 建模与元数据管理。Schema-Guided IE 提供了「schema 驱动抽取+语义评估」的完整范式，可直接迁移到业务术语表自动构建。

⚙️ 核心机制

①schema 作信息模型：编码领域知识，定义分层嵌套结构。②单次零样抽取：一次调用完成复杂结构信息抽取。③基于路径的语义匹配：对齐嵌套变基数属性。④生成式 AI 语义比较：属性值级别语义评估而非精确匹配。

🧠 深度解读

传统信息抽取是「先抽取后结构化」，Schema-Guided IE 反转为「先定义结构后抽取评估」。这种反转的意义在于：业务语义不是从文档中「发现」的，而是预先在 schema 中「定义」的——文档只是填充 schema 的数据源。对用户宽表 API 场景，这意味着先定义「这个业务实体的语义结构（哪些是度量、哪些是标识、如何关联）」，再让 AI 从 API 文档/字段描述中按此结构抽取并标注，最后用语义匹配评估抽取质量——形成「定义-抽取-验证」闭环。

💼 商业启示

Schema 先行范式的商业价值在于「把领域知识从专家脑中结构化为可复用的数字资产」。业务术语表不再是文档，而是可驱动 AI 抽取、验证、查询的结构化 schema——这降低了业务知识库的构建门槛与维护成本。

🛠️ 落地建议

2026-08-06 · arXiv
论证对财务报表、审计报告、监管报表等表格密集文档，主流 top-k 嵌入检索设计结构性失效。780 页政府财报中 86.8% 内容行是表格行，数千个近乎相同的数字在一个嵌入空间竞争，且数字继承自上方中位数 13 行外的表头——chunk 边界把数字与单位（lakh vs crore）分离，导致两个数量级误差。table-aware chunker 作为 steelman 修复单位问题，但仍有 27-30% 数值 chunk 在所有 chunk 大小下缺失财年表头。提出 READ（Reliable Embedding-free...）用可解释 Agent 化操作替换黑盒 top-k 检索。

🔍 技术视角：Structured Output 是用户「业务 API 精准调用」的底层工程抓手。宽表 API 有上百字段，Agent 需从中选择正确字段并填充正确参数——用 Pydantic schema 约束 LLM 输出，可确保生成的 API 调用参数符合 schema（字段名对、类型对、嵌套结构对），避免自由文本生成导致的参数错误。本地 LLM 还解决业务数据不出域的合规问题。

📊 架构示意

🎯 为什么值得关注

用户核心约束是通过业务 API 查数，API 调用参数必须精准——Structured Output 提供了用 schema 约束 LLM 生成可解析参数的工程方法，且本地化解决合规。

⚙️ 核心机制

①Pydantic schema 定义：嵌套结构（SchedulingContext + DeviceToSchedule 列表）。②model_json_schema() 转换：Pydantic model → JSON schema。③Ollama format 参数：schema 约束生成。④model_validate_json() 解析：响应 → Python 对象。⑤本地 Gemma 4：数据不出域。

🧠 深度解读

Structured Output 的深层价值在于「把 schema 从文档变为运行时约束」。传统做法是 LLM 自由生成再解析校验，错误率高且需大量重试；schema 约束让生成在合法结构空间内进行，从源头消除格式错误。对宽表 API 调用，这意味着：定义 API 请求的 Pydantic schema（字段名、类型、必填/可选、嵌套关系），LLM 生成即合法请求体，下游可直接调用 API 无需额外解析校验。这与 Cube 语义层、NeSy-RAG 的 schema 先行思想一脉相承——schema 是 AI 与业务系统之间的契约。

💼 商业启示

Structured Output 的商业价值是「让 AI 输出从文本变为可执行对象」——这把 AI 从「生成文本需人工处理」变为「生成结构化数据可直接接入系统」，是 AI 进入业务流程的关键工程台阶。本地化还降低了合规成本与云 API 费用。

🛠️ 落地建议

①为每个业务 API 定义 Pydantic 请求 schema（字段/类型/嵌套）。②本地 LLM + schema 约束生成 API 调用参数。③model_validate_json() 解析后直接构造 API 请求。④敏感业务数据用本地 LLM 保证不出域。⑤schema 与 API 文档同步维护，变更时更新。

⚠️ 局限与风险

①schema 约束生成不保证语义正确（格式对但值可能错），需配合字段语义标注。②本地 LLM 能力弱于云端，复杂参数选择可能不准。③嵌套深 schema 的约束生成成功率下降。④正文经 curl 抓取核实（TDS 本篇可读），具体代码细节建议看原文。
