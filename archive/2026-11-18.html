代码检索的「稠密优势」一半来自评测口径：公平词法基线 + LLM 补标识符后，BM25 在全部 Python 池追平向量检索

2026-11-16 · arXiv 2611.20455
论文构建 Repo-Premium：真实仓库级检索基准，覆盖 Python/JavaScript/TypeScript/Go/Rust/Java 六种语言、2022–2026 年的 pull request，预注册测试池 91 个仓库。作者把「稠密编码器远胜 BM25」拆成两个来源：一是评测选择偏向稠密（把文件切块后再喂 BM25、把被改动的测试计为相关），二是查询本身缺少代码里的罕见标识符。用 LLM 生成标识符再检索（generate-then-grep）对 BM25 的提升远大于稠密检索，使其在每个 Python 池都与稠密检索打平，包括 LLM 发布之后才开的 PR。没有任何方法能预测某条查询上哪个检索器会赢，作者据此给出三条准则：对公平词法基线测增益、稠密与 BM25 融合、给缺词的查询补上代码里的词。
🔍 技术视角：这条直接改写研发知识库的选型顺序：先建立「可复现的词法基线」再评估向量增益，否则会把 20 个点的评测红利当成模型红利。对 coding agent 而言，grep 不是落后工具而是与仓库符号表对齐的精确通道；工程上应把「查询扩展（补标识符）」做成检索前置步骤，而不是换 embedding 模型。

📊 架构示意

🎯 为什么值得关注

代码检索是研发知识库与 coding agent 的共同底座。过去两年大量团队按 MTEB/CodeSearchNet 类榜单直接上向量库，本文明示这些榜单的构造方式本身偏向稠密检索，选型依据可能是假的。

⚙️ 核心机制

Repo-Premium 在真实仓库上做文件级排序：查询分 curated 与 raw 两类，语料含 2022–2026 的 PR；同时控制 BM25 的输入粒度（不切块）与相关性判定（不把改动的测试算相关）。再对比原始查询、LLM 生成标识符后的查询，以及稠密/词法/融合三种检索器。

🧠 深度解读

关键在「查询缺词」这一失效模式：开发者写「怎么处理重试」时不会写出 retry_backoff_jitter 这种标识符，词法检索因此空转；而稠密检索靠语义泛化掩盖了这个缺口，于是被读成「向量更强」。一旦用 LLM 把领域标识符补进查询，词法通道的精度立刻回到同一水平——说明差距主要是查询表达问题，不是表示能力问题。作者还报告了负面结果：没有任何特征能事前预测哪一方会赢，因此线上必须融合 + 在线评测，而不是静态选一个。

💼 商业启示

商业含义是「检索层的溢价被压缩」：向量数据库厂商的相对优势从表示能力转向运维/混合检索/权限，采购谈判应要求供应商在公平词法基线上给出增益，而不是只给榜单名次。

🛠️ 落地建议

①自建研发知识库先跑「同语料、同粒度、同相关性判定」的 BM25 基线，记录 Recall@k 与 MRR；②把 query expansion 做成独立服务（LLM 读仓库符号表生成候选标识符），命中后走词法通道；③默认 hybrid（BM25 + dense + RRF 融合），并对 20–50 条真实查询做逐条归因，避免只报平均数。

⚠️ 局限与风险

基准只覆盖六种主流语言与开源仓库，私有单体仓库的命名习惯（拼音缩写、业务前缀）未覆盖；generate-then-grep 依赖一次额外 LLM 调用，仓库极大时符号表本身需要索引；Semantic Scholar 记录该文引用数为 0（新文）。

SWE-CoWork：101 个真实仓库 + 26 位「同事」的组织基准——F2P 通过约 63%，完整交付却不足 8%，31% 自称完成的需求测试失败

2026-11-15 · arXiv 2611.20218
SWE-CoWork 把 coding agent 放进模拟工程组织：101 个开发任务、101 个真实仓库、11 种语言、12 个应用域，环境里有 26 位职责不同、知识有边界、协作行为可控的「同事」。Agent 从一份简短交接开始，必须向同事与工作记录取回分散的需求、调和冲突证据，最后用私有可执行测试验收。11 个模型的结果显示：两个最强模型满足约 63% 的 fail-to-pass 测试，但完整完成的任务不足 8%；把完整需求直接给到 agent 可让 F2P 提升约 16 个百分点，完整任务成功率却不变。轨迹分析发现 Claude-Opus-5.5 平均把 93% 的首个问题指向了正确的责任人，但只拿到 64% 的同事侧需求；悬置的问题无人跟进，31% 被报告为已完成的需求通不过测试。
🔍 技术视角：研发 agent 的瓶颈已经从「写得出代码」移到「需求追踪与交接」：拿到 63% 的测试通过率却只有 8% 的交付率，说明中间那 55 个点耗在澄清、验证与交接上。对已建研发知识库的团队，这意味着知识库要覆盖「谁掌握什么」的组织记忆，而不只是代码与文档；agent 的产物必须携带需求到测试的追踪链，否则无法判定是否真的交付。

📊 架构示意

🎯 为什么值得关注

多数 coding benchmark 只给一份完整 issue 与一个仓库，隐去了真实组织里需求分散、证据冲突、责任人有限这几个前提。SWE-CoWork 把这层组织摩擦显式建模，因此它的低完成率更接近企业内实测。

⚙️ 核心机制

每个任务配 26 个模拟同事（各有 bounded knowledge 与可控协作行为）与工作记录；agent 需主动提问、读记录、消解冲突，再改代码；验收用私有 F2P 测试，并额外做需求级轨迹分析（问题是否问对人、是否跟进、报告完成的需求是否真的过测）。

🧠 深度解读

93% 对 64% 的落差是最有价值的一处：知道该问谁不等于问得出答案，提问质量与追问链才是瓶颈。再加上 31% 的「假完成」，可以把失败拆成三段——需求获取不足、需求获取后实现不完整、实现后自检失真。这三段分别对应三种基建：组织级知识索引、需求到 diff 的追踪、以及独立于生成方的验收。

💼 商业启示

采购或自研 agent 时应把「端到端交付率」写进验收指标：按本文口径，测试通过率会把能力高估约 8 倍。对外承诺交付能力时，需求澄清环节的人力投入必须计入 TCO。

🛠️ 落地建议

①给 agent 加「需求账本」：每条需求记录来源人/记录、当前状态、对应变更与测试，交接时强制携带；②把「悬置问题」做成显式待办，agent 结束前必须清零或标注阻塞；③验收不要用 agent 自评，用独立测试与需求覆盖检查；④内部评测加入「完整交付率」，不要只看 pass@k。

⚠️ 局限与风险

环境是模拟组织，26 位同事的行为由基准设定，真实企业的非正式沟通与政治因素未建模；私有测试仍是仓库内测试，不能覆盖线上验收；只测了 11 个模型，未给出成本对比。

2,870 个指令文件 PR 里逾 70% 没有实质评审：Codex / OpenCode / Claude Code 只捞回人类关切点的 1.3–3.9%

2026-11-17 · arXiv 2611.18582
论文把 AGENTS.md、CLAUDE.md、.cursorrules 一类文件定义为「可执行策略」：它们没有编译器、类型检查与测试作为每次改动的 oracle，一次编辑就能静默改变整个仓库里 agent 的行为，因此人工评审是唯一质量闸门。作者分析 2,246 个仓库中的 2,870 个指令文件 PR，发现超过 70% 的改动没有收到实质性评审；当 AI reviewer 替代人类时，它系统性看不见最需要人类判断的问题——能抓表层结构，漏掉事实错误、必要性追问与过时判断。作者给出首个 16 类关切分类法与 1,962 条人工核对关切（468 个 PR）的基准，Codex、OpenCode、Claude Code 在获得完整仓库访问权的情况下，只恢复了 1.3–3.9% 的人类关切。
🔍 技术视角：这为「AGENTS.md 即代码」提供了定量依据：既然是策略代码，就该有 CODEOWNERS、变更评审与回归测试。更关键的是 AI reviewer 的盲区是结构性的——它擅长模式匹配表层格式，而对「这条规则还需不需要」这类反事实判断无能为力，所以审查链上必须保留具名人类责任人。

📊 架构示意

🎯 为什么值得关注

用户团队已建研发知识库并大量使用 agent 指令文件，这类文件的腐化不会报错、只会让 agent 行为悄悄漂移；此前没有任何工作量化它的评审现状。

⚙️ 核心机制

抓取 GitHub 上涉及指令文件的 PR，人工标注评审是否实质、关切属于哪一类；据此构建 16 类 taxonomy 与 1,962 条关切的基准；再把三个主流 coding agent 放进评审位（给全仓库上下文），统计其恢复人类关切的比例。

🧠 深度解读

1.3–3.9% 的恢复率不能简单读成「模型弱」，而是任务性质不匹配：人类关切集中在事实正确性（这条命令真的存在吗）、必要性（还需要这条规则吗）与时效性（依赖的路径已改名），三者都需要外部世界状态与历史意图，而模型只有当前快照。作者因此主张把评审拆成「机器可查的结构项」与「必须人类的反事实项」。

💼 商业启示

把指令文件纳入变更管理是低成本高回报的治理动作：一次静默的行为漂移可能导致批量错误提交或越权操作，代价远高于评审成本。对外交付 agent 产品时，规则文件版本应与代码版本一起进发布物。

🛠️ 落地建议

①给 AGENTS.md/CLAUDE.md 加 CODEOWNERS 与必审规则，PR 模板强制填写「这条规则的失效条件」；②把可机检的部分抽成脚本（路径存在性、命令可执行、引用文件哈希），让 AI reviewer 只做这一层；③每条规则带 owner 与复查日期，过期自动降级为「需再确认」。

⚠️ 局限与风险

样本以公开仓库为主，企业内部指令文件可能评审更严；benchmark 由作者标注，存在标注者偏差；三个 agent 的配置与提示未完全标准化，横向比较应谨慎。该文 7 月 31 日首次提交，11 月中旬进入 recent 列表。

Inquest：49% 的生产故障报告不点名任何被改文件——27B 开源模型 + 代码控制流程，top-1 命中 68.6%、top-5 85.9%

2026-11-14 · arXiv 2611.19554
生产故障只有描述和日志，没有失败测试、也无法复现；日志显示的是「在哪里被发现」而不是「在哪里被造成」，作者研究的真实报告中有 49% 的文本没有提到修复时改动的任何文件。他们用两个公开数据集与 27 个开源项目（Apache、Red Hat、MongoDB、MariaDB、Qt、Sakai）构建基准，含 38,001 份已解决报告、当时仍在的代码与修复改动的文件。Inquest 用 27B 开源权重模型，但流程由代码控制：先收集证据（含报告提交前已解决的相似 issue 中被改的文件），模型只做三个有界决策——打开哪些文件、每个文件在故障中扮演什么角色、如何排序。在 26,544 份评测报告上，改动的文件排第一 68.6%、进前五 85.9%，模块正确 90.2%，函数排第一 53.8%；对不点名文件的报告仍有 52.8%/73.6%；同模型同工具的自由 agent loop 找文件相当，但函数定位低 14 个百分点。
🔍 技术视角：「Code, not the model, controls the procedure」是这条的核心：把证据收集、候选生成、验证写成确定性流程，模型只在语义判断处出手，才能同时拿到精度与可审计性。对研发知识库的启示是历史 issue→fix 的映射本身就是高价值检索资产，而不是聊天记录。

📊 架构示意

🎯 为什么值得关注

调试/根因定位是研发线里最依赖上下文的一环，也是 agent 最容易「看起来在工作」的环节。本文给出大规模真实基准，并把「模型 vs 流程」的贡献分离出来。

⚙️ 核心机制

两阶段：代码侧先做证据收集（日志指纹、相似历史 issue 的改动文件、栈帧到符号的映射），形成候选集；模型阶段只回答三个受限问题（打开哪些文件/角色/排序），每次决策都有边界，可回放。评测用修复实际改动的文件与函数作为 oracle。

🧠 深度解读

自由 loop 与 Inquest 在「找文件」上持平却在「定函数」上差 14 个点，说明开放式探索会把预算耗在文件级粗粒度上，缺少向符号级收敛的机制。把角色判定（这个文件是入口、序列化层还是配置）显式化，等价于给模型一个中间表示，让它不必在一次生成里同时做定位与归因。

💼 商业启示

调试 agent 的价值可用「减少多少跳转」计价：文件级 top-5 85.9% 意味着多数工单能在五分钟内锁定候选，这对on-call成本是直接可折算的收益。

🛠️ 落地建议

①把历史 issue 的修复文件建成可检索索引（issue 文本 → 改动文件/函数），作为调试 agent 的第一跳证据；②定位流程拆成「收集→角色标注→排序→验证」四段，每段可独立评测；③用函数级 top-1 而不是文件级作为验收指标；④保留完整 run transcript 以便审计。

⚠️ 局限与风险

基准以 Java/开源项目为主，动态语言与私有代码的栈帧质量不同；oracle 是「修复改动的文件」，多因故障下可能漏标；27B 模型的推理成本未与更强闭源模型对比。

Living Context Graph：不复制数仓、边服务边学语义——BIRD 留出集 +22.6pp；图结构只省时（成本 2.3–3.3×）不涨准确率

2026-11-16 · arXiv 2611.20976
企业数据的业务含义、关系、指标定义与报表惯例并不在 schema 里，而是散落在未文档化的系统与口口相传中。LCG 提出一个持续学习的上下文层：不复制、不转换底层数仓，先从数据本身自举基础语义与关系，构建概念图并在每次服务查询时索引业务上下文，把已验证结果写成持久语义学习，当后续结果与既有路径矛盾时撤回或重新赢得该上下文。在 BIRD 三个库的迁移感知切分（499 题，353 题构成学习历史、146 题留出且从不用于更新）上，仅自举提升 4.6 个百分点；只从历史学习可让未触碰的留出集提升 22.6 个百分点（95% CI 14.4–30.8），比同历史五-shot 检索高 12.3 个百分点；增量学习在观察噪声内追平一次到位。消融图结构对留出准确率最多影响每题一题，但使单查询成本上升 2.3–3.3 倍、中位延迟上升 1.8–3.4 倍。

🧠 深度解读

💼 商业启示

2026-11-16 · arXiv 2611.20979
NL2SQL 被 schema 检索卡住：生成器只能和它看到的那一片 schema 一样好。上百张表时选择是双向的——漏掉一张需要的表查询就不可恢复，多给几张无关表则变成噪声。当让模型自己看 schema 的 agentic retriever 太贵太慢时，退路是用 embedder 按余弦相似度取 top-k，而这条路有两个缺陷：固定预算对每个问题都不是最优，嵌入相似度会忽略 join 必需的外键关联表。作者提出 AEGT（ElbowHop）：属性图上的表检索器，用自适应肘部截断替代固定预算（单一激进度参数），并用双向 FK 遍历确定性地补回桥表。在三组候选池递增的语料（BIRD Mini-Dev 按库 3–13 张表、十一 schema 合并 74 张、Spider-train 合并图 546 张）上，按每题预算匹配的协议隔离两个机制：同等召回下，自适应肘部在较大池上把精度约翻倍，池越大差距越大；FK 遍历在单跳紧预算场景对桥表有效。
🔍 技术视角：这条把「选多少」变成一等公民：固定 top-k 是拍脑袋的预算，肘部法则让预算随问题自适应，等价于给检索器一个可解释的停止条件。对上百字段宽表 API，同构问题是「选哪些字段/维度」——字段组应按业务对象聚类，再用关系（外键/引用）补齐 join 所需的桥接字段。

📊 架构示意

🎯 为什么值得关注

用户的业务系统通过高业务含义 API 查数，部分 API 是上百字段宽表，字段选择与表选择同构：漏字段则答非所问，多字段则噪声淹没。AEGT 提供了一个低成本、可解释的前置筛选器。

⚙️ 核心机制

把 schema 建成属性图（表为节点、外键为边），对查询做嵌入相似度排序后按分数曲线找「肘部」作为每题截断点（一个激进度参数控制松紧），再沿双向 FK 做确定性扩展，把 join 必需的桥表拉回候选。

🧠 深度解读

自适应肘部在池变大时收益变大，说明固定预算的失效是规模相关的：小池里 top-5 恰好够，大池里同样的 5 张表覆盖不了问题的真实子图。FK 遍历则解决另一类失败——嵌入相似度天生不看结构，桥表往往语义上与问题无关（如 order_item 连接两张大表），只能靠图结构补。两者合起来说明 schema 检索应是「语义召回 + 结构闭包」，而不是单一排序。

💼 商业启示

schema 检索是 NL2SQL 产品的成本中心：用一个便宜的图检索器替代 agentic 探查，可在保持召回的同时砍掉多轮模型调用，这也是自建方案相对 SaaS 的现实优势。

🛠️ 落地建议

①把宽表字段按业务对象/维度组建成图，字段间引用关系（外键、枚举字典、同义列）为边；②用肘部而非固定 top-k 决定每组取多少字段；③对 join 路径做确定性补齐（订单→明细→商品），并在提示中显式标注补齐理由；④以「召回率 + 精度」双指标评估，不用最终答案准确率反推。

⚠️ 局限与风险

评测在 BIRD/Spider 的表级 schema 上，字段级（上百列）未验证；肘部检测对分数分布敏感，嵌入质量差时可能截断过早；FK 只在关系型 schema 中存在，纯 API 场景需要人工维护引用关系。

⚠️ 局限与风险

实验在 BIRD-dev 且刻意去掉 benchmark 提供的 evidence，真实系统若有高质量指标定义可削弱收益；列对构建依赖值域统计，对稀疏/加密字段无效；澄清需要多轮交互，端到端时延未优化。

OntoPoc：把「定义必须对照数据检查、由具名的人确认」做成工具——未确认或数据变更后过时的定义直接拒答并说明谁能确认

2026-11-17 · GitHub
OntoPoc 定位在知识图谱或语义层之前：从业务表格或只读数据库起草对象类型、关系与定义，用代码对照数据检查，再由另一位具名建设者确认，确认时记录数据版本与锚点。每个定义经历「提出 → 代码检查 → 具名确认」；新版本数据上传后重新检查，对不上的定义回到「需要再看」，依赖它的问答一起失效并写明原因（数据变了/定义改了/上游过时）。问答范围只含当前用户可见的已确认类型，问题涉及未确认或需再看的定义时先拒答并说明谁能确认，不去问模型；模型只看结构与含义、以及取值不多的列的取值，不看行数据；支持排除某含义、取 top-N。另有按对象类型与行级的权限、可以让某列的值不发给模型、MCP 工具用个人令牌且默认只读、血缘图按失效原因着色。
🔍 技术视角：这几乎是用户三条约束（不直连库、字段级权限、构造性拒绝）的最小可运行参考实现：把「确认」做成带数据版本的状态机，把「过时」传播到依赖它的答案，把「拒答」写成带责任人的可执行路径。它证明了可信问答的门槛不在模型，而在定义的生命周期管理。

📊 架构示意

🎯 为什么值得关注

用户的业务知识库必须能回答「这个口径现在还算数吗、谁确认的、数据变了吗」。OntoPoc 用极小的代码量把这三问做成产品机制，适合作为自建方案的功能清单与竞品基线。

⚙️ 核心机制

数据层：CSV/Excel 上传（按主键更新，每次新版本）或只读 PostgreSQL/MySQL 连接；管道算子（过滤/连接/分组/去重/计算列、合并与拆分且统计未匹配行）；本体层：对象类型、关系（检查基数）、视图、行为（审批后才写）、派生属性；确认层：提出→代码检查→他人确认，存数据版本与锚点，新版本触发重检；问答层：只对已确认定义生成结构化查询，代码执行并核对用到的定义。

🧠 深度解读

最有价值的设计是「失效传播 + 拒答理由」：定义不是静态元数据而是有状态的工件（已确认/需再看），状态变化沿血缘向下传播，问答在入口处就阻断而不是让模型自由发挥。其次是把「列值不外发」做成数据层能力而非提示约束——这比在 prompt 里写「不要输出身份证号」可靠得多。第三是 MCP 默认只读 + 个人令牌，把权限边界放在协议入口。

💼 商业启示

它示范了一条与 SaaS 相反的路径：不卖「更聪明的问答」，而卖「可确认、可失效、可追责的定义」。对受监管业务，后者才是采购门槛；对自建团队，这份功能表可直接当验收清单。

🛠️ 落地建议

①把定义建成状态机：draft → checked → confirmed(带数据版本) → stale；②任何数据刷新都触发受影响定义重检，并把依赖它的缓存答案标记失效；③问答前置一道「定义可用性检查」，不可用即拒答并给出确认人；④敏感列在查询层就过滤，模型永远拿不到原值；⑤对外只暴露只读 MCP 工具，写操作单独审批通道。

⚠️ 局限与风险

README 自述为 Alpha，除作者外尚无用户；只支持 CSV/Excel 与只读 PG/MySQL，未覆盖用户场景里的 HTTP API；单人项目、无第三方评测；默认模型绑定 DeepSeek/OpenRouter，换成自建模型需改配置。
