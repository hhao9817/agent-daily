开源项目：ai-prd-workflow（304⭐ MIT）——RFC 驱动开发让 Agent『先决定造什么再造』，7 大 coding agent 通用的规范驱动工作流

2026-10-08 · GitHub
nurettincoban/ai-prd-workflow（304⭐，MIT，2025-03 创建，10/8 仍在更新）为 AI coding agent 提供 RFC 驱动开发工作流：想法或已有代码库→经验证的 PRD→特性清单→项目规则→按依赖排序的 RFC→逐个实现与评审。以 Agent Skills 形式适配 Claude Code（原生 plugin）、Codex、Copilot、Cursor、Gemini CLI、OpenCode、Devin。每步产出 markdown 文件供下一步读取（决策存活于会话之外），配套脚本做文档间一致性检查（/workflow-status 可审计出『F7 无对应 RFC』『HTTP 301 缓存破坏点击统计』类不一致）。作者称 RFC 驱动早于 Claude Code/Cursor 的 plan mode 与 Kiro/Spec Kit。
🔍 技术视角：与本期 PACE 论文（PRD 完整交付率仅 14%）形成完美的『问题-方案』配对：PACE 诊断出 agent 的瓶颈是需求覆盖与集成缺失，ai-prd-workflow 正是把需求覆盖结构化的开源工程答案——PRD→特性→RFC 的依赖排序链让每个需求有可追踪的实现单元，一致性检查脚本充当『文档间集成验证』。对用户研发线基建的直接价值：已建成的研发知识库可接入该工作流，让 agent 在知识库约束下做 spec-driven 开发；/workflow-status 的文档交叉审计模式可迁移到业务线（API 语义标注与业务术语表的一致性检查）。

📊 架构示意

🎯 为什么值得关注

Spec-driven development 正成为 coding agent 可靠性工程的主流路线（Kiro/Spec Kit/OpenSpec 竞品林立），本项目是其中少数 MIT 许可+多 agent 通用+自带一致性审计的实现，且与 PACE 揭示的交付瓶颈直接对症。

⚙️ 核心机制

文件即接口的工作流：每阶段（PRD/features/rules/RFCs/implementation/review）产出 markdown 文件，下一阶段读取上一阶段文件作为上下文；RFC 按依赖图排序逐个实现与评审（防止并行实现产生集成冲突）；workflow-status 脚本做 traceability 检查（每个 feature 有 RFC？RFC 间矛盾？）与文档对读（文档间不一致检测）。

🧠 深度解读

设计哲学与 10/15 已收录的 SpecForge（agent 行为规范自改进）互补：SpecForge 优化规范本身，ai-prd-workflow 固化规范的执行流程。『决策存活于会话之外』呼应 ExperienceIndex（10/9 收录）的工件级记忆思想——markdown 文件是最低成本的持久化决策工件。一致性检查是亮点：20 处不一致的示例（无 RFC 建 UI/缓存破坏统计）说明文档漂移是 spec-driven 流程的真实风险，静态审计脚本是廉价解法。

💼 商业启示

Spec-driven development 工具链是 coding agent 生态的高增长细分：企业愿意为『可审计的需求-实现追踪』付费（合规+质量双驱动）。MIT 许可使其可被商业平台吸收集成——观察哪些 agent 厂商内置类似工作流可作为路线信号。咨询机会：spec-driven 流程落地服务（流程裁剪+知识库集成+审计脚本定制）。

🛠️ 落地建议

①研发知识库+ai-prd-workflow 组合试点：选一个中型需求走完整 PRD→RFC→评审链，度量交付完整度（对照 PACE 的 Code Points 方法）；②借鉴 workflow-status 做业务线文档审计：API 语义标注↔业务术语表↔知识库条目的 traceability 检查脚本；③多 agent 环境统一采用其 Agent Skills 格式（7 平台适配降低工具锁定）。

⚠️ 局限与风险

304⭐ 社区规模尚小，生产案例证据有限；markdown 工作流对小任务是过度工程（作者自己也定位在中大型需求）；一致性检查脚本的覆盖面（能查什么类型的不一致）需实测验证；与 Kiro/Spec Kit 等商业方案的功能差距未系统对比。
