BAP-SQL: Budget-Aware Observation Planning for Agentic Text-to-SQL

2026-08-03 · arXiv 2608.02876
提出把'观察形成（observation formation）'当作一个预算控制阶段的 Agentic Text-to-SQL 框架。它评估查询风险、按需改写 SQL、并把硬性上限委托给独立的 runtime shield，避免宽查询在有用证据出现前就耗尽 context 和数据库工作量。在 BIRD 衍生设定上，4B/7B 主干在 token 减少 4.5-5.0% 的同时 tight-budget 成功率提升 3.4-3.6 个百分点。
🔍 技术视角：直击你'精确查询'的隐性成本维度：agent 调业务 API 查数时，一次宽表查询可能返回上百字段、几千行，瞬间打爆上下文。BAP-SQL 的'预算前置+独立 shield'思路可直接迁移到 API 调用层——把'查前先估风险、必要时改写/限制、由独立守卫兜底'做成工程护栏。

📊 架构示意

🎯 为什么值得关注

你的场景是'通过高业务含义 API（含上百字段宽表 API）查数'，最大风险不是查错，而是一次调用就把上下文/成本/延迟打爆。现有 Agentic text-to-SQL/工具调用大多假设'观察是免费的'，BAP-SQL 正面挑战这个假设，给出了一套可量化的预算治理范式，对任何'agent 调宽表 API'的场景都适用。

⚙️ 核心机制

三段式：① 风险估计——对将要执行的查询/调用评估'会不会爆预算'（如返回行数/字段数预估）；② 预算感知改写——在有用证据出现前主动收窄查询（限制字段、加过滤、改 projection），而非事后压缩已经捞回来的数据；③ 独立 runtime shield——硬性上限（token/行数）由独立组件兜底，生成层不负责。关键贡献是把'policy-visible planning'与'budget-sensitive 执行'解耦。

🧠 深度解读

架构师视角，BAP-SQL 最大的启发是'观察形成是一等公民'。多数业务 Agent 把 API 返回值当被动输入，但实际 agent 的动作决定了下一跳拿到什么——宽表 API 尤其如此：不加投影/过滤地调一次，几百字段 JSON 直接塞满 context，后续推理必然劣化。它提出的'budget-aware planning'与'独立 shield'是把'成本治理'从 prompt 提示升级成架构层约束。落地时要注意：风险估计器本身需要 schema 语义支撑（你得知道哪些字段是高基数、哪些是大文本），这又回到你'业务语义层'的建设——预算治理和语义层是同一地基的两面。

🛠️ 落地建议

落地建议：① 在业务 API 调用编排层引入'预算前置'：调用前预估返回体量，超阈值则先做字段裁剪/分页/加过滤；② 设一个独立于 LLM 的 runtime shield 做硬兜底（token/行数/字段数上限），不依赖模型自觉；③ 复杂查询走'先窄探再宽取'的两阶段模式，呼应 BAP-SQL 的'有用证据出现前不花大预算'。

⚠️ 局限与风险

局限：论文面向 SQL 场景，对'API 型宽表 JSON 数据源'需要自行映射预算信号（如字段基数、返回大小预估）；风险估计器依赖 schema 语义标注质量，语义层没建好时预算判断会不准；论文增益（3-4pp）虽稳定但绝对值不算大，工程收益需在你们真实 API 上验证。

🔗 原文链接：https://arxiv.org/abs/2608.02876

SAFAARI: Schema-Aware Framework for Accelerated Advertiser Response Intelligence

2026-07-27 · arXiv 2607.25042
多 Agent 框架，专门解决'在没有预定义 API 端点的情况下访问企业数据'的 schema linking 瓶颈。包含 content agent、metadata agent、orchestration agent，并提出 SEAL 复合指标评估 schema 评估与 NL-to-SQL 的准确性，面向客服/广告主响应场景。
🔍 技术视角：几乎直接命中你的约束：'不直连数据库、通过业务 API 查数'，而 SAFAARI 处理的是更难的'连预定义 API 端点都没有'时的 schema 感知。它的多 Agent 分工（内容/元数据/编排）是应对宽表/复杂企业 schema 的可借鉴范式。

📊 架构示意

🎯 为什么值得关注

你的核心痛点之一是'让 AI 理解上百字段宽表 API 的业务语义'。SAFAARI 把 schema linking 拆给多个专职 agent，而不是指望单个 LLM 一次吃下全部 schema——这正是你面对宽表时应该采用的策略。它还提出了 SEAL 评估指标，补上了'语义对齐质量怎么量化'的空白。

⚙️ 核心机制

多 Agent 分工：① content agent——理解用户自然语言意图与上下文；② metadata agent——专门处理 schema/字段元数据的检索与匹配（哪些表/字段/端点与问题相关）；③ orchestration agent——编排 content 与 metadata 的结果，生成最终查询/响应。SEAL 指标复合评估 schema 选择准确率与 NL-to-SQL 正确性，强调'选对结构'是'生成对查询'的前提。

🧠 深度解读

架构师视角，SAFAARI 的价值在于把'schema 理解'独立成专职 agent 而非塞进通用 prompt。对你'上百字段宽表 API'的场景，这意味着：不要让生成 agent 同时猜字段含义，而是先有一个'metadata agent'做字段语义对齐（这恰好是你'业务语义层'的运行时化身）。它的 SEAL 指标也提示——评估业务查询质量不能只看最终结果对不对，要看'有没有选对 API/字段'这个前置环节。一个可借鉴的设计取舍：metadata agent 用检索（向量+结构）而非全量注入，避免宽表字段全塞进上下文。

🛠️ 落地建议

落地建议：① 把'schema/字段语义对齐'抽成独立 agent/服务，与'查询生成'解耦；② metadata agent 走检索式（语义索引你们的 API schema），而非全量注入上百字段；③ 引入类似 SEAL 的前置评估指标，跟踪'字段选择准确率'，而非只看最终结果。

⚠️ 局限与风险

局限：SAFAARI 面向广告主客服这一较窄场景，其 schema 感知策略在更通用的业务域需验证；论文未开源 SEAL 的完整实现；'没有预定义 API 端点'是它的特殊设定，对你们'有 API 但字段语义复杂'的场景需调整 metadata agent 的检索粒度。

🔗 原文链接：https://arxiv.org/abs/2607.25042

ACE-GraphRAG: Agentic Context Engineering for Hierarchical GraphRAG

2026-08-02 · arXiv 2608.01269
针对分层 GraphRAG 提出'representation-inference gap'问题：固定 context 构建无法把多粒度图表示适配到当前 query。提出 ACE-GraphRAG，在推理时加一层'context 策略层'，基于 gap-aware refinement 补充/调整初始 context，让生成拿到的上下文与问题真正匹配。
🔍 技术视角：回应你'语义层 vs 知识图谱'路线的深层关切：GraphRAG 不是'建好图就赢'，固定检索的 context 与具体 query 之间存在系统性失配。ACE 的'推理时 context 策略'思路可迁移到你'按需探索 API schema'的按需检索设计。

📊 架构示意

🎯 为什么值得关注

你在评估 GraphRAG 路线时一定会遇到这个问题：企业知识图谱建好了，但不同业务问题需要的上下文粒度不同（有的要看全局指标定义，有的要查某个客户的具体订单关系）。固定的一次性检索很难适配，ACE-GraphRAG 给出了'让 context 适配 query'的显式方法，对判断 GraphRAG 路线的真实收益很关键。

⚙️ 核心机制

在分层 GraphRAG 之上加一层推理时策略：① 初始 context 由图检索构建（多粒度）；② gap-aware refinement——识别当前 context 与 query 的失配（缺什么、多什么）；③ 用策略动作（补充子图、剪枝、切换粒度）调整 context；④ 生成基于调整后的 context。核心是把 context 构建从'一次性'变成'策略驱动的动态适配'。

🧠 深度解读

架构师视角，ACE 揭示了 GraphRAG 的一个真实陷阱：图的'多粒度表示'和推理实际需要的 context 之间存在系统性 gap，固定检索会让生成层拿到'看起来全但不对'的上下文。这对你'业务知识库+语义层'同样适用——语义层/知识图谱提供的上下文也需要按 query 动态裁剪，否则宽表 API 的上百字段语义又会反向塞爆推理。它支持一个判断：GraphRAG 路线要跑赢语义层，必须配上类似 ACE 的动态 context 策略，否则多粒度图本身会变成新的噪音源。

🛠️ 落地建议

落地建议：① 不管走语义层还是知识图谱，都把'context 适配 query'作为独立环节，而非依赖一次性检索；② 评估 GraphRAG 时重点测'不同问题类型下的 context 失配率'，而非只看平均精度；③ 把 ACE 的 gap-aware 思路迁移到 API schema 按需检索：先探再按需扩展，避免宽表全量注入。

⚠️ 局限与风险

局限：ACE 是推理时策略层，本身带来额外延迟与调用成本；gap 检测依赖一个能判断'缺什么'的模型/规则，这又需要 schema 语义支撑；论文为分层 GraphRAG 设计，对纯语义层路线需调整。

🔗 原文链接：https://arxiv.org/abs/2608.01269

HyperAgent: Planning and Acting over Tool-Schema Hypergraphs for Tool-Use LLM Agents

2026-07-31 · arXiv 2608.02650
把工具间关系建模在 schema 层面，构建有向 Tool-Schema Hypergraph，让 LLM agent 在超图上做规划与执行，而非仅靠文本描述推断工具组合。解决现有 tool-use agent 在复杂任务中探索低效、执行不可靠的问题。
🔍 技术视角：直接关联你的'业务 API 语义理解与精准调用'：当业务 API 之间存在依赖/组合关系（A 的输出是 B 的入参），用超图显式建模这些 schema 关系，比让 LLM 从文本描述里猜组合要可靠得多。这是'让 AI 懂 API 之间怎么协作'的结构化路线。

📊 架构示意

🎯 为什么值得关注

你的业务系统里有多个高业务含义 API，它们往往不是孤立的——一个查询可能需要'先调客户 API 拿 ID，再调订单 API 查明细，最后汇总'。现有 function calling 大多让 LLM 从每个工具的文本描述自行推断组合关系，这在 API 多、字段宽时极易出错。HyperAgent 给出了'把工具关系建模成显式图结构'的范式。

⚙️ 核心机制

① 在 schema 层提取工具间关系（数据依赖、组合约束、前置/后置），构建有向 Tool-Schema Hypergraph（超图能表达多工具共享一个依赖，普通图不行）；② agent 在超图上做规划（找到从初始状态到目标的工具路径）；③ 执行时基于超图边约束做工具调用，避免无效组合。核心是把'工具怎么协作'从隐式推理变成显式图导航。

🧠 深度解读

架构师视角，HyperAgent 的关键贡献是把'tool composition'从 prompt 级推理提升到结构级规划。对你'上百字段宽表 API'的场景，超图可以表达'API A 的客户字段是 API B 订单查询的入参'这类业务关系——这正是你'业务语义层'应该沉淀的关系。一个值得注意的点：超图 vs 普通图的选择，反映了'多工具共享同一业务对象'的现实，比二元关系更贴业务。但它依赖 schema 关系被正确抽取，这又回到你'业务知识库构建'的根基工作。

🛠️ 落地建议

落地建议：① 把业务 API 间的依赖/组合关系建模成图（先普通图，复杂场景再上超图），作为 agent 规划的显式约束；② tool 描述除了字段语义，补充'与哪些 API 有关联、什么类型的关联'；③ 规划与执行分离：先在图上规划路径，再按路径调用，降低无效调用。

⚠️ 局限与风险

局限：超图构建依赖准确的工具 schema 关系抽取，业务 API 文档不全时关系图会缺边；超图规划本身的复杂度在工具数量大时上升；论文偏方法论，工程化（如关系自动发现）需自行补足。

🔗 原文链接：https://arxiv.org/abs/2608.02650

Getting the Parameters Right: A Difficulty-Graded Benchmark and Probe-Guided Training for LLM Tool Calls

2026-08-04 · arXiv 2608.03071
聚焦 tool call 的'参数正确填充'这一被忽视环节，提出难度分级 benchmark 与 probe-guided 训练。发现即便前沿模型在云网络等场景下参数完全正确的工具调用不足一半，并利用模型生成时的 hidden states 做探针引导训练以提升参数填充准确率。
🔍 技术视角：精准对应你'业务 API 精准调用'的最后一公里：选对 API 只是开始，把上百字段宽表 API 的参数填对才是真正决定查询成败的环节。这篇把'参数填充'单独拿出来评估与训练，正是你落地 function calling 时最该盯的指标。

📊 架构示意

🎯 为什么值得关注

你的业务 API 多为高业务含义、字段众多（部分上百字段）。function calling 的成败不在'选哪个 API'，而在'入参填得对不对'——填错一个过滤条件，宽表返回的就是错误数据集。这篇首次系统地把参数填充难度分级并给出训练方法，填补了你落地时最缺的评估与改进抓手。

⚙️ 核心机制

① 难度分级——按参数数量、类型复杂度、依赖关系给 tool call 样本分难度档；② benchmark——评估各模型在不同难度下的参数完全正确率（发现前沿模型在复杂场景 <50%）；③ probe-guided 训练——利用 LLM 生成时 hidden states 编码的信息，用探针识别'参数是否填对'的信号，引导训练提升填充准确率。核心是把'参数填充'从隐式能力变成可度量、可训练的显式目标。

🧠 深度解读

架构师视角，这篇最大的价值是'把参数填充从被忽视变成一等评估对象'。业界普遍只盯 tool selection 和调用顺序，但真实业务查询里参数填错（如把'日期范围'填成单点、把'客户等级'枚举填错）才是静默错误的高发源——尤其宽表 API 字段多，填错一个不影响调用成功但结果全错。它的 probe-guided 思路（用模型内部状态探针判断填充质量）也提示：可以在运行时做'参数填充置信度'检测，低置信度的调用前先校验/人工确认。

🛠️ 落地建议

落地建议：① 建立你的业务 API 参数填充难度分级与评估集，持续跟踪完全正确率；② 复杂/高业务影响参数（如过滤条件、聚合维度）加运行时校验，而非全信 LLM 输出；③ 评估是否用 probe/置信度信号触发'低置信度先校验'的护栏，呼应你'数据可信度与验证'的要求。

⚠️ 局限与风险

局限：论文聚焦云网络场景的 tool schema，业务 API 的参数语义复杂度（业务术语、隐含口径）更高，需自建评估集；probe-guided 训练需要可访问 hidden states 的模型，闭源 API 模型难以应用训练侧方法，只能借鉴运行时探针思路。

🔗 原文链接：https://arxiv.org/abs/2608.03071

KG2Cypher: Data-Centric Pipeline for Building Enterprise Text-to-Cypher Systems

2026-06-26 · arXiv 2606.27742
面向企业知识图谱的自然语言查询构建 pipeline：先用观测到的图事实构造可执行 Cypher，再由 LLM 生成对应自然语言问题，经 LLM judge + 人工验证转成 candidate-aware SFT 数据，配合 class-conditioned schema prompting、entity 检索等服务。数据驱动降低企业图谱 NL 接口构建成本。
🔍 技术视角：你'业务知识库构建'路线（企业知识图谱方向）的工程化参考：它不靠合成数据，而是从真实图事实反向构造高质量问答对，解决了企业知识图谱'没有现成 NL 查询训练集'的根本难题。class-conditioned schema prompting 正好呼应'schema 条件化'范式。

📊 架构示意

🎯 为什么值得关注

若你走企业知识图谱路线，最大障碍是'没有训练数据'——企业图谱的 NL 查询样本稀缺，合成数据又不够真实。KG2Cypher 给出'从图事实反推问答'的数据生成范式，让你能基于真实业务图谱低成本构建 NL 接口，是落地企业知识图谱的关键一环。

⚙️ 核心机制

① 反向数据生成——从图谱观测到的真实事实构造可执行 Cypher，再让 LLM 生成对应 NL 问题（保证问题可被该 Cypher 回答）；② 质量校验——LLM judge + 人工验证双重过滤；③ candidate-aware SFT——把验证后的 Cypher-NL 对转成带候选提示的微调数据；④ 服务层——class-conditioned schema prompting（按图谱类型条件化）、entity 检索增强生成。核心是'数据驱动而非模型驱动'降本。

🧠 深度解读
