OADD：从研究问题到列的操作化感知数据发现

2026-08-05 · arXiv 2608.04536
论文定义了一个比 schema linking 更靠前的问题：operationalization-aware data discovery（OADD）——给定一个宽泛的业务/研究概念和一个数据库，判断哪些列能"度量"该概念，必要时还需组合多个互补指标。作者用论文作为"schema-in-use 的记录"自动构造 OADD-Bench（160 个问题、4682 条问题-列标注），并评测了词法/神经检索、schema-linking 系统与 LLM。结果揭示：现有方法在"概念→列"这种弱显式匹配上普遍吃力，是 NL analytics 的真正瓶颈。
🔍 技术视角：这正中你们"不直连库、靠业务含义 API 查数"的核心：宽表 API 上百字段里，用户问的是"客户活跃度"这类概念，而不是字段名。OADD 把"概念→可用列"的映射显式建模为一等公民，值得作为业务语义层设计的理论框架。

📊 架构示意

🎯 为什么值得关注

现有 schema linking / column retrieval 都假设需求相对显式、奖励直接相关；而真实业务提问是抽象概念，需要"操作化"（operationalization）——决定概念怎么测、哪些列支撑。OADD 把这一步独立评测，暴露了当前最大短板。

⚙️ 核心机制

OADD-Bench 构造：从经验论文中用 question miner 抽取并改写论文支持的问题，用 paper-conditioned column miner 重建其测量并 ground 到库标识符，只保留同时有论文与文档支撑的映射。评测对象：词法检索、神经检索、改造的 schema-linking 系统、大语言模型。

🧠 深度解读

关键洞察是"有用列不一定像查询"——它们可能只是某个可辩护度量的互补指标。这打破了"top-k 相似列"的 retrieval 直觉，要求系统能做概念分解与组合推理。对宽表 API 场景，意味着字段语义标注不能只靠"名字相似"，要标注"该字段可度量哪些业务概念"。

🛠️ 落地建议

在你们的业务 API 字段语义标注里，增加一个"可度量概念"维度：每个字段不只标业务含义，还标"能支撑哪些业务概念/指标的定义"，并记录组合关系。这能让 Agent 在面对"客户活跃度"时检索到多字段组合而非单字段。

⚠️ 局限与风险

OADD-Bench 规模有限（160 题/4682 标注），依赖论文作为 ground truth 来源有领域偏向；"可辩护度量"的判定本身带主观性，迁移到企业内部知识库需重新构造标注来源。

🔗 原文链接：https://arxiv.org/abs/2608.04536

AttnLink：把 LLM 内部注意力转为 schema 链接分数

2026-08-01 · arXiv 2608.00693
AttnLink 把 LLM 生成起始位置对候选 schema span 的注意力，转成连续相关性分数，在一次 prefill 内完成全部候选排序，无需自回归解码。提供两变体：AttnLink-U 直接探测预训练注意力（不更新参数），AttnLink-S 用 set-mass 目标+自适应概率下界正则做监督对齐。在 Spider/BIRD/Spider2-SQLite 上 mAP 达 99.22%/95.95%/83.29%，毫秒级延迟，并在 9 个生成器-数据集组合中 7 个拿到最佳执行准确率。
🔍 技术视角：宽表 API 字段越多，schema linking 的精度与速度越关键。AttnLink 用模型自身注意力做"免费"打分，避免了外挂 retriever 的双重维护，是把 schema 理解做"轻"的代表性思路，适合嵌入你们的 API 字段选择环节。

📊 架构示意

🎯 为什么值得关注

Schema linking 是 text-to-SQL/API 调用的前置瓶颈：宽表几百字段塞不进上下文，选错列后面全错。现有方法在"上下文建模能力、分数可控性、推理效率"三者间权衡，AttnLink 试图同时拿下。

⚙️ 核心机制

提取生成起始位置→候选 schema span 的 attention 作为 relevance；AttnLink-S 用 set-mass 目标（覆盖多个相关项）+ adaptive probability-floor regularizer 监督对齐；输出分数支持温度缩放与累积质量选择的精度/召回后调控。

🧠 深度解读

核心发现是"注意力即链接信号"——省去了独立 retriever 的训练与索引维护。但它是"模型内"信号，对模型家族敏感，且依赖生成起始位置这一特定探针，泛化到非该架构的模型需验证。

🛠️ 落地建议

对你们的宽表 API，可在 function-calling 前用类似注意力探针做字段预筛，把上百字段压到 Top-K 再交给 LLM 精确构造调用参数；并用精度/召回后调控满足不同业务可信度要求。

⚠️ 局限与风险

需要能访问模型内部注意力（开源权重模型友好，闭源 API 难）；预训练注意力分布对 prompt 措辞敏感；监督版需 gold schema 标注，企业场景标注成本不低。

Schema-First Retrieval：把目录元数据嵌入做检索，而非查仓里数据

2026-06-23 · arXiv 2606.28387
针对"企业 text-to-SQL 在生成 SQL 之前就选错 schema 上下文"的顽疾，论文提出 Schema-First Retrieval：索引 5 类 catalog 对象（表、列、指标、关系、查询历史），用对象专属文本模板向量化；查询时组合并行向量检索、血缘扩展、cross-encoder 重排、workload 记忆与确定性访问控制门，再交给 SQL 生成。在 CRUSH4SQL 上表 recall@20 达 96.4%，重排为列 recall@10 加 11.1 点；SEDE 上查询历史把表 recall@5 从 52.1% 提到 92.3%；BIRD 上把 SQL 执行错误从 15.6% 降到 6.2%。
🔍 技术视角：这把"元数据管理"做成了"一等检索问题"而非 prompt 格式细节——与你们"业务知识库构建"高度同构：把 API 的字段/指标/关系/历史调用沉淀成可检索 catalog，是比直接喂 schema 给 LLM 更稳的工程路径。

📊 架构示意

🎯 为什么值得关注

现代数仓有上千表、缩写列、非正式指标、隐式 join 约定、权限边界，原始表名根本承载不了这些语义。论文论证：在 SQL 生成之前，catalog 选择本身就是个 first-class retrieval 问题。

⚙️ 核心机制

五类 catalog 对象各自用专属文本模板向量化；查询时并行向量检索→血缘扩展（沿关系/依赖找相关）→cross-encoder 重排→workload memory（历史查询复用）→确定性访问控制门→SQL 生成。

🧠 深度解读

三个数字最有说服力：语义检索比 BM25 基线在表 recall@5 高 32.8 点；查询历史对"低频但有过"的表提升巨大（52.1→92.3）；schema-first 上下文让执行错误降 2.5 倍。说明"上下文质量"比"模型更强"更值钱。

🛠️ 落地建议

把你们宽表 API 的字段、指标定义、字段间关系、历史成功调用案例建成可检索 catalog（指标/关系/历史这三类尤其重要），查询时先检索再调用，而不是把整张宽表 schema 灌给 LLM。

⚠️ 局限与风险

血缘扩展与 workload memory 依赖较好的元数据治理与调用日志积累，冷启动期收益有限；cross-encoder 重排增加延迟；访问控制门需与业务权限体系打通。

🔗 原文链接：https://arxiv.org/abs/2606.28387

CoeusBI（百度）：面向宽表与 JOIN 的工业级交互式 BI 系统

2026-06-13 · arXiv 2606.15384
百度 CoeusBI 直击真实部署三大痛点：频繁 JOIN 拉低 SQL 生成准确率、宽表加剧 schema linking 难度、方言查询与多轮对话算力高且精度低。其 Dual-Agent 架构含离线 View Generation Agent（用错误反馈自主把复杂 JOIN 转成单视图查询）与在线交互 Agent；配 Hierarchical Schema Linking 模块。系统强调"语义层配 NL 接口"仍主要靠人工配指标/维度，CoeusBI 试图自动化这一层。
🔍 技术视角：宽表 + JOIN 正是你们上百字段宽表 API 的写照。CoeusBI 的"离线把复杂 JOIN 物化成单视图"思路，可直接迁移为"离线把宽表 API 调用预计算成业务视图 API"，让在线 Agent 只面对精简单视图。

📊 架构示意

🎯 为什么值得关注

商业 BI 虽越来越多用 semantic layer + NL，但指标/维度仍靠人工定义；真实场景 JOIN 频繁、schema 宽、方言与多轮代价高，工业落地远未解决。

⚙️ 核心机制

Dual-Agent：离线 View Generation Agent 用 error-feedback 自主把复杂 JOIN 查询转成简单单视图查询（消除 JOIN）；Hierarchical Schema Linking 分层处理宽表；在线交互 Agent 处理多轮与方言。

🧠 深度解读

"把复杂 JOIN 离线物化成单视图"是降低在线难度的关键工程权衡——用离线算力换在线准确率与速度。这与你们"不直连库、走 API"的约束天然契合：可把多 API 字段拼装的复杂逻辑离线固化为业务视图 API。

🛠️ 落地建议

对宽表 API：离线识别高频多字段组合/计算，预生成"业务视图 API"（单次调用即得），在线 Agent 只选视图 + 简单参数；对低频复杂查询才回退到原生宽表调用。可借鉴其 error-feedback 自动化视图生成。

⚠️ 局限与风险

离线视图生成需持续维护与刷新（数据/需求漂移）；单视图化可能掩盖底层数据血缘，影响可信度审计；论文为 extended version，完整效果数据需看正文。

TACO：任务感知的列描述自动生成（字段语义标注）

2026-06-19 · arXiv 2606.21685
列描述（如把列名 cust_mem 标注为"客户会员状态"）对 NL2SQL、table QA、entity linking 至关重要，但真实数据集普遍缺文档、列名缩写、含领域行话。TACO 提出三步管线：(1) 缩写展开规范化列名；(2) 生成带同义词与检索关键词的语义描述；(3) 用模拟下游任务做描述修订。还研究 human-in-the-loop 扩展并发布 entity linking 与 schema enrichment 评测集。
🔍 技术视角：这几乎是"宽表 API 字段语义标注"的现成方法论：三步管线（缩写展开→语义生成→下游任务驱动修订）可直接用于给你们的上百字段宽表 API 补语义，且支持人在环校验。

📊 架构示意

🎯 为什么值得关注

企业数据集普遍缺/差列文档，单 prompt LLM 生成有三大问题：缩写处理不一致、描述幻觉/不全、冗余模糊拖累下游。TACO 把它当"任务感知"问题而非单次生成。

⚙️ 核心机制

Step1 缩写展开标准化列名；Step2 生成含同义词+检索关键词的初始语义描述；Step3 用模拟下游任务（NL2SQL/table QA/entity linking）做修订，让描述对下游真正有用。支持 human-in-the-loop。

🧠 深度解读

关键创新是"下游任务驱动修订"——描述好不好由下游任务表现反推，而非人盯。这把字段标注从"写文档"变成"优化检索/生成质量"的闭环，可与你们的 query 历史结合做自演化。

🛠️ 落地建议

对宽表 API 字段：先跑缩写展开（你们一定有大量缩写字段），再批量生成语义+同义词+检索关键词，最后用历史成功调用做模拟下游任务驱动修订；建人在环校验入口沉淀人工修正。

⚠️ 局限与风险

缩写展开依赖领域缩写词典/规则，跨业务线需各自维护；模拟下游任务质量依赖有代表性 query 集；LLM 生成仍有幻觉风险，关键字段需人工复核。

TSCG：确定性 tool-schema 编译，让小模型也能用好宽 tool schema

2026-05-04 · arXiv 2605.04107
生产级 agent（OpenAI Function Calling、Anthropic Tool Use、MCP）把 tool schema 当 JSON 传，但 JSON 是为机器解析设计、非为 LLM 解释设计。在 4B-14B 小模型、生产级 tool 目录规模下，这种协议错配是 tool-use 失败主因。TSCG 是确定性 tool-schema 编译器，在 API 边界把 JSON schema 转成 token 高效的结构化文本，无需模型访问/微调/运行时搜索，组合 8 个算子并给出 ≥51% 压缩下界。在 TSCG-Agentic-Bench（约 1.9 万次调用、12 模型、5 场景）上把 Phi-4 14B 从 0% 恢复到 84.4%（20 tools）。
🔍 技术视角：你们走"业务 API function calling"，宽表 API 的 schema 往往上百字段——这正是 TSCG 说的"协议错配"重灾区。把 JSON schema 确定性编译成 token 友好的结构化文本，是低成本提升小模型调用准确率的利器。

📊 架构示意

🎯 为什么值得关注

JSON schema 对 LLM 是噪声密集、token 浪费的格式；tool 目录一大，小模型直接失效。这是个被低估的"表示层"问题，而非模型能力问题。

⚙️ 核心机制

8 个可组合算子在 API 边界把 JSON schema 编译为结构化文本；形式化压缩下界 ≥51%（well-formed schemas）；完全确定性、无模型访问/微调/运行时搜索；R² 分解证明"表示变化"是主导机制（0.88→0.03）。

🧠 深度解读

最有说服力的是"表示变化主导"的因果分解——不是模型变强了，是喂给它的 schema 变得 LLM 友好了。这对你们选型意味着：与其堆大模型，不如先把宽表 API 的 schema 表示优化掉，性价比高得多。

🛠️ 落地建议

在 function calling 前加一层 TSCG 式 schema 编译，把上百字段宽表 API 的 JSON schema 压成结构化文本再喂模型；对自研/开源小模型部署尤其实用，能显著降低 token 成本与失败率。

⚠️ 局限与风险

确定性编译对 schema 质量有要求（需 well-formed）；不同模型家族对结构化文本格式偏好不同，需按家族调参；论文自建 benchmark，需在你们真实 API 上复现验证。

数据驱动的 function calling 改进：在线金融 QA 实战

2026-04-07 · arXiv 2604.05387
金融领域 API 资产分散在各类函数中，在线金融 QA 需让 LLM 调用定制化金融 API。通用 LLM 难适配金融场景，且在线 query 多样、含与所需函数入参分布外的参数。论文提出数据驱动管线：构造数据集（基于既有研究+周期更新）、用名为 AugFC 的增强方法探索可能参数值提升多样性、两步训练法让 LLM 用金融工具集。展示了一条"让通用 LLM 精准调用业务 API"的工程闭环。
🔍 技术视角：这是"API 语义理解与精准调用"方向少有的工业落地实证：用数据驱动（AugFC 参数探索+两步训练）把通用模型调教成业务 API 调用器，思路可复用到你们的业务 API 工具集。

📊 架构示意

🎯 为什么值得关注

通用 LLM 不懂你们的业务 API 语义与参数约束，在线 query 又常"分布外"，直接 function calling 失败率高。需要一个让通用模型精准调业务 API 的工程方法。

⚙️ 核心机制

数据集周期更新（含真实 query）→AugFC 参数值增强（探索 OOD 参数提升多样性）→两步训练法让 LLM 掌握金融工具集调用。数据驱动地"开发"金融工具集使用能力。

🧠 深度解读

AugFC 的"参数值探索"是亮点——不是只造 query 多样性，而是造"入参值"多样性，针对的是"用户给的参数不在函数期望范围"这一真实失败模式。这对宽表 API 字段取值空间大的场景尤其有用。

🛠️ 落地建议

为你们的业务 API 工具集构造训练数据：收集真实 query + 用 AugFC 式方法枚举字段合法取值组合做增强；两步训练（先学工具语义再学调用）微调一个调用专用小模型，降低对大模型 API 的依赖与成本。

⚠️ 局限与风险

需持续标注/更新数据集，工程成本不低；AugFC 参数探索需字段取值域知识以防生成非法值；金融场景强合规，迁移到你们场景需补权限与可信校验。

EntSQL：企业 text-to-SQL 在长上下文业务知识上的基准（仅 15.9%）

2026-06-02 · arXiv 2606.03363
现有 text-to-SQL 基准（Spider/BIRD/Spider2.0）评 schema 泛化、大规模库、真实工作流，却忽略企业场景：SQL 生成依赖私有业务知识（内部指标、报表约定、组织规则）。EntSQL 含 1066 条中英双语语义样例、跨 5 个业务域，多数样例需问题与 schema 之外的领域知识且含复杂 SQL 结构。英文输入下最佳系统在提供长文档时仅 15.9%，凸显企业知识 grounding 之难。
🔍 技术视角：这是"业务知识库构建"必要性的硬证据：不把业务规则/指标约定/组织上下文沉淀成可检索知识，LLM 直接生成 SQL/API 调用准确率会非常低。它量化了"懂业务"这一步的价值。

📊 架构示意

🎯 为什么值得关注
