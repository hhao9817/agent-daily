AGENTS.md 到底有没有被遵守？首个逐条指令级的 ACF 遵守率实证

2026-11-10 · arXiv
作者指出，整个 agent context file（ACF，如 AGENTS.md）治理机制建立在一个未被验证的假设上：写进去的指令真的会被执行。他们采集真实 ACF 快照与对应的 agent 生成 commit，把 ACF 中的显式、可执行指令操作化成测量脚本，做指令级合规评估。结果：多数可观测指令都能被操作化；agent 整体「遵守多于不遵守」，但分布呈尖锐的两极——一部分指令被一致执行，另一部分从未被尊重，且不同指令类别、不同 coding agent 之间差异明显。作者据此指出哪些指令类型需要改写、哪些 agent 需要 ACF 之外的强制手段。
🔍 技术视角：这是把「研发知识库/上下文工程」从玄学拉回可测量工程的关键一步。对已建研发知识库的团队，含义很直接：AGENTS.md 是软提示（soft policy），不是治理层；凡是可以被机器检查的约束（分层依赖、禁用 API、测试覆盖、提交规范），都应该下沉到 CI/lint/pre-commit 的硬门禁，ACF 只负责「意图与风味」。更进一步，可以照抄论文方法：把团队 ACF 的每条规则写成可执行断言，跑一周得到自己的「遵守率热力图」，再决定哪条规则值得留在 ACF、哪条必须进 CI。

📊 架构示意

🎯 为什么值得关注

业界普遍把 AGENTS.md/CLAUDE.md 当作「给 agent 的代码规范」，但从未有人逐条验证它是否生效。这篇论文第一次给出「哪些指令能被信任」的经验证据，直接影响知识库与 agent 治理的设计取舍。

⚙️ 核心机制

三步法：①从真实仓库抽取 ACF 快照与其后 agent 生成的 commit 建立配对；②把 ACF 中显式、可判定的指令（如「新文件必须带 license header」「禁止直接调用 internal API」）翻译成可执行测量脚本；③在 commit 上跑脚本，得到指令级遵守率，并按指令类别与 agent 型号分组比较。

🧠 深度解读

「两极分化」比「平均遵守率」更有信息量：它说明 agent 对指令的服从不是连续衰减，而是被少数几个因素开关式决定的——指令是否可被局部验证、是否与模型默认行为冲突、是否在上下文窗口中被稀释。这也解释了为什么单纯把 ACF 写长没用：长上下文里的弱约束会被默认行为覆盖。对多 agent 并存的团队，同一份 ACF 在不同 agent 上的遵守差异意味着「上下文可移植」目前只是文件可移植。

💼 商业启示

「上下文工程」正在分化出可售卖的工程能力：ACF 审计、指令可执行化、agent 合规报表。对自建团队，这是低成本高确定性的一步；对工具厂商，谁能提供「规则→断言→报表」的闭环，谁就拿到了 agent 治理的入口。

🛠️ 落地建议

①把团队 ACF 规则分成三类：可机器验证（进 CI）、风格偏好（留 ACF）、业务意图（进知识库+示例）。②对每条规则写一个最小可执行检查，月度跑一次遵守率报表。③ACF 保持短小，把「必须做到」的少量规则放在最前，其余移到 skill/脚本里按需加载。

⚠️ 局限与风险

论文只覆盖「可观测、可操作化」的指令，对「代码风格是否优雅」这类不可判定规则无结论；遵守率与任务成功率之间没有建立因果链——遵守了也不代表任务做对了。ACF 生态变化快，快照结论有时效性。

ExpertCrowd-SWE：前沿 coding agent 在专家级多文件任务上封顶 67.3%

2026-11-09 · arXiv
EC-SWE 是 100 个由在职工程师撰写、针对真实仓库固定 commit 的多文件任务基准，覆盖 87 个开源项目、11 种语言，每题配密封参考解与加权评分器（must-pass blocker + pass/fail gate 编码「maintainer 会拒绝合并什么」）。中位 ticket 仅 148 词，中位参考解改动 471 行。每个任务镜像在发布前校准：参考解得 1.0、未改动仓库与惰性改动得 0；近半数任务还附带 lazy/adversarial 控制补丁要求评分器正确分类。7 个前沿模型各 5 次共 3,495 次运行：Claude Opus 5.5 67.3%、GPT-6 Astra 63.7% 领先且差距不显著，Claude Fable 5.1 46.5%、Gemini 3.8 Flash 40.0%，Qwen 3.8 Max/DeepSeek V4.1 Flash/Grok 4.6 在 32-34%。无任务被所有模型全解，80 个任务上没有任何模型 5 次全对，分数跨度 35 分；中位步数 33-166 步且与得分几乎无关。
🔍 技术视角：这个基准的价值在「校准」而非「排名」：参考解 1.0、惰性改动 0、adversarial 补丁必须被识别，才使 67.3% 这个数字可信。148 词需求 → 471 行改动的比值说明，真实工程里成本不在「写代码」而在「从稀疏需求恢复隐含约束 + 跨文件保持一致」。步数与得分无关也是一记提醒：agent 的「努力程度」不是质量信号，任何用步数/token 做效能指标的方案都会被这条数据打脸。

📊 架构示意

🎯 为什么值得关注

SWE-bench 系已被污染且偏「单点修复」，EC-SWE 用专家撰写 + 密封参考解 + 对抗性控制补丁重建了可信度，是当前判断「coding agent 到底能不能接手真实工单」最硬的尺子。

⚙️ 核心机制

任务来自实践工程师对真实仓库的 change request；评分器按加权、多为可执行的准则给部分分，must-pass blocker 与 gate 表达合并门槛；镜像先做三档校准（参考解 1.0 / 未改动 0 / 惰性改动 0），并附 lazy 与 adversarial 补丁检验评分器；统一平台 harness 给每个模型其原生 tool 接口，避免工具差异污染。

🧠 深度解读

67.3% 的天花板 + 35 分的模型跨度 + 「无任务被全解」共同指向：剩余失败不是随机噪声，而是能力结构性缺口（跨文件重构、隐式约定、边界条件）。80 个任务上无模型 5/5 全对，说明 pass@5 类指标会系统性高估可靠性——单次成功不代表可托管。步数无关则意味着 test-time scaling 在「读懂需求」这一维上收益递减。

💼 商业启示

「agent 能替代多少工程师工作量」的对外叙事需要被这个数字校准：顶级模型在专家任务上约三分之二通过率，且不可 5/5 稳定。对企业采购，正确姿势是「agent 做初稿 + 人做合并门禁」，而不是按人头替换；对工具商，「可靠性」而非「能力上限」才是下一阶段的差异化战场。

🛠️ 落地建议

①把 EC-SWE 的评分器设计（blocker + gate + 对抗补丁）借到内部评测：内部工单也要有「惰性改动必须 0 分」的校准。②用「5 次全对率」而非 pass@1 作为能否托管的门槛指标。③失败集中在跨文件一致性，团队应优先投资 repo 级图谱/依赖分析，而不是更强的单文件补全。

⚠️ 局限与风险

仅 24 个任务公开（76 个留作抗污染），第三方无法完整复现排名；100 题规模下单题权重高，模型间 3-4 分的差距容易受任务抽样影响；作者只测了 7 个模型，开源权重模型覆盖有限。

FlowPlan：在控制流图上先规划再改码，token 降到 0.32-0.47x 且不掉解决率

2026-11-09 · arXiv
现有降本方法多在「限制、压缩或跳过」信息与动作，FlowPlan 问的是互补问题：能否在抽象程序层（而非反复操作原始源码）上推理修复？它围绕 per-function 的控制流/数据流图组织定位、规划与验证：先在抽象上定位候选故障点，把预期修复表达为显式 graph delta，再改具体源码；改后重建同一抽象，比对「观察到的结构变化」与「计划的变化」，最后做完整验证再终止。六个 benchmark-model 组合中 resolution rate 相对 vanilla agent 无显著变化，而 token 在每个设置都下降（五个设置显著）：Claude Haiku 4.5 上 SWE-bench Pro 0.46-0.47x、Verified 0.32-0.35x、SecBench 0.68-0.74x；Sonnet 5 上分别为 0.72-0.76x、0.73-0.74x、0.92-0.94x。轨迹分析显示省下的是改后反复重读与反复测试，被显式验证替代，同时单次调用上下文变小。
🔍 技术视角：这是把「程序表示」重新引入 agent 循环的漂亮案例：agent 贵在两件事——探索定位与改后自检，而这两件事都可以在图上便宜地做。graph delta 作为「计划的可执行中间表示」，让「计划 vs 实际」比对成为可能，等价于给 agent 一个低成本的自我验证信号。对已建代码图谱/知识库的团队，这是把图从「检索用」升级为「推理与验证用」的直接路径。

📊 架构示意

🎯 为什么值得关注

token 成本是 coding agent 规模化的第一约束，而多数降本手段以牺牲能力为代价。FlowPlan 证明了第三条路：换表示层，不换能力。

⚙️ 核心机制

①用程序分析抽 per-function CFG/DFG；②在图上定位故障候选，产出「计划图」；③把计划与当前图的差异写成显式 graph delta（增删节点/边）；④按 delta 改源码；⑤重建图，比对结构差异是否等于计划；⑥通过后做完整验证（测试）再终止。

🧠 深度解读

关键在于「验证信号前移且变便宜」：传统 agent 改完必须重读大段代码 + 跑重测试才能确认，FlowPlan 用结构比对在毫秒级给出「改得对不对」的中间反馈，把昂贵的测试留给最后一步。token 节省与模型强弱相关（Haiku 省得多、Sonnet 省得少），说明抽象层替代的是「弱模型本来要靠大量上下文弥补的推理」——即抽象图对弱模型是能力补偿，对强模型只是效率优化。

💼 商业启示

「用更便宜的模型 + 更好的表示」可能比「用最贵的模型」更经济：Haiku 档省 65-68% token 且不掉解决率，直接改变 agent 产品的单位经济模型。对做代码智能的团队，程序图从「检索增强」变成「推理底座」，是差异化壁垒的来源。

🛠️ 落地建议

①在自建研发知识库里补 CFG/DFG 层（Tree-sitter + 简单数据流即可起步），先用于 review 的 blast radius，再用于修复规划。②把「计划-执行-比对」写成 agent 的固定三段式，比对失败即回滚，避免无效测试消耗。③对弱模型（便宜档）优先启用，ROI 最高。

⚠️ 局限与风险

依赖可静态分析的语言与构建，动态语言/宏密集代码的图质量存疑；graph delta 的表达力对「跨函数重构」类修复可能不足；论文以 SWE-bench 系为主，工业仓库的长尾依赖未覆盖。

工程师的 token 消耗不是 LOC：JetBrains 404 人 5 周实证

2026-11-10 · arXiv
组织正用工程师的 token 消耗监控 AI 采用、编预算、衡量生产力，但这个指标与工程产出的关系并不清楚。作者把 404 名 JetBrains 工程师 5 周的 coding agent token 使用与其 commit 关联，并分析 412 人的公司问卷。发现：token 花费主要在工程师之间差异，且「谁花得多」在 5 周内基本稳定；在 commit 数相近的周之间，P90 花费是 P10 的 39-240 倍；同一工程师内部，花费翻倍对应约 10% 更多 commit；现有工作指标只能解释跨人方差的 38%、周内方差的 13%。问卷中技术角色近九成的 agent 评估里，agent 被用于编码之外（分析、调研、规划）。结论：token spend 度量的是「工程师用 agent 做了多少种工作」，而非工作的产出与价值，最多用于资源核算。
🔍 技术视角：这是给「AI 研发效能度量」泼的一盆精确的冷水。39-240 倍的个体差异 + 仅 38% 可解释方差，意味着任何以 token 为分子/分母的 KPI 都在测量「使用风格」而非「产出」。对架构师，正确做法是把 token 当成本科目（capacity planning、预算分摊），把效能评估交给「任务 + 结果证据」；同时这条数据也解释了为什么 agent 成本难以预测——它由个体习惯驱动，而非由工单量驱动。

📊 架构示意

🎯 为什么值得关注

企业正在把 token 预算做成财务制度，若指标本身无效，会同时误导预算、绩效与技术选型。这是首个大规模、带 commit 关联的实证。

⚙️ 核心机制

①采集 5 周 coding agent token 用量，按工程师聚合；②与 commit 记录做面板关联；③用分位数比较同期花费离散度；④用回归估计工作指标对花费方差的解释力（跨人 38%、周内 13%）；⑤用 412 人问卷交叉验证使用场景。

🧠 深度解读

「花费翻倍仅对应 10% 更多 commit」的弹性极低，说明 token 与产出之间不是线性生产关系，而是被任务类型（探索/重构/调研）与个人习惯强烈调节。跨人方差远大于周内方差，意味着稳定的「重度用户」群体存在——这类用户往往在做 agent 的探索性使用，其产出难以用 commit 计量。因此 token 指标在个体层面几乎无信号，只有在团队/成本池层面才有意义。

💼 商业启示

AI 成本治理会从「按人头买 license」转向「按 token 成本池 + 使用规范」。能提供「任务级成本归因 + 产出证据」的工具会成为 CFO 与 CTO 的共同语言；反之，卖「token 用量看板」的产品会很快被证明是伪指标。

🛠️ 落地建议

业务过程自动化反复在同一 SOP 上跑新输入。LLM agent 能按自然语言 SOP 执行，但每次运行的每一步都要调 LLM 选动作，规模化后延迟与成本都高。ReTrace 把 SOP 加少量已记录 agent 轨迹转成可复用工作流，下一步由代码而非 LLM 决定：关键观察是 agent 每次工具调用所附的 reasoning 往往说明了「为什么做这一步」，而单独的工具调用不含此信息。ReTrace 抽出每步背后的条件，跨轨迹合并成紧凑 rule document，再生成可执行工作流；只有最后一步依赖平台，因此 rule document 可编译到不同编排平台。在 79 条生产流程上，工作流完成率 93.8%（agent 96.8%），单任务成本低 24%；τ²-Bench 上 75.8% 任务成功（agent 80.6%），但运行 1.3s 而非 170s；对训练失败做三轮 repair 可把 k=2 工作流从 66.7% 提到 81.2%。在 8 条 SOP-Bench 流程上，未 repair 的 ReTrace 落后 few-shot 生成（80.6% vs 83.6%），但从有标注训练失败 repair 后升到 87.8%、0.40s/任务，而 agent 是 85.5%、46.6s。
🔍 技术视角：这是「企业 agent 架构」里最实用的一条定量法则：对高频、结构稳定的 SOP，把决策从 LLM 蒸馏到代码，用 3 个点的完成率换 130 倍延迟与 24% 成本，几乎总是划算。更妙的是「reasoning 是条件来源」这一观察——它把 agent 日志从「调试材料」变成「流程挖掘语料」，让 agent 自己成为工作流的编译器输入。

📊 架构示意

🎯 为什么值得关注

企业 agent 的落地成本主要来自「每次都重新推理」。ReTrace 给出了从 agent 到确定性工作流的可操作迁移路径，且保留了跨平台可移植性（rule document 与平台解耦）。

⚙️ 核心机制

①收集 SOP 与少量成功轨迹（含每步工具调用与 reasoning）；②从 reasoning 中抽取该步的触发条件；③跨轨迹对齐与合并，去重冲突，形成紧凑 rule document；④由 rule document 生成可执行工作流（代码选择下一步）；⑤用有标注的失败做 repair 迭代。

🧠 深度解读

「只有最后一步依赖平台」是工程上的关键设计：rule document 是平台无关的中间表示，等价于把「流程知识」与「执行引擎」解耦，避免被某个编排框架锁定。repair 的增益（66.7%→81.2%，SOP-Bench 80.6%→87.8%）说明蒸馏不是一次性的，需要「失败样本驱动的迭代」才能超过 few-shot 生成。1.3s vs 170s 的差距意味着从「分钟级批处理」进入「交互式」的可用区间。

💼 商业启示

「agent 先探索、再蒸馏成工作流」会成为企业自动化的标准两阶段模式：探索期用 LLM 拿覆盖率，稳定期用代码拿成本与确定性。这也给 RPA/编排厂商一个新叙事——不是「用 LLM 替代 RPA」，而是「用 agent 生成 RPA」。

🛠️ 落地建议

①选出团队里调用量最高的 5-10 条 SOP，先用 agent 跑出 20-50 条轨迹并保留 reasoning。②把 reasoning 当语料做规则提取，产出 rule document 并人工评审条件边界。③按「确定性工作流优先、LLM 兜底」做路由：规则命中走代码，未命中回落 agent。④建立失败样本回流与 repair 机制。

⚠️ 局限与风险

完成率仍有 3 个点损失，对高合规场景可能不可接受；依赖 reasoning 质量，若模型不写解释或解释不忠实，条件抽取会失真；SOP 变更需重新蒸馏；8 条 SOP-Bench 上未 repair 版本反而不如 few-shot 生成，说明冷启动期不宜直接替换 agent。

DEPUTYBENCH：无法验证权限时，agent 并不会停下来（10.3% vs 3.5%）

2026-11-09 · arXiv
企业 agent 必须判断普通请求是否被组织记录与政策允许，同时继续做合法工作。DEPUTYBENCH 是可执行基准：79 个基项、375 个实例、成对权限上下文、分级证据要求。12 个模型上，修订审计给出 pooled safety 88.0%、paired success 79.1%。受控研究用 28 个派生任务、6 个模型测试三种扰动：授权事实翻转、证据遮蔽、无关改写。结果显示结果与后端权限一致，但「证据缺失」时的受限执行率高于「明确无权限」：27 个匹配任务上 10.3% vs 3.5%，差 6.8 个百分点（95% CI 1.9-13.0）。事后分析把 100 次遮蔽条件执行中的 61 次定位到四个隐私任务（需完整累计计数或本人同意）。排除最易错模型或最大贡献任务后差异仍在，但在那四个任务之外小得多。因此「有证据时的高安全分」不能证明「无法验证权限时能可靠停止」。无关改写下 paired success 在预设 5 点边际内等价，强模型安全接近上限。评分器验证从 178 提升到 266/284 个held-out 反例正确判分。两名安全专家用两周人工核验任务 ground truth，阶段标签仍由 LLM 生成。
🔍 技术视角：这条直接改写「构造性拒绝」的设计假设：模型不是不知道要拒答，而是在「证据缺失」这种模糊态下倾向于继续执行。10.3% vs 3.5% 的对比说明「明确禁止」比「无法确认」更容易被遵守——这是典型的默认放行（fail-open）倾向。对企业 agent，结论是把「证据不可得」显式升级为「拒绝并请求授权」，而不是让模型自己在模糊中判断。

📊 架构示意

🎯 为什么值得关注

字段级 RBAC、数据主权、审计日志都建立在「agent 会守住边界」的前提上。这个基准第一次量化了「边界模糊时 agent 的失守率」，且给出了可复现的扰动方法。

⚙️ 核心机制

成对权限上下文（同一请求，允许/禁止两版）+ 分级证据要求（有的任务必须看到授权记录才能执行）；三种扰动：授权事实翻转（权限其实相反）、证据遮蔽（授权记录不可见）、无关改写（干扰项）；评分看「是否执行了不该执行的动作」与「是否完成了合法工作」。

🧠 深度解读

「遮蔽比明确禁止更危险」的机制解释是：明确禁止提供了一个可直接检索的拒绝理由，而遮蔽只留下「查不到」——模型把「查不到」解释为「大概可以」。61/100 集中在四个需要「完整累计计数或本人同意」的隐私任务上，说明这类要求对信息完整性极敏感：少一条记录就无法证明合规，而模型会退化为按部分信息放行。

💼 商业启示

「构造性拒绝」从理念变成可测指标：企业采购 agent 时应要求供应商提供「证据缺失场景下的执行率」，而不只是准确率与安全分。对做企业 agent 的团队，policy engine 前置 + fail-closed 默认值是最便宜的合规护城河。

🛠️ 落地建议

①把权限判断做成前置确定性检查（policy engine），不交给模型推理；模型只能看到「已判定为允许」的子集。②证据缺失时默认拒绝，返回明确的「需授权」而不是让模型自行解释空结果。③对「累计计数/同意」这类完整性敏感操作单独设硬门禁。④把证据遮蔽纳入红队用例，因为它比显式越权更容易漏。

⚠️ 局限与风险

阶段标签由 LLM 生成（虽有人工核验 ground truth）；28 个派生任务的结论是 secondary analysis，效应量在剔除四个隐私任务后大幅缩小；12 个模型的覆盖面与版本未全部公开；基准规模（79 基项）偏小，适合诊断而非排名。

Auto-Ontology 是 Apache-2.0 的 Python 框架，用五个动词组织能力：Discover（从 metadata 生成企业 ontology、接入已有 ontology 与语义模型、构建 AI-ready 知识图谱）、Ground（给 agent 可信的业务含义：指标、实体、关系，并跨系统调和冲突定义）、Validate（用 certified definition 与 lineage 校验生成查询，每个答案带 provenance）、Expose（通过 MCP、CLI、API 把上下文提供给任意 agent harness）、Learn（把 certified correction 与使用情况回灌本体）。工作流是三段式：自动生成草稿 ontology → 人工 certify 术语/描述/SQL 属性 → 服务端用 lineage 校验并执行。架构为 FastAPI + LangChain 后端、Postgres 17 + pgvector（catalog/ontology/向量）、FastMCP 只读 MCP server，另有 Next.js 前端；支持 Apache Ossie YAML 导入导出，可与 Wide World Importers 数据集用 Docker Compose 直接跑通。仓库 12.2k⭐，2026-11-12 仍在活跃提交。
