代码库查询会拼出「从未同时存在」的事实：完整版本发布契约把 150 次更新试验的 2 次错答降到 0

2026-11-18 · arXiv 2611.21616
编辑型 agent 一边查仓库一边改仓库，源码、符号、图关系、检索状态往往由不同存储维护、不同时刷新，于是「成功」的查询可能把不属于同一仓库版本的几条事实拼在一起，作者称之为 mixed-revision code context。论文提出面向 agent 的 complete-revision publication contract：在一次响应内所有视图共享同一版本标识与发布边界，边界前要么等、要么报不可用、要么给完整的旧版本，边界后给完整的新版本。实现 Codetrip 后在冻结的 Gin v1.12.0 上，live-source 组合在 150 次更新试验里出现 2 次不安全响应，完整版本发布为 0。

2026-11-18 · arXiv 2611.21625
论文在 Apache Kafka 上构建 AST 派生的归属图，覆盖 1,600 条与源码关联的日志记录，并用 315 条事件式查询（103 个不同目标）做审计过的基准。纯向量检索是强基线，Recall@20 达 0.956；无论静态还是置信度引导的分阶段 AST 扩展，都没有显著提升。作为外部对照，已发表的文本图谱系统 HippoRAG 在其自身 ColBERTv2 骨干上从 0.803 掉到 0.308，事后文档集成只回到 0.648。分阶段扩展确实把 cross-encoder 配对量与重排时间降了约 52%；人工评估的 100 条下游查询中，AST 结构证据对根因正确率没有显著优势。

先问再查：把「该澄清什么」定义为多个 SQL 解释之间的分歧，关键歧义覆盖率 48.6%→82.8%

2026-11-18 · arXiv 2611.21645
交互式 text-to-SQL 的难点不是生成 SQL，而是在有限轮次内决定澄清哪一个不确定性。DisGuAD 的做法是：先建查询词项清单，用互补的探针族诱导出多个对比性 SQL 解释，比较它们的规范化 SQL 组件，把反复出现的差异归因到面向用户的澄清目标，再用轻量优先级 + 对话状态机制只问一个高影响目标。在 BIRD-Interact Lite/Full 与两个 LLM 骨干上，归一化 Reward 提升 4.40–8.97 分，关键歧义覆盖率从 48.62% 升到 82.75%、45.76% 升到 85.14%；把澄清信号接给两个独立的静态 text-to-SQL 框架（生成器固定）还能再涨最多 13.97 Reward。
🔍 技术视角：这条给出「构造性拒绝」的上游形态：构造性提问。用户不直连数据库、面对上百字段宽表时，真正的风险是「问了一个有歧义的问题，agent 却自信地选了一种解释」。DisGuAD 把歧义检测从「表面语言歧义」改成「SQL 结果差异」，本质是用多次采样的分歧做不确定性估计——这在工程上比训练一个歧义分类器便宜得多，也更可审计：每个澄清目标都能指回具体 SQL 组件的差异。

问题、schema、库内值三种语言不一致：库内值语言最多吃掉 23 分，翻译问题无效

2026-11-18 · arXiv 2611.22333
现有 text-to-SQL 评测默认单语言，但国际业务里问题语言、schema 语言、库内存储值语言常常不同。MoL-SQL 把三者语言独立切换而任务固定，并把每个跨语言实体映射分为四个难度等级；用统一对齐管线迁移五个不同领域的基准，构建共享跨语言实体表、按约束迁移数据库、在执行等价校验下重写 gold SQL、再由已验证 SQL 反向生成问题。MoL-Full 16,892 条、MoL-Cube 3,840 条（覆盖所有语言组合）。八个 LLM、四类方法的结果显示：schema 语言与值语言影响不同，库内值最多造成 23 分损失，且主要来自跨语言实体映射；翻译问题或增加推理都不能缩小差距，只有拿到目标库取值才明显缓解。
🔍 技术视角：对「通过高业务含义 API 查数」的团队，这是一条直接可用的结论：值域对齐（枚举值、状态码、商户名、科目名）是独立工件，不能指望模型把中文问题映射到英文枚举。语义层里应该有一张「实体/值字典」，并在 function calling 的参数描述里显式给出候选值与同义词。翻译问题是最常见的错误投入——它改善的是表层，不是映射。

1,000 条自然语言准则对 4K 上下文 <2 秒：逐条三值裁决把「违反了哪条」变成可审计输出

2026-11-18 · arXiv 2611.23074
Agent 受上百条自然语言准则约束，但现有验证器无法对大批准则高效给出「满足/违反/不适用」的逐条判定。论文提出 VFM：树注意力验证器，编码共享上下文与目标文本后并行给 N 条准则打分，输出独立的三值裁决；在 CriteriaBank（394K 条 context/target/criterion/verdict 元组、321K 条不同准则字符串）上预训练。微调后的 VFM-4B 在合成治理基准上超过 GPT-5.4，在 DynaBench 多准则基准的 trace 级失败检测上超过 DynaGuard-4B，且逐条裁决能定位违规规则并支持定向升级到更大的 CoT judge。单张 H100 上对 4K 上下文评估 1,000 条准则 <2 秒、显存 <11GB。

信息够了还继续调工具：JET 在「足够」处截断轨迹并写理由，工具调用降 11–33%

2026-11-18 · arXiv 2611.22539
仓库级问答里，agent 用工具探索代码库，本应在信息足够时作答，但论文发现它常常继续调用工具，称为 over-exploration；更麻烦的是，用专家轨迹做 SFT 会把这个习惯一起学进去。JET 的做法是：把每条训练轨迹在「信息已足够」的那一步截断，插入一段解释「为什么此时可以回答」的 rationale，并对 rationale 加大损失权重。两个仓库级 QA 基准、两个 8B 开源模型上，自生成轨迹的工具调用减少 11–33% 而分数基本保持；在专家轨迹上比 SFT 少 18–28% 调用，同时保留大部分分数增益，推理成本也随之下降。
🔍 技术视角：对业务线是同一病理：宽表 API 一次返回上百字段，agent 容易「再查一次确认」，每次调用都带延迟与配额成本。JET 的启示不是训练技巧，而是「足够」这个判据必须显式化——要么在轨迹里标注，要么在运行时用覆盖度检查。SFT 会放大坏习惯这一点尤其值得警惕：拿专家日志微调，等于把专家的犹豫也学了进去。

环境一变，旧技能可能倒扣 10 个点、多花 40% 步数：选择性维护把准确率拉回最多 +67pp
