Never the Number: Structural Abstention —— 可生成者只影响问哪个问题，永不影响返回什么值

2026-08-14 · arXiv 2608.13926
论文指出 LLM text-to-SQL 系统以一种对部署至关重要的方式失败：幻觉列或错误聚合产生流畅的错误答案，在使用点与正确答案不可区分。当消费者无法检查生成的查询（企业 AI 部署、运营仪表板），或消费者是 tool-using agent 而非人时，仅靠准确率不够——没有任何标记告诉你哪些答案不该信。作者提出结构化弃答（structural abstention）架构模式：trusted kernel + generative shell，基于一条不变量——能编造的组件可以影响系统回答哪个问题，但永不影响返回什么值。生成外壳解释欠规格输入并措辞回复；确定性 kernel 把完全规格化的问题匹配到有界可回答问题形状集合并编译为查询；两者在用户读取的确认处汇合，kernel 无法表达的请求被拒绝而非近似。弃答不需置信度估计，因为不可回答的请求是不可表示的。引用数已核实：0（Semantic Scholar）。
🔍 技术视角：这是本周对用户"业务系统精确查询"课题最直接相关的架构论文。它把"可靠性"重新定义为"能告诉你什么时候不该信"而非"更准"。用户场景中 agent 通过宽表 API 查数，消费者是下游 agent 而非人——Never the Number 的 trusted kernel 模式可直接迁移：把宽表 API 的合法查询形状用确定性 kernel 枚举（哪些字段组合可查、哪些聚合合法），生成外壳只负责把自然语言映射到合法形状，映射不上的直接拒绝。这比靠模型 self-confidence 更可信，因为拒绝不需置信度估计。

SemPlan: 结构化语义规划比直接 SQL 更正确但非万能——4800 条记录的架构权衡实证

2026-08-14 · arXiv 2608.13612
SemPlan Benchmark 评估 LLM 查询企业数据的架构设计空间：用确定性合成双语 benchmark（1800 案例，英+巴西葡语，1200 案例冻结科学评估子集），对比四种架构——A1 直接 SQL 生成、A2 bounded tool-agent 基线、A3 结构化语义请求+确定性规划执行、A4 带澄清的状态机语义计划变体。4800 条主记录显示正确率绝对值低：A1 22.25%/A2 22.58%/A3 25.67%/A4 24.25%。A3 正确率最高且在配对正确性分析中显著优于 A1/A2/A4，但 A1 保留最高策略正确率和最低不安全/无效率，A4 平均 API 成本最低且误拒率最低。150 案例稳定性子集重复性 92-98.67%。结论支持权衡解释而非通用排名：额外结构约束改变失败模式和效率，但不单调提升正确率也不解决歧义和多轮状态一致性。
🔍 技术视角：SemPlan 是对用户"语义层 vs 直接生成"路线选择的硬数据。A3（结构化语义请求+确定性规划）正确率最高，证明语义层路线在正确性上有优势；但 A1（直接 SQL）策略正确率和安全性最高，说明直接生成在合规性上有优势。关键洞察是"非单调提升"——加结构不是万能药，它改变失败模式而非消除失败。这对用户选型意味着：如果优先正确率选 A3 语义层路线，如果优先合规/安全选 A1 受控生成，但要预期每种架构有不同失败模式需要不同治理。

Polaris: 多 Agent 企业分析框架——把 agent-task 分配建模为自适应二部图匹配

2026-08-14 · arXiv 2608.14246
Polaris 是一个 supervisor-led 多 agent 框架用于对话式企业分析，解决"组织数据丰富但洞察贫乏"的问题。核心创新是 Dynamic Task Coordination（DTC）——一个决策论编排层，把 agent-task 分配建模为自适应二部图匹配（adaptive bipartite matching），实现跨专业 agent（查询/可视化/推理）的实时协调、恢复和优化。DTC 配合 reason-first ReAct-style agent，把自然语言查询转化为连贯的分析工作流：不仅检索和可视化数据，还解释背后的"why"。在结构化企业数据集上评估显示高语义保真度和答案相关性，展示多 agent 编排在规模端到端商业智能中的潜力。
🔍 技术视角：Polaris 的 DTC 把多 agent 编排从"固定 pipeline"升级为"动态匹配"，这对用户"agent 调多个业务 API 串联查数"场景有直接参考。固定 pipeline 假设每个查询走相同步骤序列，但企业分析常需根据问题性质动态选择"先查哪个 API、要不要可视化、要不要推理因果"。DTC 的二部图匹配让 supervisor 根据任务特征和 agent 能力实时分配，而非硬编码流程。这与 TDS Loop Engineering（本日收录）的"trigger/termination/recovery 控制面"互补——DTC 管 agent 间分配，loop engineering 管 agent 内循环。

agent 可信 API 消费栈成型——何时拒绝+喂什么+如何审+如何扩四层分工

2026-08-18 · 综合研判（基于本日收录来源 + 历史链路）
本日 8 条情报串成一个完整链路，指向"agent 可信 API 消费栈"四层分工成型。Never the Number（结构化弃答）定义"何时拒绝"——可生成者影响问哪个问题不影响返回什么值，不可表示的请求被拒绝。SemPlan（语义规划 benchmark）定义"如何查"——结构化语义请求+确定性规划正确率最高 25.67%，但非单调提升，需配合弃答处理 74.33%。Polaris（多 agent 动态匹配）定义"如何分工"——DTC 二部图匹配让专业 agent 各走一跳应对 multi-hop 衰减。dbt token 压缩定义"喂什么"——transactional API 压缩为 warehouse context 层降 99% 成本。dbt Core v1.12 Rust parser 定义"如何编译"——语义层引擎 Rust 核心化 5-10x 更快。Cube v1.7.21 分支 CLI 定义"如何审"——语义层定义可分支审阅合并。TDS Loop Engineering 定义"如何恢复"——trigger/termination/recovery 三控制面。TDS Autoscaling 定义"如何扩"——request velocity + payload diversity 检测循环。
🔍 技术视角：四层分工把"语义层 vs 知识图谱"二元选择彻底升级为"何时拒绝+喂什么+如何审+如何扩"四维治理架构。Never the Number 管"何时拒绝"（结构化弃答，不可表示=拒绝），dbt token 压缩管"喂什么"（warehouse 压缩 context 层），Cube 分支 CLI 管"如何审"（语义层定义分支审阅），TDS Autoscaling 管"如何扩"（agentic traffic 循环检测）。这与 8/16 已收录的四层分工（约束建模+记忆治理+语义暴露+流量管控）精确映射：结构化弃答=约束建模层的拒绝机制，token 压缩=语义暴露层的 context 压缩，分支 CLI=语义暴露层的治理，循环检测=流量管控层。最核心战略研判：agent 可信不靠更强模型，而靠四层分工——每层解决一类不可靠：弃答解决"幻觉值"，压缩解决"token 膨胀+速率限制"，分支审阅解决"定义误改"，循环检测解决"失败空转"。

dbt《Model for the token, not the table》——Gong MCP 直连烧 24 万 token，warehouse 压缩降 99% 成本

2026-08-17 · dbt Blog
dbt Labs 博客详述 Gong（通话录音）案例：团队想让 Claude 使用 Gong 通话历史，最短路径是 MCP 包裹 Gong REST API。但单客户历史约 30 通电话，每通 transcript 8300 token，一次账户历史约 24 万 token——这迅速触达 Gong API 每秒/每日速率天花板。根本问题是把 transactional API 当高吞吐 context 层用。解法：Fivetran 已持续把 Gong 数据导入 Snowflake，在 warehouse 里用 dbt 建模——把每通电话摘要压缩，60 分钟通话从 1 万+ token 压到几百（20x 压缩/74x 更少 token/99% 更便宜）。压缩作为增量 dbt job 在数据入仓时跑，推理成本通过 Snowflake credits/Vertex batch/Databricks AI Function 定价，比交互式 API 调用便宜得多且每通电话只付一次。压缩 1000 通电话批量成本在几十美元级别。通过 dbt MCP server 从 warehouse 提供数据，移除 API 天花板且可 join 全仓库数据构建丰富 context 层。
🔍 技术视角：这篇博客直接命中用户"通过业务含义 API 查数"课题的核心张力：业务 API（如 Gong）是为 transactional 交互设计的，不是为 agent 高吞吐 context 消费设计的。直接用 MCP 包裹 API 让 agent 调，会因 token 膨胀和速率限制迅速触顶。正确模式是"API→warehouse→dbt 建模压缩→dbt MCP server 暴露"——让 agent 消费的是压缩后的 warehouse context 层而非原始 API。这与本日收录的 Never the Number 结构化弃答、SemPlan 结构化语义规划形成三角：结构化弃答管"何时拒绝"，结构化语义规划管"如何查"，token 压缩建模管"喂什么"。

TDS《Loop Engineering for RAG》——四块砖处理干净路径，loop engineering 处理其余所有路径

2026-08-17 · Towards Data Science
TDS 博客深入 RAG 的 loop engineering。核心论点：AI 工程师今天常谈 loop engineering（源于 Claude Code 工程师 Boris Cherny 说他已基本停止 prompting，改为写循环让模型在条件满足前持续 prompting）。对编码 agent 有测试套件可对照，这可行；但对企业 RAG pipeline，循环本身是需要工程化的部分，因为它要吸收的失败是普通的：parser 把答案所在的表展平、retrieval 返回正确页的下一页、模型返回违反 schema 的 JSON、API 批处理中超时。四块砖（解析/检索/生成/返回）处理干净路径大部分时间；loop engineering 是系统在其余所有路径上做的事——做好它让 pipeline 恢复而非空转。一次性 pipeline 承诺首次尝试：解析一次、检索一次、生成一次、返回结果。循环给 pipeline 第二次机会：发现缺失、调整、在用户看到前重跑弱步骤。三个控制面：trigger（何时触发循环）、termination（何时停止）、recovery（如何恢复）。两尺度：步内小循环（单步内重试+调整）、管道大循环（跨步骤编排+整体重试）。一条规则区分有用循环与空转循环。
🔍 技术视角：这篇博客为用户"agent 调业务 API 查数"的可靠性工程提供了精确方法论。agent 调 API 的失败模式与 RAG pipeline 高度同构：API 超时（对应 retrieval 空）、返回字段语义不符（对应 JSON 违反 schema）、宽表字段缺失（对应 parser 展平表）。三个控制面（trigger/termination/recovery）可直接迁移到 API 调用循环：trigger=API 返回空或字段缺失时触发重试，termination=最多重试 N 次或字段语义校验通过，recovery=换 API 参数/换字段映射/降级到更宽查询。两尺度区分对架构设计重要：步内小循环（单 API 调用内参数微调重试）vs 管道大循环（多 API 串联重试）。

2026-08-17 · Towards Data Science
TDS 博客（后端架构师视角）论述三代扩缩容如何被 agentic traffic 打破。第一代 on-demand 预置：人类驱动流量可预测（直播事件提前知 spike），预置 EC2 + min/max autoscale + war room。核心假设：spike 可预测所以提前预置。第二代 serverless：API Gateway+Lambda+Step Functions，不再预置信任平台反应。核心假设：不需预置因为平台反应比需求 ramp 快。第三代 agentic traffic 同时打破两者：流量不可预测突发、重试无情、近重复请求耗尽成本。作者给出四层响应模式和 AgentLoopDetector 代码——用 request velocity（请求速度）+ payload diversity（载荷多样性）检测循环：近相同请求从同一调用者高速到来是 agent 循环信号，应在 CPU 指标反映前隔离。核心论点：停止用 CPU 做扩缩容信号（lagging），改用 request velocity + shape；agent 一个循环可在秒级发数百近相同请求，CPU 反应时已耗尽资源。

Never the Number: Structural Abstention —— 可生成者只影响问哪个问题，永不影响返回什么值

2026-08-14 · arXiv 2608.13926

📊 架构示意

🎯 为什么值得关注

用户的核心痛点之一是"业务数据可信度验证"。当前主流做法靠模型自评置信度或执行后校验，但 Never the Number 指出这些是统计弃答（依赖置信度估计），而真正的可靠性来自结构化弃答（不可回答=不可表示=直接拒绝，不需置信度）。这对"agent 调 API 查数喂给下游决策"场景是根本性的——下游 agent 无法像人一样检查查询，必须由系统层保证要么对要么拒。

⚙️ 核心机制

Trusted kernel + generative shell 双层：(1) generative shell 用 LLM 解释用户自然语言意图、消歧、措辞回复；(2) trusted kernel 持有有界可回答问题形状集合（bounded set of answerable question shapes），把完全规格化的问题匹配到形状并编译为确定性查询执行；(3) 两层在"用户读取的确认"处汇合——用户在值被计算前读到确认；(4) kernel 无法表达的请求被拒绝而非近似。不变量：可生成者影响问哪个问题，不影响返回什么值。

🧠 深度解读

结构化弃答 vs 统计弃答的关键区别：统计弃答（selective prediction / calibrated confidence）需要模型输出置信度，而置信度本身可能错误且在高维空间不可靠。结构化弃答把"不可回答"定义为"不可在 kernel 的合法形状集合中表示"——这是一个语法/结构判定而非概率判定。论文强调"在消费者是 agent 而非人的部署中"这一约束最关键：agent 无法做人在环检查，必须由系统架构保证。这直接呼应 EnterpriseRAG（8/12 已收录）的 57 点编排鸿沟——单约束 80% 但全约束 26.8%，Never the Number 的解法是把约束前移为 kernel 的合法形状定义，让违反约束的请求不可表示。

💼 商业启示

商业启示：对"AI for 业务"产品决策而言，Never the Number 提供了一个可向客户承诺的可靠性保证——"系统要么给你对的值，要么明确拒绝"，而非"大概率对"。这种确定性承诺对金融、合规、运营等高风险场景是差异化卖点。同时它降低了对模型能力军备竞赛的依赖——可靠性来自架构而非更大模型，这对成本和可审计性都有利。

🛠️ 落地建议

落地建议：(1) 为用户的核心宽表 API 构建"合法查询形状"注册表——枚举哪些字段组合可查、哪些聚合合法、哪些过滤条件必须有；(2) 用确定性 kernel 做形状匹配+编译，LLM 只负责自然语言→形状映射；(3) 映射不上的请求走确认或拒绝流程而非让模型自由生成 SQL；(4) 这与语义层路线天然契合——语义层本身就是"合法查询形状"的声明式定义，Cube/WrenAI 的 metric/dimension 定义可作为 kernel 的形状来源。

⚠️ 局限与风险

引用数 0（2026-08-14 新文，符合预期）。论文是架构模式论文而非实证 benchmark，trusted kernel 的合法形状集合需要人工或半自动构建，对 schema 频繁变化的场景维护成本高。覆盖范围受限于形状集合完备性——未枚举的合法查询会被误拒。信息待核实：论文未给出大规模生产部署的量化数据。

📊 架构示意

🎯 为什么值得关注

用户一直在"语义层 vs 知识图谱"两条路线间权衡。SemPlan 提供了第三维度的数据：在"语义层 vs 直接生成 vs 工具 agent vs 状态机"四种架构间，正确率差异只有 3.42 个百分点（22.25%→25.67%），但失败模式质的不同。这说明架构选择不应只看正确率排名，而要看哪种失败模式对业务更可接受。

⚙️ 核心机制

四架构对比：(1) A1 直接 SQL 生成——LLM 直接从自然语言生成 SQL；(2) A2 bounded tool-agent——LLM 调用有界工具集查询；(3) A3 结构化语义请求+确定性规划——LLM 生成结构化语义请求，确定性规划器编译执行；(4) A4 带澄清的状态机——在 A3 基础上加多轮澄清和状态管理。确定性合成双语 benchmark 控制变量，1200 案例冻结子集保证可复现。稳定性子集测重复性。

🧠 深度解读

SemPlan 的结果与 Never the Number 形成精确呼应：A3 的结构化语义请求本质就是 trusted kernel 的合法形状集合的 LLM 前端——LLM 生成结构化请求而非 SQL，确定性规划器编译执行。A3 正确率最高证明了这条路线价值，但 A1 策略正确率最高说明直接生成在遵守业务规则上更可控（因为 LLM 生成 SQL 时约束可嵌入 prompt）。A4 加澄清反而降低正确率（24.25%<A3 25.67%），说明多轮状态引入新失败模式（状态不一致）。这与 EnterpriseRAG（8/12 已收录）的"全约束 26.8%"数据交叉验证——约束叠加引入乘法衰减，SemPlan 的 A4 就是约束叠加的实例。

💼 商业启示

商业启示：SemPlan 的 3.42 个百分点差异和"非单调提升"结论对"AI for 业务"立项决策有直接影响——不要指望换架构就能大幅提升正确率，25% 左右的正确率意味着 75% 的查询需要人在环或结构化弃答兜底。这为"agent 辅助而非替代"的定位提供了数据支撑。同时 A4 的澄清反而降正确率警示：不要盲目加交互复杂度。

🛠️ 落地建议

落地建议：(1) 对用户宽表 API 场景，A3 路线最契合——定义结构化语义请求 schema（哪些字段、哪些过滤、哪些聚合），LLM 生成语义请求而非直接调 API，确定性规划器编译为 API 调用；(2) 但要接受 25.67% 的正确率天花板，配合 Never the Number 的结构化弃答处理剩余 74.33%；(3) A1 的策略正确率优势提示：对高合规场景可考虑 A1+强约束 prompt 作为 baseline；(4) 稳定性 92-98.67% 说明同架构同输入仍有一致性问题，需确定性规划层兜底。

2026-08-14 · arXiv 2608.14246

📊 架构示意

🎯 为什么值得关注

用户场景中 agent 需调多个宽表 API（如先查客户 API 再查订单 API 再查财务 API）串联分析。固定 pipeline 在问题性质变化时僵化，单 agent 在多步推理时 context 膨胀。Polaris 的多 agent + 动态匹配提供了中间路线：专业分工降 context 压力，动态匹配保适应性。

⚙️ 核心机制

DTC 决策论编排层：(1) 把 agent-task 分配建模为自适应二部图匹配——左侧是任务（查询子任务/可视化子任务/推理子任务），右侧是专业 agent，匹配算法根据任务需求和 agent 能力/可用性实时分配；(2) supervisor agent 监控执行，失败时触发恢复和重新匹配；(3) reason-first ReAct-style agent 每步给出推理理由而非盲目行动；(4) 输出是连贯分析工作流含数据+可视化+"why"解释。

🧠 深度解读

💼 商业启示

商业启示：多 agent 动态协调模式对"AI for 业务"产品的可扩展性是关键——不同业务线（销售/财务/运营）有不同数据 API，专业子 agent 分工让系统可水平扩展（加新业务线=加新子 agent），supervisor 统一编排让用户体验一致。DTC 的"恢复"能力对 SLA 承诺重要——agent 失败可重新分配而非整体失败。

🛠️ 落地建议

落地建议：(1) 对用户的多 API 串联查询场景，可参考 DTC 模式——supervisor agent 接自然语言查询，分解为子任务，动态分配给"客户 API agent""订单 API agent""财务 API agent"等专业子 agent；(2) 每个子 agent 只管一个宽表 API 的语义理解+调用，降 context 膨胀；(3) supervisor 聚合结果并生成"why"解释；(4) 关键是定义 agent 能力描述（capability descriptor）让匹配算法可决策。
