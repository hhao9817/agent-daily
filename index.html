AI code review 的天花板：584 个真实缺陷，最强 agent 只检出 1/3，Gemini Code Assist 8.1%

2026-11-02 · arXiv
CR-Bench 把 SWE-Bench 的 issue 反转为 PR review 任务：每个实例带完整仓库上下文、一个已知缺陷、ground-truth 修复，以及 bug 类别/影响/严重度的分类标签，共 584 个实例（Verified 子集 174）。论文提出两个互补指标：KDDR（是否命中标注缺陷）与 Usefulness Rate（评论中可执行的比例）。评测 8 个 review agent × 4 个 backbone，外加商用 Gemini Code Assist，并用 3 个独立 LLM judge：最强系统 KDDR 约 33%，Gemini Code Assist 仅 8.1%。
🔍 技术视角：AI review 的瓶颈不是「看不看得懂 diff」，而是「能不能把缺陷锚定到可验证的那一处」。KDDR 只有 1/3 意味着 review agent 不能当质量门禁的唯一执行者，只能做召回补充——必须用 Usefulness Rate 约束噪声，并把评论落成测试或静态规则才算闭环。对已建研发知识库的团队，真正的价值是把 review 从「生成评论」改造成「生成可执行反例」。

Claude Code 上的门控式规格驱动工作流：581 个任务只完成 288 个，唯一的硬拦截是文件清单检查

2026-11-03 · arXiv

text-to-SQL 最贵的问题不是算错，而是「替你做了选择却不说」：开放请求只有 15%–58% 给出两种口径

2026-11-03 · arXiv
论文指出一类静默失败：问题本身留有计算口径的选择（按行计数还是按去重实体计数），模型自行选定一种、不声明，结果能跑且看起来合理。提出 SpecBridge：对同一请求构造三个版本（一个留空、两个各指定一种解释），用真实数据库执行打分。204 个人工验证测试上，四个模型在被明确要求时通常能算出对应口径，但对留空请求只有 15%–58% 会同时给出两种解释，且多数不提及做了选择——差距在报告而非计算。在 BIRD 上，超过 2/5 被判错的答案在另一种解释下其实是对的。解法不需要更强模型：先判定请求是否留下开放选择，再对每种解释各调一次。
🔍 技术视角：这是把「歧义」从 prompt 层拉到「输出契约」层的关键一步。对不直连库、走高业务含义 API 的场景尤其重要：宽表 API 的每个指标几乎都有口径选择。架构上应把「口径判定 + 多解释并列」做成查询前置门，而不是寄望模型自己声明假设——实证说明它不会说。

2026-11-02 · arXiv
论文从源码两侧测量 MCP 的破坏性操作审批：官方 registry 1,000 个仓库抽样中，估计 90%（95% CI 82–95）的破坏性工具没有服务端确认；多数会 elicitation 的服务器在宿主无法转达时选择继续执行，或退回到模型可自行设置的 flag。41 个流行开源宿主/agent SDK 中 32 个默认无审批步骤（25 个应用中 16 个）。把规则提取器标出的破坏性工具与这些应用配对，60.7% 的组合默认没有强制人工批准。通过 4 个 agent SDK，5 个低成本模型中 4 个在 960 次运行里执行了注入的删除操作共 479 次。若宿主对所有「未标注只读/非破坏」的工具都提示，未批准比例降到 5.4%；仅普及 elicitation 支持则仍有 56.7%。

正确性防火墙：让 coding agent 随便生成数据库组件，但结果永远不可能错

2026-11-03 · arXiv
论文提出 correctness firewalls——一类轻量设计模式，让 agent 合成的组件可以影响系统性能但永不改变结果。三类案例：基数估计（advisory，仅影响计划）、有序数据检索（guarded，结果由确定性结构兜底）、数据压缩（certified，解压后可验证）。早期实验中，合成组件在有序数据检索上比人工设计的 learned index 快最多 3 倍，文本压缩比 Zstd 小 1.5 倍。
🔍 技术视角：这是今天最有架构价值的一条：它把 agent 的不确定性关进「性能边界」而不是「结果边界」。对业务线可直接借用——让 agent 生成查询计划、检索策略、字段裁剪，但最终结果由确定性执行器校验；失败了只是慢，不会错。这比「让 agent 更准」的路线成本低一个数量级。

QueryWeaver：把 schema 做成图再检索，开源 text-to-SQL 走「相关性拒答 + 澄清 + 自修复」三段

2026-11-03 · GitHub
FalkorDB 开源的 text-to-SQL 工具（1,089★，2026-11-03 仍在更新），schema 以图结构存储（tables/columns/foreign keys 作为 nodes/links，可前端可视化），支持 REST 与 MCP 两种暴露方式（list_databases / connect_database / database_schema / query_database）。代码里的 agent 流水线分工明确：RelevancyAgent 判 on-topic/off-topic/inappropriate（支持拒答）、AnalysisAgent 结合 schema 与历史做分析、TaxonomyAgent 针对 WHERE 条件生成澄清问题、HealerAgent 做 SQL 修复、ResponseFormatterAgent 把结果转自然语言，另有 follow-up agent 处理多轮追问。对话记忆存 FalkorDB，可用 MEMORY_TTL_SECONDS 设过期。

Google 开源 Agile Deliberation：定义不是先想清楚的，是被边界样本逼出来的

2026-11-04 · Google Research Blog
Google Research 11/4 发布 Agile Deliberation，用于构建「主观类别」分类器：把定义过程拆成概念定界（拆子概念 + 显式排除项）与概念迭代（用 VLM 主动挖语义边界样本，让人判断，再自动精炼提示）。关键设计是不把标注者当成「有完整规则的 oracle」，而是承认定义会在遇到样本时演化。18 场 1.5 小时真人会话评估（不做模拟测试），报告显著降低用户疲劳与焦虑、模型一致性更好并优于基线；代码与算法已开源。

AI code review 的天花板：584 个真实缺陷，最强 agent 只检出 1/3，Gemini Code Assist 8.1%

2026-11-02 · arXiv

📊 架构示意

🎯 为什么值得关注

code review 是 AI for 研发里最容易被「看起来很有用」欺骗的环节：文本相似度指标奖励表面重合，不惩罚瞎报。缺一个缺陷中心、带 precision 口径的基准，团队就无法判断 review agent 到底能拦多少真问题。

⚙️ 核心机制

缺陷中心构造：从 SWE-Bench 的 issue/PR 中筛出「review 可发现」的缺陷，并归因到单一原始 PR；每个实例给出 PR + 已知缺陷 + 修复 + 分类标签（类别/影响/严重度）。指标侧 KDDR 判「是否点出标注缺陷」，Usefulness Rate 判「评论中有多少可执行」。评测用 3 个独立 LLM judge 交叉以降低单一 judge 偏好，并引入商用产品作参照点。

🧠 深度解读

💼 商业启示

对采购与自建：AI review 的 ROI 不在「减少 review 人力」，而在「把漏检的高危缺陷变成可回归的测试」。若按 KDDR 计价，商用产品当前溢价缺乏证据支撑；自建方的差异化应押在「缺陷→测试」的转换器，而不是更强的评论生成。

🛠️ 落地建议

① 接入 review agent 前，先用历史已修复缺陷做回放集，测 KDDR 而不是评论数；② 用 Usefulness Rate 作上线阈值，低于阈值时降级为「只报高置信」；③ review 结论必须能落成测试或规则，否则不计入质量门禁；④ 不要用单一 LLM judge 做 A/B，至少 3 judge 加人工抽检。

🧠 深度解读

这实际上是把可验证计算的思路落到 agent 工程：不是验证 agent 对不对，而是设计一个「错了也不影响结果」的接口。对数据系统尤其自然，因为结果集可重算。论文同时提出「correctness 成本」的度量议程——firewall 不是免费的，兜底路径的额外开销必须计入。对双线课题可迁移三处：text-to-SQL 让 agent 生成候选查询，正确性由与语义层定义的一致性检查兜底；宽表字段裁剪由 agent 提议，最终取数走完整确定路径；RAG 检索策略由 agent 选，答案必须能回到源文档验证。
