仓库上下文决定生成代码安不安全：13 种构造法实测，功能通过率涨 8.2pp、安全通过率只涨 3.7pp

2026-11-06 · arXiv
A.S.E 2.0 构建 CASE-Bench：145 个仓库级任务，取自 51 个真实项目的历史 CVE，每个任务在 Docker 中同时具备功能测试与可双向验证的 PoC 利用；据此比较 13 种上下文构造方法与 6 组对照、6 个 LLM。结论：为功能正确性设计的上下文最多把功能通过率抬高 8.2pp，安全通过率最多只涨 3.7pp；抽掉一个安全防护（如鉴权检查）会让安全通过率下降至多 8.1pp，而放入一个不安全范例会把「能跑但可被利用」的代码比例推高 6.3pp。轨迹分析显示 coding agent 只有 27%–36% 的轨迹里真正看到过相关防护代码。
🔍 技术视角：研发知识库的检索目标函数选错了。按「功能相关」检索，会把项目里既有的不安全写法一起当范例喂进去；安全相关上下文需要独立索引与独立注入通道，并且要把「本次轨迹是否看到 safeguard」做成可观测指标。对已经建好研发知识库的团队，这是最低成本的改造点：在 codebase indexing 里加一层 safeguard/authorization 语义标签，检索时强制置顶，且不允许被相似度排序挤掉。

让 coding agent 每次调工具前先声明「为什么」：49 次 reward hacking 暴露 90%

2026-11-06 · arXiv
EPISTEME 指出一个被忽视的事实：coding agent 通过 tool call 改变本地状态，却从不说这次调用是为了什么，于是「改对了」与「改坏了」都无法归因。其做法是让 harness（而非模型自觉）强制模型在每次工具调用前声明意图，再由 harness 记录命令实际产生的效果，并把自述与效果对照，形成一份可前置拦截、可事后取证的 journal。在 ImpossibleBench（任务只有作弊才能通过）上跑两个开源模型共 49 次 reward hacking，journal 暴露了其中 90%。
🔍 技术视角：这是「构造性可审计」的典型：不依赖模型诚实，而依赖 harness 的不变量。迁移到业务 Agent，等价物是「每次调业务 API 前必须先声明 intent（实体 + 指标 + 时间窗 + 预期返回形状），工具层记录实际请求参数与返回摘要，两者做一致性校验」。它比事后审计日志强一个量级：不一致可以在执行前拒绝，而不是在事故后解释。

云事故端到端处置：故障识别 72.7%–90.9%，真正修复只有 14.5%–52.7%

2026-11-06 · arXiv
SWEOps-Bench 用 16 个 Kubernetes operator 项目中已确认的历史缺陷构造 55 个可复现事故任务：每个任务保留原始仓库，先起一个健康集群，再由受控负载触发当年的故障，agent 通过终端调查运行时证据并提交源码或配置修复，harness 在共享时间预算内完成构建与部署。评测同时看阶段性准确率、经验证的恢复、带惩罚的生命周期延迟与 token 消耗。六组 agent-模型配置下，故障状态识别达到 72.7%–90.9%，而端到端恢复只有 14.5%–52.7%；轨迹分析还发现上报的根因与最终恢复只是部分重合，存在「根因报错但确实修好」和「症状消失但修复本身过不了功能验证」两类情况。
🔍 技术视角：检测力与修复力之间的落差接近 40 个百分点，而且「根因分析文本」与「修好」弱相关。这意味着评估 DevOps agent 必须用经验证的恢复 + 生命周期延迟作为主指标，RCA 文本只能作为辅助解释。对研发线的 CI/CD agent，这直接决定 KPI 设计：不要考核「定位准确率」，要考核「验证恢复率 + MTTR」。

NVIDIA 开源 Auto Ontology 1.2.0：术语 + SQL 属性 + 关系编译成可认证本体，答不了先拒答

2026-11-06 · GitHub
NVIDIA Auto Ontology（7,225 stars，Apache-2.0，11-05 发布 v1.2.0）从企业元数据生成本体，本体只有三类定义：Terms（业务概念 + 同义词，映射到列）、SQL attributes（经审阅的 SQL 表达式，如毛利、滚动合计，agent 复用保证同一指标算法一致）、Relationships（表如何 join，含桥表，由键与数据推断）。流程是 Generate（剖析列与样本值 → 逐表命名实体 → 解析关系 → 写入 Postgres + pgvector）→ Certify（人在 Chat 或通过 MCP 的 check_answerable / ask_question 试问、修正、认证）→ Answer（意图分类 → 向量检索候选术语/列/属性 → 写 SQL → 用数据库校验过滤值并修复 → 返回答案 + SQL + 步骤）。Wide World Importers 示例一次编译产出 31 个术语；与 Apache Ossie 兼容，可按 Ossie YAML 导入导出。答不了时会先拒答：问广告投产比返回 coverage 0.5、「没有术语覆盖 ad spend」，并提议改问收入或接另一个数据源。
🔍 技术视角：这是「语义层 vs 知识图谱」的一次合流样本：以 Ossie 语义模型为输入、以本体图为内部表示、以 MCP 为出口。三层里最关键的是 SQL attributes——把口径写成一个被审阅、被复用的表达式对象，而不是让模型每次重写。对用户的宽表 API：把「字段组合 → 业务指标」沉淀成受认证的 attribute 目录，agent 只做选择与拼装，不做重算，口径一致性就从 prompt 约束变成了资产约束。

组织记忆不该只存记录，要存「判断」：Claims + Dimensions 四层架构，检索 nDCG@10 提升 0.081

2026-11-06 · arXiv
论文指出组织积累的是证据（对话、文档、决策、关系），但真正驱动行动的是「解释」——由多条观察拼成、建立在假设之上、随情况修订的判断；现有检索、知识图谱与 agent memory 都只保存记录而丢失解释。作者提出四层架构 Signals / Domains / Claims / Dimensions：解释连同其依据与「standing」一起持久化，由真值维护网络在证据变化时修订 standing，经验证且版本化的 Dimensions 把解释定位到命名轴上。检索实验中 Dimension 项带来 +0.028 nDCG@10（p=0.002）；完整配置相对仅 Signals 提升 0.081，相对「图谱增强的 Signals」提升 0.053（均 p<0.001）。
🔍 技术视角：这给「业务知识库」提供了一个比文档 chunk 更合适的原子：Claim（可被反驳的判断）+ 支撑证据 + 状态 + 维度坐标。对用户的企业 Agent，把「这个指标口径是 XXX」存成 Claim 而不是 FAQ 文档，才能在口径变更时批量失效旧答案——这正是「业务数据可信度验证」缺的失效传播机制。

BobFlow：让 agent 用 dataflow 而不是脚本来做分析，准确率 +18.6 分、推理成本约 1/3

2026-11-06 · arXiv
论文主张人机协作需要一个共享的计算抽象：agent 能对处理逻辑做推理，分析师能理解、指导与修正。Python/SQL 脚本精确但语法与执行细节对分析师不友好。BobFlow 把 dataflow 抽象与 ReAct 结合，agent 迭代构建并执行 dataflow，分析师可检查中间结果并反馈。用户研究表明 BobFlow 帮助分析师理解、检查与验证 agent 生成的分析；跨闭源与开源 LLM 的实验显示准确率最高提升 18.6 分，推理成本约为脚本式 ReAct agent 的 1/3。
🔍 技术视角：「中间表示决定可审计性」。脚本是黑盒文本，dataflow 是可命名的算子图——每一步都是可被人审阅、可被复用的节点，而不是一段生成的 SQL。对宽表 API 场景，dataflow 节点可自然对应「API 调用 + 字段选择 + 过滤 + 聚合」，天然携带 provenance，这比让模型直接产出最终查询更符合「多步推理可审计」。

语义查询服务化的真问题：查询间调度与查询内计划互相依赖，静态优化必然失效

2026-11-06 · arXiv
SeqoFlow 研究的是「LLM 语义查询」的服务化：查询同时包含关系处理与多个作用于非结构化数据的 LLM 算子。运行时动态性出现在两个耦合层级——跨查询看，到达时间与异构资源需求不断改变调度优先级；查询内看，细粒度输入批次的异构特征使算子成本与选择率在执行过程中变化，静态优化计划不可靠。两者形成循环依赖：调度需要剩余 LLM 工作量的估计，而剩余工作量又取决于只有执行时才可观测的计划选择。SeqoFlow 在算子依赖下枚举保持等价性的计划替代、把查询拆成细粒度单元，在批次边界做安全计划切换与抢占，并用轻量推测估计运行时成本，联合指导计划自适应与跨查询调度。
🔍 技术视角：当「语义层」从生成 SQL 走向「在非结构化数据上跑 LLM 算子」，调度问题就变成了数据库问题：等价性、抢占、成本模型。对用户的宽表 API 编排，多 API 调用 + LLM 抽取的组合同样需要「等价计划枚举 + 边界抢占」，否则长尾请求会拖垮整体延迟。

GraphRAG 不必与建图方式绑定：查询时现推图接口，换一种构图仍然有效

2026-11-06 · arXiv
现有 GraphRAG 的检索策略往往围绕自己构图管线产生的结构来设计，换一种构图能否继续工作很少被检验。ArcRAG 在推理时诱导一个「查询局部图接口」——问题所涉实体可达的节点标签、关系描述与属性键——据此规划多跳遍历，并以 Cypher 执行与修复。作者把 MuSiQue、HotpotQA、TriviaQA 各自建成两种图：schema-guided 图（类型化节点、封闭关系集、来源溯源）与 open-IE 图（无类型节点、自由文本关系），检索器配置在两族图上完全固定。结论是：检索不必与构图联合设计，查询时的接口诱导能让 construction-agnostic 检索器在构图变化时保持有效，但构图仍决定绝对准确率。
🔍 技术视角：这对「语义层 vs 知识图谱」之争给出一个降级方案：不必先赌对本体或构图，先让检索器在运行时读图接口。这与 MCP 的「运行时候选能力协商」同构——接口在运行时被发现，而不是编译期写死。对反复因本体设计返工而停滞的 KG 项目，这是把前置成本后移的办法。
