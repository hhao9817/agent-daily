MIRA：证据验证的记忆复用让 Text-to-SQL 修正不破坏正确查询

2026-08-07 · arXiv
Text-to-SQL Agent 仍产出可执行但语义错误的 SQL。可靠修正器必须「修对的不破坏对的」——否则把对的查改错。MIRA 提出将历史修正拆解为独立可复用的 memory items，而非粗粒度整条经验。对每个当前查询，按问题与 SQL 检索 memory items，然后用数据库证据逐条校验，仅适配有证据支持的条目。在 3 个 Text-to-SQL Agent 生成的 1785 条测试查询上（覆盖 BIRD 与 ScienceBenchmark 14 个数据库），执行准确率分别提升 16.53% 与 8.78%。
🔍 技术视角：MIRA 的核心贡献是把「修正复用」从整条经验升级为细粒度 memory items + 证据门控。与 MERIT（昨日已收录的双极性记忆）互补：MERIT 记成功与失败方向，MIRA 记可独立复用的修正原子，且强制 evidence verification 防止误用。对用户业务 API 查询场景，memory items 可对应「某字段语义混淆→改某参数」「某聚合口径错→改某选项」等原子修正，组织级沉淀为查询知识库。

CWS：为 Agentic AI 建因果层——从相关关系到处方决策

2026-08-07 · arXiv
现代 AI 不再是单模型，而是经典 ML 预测器、深度多模态模型、LLM 与 Agent 的生态：各自在不同数据源上训练调优，产出又成为彼此输入。运维这样的生态本质是数据集成问题——知识碎片化在数十个异构独立治理的源中需持续协调。但集成不够：预测被众多因子塑造，驱动结果的变量与仅伴随的变量常纠缠，基于相关关系行动会招致混淆决策。Agent 自主行动后此问题加剧——可信可靠要求 Agent 预见行动后果而非仅从历史共现外推。论文主张集成生态需显式因果层，提出构建为共享、持久、可查询的 Causal World System (CWS)。
🔍 技术视角：CWS 是本周最具架构视野的论文。它精准命中用户「业务系统精确查询分析」的深层痛点：Agent 查对数据算对指标后，仍可能因混淆因果与相关而推荐错误行动。CWS 的主张——在数据集成层之上叠加因果层——与语义层（管指标定义一致性）、知识图谱（管实体关系）构成三层：语义层管「算什么」、知识图谱管「什么关联什么」、因果层管「什么导致什么」。对架构师而言这是业务决策可信度的终极一公里。

SemBaker：语义算子从「逐项 LLM 解释」到「一次编译本地执行」

2026-08-07 · arXiv
语义算子（semantic operators）用自然语言谓词扩展数据处理，如「找出描述提到安全事件的记录」。现有系统用解释式执行：对每条数据项调 LLM 解释谓词产出结果，昂贵且随基数线性增长。SemBaker 是编译式执行引擎：对选定的语义 filter/map/join，调 LLM 一次生成确定性 Python 函数，本地执行无需逐项 LLM 调用。基于代价的优化器将每个算子路由到原生或编译执行，编译与流水线重叠。支持 Palimpzest、LOTUS、Nirvana、DocETL（通过薄适配器）。在 3 个 200 问 QA 工作负载上，平均加速 4.8-6.3 倍、降本 5.4-10.7 倍，处理质量保持竞争力。
🔍 技术视角：SemBaker 直击用户场景的工程痛点：用 LLM 理解业务 API 宽表字段语义时，逐行调 LLM 代价高。编译范式——一次让 LLM 生成处理函数，本地批量执行——是把 LLM 从「逐项推理器」变为「函数生成器」的关键架构转变，与 function calling/tool-use 范式高度契合：让 LLM 先理解业务语义生成确定性工具，再由工具处理数据。

FHS：因子化假设搜索——表格单元格的检索就绪鸿沟

2026-08-06 · arXiv
大分类法检索常假设输入已表达目标概念。但许多场景输入是间接证据——如表格单元格，其含义依赖行、列、数据类型与上下文。论文称此为「检索就绪鸿沟」（retrieval readiness gap）：当前索引在语义明确时能可靠检索目标，但原始证据常把目标埋在排名深处。提出 Factorized Hypothesis Search (FHS)：在命名语义维度上维护多个部分解释，支持结构化查询渲染、多假设检索、维度级候选验证。在金融分类标注与 CodiEsp 临床编码任务上，FHS 取得非 oracle 方法中最优 Recall@1、MRR 与最终准确率。
🔍 技术视角：FHS 精准命中用户宽表 API 场景的核心难题：上百字段 API 的每个单元格值语义依赖其字段名、记录上下文与 API 整体含义。直接 embed 单元格值无法正确检索——FHS 的因子化假设（沿行/列/数据类型/上下文多维度部分解释）为宽表字段语义理解提供了比 chunk+embed 更结构化的范式，与昨日 Beyond Top-K（表格密集文档 chunk+embed 结构性失效）形成主题呼应。

FinRank：金融溯源问答基准——答案对≠证据对

2026-08-07 · arXiv
金融问答通常按答案正确性评估，但在 SEC 文件中一个合理甚至数值正确的答案可能基于错误证据——相似事实与披露在文件各章节、同一公司不同报告期、可比公司间反复出现。FinRank 聚焦此溯源敏感的检索问题：要求系统定位正确实体、报告期与披露上下文的证据。基准含 1185 条人工编写问答（覆盖 22 家公司 10-K/10-Q），每条含参考答案、金标支撑段落与人工策划的硬负例。FinRank 将段落检索、重排序与硬负例判别作为独立测度任务。基线显示难度：7B 指令微调 embedder 在汇总证据语料上仅 44.8% Recall@10；十亿参数以下编码器较 BM25 至多提升 3.5 个百分点；金融适配 embedder 反落后 BM25 9.7 个百分点；随机负例替换为策划硬负例后 pairwise accuracy 降 13-20.5 个百分点。
🔍 技术视角：FinRank 用硬数据证明「答案正确≠证据正确」——在金融文档中相似事实反复出现，Agent 可能答对数但引错证据。这与用户「业务数据可信度验证」需求直接对应：业务 API 返回的数据可能看似正确但来源/口径/时效错误。FinRank 的硬负例设计（同文件不同章节、不同报告期、可比公司）为业务场景的「可信度验证」提供了评估范式——不仅要验答案，更要验证据溯源。

TDS：Agent-Ready 数仓≠可查询数仓——缺 Decision Contract 的正确 SQL 会推错行动

2026-08-10 · Towards Data Science
Shafeeq Ur Rahaman 论证：给 AI Agent 访问数据仓库不自动使其 Agent 就绪。企业数仓为人检点设计——工程师备数、分析师写查询、仪表盘展示受批指标、高管决策。Agent 能查元数据、选源、写 SQL、用结果推荐下一步。但问题在于：Agent 能写出正确 SQL 正确计算指标，仍可能推荐错误行动——因为仓库提供数据但不提供业务规则（费用是否含代理费、币种是否标准化、转化是否已扣退款）。论文提出 Decision Contract：指定批准数据源、最小历史时间窗、指标定义、数据时效上限、必需完整性校验、允许 vs 禁止的执行边界，比 Data Contract 多一维「决策适合度」。

🎯 为什么值得关注

⚙️ 核心机制

💼 商业启示

CWS 对业务的启示是「AI 决策可信度的终极门槛是因果而非相关」。当前多数「AI for 业务」停留在查数算指标，但业务真正需要的是「为什么」与「如果怎样」——这正是因果层要解决的。率先在关键决策链路建因果层的团队，能让 Agent 从「报告发生了什么」升级为「建议该做什么」与「预测如果怎样会怎样」，这是从 BI 到 AI 决策的质变。

🛠️ 落地建议

⚙️ 核心机制

①可查询≠就绪：数仓 queryable 但不提供业务规则，Agent 选原始表而非受控语义视图。②正确 SQL 错误决策：Agent 算对指标但不了解口径/时效/完整性，推荐错误行动。③传统治理不足：只管谁可查表/看列，不管数据是否适合做某类决策。④Decision Contract：批准源+最小时间窗+指标定义+时效上限+完整性校验+允许/禁止执行边界。⑤分层排查：源数据→时效规则→语义模型→生成查询→行动策略，各层独立可审计。⑥查询执行服务：dry run 验证+字节上限+只读+结果大小限+批准数据集+超时+禁止语句类型。⑦从单一决策起步：不从整库开始，从一个业务领域（如活动表现）的接口起步。

🧠 深度解读

本文的深层洞察是「数据可用性 ≠ 决策适合度」。传统数据治理问「谁可查」，Agent 时代需问「此数据适合做某类决策吗」。Decision Contract 比语义层更进一步：语义层定义指标是什么（如 ROAS 的计算公式），Decision Contract 定义指标在什么条件下可用于什么决策（如「ROAS 需 7 天转化窗口完整后才可用于暂停建议，且只能建议不能执行」）。这与用户场景完美对应：上百字段宽表 API 的每个字段都有业务口径，Agent 调用前需 Decision Contract 约束「此字段值在什么时效/完整性下可做什么决策」。文章的「分层排查」设计（源/时效/语义/查询/行动）也为业务查询可信度验证提供了可归因的故障定位框架。

💼 商业启示

本文对业务的启示是「AI for 业务落地需要 Decision Contract 作为治理层」。当前多数团队止步于让 Agent 查到数据，但「查到≠能信、能信≠能做决策」。Decision Contract 把治理从「数据交付」延伸到「决策适合度」，让 Agent 的行动有可审计的业务依据。率先建 Decision Contract 的团队能让业务方信任 Agent 的行动建议——这是从「AI 查数」到「AI 做业务决策」的治理门槛。

🛠️ 落地建议

①为每个关键业务 API 定义 Decision Contract：批准字段、最小历史窗、指标口径、时效上限、完整性校验、允许/禁止操作。②Agent 默认访问受控业务接口而非原始宽表。③API 调用前 dry run 验证：参数合法性、预期返回量、口径匹配。④记录允许/拒绝原因（模型错误/策略规则/数据问题），分层可审计。⑤从单一业务领域起步——不为整库建合同，先为一个高频决策场景（如活动暂停建议）建端到端合同。⑥Contract 随数据平台演进——归因模型或阈值变更需更新合同。

⚠️ 局限与风险

①Decision Contract 是概念框架，非已实现产品，需团队自行设计机器可读格式。②合同维护成本高——随业务规则变更需持续更新。③过度约束可能限制 Agent 灵活性，需平衡治理与能力。④文章基于多源活动分析场景，泛化到其他业务领域需调整。⑤作者为 phData 相关从业者，有立场倾向（倡导受控语义层）。
