「能跑通但算错」：迁移后 41% 的错误修复能过全部断言，一条边界输入把它压到 6.5%

2026-11-05 · arXiv
论文做了一项预注册研究：73 个任务、覆盖 CPython、SQLite 及另一个运行时（arXiv 摘要中链接被剥离）的 60 处有文档的 API 变更，让 LLM 修复迁移后的代码，再用真实运行时 + 未公开的契约（withheld contracts）验证。结果是最刺眼的：只用「典型输入」上的全部断言做发布门禁，会放行 41.0% 的错误修复——它们跑得干净、返回错误结果。仅补一条从 release note 写出的边界输入，错误放行率降到 6.5%，在 15 个未见过的集群上为 6.1%；由一个从未看过程序的盲写模型（GPT-5.6-luna）写 3 条输入也能到 7.0%。作者随后把菜单扩到 1491 个片段，再加入 233 个「在典型输入上与旧输出完全一致」的困难干扰项：边界输入与前沿模型写作仍能通过预注册检验，但分别有 16.8% 和 15.3% 的困难错误程序蒙混过关；两个本地小模型写作未通过预注册。跨四个模型家族、三个菜单，边界输入在三个开源权重家族上都把「每次尝试的错误发布率」压低（例如 0.233→0.057），且不降低正确完成率。自测（self-tests）帮助更小。另有一个盲 AI 审计指出 34 条契约比需求更严，删掉这些争议检查后判定结果零变化。
🔍 技术视角：这条直接打在「AI 代码审查/测试门禁」的度量上：我们平时报的「测试通过率」在分布偏移后几乎失效，真正该报的是「错误发布率（wrong-release rate）」。工程上可复现的做法有三点：①门禁输入必须从变更说明（release note / 迁移指南）反推，而不是复用历史用例；②把「典型输入上输出与旧实现一致」当作对抗样本筛选条件，专门构造干扰项来压力测试门禁，否则通过率会虚高 2-3 倍；③门禁要跨模型家族验证泛化，本地小模型写不出有效边界用例。对已建研发知识库的团队，这提供了一个高价值的知识库条目类型：每个 API 变更都挂一条「边界契约」，让 review agent 检索复用。

ReConMem：对话记忆与代码实体各建一张图，仓库级多轮任务 Pass@1 提升 7.9pp

2026-11-05 · arXiv
论文指出通用对话记忆系统在仓库级开发中不够用：它们不把「对话里说过什么」与「对话指向的代码实体」协调起来。ReConMem 建双图——语义记忆图（蒸馏后的对话记忆）与结构记忆图（与对话相关的代码实体），并随交互演进维护跨图关联。召回时用「代码草稿」做 query grounding，把自然语言查询落到代码符号上；再沿图内与跨图关系扩展；最后按结构粒度压缩检索到的代码。在 LoCoEval 上，单跳与多跳子集的 Pass@1 分别比最强基线高 7.917 和 7.292 个百分点，上下文压缩率相当；在 CodeAssistBench 上达到 27.61% Correct、44.03% Partially Correct，比「全量历史」基线高 4.10 和 7.09 个百分点，交互质量也更好。
🔍 技术视角：研发知识库的下一层不是「更好的代码检索」，而是「对话与代码的联合索引」。已有代码图谱/RAG 的团队，边际收益最大的增量是把 PR review 讨论、issue 争论、设计决策绑定到符号节点上，形成可跨会话复用的结构记忆；同时 ReConMem 的「按结构粒度压缩」提示我们：检索回来的不该是整文件，而是函数/类/调用片段级的裁剪结果，这直接决定上下文预算。

Req2Rust：先写「必须保持的行为」再迁移，C++→Rust 测试通过率 69.5%→91.9%

2026-11-05 · arXiv
项目级 C++ 转 Rust 的两难是：保留源码结构能追踪底层行为，但会把 C++ 的组织方式、unsafe 惯用法和项目假设一起搬进 Rust；让 agent 自由重写则语义覆盖取决于模型能否识别必须保留的行为——而 C++ 的行为常藏在对象模型、析构驱动的生命周期协议里，极难定位。Req2Rust 的做法是先产出证据支撑的 Migration Requirements Specification（MRS，记录必须保持的行为与约束），再合成 Rust Design Specification（RDS）并落地为初始 Rust 项目；随后把该项目视为「可执行精化状态」，用编译器、语义校验器、unsafe 削减校验器产出报告，迭代改进可构建性、行为对齐与 unsafe 使用。在通用 C++ 项目与 OpenHarmony 大规模代码库模块上，均产出可构建 crate；测试通过率从 69.5% 提到 91.9%（通用项目）、从 45.4% 提到 87.9%（OpenHarmony），基线为 ClaudeCode。
🔍 技术视角：这是「规格先行」的 agent harness 范式：复杂改造不应让模型直接翻译代码，而应先产出可核验的行为清单，再让编译器/测试/静态检查构成验证回路。对做架构辅助的团队，MRS 这一层可以直接复用到任何「行为必须等价」的改造（框架升级、服务拆分、语言迁移）：把隐式假设显式化，是 agent 能自我纠错的前提。

Reaper：把历史 bug fix 抽象成规则再投影到「语法兄弟」，在四个数据库里挖出 61 个新 bug

2026-11-05 · arXiv
DBMS 用语法驱动的 dispatch handler 实现 SQL 构造，不同 SQL 构造的 handler 往往共享同一套实现模式（取参、类型检查、权限校验）。于是修好一个 handler 的历史 bug 后，它的「语法兄弟」可能仍然带着同一个语义缺陷——论文称之为 sibling bugs。Reaper 先从历史 fix 推断 trigger profile（缺陷暴露条件）与 validation profile（区分错误/正确的语义证据），再用 grammar-guided test mutation 把 trigger profile 投影到语法兄弟上生成测试，最后用 validation profile 做分阶段验证以压低误报。在 MariaDB、MySQL、OceanBase、CockroachDB 上共发现 61 个此前未知 bug，57 个被开发者确认，13 个已修复。
🔍 技术视角：历史缺陷库是被严重低估的资产：把每个 fix 抽象成「触发条件 + 判据」两条规则，就能在结构相似的代码上批量复用。这给自建 AI 代码审查提供了一条不依赖大模型「悟性」的路径——先做结构同构检索（同一模式家族的 handler），再用规则化测试验证，模型只负责把 fix 翻译成 profile。对研发知识库，bug fix 应带结构化元数据（触发条件、判据、影响构造），而不是只存 diff 文本。

DiagDBench：6,940 条可执行数据库故障样本，最强 agent 只考 56.24 分

2026-11-05 · arXiv
数据库诊断与异常修复需要 agent 在活的 DBMS 环境里观察、交互、修复，但大规模构造可复现的异常环境很难，导致缺少可执行样本。DiagDBench 的每个样本把「用户请求（问题描述 + 异常已验证的工作负载）」与「自包含可执行 DBMS 环境」配对，支持实时监控、交互诊断、修复与工作负载重跑。构造用两条流水线：Manual-Guided Anomaly Synthesis（按 DBA 手册与官方文档顺序合成请求、库改动、注入脚本）与 Incident-Guided Anomaly Reproduction（从企业真实在线诊断事故端到端重建）。经样本过滤、专家复核后，含 6,940 条合成训练样本 + 454 条专家标注的 held-out 测试集，覆盖三种硬件配置、两种 DBMS、三种 schema。多模型评测中最好的 ReAct + GPT-6 Astra 仅 56.24 分，多数 agent 低于 45。
🔍 技术视角：两个可迁移的点：①「可执行环境 + 注入脚本 + 验证工作负载」是 agent 训练数据的通用工厂，业务系统同样可以造 sandbox（脱敏数据 + 故障注入 + 判据），这比人工标注轨迹便宜得多；②数据库诊断是 agent 能力的长尾，最好模型 56 分意味着运维自动化仍有明显空间，别把 demo 当产能。对自建业务 agent 的团队，这套「环境即样本」的思路可直接用于 API 层的故障/边界场景构造。

CascadeFilter：自然语言谓词筛选走三级级联，用小模型看证据、大模型兜底，并给出误差界

2026-11-05 · arXiv
语义筛选（判断一条记录是否满足自然语言谓词）是 LLM 数据分析里的高频操作，但逐条调用大模型成本高。已有 cascade 方法接受便宜模型的判断、把不确定记录转给 oracle，但阈值校准是在级联装配后按既定顺序调整，而不是在阈值组合上最小化成本。CascadeFilter 用三级：小模型先看抽取出的证据、再看全文，仍未解决的记录转 oracle；对固定级联，把阈值选择建模为「在 oracle 相对误差约束下最小化 token 感知成本」，并在预设网格中选最省且可认证的配置；用有限总体校准 + 固定序列检验分配多重检验预算，给选择后的误差界。另结合 lexical + dense 检索、rerank 与邻域支持的置信度改进证据抽取与路由。在 6 个数据集、13 个评测设置中，12 个设置取得最高准确率与 macro-F1（论文声明这些是报告工作点，保证针对与 oracle 的一致性）。
🔍 技术视角：把「自然语言谓词」当成一个可优化的算子，而不是一次 prompt：先用便宜模型在「抽取出的证据」上判断（证据比原文短，省 token），不确定才升级。对用户的宽表 API 场景高度契合——宽表返回上百字段，先用小模型抽取与谓词相关的 3-5 个字段值作为 evidence，再判定「这条记录是否属于某类业务对象」，可把成本压一个量级；阈值要用校准集选，且必须报告「与人工判定的一致率下界」，否则无法向业务方承诺可信度。

CoRE：数据清洗的高分有多少是「认识这些实体」？换个名字，年份修复准确率从 91% 掉到 18%

2026-11-05 · arXiv
公开数据清洗 benchmark 上的高分可能只反映模型「认识这些实体」，无法评估它修复陌生数据的能力。CoRE 设计对照协议：公开 benchmark vs 新鲜真实记录 vs 成对的名字替身（用英文单词或音节替换实体名，保留错误位置与非身份值，同时转移 benchmark 的错误机制）。在 21 张受控表、8 个 LLM 上：Hospital 上修复表现随实体名显著变化，商业模型在 Movies 上也如此；改名字会删掉修复所需的信息（如影片标识映射），即使候选仍可用也会影响——把实体名换成词基替身，DeepSeek-V4-Pro 的年份准确率从 91% 降到 18%。Hospital/Movies 上商业模型在新鲜记录上的分数高于词基替身。一个带筛选的续写探针未发现这些模型记忆 benchmark 行的正证据。熟悉事实会与任务冲突：即便给了明确的「以表格证据为准」指令，商业模型在已知影片上改写指定导演的比率仍为 0.000-0.404。参考评分也可能与外部记录不一致：Rayyan 上一条与标题匹配的 PubMed 记录相符的 ISSN 修正拿不到分，而 TabClean 被记分的修复里有 94% 只是复现了参考的日期变换。
🔍 技术视角：这是给「LLM 做数据修复/补全」的一记警钟：benchmark 分数里混入了世界知识，业务数据恰恰是模型不认识的（内部编码、客户名、自定义枚举）。做可信度验证必须加 counterfactual 对照——把实体名替换成无语义替身，看准确率掉多少；掉得越多，说明系统越依赖「猜」，越不能用于陌生业务数据。另一个细节同样重要：模型在「已知实体」上会违背表格证据去改写（0-40.4%），所以「以数据为准」的指令不能替代代码级校验。

RouteBR：模型只提议、代码做校验，客服路由 97.5% 最终路径匹配且 166 例零误派发

2026-11-05 · arXiv
金融机构的 LLM 客服系统必须在回复前选定下游服务，而「分类器/路由器给出相关标签」不等于「组合系统能完成派发」——还要校验派发权限与实体注册。论文把这个问题定义为 boundary-aware pre-response routing，提出 RouteBR：一次模型调用提议主服务动作与注册对象，随后由确定性代码检查标识符与版本化规则，才允许派发或给出指定的「不派发」结果；排名更低的候选不能替换被阻断的主路由。作者用某真实金融机构反复出现的保密请求模式构造 600 个隐私保护场景，由三名工程师共同复核场景与标签。在 200 例 CONFIRM MAIN 划分上，RouteBR 最终路径精确匹配 97.5%；同样规则下的单次调用基线 95.5%；没有规则程序的诊断基线动作准确率 94.0%，但最终路径精确匹配只有 41.0%。在 166 个非派发（MAIN/FLIP）案例上，RouteBR 零误派发。工件把 1,960 条预测行与原始回执配对，且模型请求中排除 gold 与 reviewer 字段。
🔍 技术视角：94.0% 的动作准确率 vs 41.0% 的最终路径匹配，是「意图分类指标」最典型的假象：模型知道该干什么，但系统不知道该不该让它干。对用户的业务查询 agent 直接对应——API 调用的对象校验、参数合法性、版本化权限规则必须是代码，不能写进 prompt；模型只负责「提议调用哪个 API、操作哪个对象」，编排层负责 fail-closed。这条也给出可审计性的具体形态：所有预测行与原始回执配对，模型看不到 gold。

HEELO：同一模型换 harness，Terminal-Bench 37.3%→55.5%；真实任务完成数 9→39

2026-11-05 · arXiv
论文先给出差距：Terminal-Bench 4.0 上 GPT-5.6 Sol + Codex 解决 37.3%，Claude Opus 5 + Claude Code 解决 51.8%，失败集中在「够到资源之后不会用」这一步，作者称为 last mile to the real world。现有做法把资源放到手边，却把「怎么用」留给调用方，于是每个 harness 都要重造这份能力。他们提出 agent-native primitives——给每个资源配一个驻留 LLM、能在上下文中应用该资源并与其他 primitive 通信的可复用单元，以及 HEELO 框架：按任务把所需 primitive 组合成任务特定图，用环境证据验证结果，修正失败牵涉的 primitive，验证通过后接纳新 primitive。八个 primitive 家族、二十多个 benchmark：Dev-Primitives 把 Terminal-Bench 4.0 从 37.3% 提到 55.5%（同 backbone）；Harness Primitives 把 Terminal-Bench 2.0 Pass@1 从 60.0% 提到 72.2%；Tool Primitives 把 ToolBench 通过率 55.8%→75.1%；Navigation Primitives 把 GAIA-Text-103 从 45.6% 提到 58.3%。在 46 个真实任务上，Claude Opus 5.5 + Claude Code 单独完成 9 个，接入 HEELO（MCP server）后完成 39 个；GPT-6.1 Sol + Codex 从 9 到 35，单任务耗时降 1.9x/2.3x，成本降 1.55x。
🔍 技术视角：这是「harness 比模型更重要」的量化版本：同一 backbone、只换 harness，真实任务完成数翻四倍。对同时做研发与业务 agent 的团队，含义是能力应沉淀为可复用 primitive（资源 + 驻留 LLM + 通信协议），而不是每个场景重写 prompt 链；且 primitive 要能被验证与替换，否则会变成新的技术债。MCP 作为接入方式（9→39）也说明协议标准化能直接放大已有 harness 的覆盖面。

「能跑通但算错」：迁移后 41% 的错误修复能过全部断言，一条边界输入把它压到 6.5%

2026-11-05 · arXiv

📊 架构示意

🎯 为什么值得关注

LLM 修迁移代码的失败模式不是编译不过，而是「语义悄悄变了但测试全绿」。这类缺陷在生产上是事故级的（金额、日期、权限判断），而现有 CI 门禁几乎完全无法发现。

⚙️ 核心机制

预注册 + 真实运行时执行：每个候选修复都在 CPython/SQLite 等真实运行时上跑，并对 withheld contracts（作者保留、模型不可见的契约断言）求值。变量是「门禁输入从哪来」：典型输入、release note 手写边界输入、盲写模型生成输入；再叠加菜单规模（1491 片段）与困难干扰项（在典型输入上与 legacy 输出一致）两个压力维度。

🧠 深度解读

三个反直觉结论：①「全部断言通过」在典型输入上是弱信号，41% 的错误修复能过；②干扰项让门禁重新变脆——因为干扰项专门匹配旧输出，任何只看典型行为的门禁都会被骗过，错误放行率反弹到 15-17%；③自测（模型自己写测试）帮助有限，说明「生成者自证」不可靠，验证必须来自变更文档或独立写作者。此外「盲 AI 审计契约严格性」删掉 34 条争议检查后判定不变，提示契约本身也有 over-specification 风险，需要人审边界。

💼 商业启示

对外包/迁移类项目这是报价与验收的抓手：验收标准应从「测试通过」改为「变更契约 + 边界输入覆盖」，可直接写进交付条款，降低返工与事故赔付风险。对内部平台团队，这意味着「迁移即服务」的产品化需要内置契约库，而不是卖模型调用。

🛠️ 落地建议

把发布门禁改成三段：a) 从变更说明抽取「必须保持的行为」写成契约；b) 每条契约至少一条边界输入（可由独立模型盲写，不要用修复模型自测）；c) 用「典型输入 + 边界输入 + 与旧输出一致的干扰输入」三组跑，报告错误发布率而不是通过率。在 CI 里对高风险模块（计费、时间、权限）强制开启。

⚠️ 局限与风险

研究规模是 73 任务/60 变更，集中在标准库与数据库 API 迁移，不代表大型业务系统的跨服务迁移；「错误」由 withheld contracts 定义，契约若有争议（34 条被判过严）会影响结论；论文明确「没有执行任何模型写的代码」，安全结论不外推；语义 Scholar 引用数本次 429 限流未能核实，11/05 新文预期为 0。

⚙️ 核心机制

🧠 深度解读

「把初始项目当作可执行精化状态」是本文最有价值的概念：不是一次性生成，而是把「当前代码 + 校验报告」当作状态，每次迭代都在缩小与规格的差距，这让长任务有了可中断、可审计的中间态。另一个细节是显式的 unsafe 削减目标——多数迁移工具只看编译通过，而 Rust 迁移的真实价值在安全性，这条约束把「能编译」提升为「更安全」。

💼 商业启示

存量系统现代化是明确的付费场景（内存安全合规驱动）。这套「规格 + 校验回路」的方法论可产品化为迁移评估报告，先卖诊断（MRS + 风险清单）再卖执行，降低交付风险。

🛠️ 落地建议

做框架/语言迁移时，先让 agent 产出 MRS（每条带源码证据与测试引用），人审后再让它写目标侧设计；CI 里挂三类校验（构建、行为测试、unsafe/坏味道计数），把报告回灌给 agent。MRS 本身可作为知识库资产，后续同类迁移直接复用。

⚠️ 局限与风险

评测以测试通过率为代理，测试集未必覆盖全部行为；OpenHarmony 模块样本量未在摘要中给出；unsafe 削减的度量方式需看全文；引用数未核实（S2 429）。

CascadeFilter：自然语言谓词筛选走三级级联，用小模型看证据、大模型兜底，并给出误差界

2026-11-05 · arXiv

📊 架构示意

🎯 为什么值得关注

业务分析里大量问题是「筛出满足某条件的记录」（高风险客户、异常订单、符合条件的合同），逐条大模型判断贵到不可用；而便宜模型单独用又不确定哪里不可信。

⚙️ 核心机制

三级级联：SLM(evidence) → SLM(full doc) → oracle；阈值联合搜索（不是顺序调参）以最小化 token 成本、受 oracle 相对误差约束；有限总体校准 + fixed-sequence 多重检验给认证界；检索/rerank/邻域置信提升 evidence 质量。

🧠 深度解读

三个方法要点：①「先看证据再看全文」是成本结构的关键，证据抽取质量直接决定第一级能拦下多少；②阈值是联合搜索而非逐级调，因为级联各段的通过率互相影响，顺序调参容易落在次优组合；③认证界是相对 oracle 而非绝对真值——工程上这意味着你要先有一个可信的 oracle 抽样集。

💼 商业启示

这是把「LLM 分析」从按条付费变成可预算服务的关键工程：成本可预测、误差可承诺，才敢卖给业务方。对内部团队，可作为宽表 API 的增值层（筛选/打标/风控初筛）单独计价。

🛠️ 落地建议

在业务 API 之上做「语义过滤服务」：为每类谓词维护 evidence 字段集（从宽表字段里选），小模型只读这些字段；不确定记录进人工/oracle 抽样队列；每月用抽样集重校准阈值并复核误差界。计费与 SLA 按「每千条记录成本 + 一致率下界」定。

⚠️ 局限与风险

oracle 本身可能是人或有偏模型，「相对 oracle 误差」不等于绝对正确；13 个设置中仍有 1 个未取最佳，说明并非普适；级联增加了系统复杂度与延迟；引用数未核实（S2 429）。

📊 架构示意

🎯 为什么值得关注

⚙️ 核心机制

四阶段工作流：Plan（上下文聚合 → 可评审计划 + 显式验收标准 + 切分 issue）、Build（任务独立推进、跨设备续接、共享项目知识）、Verify（agent 先跑例行检查与修复，缩小 diff，人审意图与风险）、Observe（日志/发布历史/客户报告聚合 → 事故文档 + follow-up issue → 回灌）。

🧠 深度解读

💼 商业启示

🛠️ 落地建议
