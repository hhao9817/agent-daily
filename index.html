GDPevo：首个聚焦真实企业业务工作流的 Agent 自进化基准（CRM/ERP/Finance/Healthcare/Legal 全覆盖）

2026-08-04 · arXiv 2608.03764
来自国内团队（Zhejiang Univ./Ant 等）的 GDPevo 提出"进化原生(evolution-native)"基准，核心机制 rule hybridization（规则杂交）：把每个企业工作流拆成原子业务规则，训练任务只暴露部分规则，测试任务重组剩余规则，从而让测试时的提升可归因于训练经验而非数据污染。覆盖 CRM、ERP、财务、医疗、法律、数据流六大领域，V1 含 120 任务/12 组，V2 可两天内扩到 240 任务。评测 4 个 Agent×4 种监督方式：自进化稳定提升留出集准确率最高 16.44 个百分点，但最强进化 Agent 仍远低于 91.6% 的全知 oracle 上限——说明当前 Agent 自进化能力远未兑现。Semantic Scholar 引用数因 429 限流未能核实，属 2026 新论文，预期为 0。
🔍 技术视角：架构师点评：这是少有地把"业务规则"作为一等公民的 Agent 基准。用户团队正从"AI for 研发"转向"AI for 业务"，GDPevo 的 rule hybridization 思路与用户的"业务知识库构建"方向高度同构——把业务流程拆成可重组的原子规则，本质就是业务知识图谱的运营化。"进化天花板 91.6% 但实测远未达标"这一结论，对用户是清醒剂：别指望一次 prompt 调优就让 Agent 懂全业务，需建立持久化状态 + 归因式评估。建议把 GDPevo 的评估范式（训练/测试规则隔离）移植到内部业务 API 评测上。

DBLifeBench + Progressive-Text2SQL：把 text-to-SQL 从"单点翻译"升级为"数据库全生命周期智能"基准

2026-08-04 · arXiv 2608.03794
DBLifeBench 是首个覆盖数据库全生命周期五阶段（Design/Implementation/Operation/Debugging/Maintenance）的 LLM 评测基准。团队指出当前基准过度聚焦 Text-to-SQL，忽视了 schema 设计、运维、调试、维护等真实 DBA 工作。配套提出 Progressive-Text2SQL 任务：用结构化推理图模仿人类迭代式问题求解，缓解自然语言歧义与复杂 SQL 逻辑间的认知错配。关键发现：通用模型表现均衡，而专精 Text-to-SQL 的模型在非编码阶段（设计/维护）出现"灾难性遗忘"。Semantic Scholar 引用数因 429 限流未核实，2026 新论文预期 0。
🔍 技术视角：架构师点评：这条对用户"语义层 vs 直连数据库"路线选择有直接启示。用户不直连 DB，但 DBLifeBench 揭示的"专精模型在非编码阶段灾难性遗忘"恰是警示——如果只把 LLM 当 text-to-SQL 翻译器，它在 schema 理解、数据治理、维护上会短板明显。Progressive-Text2SQL 的"推理图"思路与用户"业务语义层"方向一致：都试图把模糊自然语言锚定到结构化语义骨架。建议把 Progressive-Text2SQL 的推理图作为语义层的中间表示来研究。

MCTS-Report：用蒙特卡洛树搜索把"表→多模态报告"做成渐进式搜索，数值准确性靠 SQL 兜底

2026-08-04 · arXiv 2608.04071
MCTS-Report 用蒙特卡洛树搜索（MCTS）把"表格数据→文字+图表多模态报告"建模为结构化搜索空间内的渐进构造：原子动作含章节规划、可视化任务识别、图表生成、洞察组织、叙述精修，每步由 LLM 基于当前报告状态动态推理执行。奖励函数多维度联合评估数值事实一致性（通过 SQL 校验）、图表质量、图表-文本对齐、结构完整性，并加多样性惩罚抑制重复图表、前置条件检查剪枝无效动作。配套 MMRBench（六领域真实表+专家参考结构）。实验显示 MCTS-Report 在结构完整性、数值准确性、图文对齐、洞察新颖性上显著超越基线，总分 77.9。Semantic Scholar 引用数因 429 限流未核实，预期 0。
🔍 技术视角：架构师点评：这条对用户的"业务系统精确查询分析"方向极有价值。MCTS-Report 的精髓在于用 SQL 做数值事实校验——把 LLM 生成的洞察回写到 SQL 验证，这正契合用户"业务数据可信度验证"诉求。把报告生成拆成原子动作 + MCTS 搜索，也示范了"Agent 不是一次性生成，而是搜索+验证"的范式，可直接迁移到"业务 API 查数→分析→报告"链路。

EvolveNet：联邦式 Agent harness 进化——各业务部署本地进化、只共享学到的程序改编

2026-08-05 · arXiv 2608.04968
EvolveNet 提出"协作式 harness 进化"范式：一个共享 harness 广播给数据本地的 Agent 部署，各自在自己的工作负载上进化，只把学到的程序改编（program adaptations）回传组合成新的共享 harness 再分发——原始工作负载不离开本地。关键解决"experience 最有价值的地方恰好是无法集中的"难题（用户/组织/环境隔离的 experience 流）。引入 scope-typed、evidence-guided 程序聚合解决独立修改的程序无法像模型参数那样平均、组合时可能冲突的问题。在 text-to-SQL、数据科学编程、竞赛编程、软件工程、agentic workflows 五场景均提升共享 harness，异构工作负载下增益最大。消融证明增益来自多 Agent 改编的组合而非单纯选择。
🔍 技术视角：架构师点评：这条对用户"多业务线、多团队"场景极有启发。用户团队若在不同业务域（如多业务线的 API 查数 Agent）各自部署，原始业务数据因合规不能集中，但各团队学到的"如何更好地调该业务的 API"改编却可共享。EvolveNet 正是这种联邦式进化的范式。其 text-to-SQL 场景的增益也直接对应用户"业务精确查询"方向。

关键创新在"归因可分离"——传统 Agent 基准无法区分"模型本来就会"和"从经验学到"。GDPevo 通过规则子集分配强制训练/测试不重叠，使任何测试增益都可归因于自进化机制。这对用户团队有直接方法论价值：评估业务 API Agent 时，应设计"训练见过的业务规则 vs 未见过的规则组合"两套集，否则会被模型先验知识骗过。覆盖六大业务域也意味着可作为内部 Agent 跨域泛化的标尺。

🛠️ 落地建议

DBLifeBench + Progressive-Text2SQL：把 text-to-SQL 从"单点翻译"升级为"数据库全生命周期智能"基准

2026-08-04 · arXiv 2608.03794

📊 架构示意

🎯 为什么值得关注

现有 text-to-SQL 基准（Spider/Bird）只测"写 SQL"，忽略 DBA 真实工作链路；而企业要的是"全栈数据库智能"。DBLifeBench 是首个刻画完整生命周期的基准，直击评估盲区。

⚙️ 核心机制

1) 五阶段任务设计：Design(schema)/Implementation(SQL)/Operation(运维)/Debugging/Maintenance；2) Progressive-Text2SQL：结构化推理图节点化拆解问题，迭代收敛；3) 对比通用模型 vs 专精 text-to-SQL 模型，揭示灾难性遗忘。

🧠 深度解读

最深刻的是"灾难性遗忘"发现：专门刷 text-to-SQL 分数的模型，在 schema 设计、维护任务上反而不如通用模型。这给用户一个反直觉结论——选业务查询 Agent 时，别迷信 text-to-SQL 榜单分高的模型，它在理解业务 schema、做数据治理时会掉链子。Progressive-Text2SQL 的推理图可看作"轻量语义层"：把自然语言先映射到结构化推理骨架再落 SQL，这与 Cube/WrenAI 的语义层理念同源，只是粒度更细。

💼 商业启示

商业上，"灾难性遗忘"结论会冲击 text-to-SQL 专用模型供应商的叙事——企业会更倾向选全栈能力强的通用模型 + 语义层方案，而非专用 SQL 模型。对用户团队，这为"语义层路线"提供了选型论据：与其赌一个偏科的 text-to-SQL 模型，不如用通用模型 + 语义层（Cube/WrenAI）把业务语义固化，规避模型短板。市场层面，DBLifeBench 可能成为 DBA Agent 采购的新标尺。

🛠️ 落地建议

① 内部选型：用 DBLifeBench 五阶段评估候选 LLM，别只看 text-to-SQL 分数，重点看 Design/Maintenance 阶段表现。② 借 Progressive-Text2SQL 的推理图设计语义层中间表示，让自然语言→推理图→API/SQL 两段式落地。③ 把"灾难性遗忘"作为内部 Agent 评测的必检项，防止选了偏科模型。

⚠️ 局限与风险

Semantic Scholar 引用数因限流未核实（预期 0）。DBLifeBench 仍以关系型 DB 为中心，未覆盖用户场景的"业务 API 查数"（非直连 DB）。Progressive-Text2SQL 推理图需人工/LLM 构造，规模化成本待评估。信息待复核。

MCTS-Report：用蒙特卡洛树搜索把"表→多模态报告"做成渐进式搜索，数值准确性靠 SQL 兜底

2026-08-04 · arXiv 2608.04071

📊 架构示意

🎯 为什么值得关注

现有 table-to-report 方法用固定线性管线、子任务孤立处理，无法联合优化事实准确性、视觉质量、叙述连贯。MCTS-Report 用搜索+多维度奖励首次实现联合优化，并解决"LLM 报告数值常错"这一顽疾。

⚙️ 核心机制

1) 报告生成=搜索空间渐进构造，原子动作：章节规划/可视化识别/图表生成/洞察组织/叙述精修；2) 每节点存推理轨迹供上下文连贯；3) 多维奖励：数值一致性(SQL校验)/图表质量/图文对齐/结构完整+多样性惩罚+前置剪枝；4) MMRBench 六领域真实表评测。

🧠 深度解读

最值得用户借鉴的是"SQL 兜底数值准确性"。LLM 生成业务洞察时最大的信任障碍就是数字错——MCTS-Report 用 SQL 把 LLM 产出的每个数值声明回查源表，不一致即剪枝/重生成。这给用户"业务 API 语义理解+可信度验证"提供了具体范式：把业务 API 返回结构化数据→LLM 生成洞察→用确定性校验（SQL 或 API 二次查询）回验关键数字。MCTS 搜索而非一次生成，也意味着 Agent 会在"查数→验证→修正"循环里收敛到可信结果，这对业务决策至关重要。

💼 商业启示

对用户团队的直接商业价值："可信业务报告"是数据团队对业务方最直接的产出，MCTS-Report 的"搜索+SQL 回验"范式可把内部报告 Agent 的数字错误率显著降低，直接提升业务方信任度，是"AI 懂业务"的信任基建。市场层面，table-to-report 是 ChatBI 的核心场景，该方案可产品化为"可信 BI 报告生成"能力，有差异化空间。

🛠️ 落地建议

① 在业务报告 Agent 中引入"SQL/API 回验"环节，对 LLM 产出的每个关键数字做确定性校验。② 借 MCTS 原子动作拆解设计"查数 Agent"的 action 空间：字段选择→API 调用→结果解析→洞察生成→验证。③ 用多维奖励函数评估内部报告质量，不只看生成流畅度。④ 关注 MMRBench 作为内部报告 Agent 评测基准。
