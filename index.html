TraceSQL：reference-free 的可追溯 SQL 验证模型，67 个诊断特征

2026-08-20 · arXiv
Text-to-SQL 系统在真实部署时没有 ground-truth SQL 可供比对，验证成为部署期核心难题。TraceSQL 用 67 个显式诊断特征（question ambiguity、question requirements、question-schema-SQL consistency、SQL structure、intent alignment）构建轻量可解释验证模型，在 BIRD dev 上达 66.47% F1 / 64.48% ROC-AUC，胜过 GradeSQL-7B ORM 基线的 61.87% F1。特征归因可回溯每一处预测，把"为什么判这个 SQL 可能错"变成可检查的诊断证据，而非 ORM 的不可解释分数。论文发表于 2026-08-18（引用数待核实，Semantic Scholar 限流）。
🔍 技术视角：这是本周最贴合用户"业务数据可信度验证"方向的论文。用户通过业务 API 查数而非直连数据库，但同样面临"agent 生成的查询/调用是否可信"问题，且无 ground-truth 可比。TraceSQL 的 67 特征可迁移到"业务 API 调用验证"：question-schema-API consistency（问的与 API 字段是否对得上）、intent alignment（调用意图与返回字段是否匹配）、SQL structure（调用结构是否合理）。关键是"可追溯"——ORM 黑盒给分，TraceSQL 给证据，这与 8/19 TDS Sheila 的"reviewable evidence 为有意输出而非事后补充"共振。特征级证据是 agent 可信治理栈"验证层"的工程化形态。

LAVA：金融文档四阶段可审计验证，符号/算术校验保可复现

2026-08-20 · arXiv
金融文档生产验证（薪酬审计/税务合规/贷款核保）要求异常精度+一致性+可复现性，受严格企业约束。LAVA（Logic-Aware Validation and Augmentation）是 modular、backbone-agnostic 的流水线，基于多模态大模型，四阶段设计：document-rule retrieval（文档-规则检索）→layout-preserving information extraction（保版式信息抽取）→auxiliary metadata enrichment（辅助元数据增强）→auditable symbolic/arithmetic verification（可审计符号/算术验证）。支持 robust rule grounding（规则锚定）、fine-grained error attribution（细粒度错误归因）、consistent traceable end-to-end execution。在大型真实金融文档+数十条专家规则基准上，幻觉控制与边缘案例处理优于基线，且 token 使用高效。论文发表于 2026-08-17（引用数待核实）。
🔍 技术视角：LAVA 是"业务数据可信度验证"在企业金融场景的工程化范式。用户虽非金融场景，但"可审计符号/算术验证"机制直接可迁移——业务 API 返回的数值（订单金额、库存、指标）同样需要"LLM 抽取+符号校验"双轨，而非全靠 LLM 算。四阶段中"document-rule retrieval"对应业务 API 的"问句-API 字段-规则"检索，"auxiliary metadata enrichment"对应宽表字段语义标注，"auditable symbolic verification"对应业务数值的可复现校验。与 8/19 Quipu bitemporal KG 写入治理的"审计即查询"共振——都把审计从事后补充变为一等输出。

Noesis：跨知识库 Graph-RAG，35B 本地模型+Mesh 路由做多跳跨域推理

2026-08-20 · arXiv
Noesis 是解耦 Graph-RAG 架构，解决三顽疾：静态 chunk 碎片化丢失跨节语义连接、ingestion 不自适应扩展、多域部署需单体 KB（稀释精度）或人工路由。四算法：(a) 双向图遍历+Graph-Feedback Context Resolver 模拟人类阅读带衰减记忆；(b) AIMD 并发控制器（TCP 拥塞控制启发）23x 加速零 OOM；(c) Moesis 域感知选择性量化让 12GB 消费级 GPU 上 MoE 6.3x 加速；(d) Mesh 跨 KB 语义路由+运行时结构发现让小本地模型做多跳跨域推理。HotpotQA 1000 题 59.5 EM / 74.7 F1，超 GraphRAG +27.8 EM，用 35B 本地模型而非 GPT-4o 做图构建。193 页文档源文本验证 90% 精度长程因果边。论文发表于 2026-08-16（引用数待核实）。
🔍 技术视角：Noesis 是用户"语义层 vs 知识图谱"双路线中知识图谱路线的最强工程证据。Mesh 跨 KB 语义路由直接对应用户"多业务 API/多知识库"场景——不同业务域（订单/库存/财务）各有 KB，agent 需跨域多跳推理而非塞进单体 KB。35B 本地模型做图构建+小本地模型做推理，是"数据不出域"的合规友好架构，与 8/14 TDS 本地 LLM 实测的"256K+122B 把破损率 25%→0"呼应——本地模型足够做 Graph-RAG，关键在架构而非堆参数。AIMD 并发控制把网络拥塞控制引入 RAG ingestion 是创新，解决静态 chunk 不扩展的根因。

TraceSQL：reference-free 的可追溯 SQL 验证模型，67 个诊断特征

2026-08-20 · arXiv

📊 架构示意

🎯 为什么值得关注

用户课题第三方向"业务系统精确查询"明确要求"业务数据可信度验证"。TraceSQL 是 reference-free 验证——部署期可用，不依赖 ground-truth，这正是用户场景（agent 查业务 API 无法预先知道正确答案）的刚需。

⚙️ 核心机制

67 特征分五类：question ambiguity（问题本身是否模糊）、question requirements（问题要求什么粒度/聚合）、question-schema-SQL consistency（问题-schema-SQL 三者一致性）、SQL structure（SQL 结构合理性）、intent alignment（生成 SQL 与用户意图对齐）。轻量学习模型基于这些显式特征预测，特征归因可回溯每个预测依赖哪些信号。

🧠 深度解读

TraceSQL 与 8/19 Never the Number（结构化弃答）形成"验证"主题两种实现：Never the Number 管"何时该拒绝答"（不可表示=拒绝），TraceSQL 管"生成后如何验证可信"（67 特征诊断）。两者互补——前者在生成端设 gate，后者在验证端给证据。与 8/18 SemPlan A3 结构化语义请求+确定性规划同构：都是"LLM 生成→确定性诊断"路线。ORM（Outcome Reward Model）从执行标注候选 SQL 学习给分，但黑盒；TraceSQL 用显式特征换可解释性，代价是需手工设计 67 特征——这是"可解释 vs 性能"的工程权衡。

💼 商业启示

商业启示：reference-free 验证是 agent 产品化的"信任闸门"——客户不会接受"agent 说对就对"，必须给可检查证据。TraceSQL 的"67 特征+可追溯"模式可成为 ChatBI/Agent 数据产品差异化卖点：不只给答案，还给"为什么这个答案可信"的诊断报告。这是企业采购决策的硬指标，与 8/17 TDS Partha 安全治理三件套的"HITL REQUIRES_HITL"形成验证-审批闭环。

🛠️ 落地建议

落地建议：将 67 特征框架迁移到业务 API 调用验证——question-schema-API consistency 改为 question-API-field consistency（问的与宽表 API 字段是否对齐），intent alignment 改为 call-intent vs response-field alignment（调用意图与返回字段是否匹配）。先建特征工程做轻量验证模型，与 LLM-as-judge 并行，对比可解释性与准确率。

⚠️ 局限与风险

67 特征需针对业务 API 重新设计，迁移成本非零。F1 66.47% 仍低，约 1/3 错误未捕获，必须 HITL 兜底（与 8/19 DEW Anthropic 平台原语一致）。特征归因虽可追溯但特征本身是启发式，可能系统性遗漏某类错误。引用数待核实（8/18 新文预期 0，Semantic Scholar 429 限流）。

🎯 为什么值得关注

🛠️ 落地建议

落地建议：业务 API 查数后增加"符号校验层"——对返回数值做算术一致性检查（如订单明细之和=总额、库存增减平衡、指标随时间单调性）。先在金额/库存/核心指标三类高价值字段试点，与 LLM 抽取并行，差异即告警。保版式 IE 对宽表 API 响应同样适用——保留字段顺序与层级，避免 LLM 重排致语义错位。

四阶段流水线工程复杂度高，需先有规则库与版式解析能力。符号/算术校验只覆盖可形式化的规则，模糊业务判断仍需 HITL。token 高效是相对基线，绝对成本在高量场景仍可观。引用数待核实（8/17 新文预期 0）。

TDS：Kimi K3 1M 长上下文 vs RAG 实测——长上下文满分但延迟与配额打穿

📊 架构示意

🎯 为什么值得关注

用户面临"语义层 vs 长上下文倒"的路线之争——1M 窗口出现后，是否可跳过语义层/知识图谱直接全量喂入？本文是该问题的受控实验答案。

⚙️ 核心机制

实验设计：32 文件 33 篇文章 127,068 tokens（tiktoken cl100k_base 计），Moonshot 实计 127,346 input tokens/request（含 system+question）。两路：RAG（5 selected passages）vs long_context（全 32 文件）。12 题三级：A1-A4 单事实、B1-B4 跨文章、C1-C4 语料级。blind grading 三维：correctness/completeness/grounding 各 0-2 分。三处意外：(1) 半数答案空（未注意）；(2) 同调用一次失败一次成功；(3) 单次完整 pass 不 fits 一日（1,528,152 tokens 打穿 1.5M 配额）。

🧠 深度解读

三层发现：(1) 质量层——long_context 12/12 满分，RAG 的 gap 全在 completeness（0.83/2），grounding 平手（2.00），correctness 略低（1.92）。这颠覆"RAG 会幻觉"预期——RAG 不幻觉但不完整，是"不知道"而非"说错"。(2) 延迟层——单事实题两路接近，跨文章 long_context 慢 2-3x，语料级 C3 273.7s vs 46.3s，因思考 token 多 2-10x。瓶颈在推理非读取。(3) 成本层——12 题 1,528,152 input tokens 打穿 1.5M 日配额。与 8/17 dbt token 压缩共振——Gong MCP 直连 24 万 token 触发 API 天花板是同一问题在更大语料上的重现。与 8/15 Beyond Top-K（表格密集文档 top-k 失效）共振——跨文章问题需结构化预聚合而非 chunk 检索。语义层的价值正是补 completeness gap——把跨文章/跨域信息结构化，让 RAG 一次取完整答案而非 5 碎片。

💼 商业启示

商业启示：1M 长上下文不消灭 RAG/语义层市场，反而强化其价值——长上下文的延迟与成本随语料级问题爆炸，企业不可能为每个查询烧 1.5M tokens。语义层/知识图谱的"结构化预聚合"是长上下文的互补而非替代：长上下文管单文档深度，语义层管跨文档/跨域完整性。这是"语义层 vs 长上下文"二元选择的破除——两者解决不同问题。dbt 的 99% 降本与本文的配额打穿是同一 ROI 的两面。

🛠️ 落地建议

落地建议：不要因 1M 窗口放弃语义层——语料级问题延迟爆炸+配额打穿证明全量喂入不可扩展。语义层压缩 schema context 的目标不是省读取 token（占比小），而是省思考 token（long_context 思考量 2-10x）+补 completeness（结构化预聚合跨域答案）。对跨业务 API 问题，先用语义层把多 API 字段预聚合为指标/维度，再让 agent 查，而非让 agent 从 5 个 API 响应碎片拼。

⚠️ 局限与风险

实验规模小（12 题，作者自评），不可直接推广。12% 占用非极端，800K tokens 行为未知（作者明说）。RAG 的 completeness gap 可能因检索器弱而非 RAG 范式本身弱——强检索器可能补齐。long_context 满分部分因作者自评自有文章（高确定性基准）。配额打穿是入门 tier，高 tier 可承受但成本线性增长。
