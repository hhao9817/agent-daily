代码表示即设计变量：五种仓库地图让 Claude Code 省 25-39% token，但只在定位瓶颈时提分

2026-11-05 · arXiv
论文把「agent 如何看代码」当成独立设计变量，比较五种 repository map 工作流：AST、调用图、模块依赖、文档增强检索、以及混合视图，每种都以可查询的仓库地图形式暴露给 agent。用 Claude Code + Haiku 4.5 在四个仓库级任务上对照 raw-tool 基线：故障定位（LinuxFLBench）、仓库级生成与修复（SWE-bench Pro）、测试生成（SWT-bench）、安全补丁（SecBench）。定位任务上五种视图都把 recall@10 从 0.717 提到 0.757-0.829，token 降 25-39%；SWE-bench Pro 解决率 44.3-50.6% 对基线 49.0%，基本持平但 token 降 17-26%；SecBench 上调用图补丁解决率最高（34.3% vs 28.9%）。
🔍 技术视角：对已经建好研发知识库的团队，这条的实操含义是：代码图谱的 ROI 集中在「检索与定位」环节，不要指望它直接提升补丁与测试的质量。更合理的做法是把 map 做成按需调用的工具（定位阶段开启），而不是每轮都全量注入上下文——否则 SWT-bench 那种「更贵更慢、只多 3 个点」的结果会反复出现。

失败预测器其实在猜题：题目难度单项 0.92 AUROC，轨迹信号≈0，重试只能救「坏 run」

2026-11-05 · arXiv
论文检验 SWE-bench Verified 上的轨迹式失败预测器到底学到了什么。结果显示两个与 run 无关的因素主导性能：其一是题目难度——一个完全不看轨迹、只看该题对其它模型有多难的参考分数就能达到 0.92 AUROC，而轨迹预测器只有约 0.62；其二是模型能力——同一题内只要知道是哪个模型在跑，就比预测器更准。扣除难度与能力后，轨迹带来的增益在统计上等同于零。后续动作也站不住：模型切换所依据的「最佳单模型 vs any-model oracle」差距不超过随机波动，per-issue 切换在留出集上没有收益；重复运行实验显示同模型同题有时成有时败，重试能修复「坏 run」，但救不了超出模型能力的题。
🔍 技术视角：这条对 agent 平台的控制面是直接的否定证据：不要用「轨迹置信度」做自动熔断或自动切模型，它很可能只是在复述题目难度。可落地的替代是把重试策略分成两类——同题多次重试（对 bad run 有效，值得给预算）与跨模型路由（收益被高估）。评估一个「自愈/自愈路由」方案时，必须先扣掉难度与模型能力这两个基线。

Skillware：把技能做成「类型契约 + 确定性代码 + 单测」的软件包，3B-8B 小模型反超前沿模型

2026-11-05 · arXiv
论文批评当前「让模型动态写代码、猜 API 载荷、靠 prompt 记约束」的假设，提出 Skillware：一个开放架构与能力注册表，把「想做什么」和「怎么做」正式分离。每个能力包由 typed JSON 输入契约、确定性 Python 实现、任务指令、随包数据集、自动化单测组成，通过 in-process adapter 翻译成任意模型的原生 tool 声明（云端前沿 API 到本地开源权重均可）。在 23 个前沿与开源模型、368 个基准条件上，装备 Skillware 的 3B-8B 小模型在复杂多步工作流上稳定超过未装备的前沿模型；token 最多降 84.8%，推理成本最多降 97.3%，参数错误被完全消除。
🔍 技术视角：这是对 AGENTS.md / skills 热潮的一记工程化纠偏：自然语言 skill 适合「指导」，不适合「承载执行」。对用户团队的宽表 API 场景尤其直接——与其让模型读两百个字段的文档并猜参数，不如把高频查询写成带 JSON Schema 的能力包，模型只负责选能力、填参数、读结果。可靠性来自确定性代码与契约，而不是更大的模型。

基准也是软件：Terminal-Bench 审计出约 30% 题目有缺陷，修复后准确率 +10pp、排名移动 3 位

2026-11-05 · arXiv
论文提出「benchmark maintenance debt」：即使发布时经过严格验证的基准也会腐化——模型变强后会给出 verifier 拒绝的合法解，评测基建的改动也会让任务里嵌入的假设失效。作者给出一套持续验证工作流（社区报告、任务工件、agent trace、自动 oracle 检查、人工闸门修复），并对 Terminal-Bench 2.0 做审计：约 30% 的题目存在问题，修复后作为 2.1 发布。修复改变结论：准确率提升超过 10 个百分点，榜单名次最多移动 3 位，但整体排序仍高度相关（Spearman ρ=0.958）。论文还显示资源口径会改变结论：延长 wall-clock 时限把 GPT-5.4 的 harness 差距抹平 20pp，把 GPT-5.4 mini 的 30pp 差距缩到 5pp。
🔍 技术视角：对自建 eval 的团队，这条的核心不是「别人的榜不可信」，而是「你的内部评测集同样会腐化，而且腐化是静默的」。把 eval 当代码库管理：任务有 issue 模板、verifier 有回归测试、修复走人工闸门，并固定时间/预算口径。否则你会在「模型升级」和「评测漂移」之间做出错误归因。

tok：给 BPMN/DMN 一套纯文本语法，token 只有 XML 的 1/2.2，agent 写流程 97.6-100% 合法

2026-11-05 · arXiv
tok 是 BPMN 2.0.2 流程模型与 DMN 1.5 决策模型的纯文本具体语法：一个引擎同时按两套标准校验文档、编译成带自动绘图的 XML，并通过 Model Context Protocol 服务 LLM 应用。在 37 个工具导出的 893 个 BPMN 文件上，一个 tok 模型比最小的 BPMN XML 少 2.2 倍 token、比文件原样少 7.7 倍；对 1,411 个注入故障检出 98.2%，而 XML Schema + bpmnlint 为 85.8%。四个首次接触 tok 的模型只看一页参考，就能对 87 个流程描述写出 85.7-100% 合法的 tok；配上 lean skill 与一个 checker 工具后达到 97.6-100%，最强模型写 tok 比写 BPMN XML 少 21%/14% token。47 个仿真事件日志中有 44 个与源模型吻合。
🔍 技术视角：业务知识与研发知识的一个关键差别是：流程与决策规则天然是图/表结构，但长期以 XML、PDF、截图形式存在，agent 既读不懂也改不动。tok 提供的是「机器可写、可校验、省 token」的表示层，恰好补上语义层（管指标）之外的流程与决策维度。对自建业务知识库，这意味着流程资产应当是可 diff、可 lint 的文本，而不是附件。

Agent 行为契约：把「可观察行为」当版本化工件，按场景 pass^k 卡发布，权威判定移出模型

2026-11-03 · arXiv
论文指出企业 agent 的维护问题不在模型不确定性本身，而在于「改变行为的因素大多来自团队之外」：模型版本退役、策略修订、上游 schema 变更、为修一个 case 而改的 prompt，往往在线上才被发现，而不是作为回归被拦住。ABE（Agentic Behavior Engineering）把 Design by Contract 移植到非确定性系统：以「仅规格」的行为契约为版本化工件，带稳定规则 ID，写明必须做、不得做、以及证据不足时必须弃答；轻量场景库把每条规则变成具体情境；测试、运行时策略、遥测都单向引用契约，使规格与实现可独立演进而不漂移。方法分五职责（Specify/Ground/Control/Verify/Observe），区分「缺证据」与「已验证否定」，把权威放在模型之外，按场景 pass^k 而非聚合准确率放行，并把每次生产运行按契约归类、路由到该改的资产。
🔍 技术视角：这是目前看到对「构造性拒绝」最工程化的表述：弃答不是模型的美德，而是契约里的一条显式规则，且「查不到」不能等同于「没有」。对用户团队，ABE 提供了一个可审计的骨架——规则 ID、场景、单向引用、pass^k 门禁——可以直接映射到业务 API agent 的发布流程。

AgentTrustCI：把策略/接地/轨迹三类断言写进 JUnit，录制 trace 在 CI 里确定性回放

2026-11-04 · arXiv
论文指出基础设施安全并不能回答应用层问题：agent 是否选了允许的工具、答案是否真的落在工具输出上、是否按规定的顺序走完流程。AgentTrustCI 是一个 Java/JUnit 5 框架，把这些期望表达为对录制 trace 的三类检查——policy（工具选择合规）、grounding（答案接地）、trajectory（调用序列合规）；确定性 replay 让测试可在构建期重复执行，judge 接口为可选的语义评估留扩展点。在覆盖 7 个企业域的 55 个合成用例上，完整流水线把 30 个注入故障与 25 个通过控制全部分类正确（含 10 个非平凡控制），12 个指定关键用例零漏检；单层配置各正确分类 35 个用例，因为语料按层故意隔离了每层 10 个故障。一个「答案正确但通过不允许的调用序列获得」的用例，展示了轨迹层独有的覆盖。
🔍 技术视角：对已有 Java 发布流水线的团队，这是成本最低的落地路径：不需要重构 agent，只要把 trace 录下来，在 CI 里加三类断言。三层正交设计也很关键——别用一个 LLM judge 同时判断策略、接地和顺序，那样失败无法归因，回归也无法定位。

交接摘要会变成指令：模型自写的「需要审批」被后继实例当真，误批准使越权动作 24→7/120

2026-11-04 · arXiv
长任务 agent 会压缩上下文，用摘要替代大部分历史。论文追问：交接摘要是否会写入记录并不支持的权限或要求？这些句子是否会改变后继实例（successor）的行为？它们从哪来？方法是在合成工具任务中携带 ground-truth 权限账本，用同快照回放把整句替换为中性填充做因果检验。两名 AI 读者只读被规则标记的留出摘要，确认「不支持的限制」占全部可读摘要的 1.2% 与 2.4%，「不支持的授权」占 0.1% 与 1.3%。中和误批准后，越权动作从 24/120 降到 7/120（后置检验；另一组 17→11/48）。多数「限制」源自 agent 早前「这个动作需要审批」的推理（后置分析）。预注册检验中，把系统提示里的「有些动作需要审批」改为说明「要求来自哪里」，使不支持的限制从开发集 5.0% 降到 1.8%、留出模板 1.8% 降到 0.3%（p<1e-9），而对账本要求的合法审批请求影响很小。
🔍 技术视角：上下文压缩不是无损的语义操作：它会把推理过程中的假设固化成「规则」，并在下一个实例里获得执行力。对长流程单据/审批 agent，这意味着摘要必须与权限账本分离——后继实例只信账本，不信摘要里的自然语言。这条与 ABE 的「权威在模型之外」互为印证。

API 的 AI 就绪度打分：6 维约 35 个信号，把「OpenAPI 能校验」和「agent 真能用」分开

2026-11-06 · GitHub
Jentic API Scorecard 的出发点是：通过 schema 校验的 OpenAPI 文档，不等于 agent 能用的 API——语法是一回事，语义清晰度、安全性与可发现性是另一回事。它按 JAIRF（Jentic API AI Readiness Framework）六维打分：基础合规（FC）、开发者体验与工具兼容（DXJ）、AI 就绪与 agent 体验（ARAX，语义清晰度与每个 operation 所需上下文）、agent 可用性（AU，可预测安全的多步编排）、安全（SEC）、AI 可发现性（AID）。实现为两阶段：分析阶段跑一批验证器与结构检查，打分阶段映射到约 35 个信号、聚合成维度分与加权总分/等级；评分在本地 Docker 内完成，文档不出环境；配套 api-improve skill 用 OpenAPI Overlay 做非破坏性修改并生成前后 changelog。
🔍 技术视角：这正是「上百字段宽表 API」缺的体检表：字段描述缺失、枚举没有业务含义、operation 没有副作用与幂等标注，都会在 ARAX/AU 上掉分，而这些恰是 agent 猜错参数、误重试的根因。把它接进 CI 当「API 语义门禁」，比等 agent 线上失败再回头补文档要便宜得多。

MCPHallu：358 任务 / 36 个生产 MCP server，14 个前沿 agent 平均 0.642，「目标不可达」仅 23.2% 能识别

2026-11-05 · arXiv
MCPHallu 是面向 MCP 环境的幻觉诊断基准，按 reasoning / execution / memory 三轴构造四类结构性触发：Branch Collapse、Unreachable Goal、Tool Misuse、Context Forgetting，使每道题有明确的「主导失败风险」而不是笼统的任务完成率。基准含 5 个能力域的 358 个任务，跑在 36 个容器化的生产 MCP server 上；评测 8 家厂商的 14 个前沿 agent、5,012 条轨迹。结果：平均得分 0.642（0-1），失败集中在 Unreachable Goal——平均 0.458、仅 23.2% 的运行通过，说明 agent 往往会继续发工具调用或直接宣称成功，而不是识别目标不可达。子类型排名差异极大：模型名次平均移动 6.9/13 位，Branch Collapse 与 Unreachable Goal 之间不相关（r=-0.12）。
🔍 技术视角：「构造性拒绝」不是措辞问题，是能力短板：在工具环境里，agent 缺少一个显式的「可行性判定」环节，于是用更多工具调用掩盖「做不到」。这与 ABE 的弃答规则、以及状态化工具调用的结构审计互为三角——一个给契约，一个给度量，一个给结构诊断。

什么结构会压垮 agent：把调度/状态保持/候选选择拆开测，依赖深度与可达状态数被耦合

2026-11-02 · arXiv
论文认为聚合任务分无法区分「调度失败」「状态保持失败」「候选选择失败」。作者做了一个小型可执行仪器：固定必需操作数，只变化四个结构参数——依赖深度、候选数量、活跃状态宽度、是否能读到当前状态快照。两个依赖图族显示，在固定工作量下加深依赖会同时改变调度自由度与可达完成状态数，两者被耦合，论文对这一耦合做了量化。主研究含 49,152 个生成任务与 393,216 次参考控制器 rollout；另有一个冻结的后续设计，追加 295,936 次 rollout，覆盖状态保持策略、快照节奏、隐藏状态重采样、恢复、查询局部性、候选索引与重标注。结果：residue cache 与预计算计划能解决 raw-value cache 解不了的题；索引化选择消除了串行扫描的分支缺陷；隐藏状态重采样给出精确的成功率上限，再多状态跟踪也越不过。作者明确声明：0.5B 小模型的本地 CPU 研究未完成任何工作流，16 次 Copilot 路由实验仅具描述性，不支持一般能力结论。

📊 架构示意

🎯 为什么值得关注

💼 商业启示

⚠️ 局限与风险

单一模型（Haiku 4.5）与固定 harness，结论未必外推到更强模型；四个 benchmark 各自的样本量有限，SecBench/SWT-bench 的差异在样本内；延迟代价未量化成成本。

🛠️ 落地建议

最有洞察力的是「通过测试的错误」：管道跑通、记录到达、测试通过，但业务问题被答错。这类失败不会出现在数据质量监控里，只能靠「解读前置 + 人工确认」拦住。另一个细节是「7 天内购买」只证明购买发生在邮件之后，不证明因果——这种区分正是业务语义层应当承载、而 SQL 生成器无法自动推断的内容。

💼 商业启示

数据团队的护城河从「会写 SQL/建模」转向「能把业务决策显式化并审计」。对自建业务 agent 的团队，验收标准应是「人能否审出 agent 的假设」，而不只是答对率——这也是把 AI 从 demo 推向生产的分水岭。

🛠️ 落地建议

在 agent 的产出流程里加一个「解读卡」环节：定义来源、关联键、推断 vs 确认、未决问题四项，必须人工确认后才能生成管道；把这些决策写进模型文档并与代码双向链接；对跨部门术语（活跃客户、响应、收入）建立适用范围与 owner。

⚠️ 局限与风险

观点性文章，无量化实验；ADDLC 仍是概念框架；「解读卡」在大规模变更下的人工成本未评估。
