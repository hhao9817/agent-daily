Agentic AI for Manufacturing Data：跨源系统直查 Agent 在真实工厂 schema 上的诚实架构（87 数据集/3600 表/92000 列）

2026-08-26 · OpenAlex / Zenodo (DOI 10.5281/zenodo.22087584)
本书以一个复合 tier-2 航空供应商为案例（4 站点、2100 员工、加工结构件），构建跨源系统直查 Agent 完整架构。系统景观：SAP ECC 管订单与财务、商业 MES 在两工厂+自建 SQL Server 应用在 2019 收购的两工厂、Teamcenter 持工程 BOM 且制造 BOM 在 SAP 重派生、不合格品在独立质量系统且有自己的 part master、机器遥测在 controls 组拥有的过程 historian 中。全书 16 章数字一致：87 注册数据集、约 3600 表、约 92000 列。Part I（1-4 章）建立问题：为何制造数据抵抗普通方法、Agent 是什么及何时不用、系统景观结构、为何公开 text-to-SQL 精度不预测工厂 schema 表现。Part II（5-9 章）是架构与核心：跨远超 context window 的注册表路由问题、HANA/Oracle/PostgreSQL/T-SQL/Trino 五方言 SQL 生成、过程 historian 为何不走 SQL pattern、模型看到 schema 前过滤的 access control（因表名列名常是受控资产）、记忆与决策节奏。Part III（10-13 章）是建设：实现、无代码 onboarding 数据集、网络不可达互联网的部署、如何知道是否有效。Part IV（14-16 章）覆盖之后的可能、完整 ontology、作为企业能力运行。
🔍 技术视角：这本书几乎是对用户课题的"镜像案例"——用户场景是不直连数据库、通过高业务含义 API 查数（含上百字段宽表 API），本文的案例是跨 SAP/MES/Teamcenter/质量系统/historian 直查源系统。关键洞察：公开 text-to-SQL 精度不预测工厂 schema 表现（因真实 schema 的表名/列名本身是受控资产+语义密度远超 benchmark），这与用户宽表 API 字段语义标注痛点完全共振。access control 在模型看到 schema 前过滤=表名列名是受控资产，直接对应用户宽表 API 场景中部分字段是业务敏感字段的治理需求。过程 historian 不走 SQL pattern 提示：不是所有业务数据源都能被 SQL 化，用户 API 语义理解需兼容非 SQL 数据源。

Interpretability Engine Optimization (IEO)：SEO/AEO/GEO 之前的"机器能否正确解读业务"层

2026-08-26 · OpenAlex / Zenodo (DOI 10.5281/zenodo.22104280)
本文提出 Interpretability Engine Optimization (IEO)：结构化、解析、丰富、验证、表示 commerce data 使 AI 系统在检索/比较/推荐/交易前正确解读 offer。现有优化学科——SEO/AEO/GEO 及相关 AI 优化实践——解决业务是否被发现、被提取、被引用、被行动。无一解决先于它们的问题：机器能否正确解读业务卖什么？IEO 定义三解读对象（product/brand/transaction）、核心操作（structuring/resolving/enriching/validating/representing）、与邻域实践的边界测试、工作仪器实现的测量方法。实证审计语料显示解读失败在语料内常见、可测、可修正——修正产生 machine-facing readiness 的大幅提升。IEO 被提出为开放学科：任何人可用任何工具实践，不提出新数据格式/协议/模型/丰富技术，其提案是学科本身：将 commerce data 的机器解读视为一等工程对象。
🔍 技术视角：IEO 的"解读先于检索"论点与用户业务语义层课题直接共振——用户需在 AI 查询前确保 AI 正确解读业务 API 字段语义。IEO 的三解读对象（product/brand/transaction）可迁移为用户宽表 API 的三解读对象（字段语义/业务实体/查询意图）。核心操作（structuring/resolving/enriching/validating/representing）是一个完整的字段语义标注流水线。"解读失败常见、可测、可修正"为用户建立字段语义标注质量度量提供参考。

TDS《Stop Giving Your AI Agent a Search Box》：typed tool vs search box 全程实测，Agent 价值在工具词汇表而非循环

2026-08-27 · Towards Data Science
这是知识层三部曲 Part 3，全程实测"typed tool 边界 > search box 重试"。核心论点：Agent 的推理受限于其工具的词汇表——给模型 search box + 重试预算，迭代买的是重述猜测；给知识层真实词汇（typed traversal/timelines/diffs/entity resolution/contradiction register），迭代变成导航。设计八个 read-only typed tool（search_evidence/search_knowledge/resolve_entity/traverse/timeline/diff/list_contradictions/get_source），每个返回统一信封（results/source ids/validity metadata/insufficient flag）。Agent 循环仅 80 行代码、无编排框架（刻意为之以保实验 custody）。三路消融：A=固定融合管线、B=search-box agent、C=八工具 agent。结果：C 多跳正确率 0.92 vs A 0.83 vs B 1.00（B 是 verbosity trap——metric 奖励冗长而非真推理）；A 单跳正确率 0.95 vs C 0.70（Agent 在简单问题上过度工作）；naive agent 未如预测冲破 contradiction gate（预测被推翻——指令遵从在 21 文档+1 好提示词下足够）。四模型对比（gpt-4o-mini/gpt-4.1/gpt-5-mini/gpt-5）：gpt-5-mini 是最佳甜点（多跳 0.92/健康 tool-seeking/中等成本），gpt-5 花最多返最少。最终架构：escalation——固定管线为默认，Agent 仅在信号触发时介入（sequential dependency/insufficient flag/contradiction/多时间窗比较/人请求深度）。
🔍 技术视角：这篇文章是用户课题的工程模板级文献。核心洞察：①"Agent 价值在 tool vocabulary 而非 loop"——80 行循环是便宜部分，两篇知识层基建才是真正投入，这对用户评估"建 API 语义层 vs 直接上 Agent 框架"的投入分配是直接指导。②八 typed tool 的设计（每个返回 insufficient flag）对用户上百字段宽表 API 场景直接可迁移：resolve_entity 对应字段实体消歧、traverse 对应字段间依赖导航、timeline 对应字段有效时间窗、list_contradictions 对应字段语义冲突检测。③"search-box agent 的 1.00 是 verbosity trap"警示：用 keyword-coverage 评估 Agent 会系统性高估 search-box 类方案，对用户评估宽表 API 查询效果有方法论启示。④escalation 架构（固定管线默认+Agent 介入）为用户"何时不该跑 Agent"提供工程判据——大部分流量走固定管线，Agent 仅在多跳/信号触发时介入，这是成本与效果的平衡点。

Agentic AI for Manufacturing Data：跨源系统直查 Agent 在真实工厂 schema 上的诚实架构（87 数据集/3600 表/92000 列）

2026-08-26 · OpenAlex / Zenodo (DOI 10.5281/zenodo.22087584)

📊 架构示意

🎯 为什么值得关注

这是极少数用真实企业系统景观（非 benchmark）完整阐述跨系统查询 Agent 架构的文献，且直言公开 text-to-SQL benchmark 精度不预测真实 schema 表现——这对用户判断"benchmark 成果能否迁移到宽表 API 场景"是关键参考。

⚙️ 核心机制

跨远超 context window 的注册表路由问题 → 五方言 SQL 生成（HANA/Oracle/PostgreSQL/T-SQL/Trino）→ 模型看到 schema 前的 access control 过滤 → 过程 historian 非 SQL pattern 的特殊处理 → 记忆与决策节奏适配。全书数字一致（87 数据集/3600 表/92000 列）使第 1 章的图在第 12 章仍成立。

🧠 深度解读

核心架构张力在"路由跨超大注册表"与"access control 在模型看到 schema 前过滤"。前者直接对应用户上百字段宽表 API 场景：不能把所有字段塞进 context window，需先路由到相关子集。后者把 access control 从"模型生成 SQL 后过滤结果"前移到"模型看到 schema 前过滤"——因为表名列名本身泄露业务语义（如列名=利润率），这是对用户字段级权限治理的直接启示。过程 historian 不走 SQL pattern 提示：用户业务 API 语义理解需兼容非 SQL 数据源（如时序数据库/事件流），不能假设所有数据源都 SQL 化。

💼 商业启示

这本书的商业价值在于它提供了"跨系统查询 Agent"的真实 ROI 论证框架——Getting an answer still takes days, because the question crosses four systems and four people, and every crossing costs time。对用户团队从"AI for 研发"转型"AI for 业务"，本书的"跨系统直查 Agent"是企业级业务查询 Agent 的架构蓝图，且其"公开 text-to-SQL 精度不预测真实 schema"的论断为内部立项提供了"为何不能直接用 benchmark 成果"的硬论据。

🛠️ 落地建议

①用本书的"注册表路由"思路组织用户的上百字段宽表 API：先路由到相关字段子集再进 context window。②把 access control 前移到 schema 可见前：对敏感字段名/列名在模型看到前过滤，而非事后过滤结果。③建立"公开 benchmark 精度≠真实 schema 精度"的预期管理：不要用 Spider/Bird benchmark 精度承诺业务系统效果。④Part II 的五方言 SQL 生成对用户 API schema 理解有参考：不同源系统的"方言"需要适配层。

⚠️ 局限与风险

案例为制造业航空供应商，行业特定性强；跨系统直查 vs 用户"不直连数据库通过 API 查数"有架构差异（直查需数据库连接，API 查数需 API schema 理解）；本书 16 章为 book 而非论文，深度但非实验对比型；OpenAlex 无 Semantic Scholar 引用数据（8/26 新 preprint，引用数待核实预期为 0）。
