BIRD-History：历史 SQL 日志驱动的 Text-to-SQL 基准（业务逻辑/数据约定/分析实践知识标注）

2026-08-29 · arXiv
BIRD-History 是一个 history-driven text-to-SQL benchmark，针对现有系统在“用户查询隐含领域知识”（business logic、data conventions、analytical practices）时表现断崖的缺口设计。这些知识既不被 schema 捕获也不在 NL 问题中显式声明，但历史 SQL 查询日志是其宝贵来源。benchmark 含 1393 任务跨 11 库，每任务标注哪些历史查询含相关知识以及哪些 SQL 子句编码该知识。这填补了“标准 benchmark 精度高但真实业务场景断崖”的关键评测缺口。

MaP-SQL：用可复用结构化记忆替代 Listwise Selector 微调（NL→Schema/SQL/Output 三维记忆蒸馏）

2026-09-01 · arXiv
MaP-SQL 提出 fine-tuning-free 的 listwise selector：用从训练数据蒸馏的可复用结构化记忆替代微调选择行为。记忆编码 NL 如何映射到 schema elements、SQL operations、expected outputs 三维。给定新问题，检索相关记忆作为显式决策准则 listwise 评估候选查询，再用推理时重排序缓解定位偏置。这把 selector 从“学进模型参数的行为”变为“可跨问题复用的显式知识资产”。
🔍 技术视角：这篇论文是“把隐式选择能力外化为显式可复用记忆资产”的范式转移，与用户“业务知识库构建”方向高度契合。记忆的三维（NL→schema elements/SQL operations/expected outputs）正是用户宽表 API 场景所需：NL→API 字段语义/NL→API 操作语义/NL→API 返回结构。

Relational-Core Graph Analytics：列存关系引擎上的图查询（node/edge 属性图是性能税非更真实模型）

2026-09-01 · arXiv
论文论证图分析不需要专用图引擎：列存关系引擎（ClickHouse/Databricks Delta）前端配图查询语言（Cypher）可匹配甚至超越原生图引擎，且 scale 过内存图引擎崩溃点。核心论点：node/edge 属性图非更真实的连接数据模型，而是关系表已有关系的重编码，查询时重建是纯开销。ClickGraph/DeltaGraph 将 Cypher 直接翻译到原生关系 schema（表/列/外键如已存在）就地执行。

TIDE-Bench：对话式 Text-to-SQL 在 Chain Ambiguity 与 Intent Drift 下的评测

2026-08-30 · arXiv
TIDE-Bench 针对对话式 text-to-SQL 中“用户意图在多轮间展开与漂移”的评测缺口设计。两种模式：chain ambiguity（欠规范问题触发分层澄清含条件依赖）和 intent drift（用户撤回并替换已提交请求元素）。基于 514 anchor SQL 构造 1542 样本，引入 chain identification 与 drift recognition-resolution 专用指标，超越仅评 execution accuracy 的现有 benchmark。
🔍 技术视角：这篇论文直击用户业务场景中“对话式数据查询”的真实痛点——业务用户常先问一个模糊问题，再分层澄清，且会中途改主意。现有 text-to-SQL benchmark 只评单轮执行精度，完全错过对话状态管理这一业务系统精确查询的关键能力。

🎯 为什么值得关注

现有 text-to-SQL benchmark（BIRD/Spider）在标准任务上精度已达 80%+，但真实业务查询常因隐含领域知识而断崖。BIRD-History 首次系统化评测“历史查询日志作为业务知识来源”的能力，是用户“为何 benchmark 精度不等于真实业务效果”的硬论据，也为业务知识库构建提供了新数据源范式。

MaP-SQL：用可复用结构化记忆替代 Listwise Selector 微调（NL→Schema/SQL/Output 三维记忆蒸馏）

2026-09-01 · arXiv

📊 架构示意

🎯 为什么值得关注

现有 generate-execute-select 管线中 listwise selector 须微调，成本高且选择行为焊在模型参数中不可解释不可复用。MaP-SQL 把选择准则外化为结构化记忆，不仅免微调，更让选择逻辑成为可审计、可治理、可跨问题复用的知识资产——这正契合用户“业务语义理解”方向对“API 语义可治理”的要求。

⚙️ 核心机制

从训练数据蒸馏三维记忆：(1) NL→schema elements（问题映射到哪些表/列/字段）；(2) NL→SQL operations（问题映射到哪些 SQL 操作 join/group/filter）；(3) NL→expected outputs（问题映射到期望输出形状）。新问题来时检索相关记忆，记忆作为显式决策准则评估多个候选查询，推理时重排序缓解 listwise 定位偏置。

🧠 深度解读

核心创新在“记忆即决策准则”而非“记忆即检索增强”。与 8/27 Self-Optimizing Enterprise RAG+SQL 的“四能力统一自优化”互补——Self-Optimizing 把检索/Schema 翻译/事件图推理/模型路由统一进闭环，MaP-SQL 把选择准则单独抽为可复用记忆。两者都指向“把隐式能力外化为显式资产”。对用户宽表 API：NL→API 字段语义（哪些字段回答此问题）+NL→API 操作语义（调用哪些 API+参数组合）+NL→API 返回结构（期望返回哪些字段）三维记忆可直接迁移。

💼 商业启示

MaP-SQL 的“记忆即资产”范式把 AI 能力从“模型黑箱参数”变为“可治理知识资产”，这对企业 agent 投资决策意义重大——能力可审计、可移交、不绑死特定模型。三维记忆蒸馏为“业务语义理解”方向提供了工程化模板：把隐式 API 调用知识外化为结构化可复用资产。这与 8/29 dbt context gap 的“机器可读计算式治理”共振——治理对象从文档变为可执行记忆。

🛠️ 落地建议

用户可为高频业务问题构建三维记忆表：(1) 此类问题对应宽表 API 哪些字段；(2) 此类问题调用哪些 API+什么参数；(3) 此类问题期望返回什么结构。记忆存为结构化 JSON/YAML 而非微调模型。新查询来时先检索相似记忆作为选择准则评估候选 API 调用。这与 BIRD-History 的历史日志检索互补——BIRD-History 从行为侧，MaP-SQL 从知识结构侧。

⚠️ 局限与风险

记忆蒸馏本身需高质量训练数据，蒸馏质量决定上限。listwise 选择仍需多候选生成，成本非零。记忆维护有生命周期问题（业务逻辑变更时记忆需更新）。引用数待核实（Semantic Scholar 限流，9/1 新文预期 0）。定位偏置缓解是推理时策略，引入额外延迟。

TIDE-Bench：对话式 Text-to-SQL 在 Chain Ambiguity 与 Intent Drift 下的评测

2026-08-30 · arXiv

📊 架构示意

🎯 为什么值得关注

现有 text-to-SQL benchmark 评 execution accuracy（单轮正确性），但真实业务对话中用户意图在多轮间展开（chain ambiguity）与漂移（intent drift），这是业务系统精确查询分析的真实场景。TIDE-Bench 首次系统化评测对话状态管理能力，填补“单轮精度高但多轮对话断崖”的缺口。

⚙️ 核心机制

514 anchor SQL（源自 BIRD）构造 1542 样本。chain ambiguity：欠规范问题触发分层澄清，后续问题依赖前序澄清答案（条件依赖）。intent drift：用户撤回并替换已提交请求元素（如先问'按地区'再改'按产品'）。引入 chain identification（识别澄清链结构）与 drift recognition-resolution（识别漂移并重新解析）专用指标。

🧠 深度解读

与 BIRD-History（隐含领域知识）互补——BIRD-History 管“查询隐含什么知识”，TIDE-Bench 管“查询如何在多轮间演化”。两者共同指向“业务查询的非功能性维度比 SQL 生成更决定真实效果”。对用户宽表 API 场景：业务用户常先问模糊问题（'上个月销售情况'）再分层澄清（'按区域'→'华东区'→'不含退货'），且会改主意（'不对，按产品线'）。API 调用须维护对话状态：已确认的澄清参数+被撤回的参数。chain ambiguity 的条件依赖意味着不能独立解析每轮，须维护澄清上下文图。

💼 商业启示

TIDE-Bench 为企业 agent 投资决策提供了“单轮精度≠对话效果”的硬论据——业务用户不会一次问对问题，对话状态管理是业务系统精确查询分析的必备能力。这对用户“AI for 业务”转型是方法论提醒：评测不能只看单轮 SQL/API 调用精度，须评多轮对话状态管理。与 8/28 dbt context gap 的“agent 消费数据是连续非间歇”共振——连续消费意味着对话状态须跨轮维护。

🛠️ 落地建议

用户业务 Agent 须实现对话状态管理：维护已确认参数集+被撤回参数标记+条件依赖链。TIDE-Bench 的 chain identification 与 drift recognition-resolution 指标可作为内部评测套件设计模板。chain ambiguity 的条件依赖可用 8/27 DEW 操作型本体的“前置条件”机制治理——参数 B 的依赖参数 A 须先确认。

⚠️ 局限与风险

1542 样本规模适中，chain ambiguity 与 intent drift 的模式覆盖可能不全（真实业务对话更杂乱）。基于 BIRD anchor SQL 构造，可能继承 BIRD 的领域偏置。对话状态管理的工程实现复杂度高（状态序列化+条件依赖图+撤回回滚）。引用数待核实（Semantic Scholar 限流，8/30 新文预期 0）。

📊 架构示意

🎯 为什么值得关注

用户评估“语义层 vs 知识图谱”双路线，Cube 是语义层引擎的核心选项。连续两版密集修复是工程成熟度信号——尤其 window/aggregate 下推+nested join 折叠是查询性能，calendar/rolling_window/timezone 是时序正确性，refresh key cache 是缓存生命周期。这延续 8/24 v1.7.26 tesseract pre-agg+filter 注入→8/26-27 v1.7.27-29 SQL 下推+LRU 释放→8/28 v1.7.30 cold-cache 双竞态→今日 v1.7.31-32 window 下推+nested join 折叠+calendar 的可靠性链。

⚙️ 核心机制

v1.7.31：(1) cubesql push down window functions+multi-argument aggregates #11684——将窗口函数与多参数聚合下推到数据源执行减少引擎开销；(2) tesseract fold nested multi-fact join legs into one scan #11643——将多事实 join 的多腿折叠为单 scan 减少往返；(3) expression measures 排除 nested group merging #11707——防止表达式度量被错误合并进嵌套分组；(4) refresh key cache entries consistently #11607——延续 v1.7.30 refresh key cache identity 修复，确保缓存条目一致；(5) interval refresh keys 本地计算（flag）#11614——interval 类型刷新键本地计算减少数据源往返；(6) cubestore performance toggles 默认开启 #11600。v1.7.32：(1) tesseract calendar sql granularities 崩溃修复 #11709——calendar 日历粒度 SQL 致每查询崩溃；(2) grain.include compose rolling_window #11639——时间粒度 include 与 rolling_window 正确组合；(3) view raw time dimension timezone 仅转换一次 #11712——防止重复时区转换；(4) 保留 Interactive priority on user query paths #11715——用户查询路径保留 Interactive 优先级。

🧠 深度解读

三组共振：(1) window/aggregate 下推+nested join 折叠+interval refresh keys 本地计算=“计算下推减少引擎开销”共振（延续 8/27 v1.7.29 SQL pushdown 优先）；(2) calendar 崩溃修复+rolling_window compose+timezone 一次转换=“时序正确性”共振——calendar/rolling_window/timezone 是时间维度计算的三个 correctness 坑；(3) refresh key cache consistently+Interactive priority 保留=“生命周期正确性”共振（延续 8/28 v1.7.30 cold-cache 双竞态+refresh key identity）。对用户：Cube 作为语义层引擎的时序正确性（calendar/rolling_window/timezone）对业务指标计算（如“上月环比”“滚动 7 日均值”）是关键——时序错则指标错。window 下推对宽表 API 场景（窗口函数在数据源执行而非引擎内存）是性能关键。

💼 商业启示

Cube 连续两版密集修复延续语义层引擎从功能正确走向生命周期正确+时序正确性的工程化信号。这对用户“语义层 vs 知识图谱”双路线决策是工程成熟度数据点——语义层引擎（Cube）在时序正确性+缓存生命周期+查询下推上持续迭代，是生产可用信号。与 8/28 v1.7.30 cold-cache 双竞态+8/27 v1.7.29 LRU 释放形成“缓存/生命周期正确性”连续修复链——语义层引擎的可靠性是逐版本累积的。window 下推对宽表 API 查询性能有直接经济价值。

🛠️ 落地建议

用户选型 Cube 作语义层引擎时关注：window/aggregate 下推对宽表查询性能（窗口函数在数据源执行）；calendar/rolling_window 对业务时间指标正确性（上月环比/滚动均值）；refresh key cache 对缓存一致性（v1.7.30+31 两版修复 identity+consistency）；Interactive priority 对用户查询 vs 后台刷新的优先级隔离。若用户业务指标含日历粒度（周/月/季）或滚动窗口，v1.7.32 的 calendar+rolling_window 修复是必须升级版本。

⚠️ 局限与风险

calendar sql granularities 崩溃是严重 bug（每查询崩溃）——若用户业务指标含日历粒度且在 v1.7.31 以下须立即升级。rolling_window compose 是时间窗口计算正确性关键。timezone 一次转换防止重复转换致时区错。interval refresh keys 本地计算是 flag（默认关闭），需手动开启评估。cubestore performance toggles 默认开启可能有回归风险。两版发布间隔仅 1 天，稳定性需观察。

WrenAI wren-v0.13.4：查询路径安全化（只读 SELECT+autocommit+view 升级拒绝）

2026-09-02 · GitHub

📊 架构示意

🎯 为什么值得关注

用户“业务系统精确查询”方向关注写/读分离治理——查询路径须只读，写操作须走治理门。WrenAI v0.13.4 的只读 SELECT+autocommit+view 升级拒绝是查询路径安全化的三项关键：只读防误写，autocommit 防失败污染，view 升级拒绝防映射冲突。延续 8/26 #2668 fail loud+#2675 截断标注+#2657 宽小数位+#2676 关系键 fail-loud 线。

⚙️ 核心机制

七项修复：(1) 只接受只读 SELECT 语句 #2679——查询路径强制只读，非 SELECT 拒绝（防误写/恶意写）；(2) autocommit 防失败语句污染连接 #2683——失败语句不毒化连接状态，每语句独立提交；(3) 拒绝映射两个 view 到同一目标的 v1 view 升级 #2696——防 view 升级致映射冲突（两个 view 指同一目标）；(4) load_models 规范化 model columns #2614——model columns 名称规范统一；(5) 验证 imported query pair 字段类型 #2656——imported query 对的字段类型须一致；(6) fail loud on mdl.json #2668——mdl.json 解析失败大声报错非静默；(7) 截断值标注 skipped-row report #2675+保留 MySQL/Doris 宽小数位 #2657+非标量 model/view 名称验证错误 #2681（8/27 已收录故不重复但同版）。

🧠 深度解读

核心是“查询路径安全化”三原则：(1) 只读——只接受 SELECT，写操作在查询路径不可达（与 8/27 DEW 操作型本体的“命名动作+前置条件+写回源系统”写侧治理互补——DEW 管写侧治理动作，WrenAI 管读侧只读强制）；(2) 隔离——autocommit 防失败语句污染连接（失败不传播）；(3) 拒绝冲突——view 升级拒绝映射冲突（防两个 view 指同一目标致歧义）。这与 8/29 ERF-SQL 的“Policy-Aware Query Guard 执行前重写 AST 强制行级访问”+8/27 GRID 的“RBAC 编译进文法 mask 层不可达”共振：三者都在说“安全在路径层强制非依赖模型遵从”，但 WrenAI 是“只读强制+隔离+拒绝冲突”最简形式。对用户：业务 API 查询路径须只读强制（防 agent 误写），调用失败须隔离（autocommit 防毒化），view/字段映射冲突须拒绝（防歧义）。

💼 商业启示

WrenAI v0.13.4 的查询路径安全化三原则（只读+隔离+拒绝冲突）是企业 agent 调用业务 API 的安全治理最低标准。这对用户“业务系统精确查询”方向是工程模板：查询路径只读+失败隔离+映射冲突拒绝。与 Cube v1.7.31-32 的“生命周期+时序正确性”形成语义层引擎两面——Cube 管运行侧正确性，WrenAI 管定义侧+查询路径安全化。两者都是语义层引擎从功能正确走向安全隔离的工程化信号。

🛠️ 落地建议

用户业务 Agent 调用宽表 API 须：(1) 查询路径只读强制——只接受查询类 API 调用，写类 API 走治理门（类似 WrenAI 只读 SELECT）；(2) 调用失败隔离——单次调用失败不毒化后续调用状态（类似 autocommit）；(3) 字段/view 映射冲突拒绝——同一业务概念映射到多个 API 字段/view 须拒绝并报错（类似 view 升级拒绝）。fail loud on mdl.json 对用户 API schema 定义文件有参考——解析失败大声报错非静默。

⚠️ 局限与风险

只读 SELECT 是查询路径限制，不影响 WrenAI 的写能力（写走其他路径）。autocommit 是连接级隔离，跨连接的事务一致性需其他机制。view 升级拒绝是 v1→v2 迁移保护，新部署无此问题。fail loud 增加配置错误暴露但可能增加噪音。截断值标注+宽小数位保留是数据保真。非标量名称验证是定义侧质量。版本号 0.13.x 表明 WrenAI 仍在快速迭代期。

⚙️ 核心机制
