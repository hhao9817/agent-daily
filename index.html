VAKRA：首个评测 API+知识检索 multi-hop 推理的企业 Agent 基准

2026-08-14 · arXiv (cs.AI)
VAKRA（Evaluating API and Knowledge Retrieval Agents）是首个同时评测结构化 API 推理与文档知识检索的基准：8000+ 可执行 API×62 域，任务跨三档难度（多样 API 交互风格→multi-hop 跨 API 推理→带自然语言 tool-use policy 约束的多源推理）。正确性通过 re-executing 预测的 tool calls 对照 live API 验证，允许多条合法路径。用固定 ReAct harness 隔离模型能力与 agent 架构后，评测前沿与开源权重模型发现：最佳模型 single-hop endpoint-style 任务仅 70.4%，multi-hop+policy 约束下骤降。
🔍 技术视角：VAKRA 直击用户「通过业务 API 查数」场景的核心评测空白——既有 benchmark 要么只测 SQL（BIRD/Spider），要么只测检索（BEIR），而真实业务 agent 必须跨 API+知识库联合推理。用固定 ReAct harness 隔离 agent 架构变量是关键设计——让你看到的是模型在 multi-hop 下的真实衰减，而非 harness 工程的差异。re-execute 验证（而非字符串匹配）是生产级评测的必备范式。对企业落地最硬的信号：single-hop 70.4% 意味着每 3 个简单 API 调用就有 1 个出错，multi-hop 衰减更意味着链式调用可靠性呈乘法下降——这正是用户上百字段宽表 API 精准调用痛点的量化镜像。

EnterpriseRAG：揭示企业级 RAG 的 57 点编排鸿沟

2026-08-14 · arXiv (cs.AI)
EnterpriseRAG 基准揭示企业 RAG 部署的关键可靠性鸿沟：LLM 满足 80% 的单项约束，但仅 26.8% 的回复同时满足所有要求——57 点的 orchestration gap。现有基准假设干净检索+简单查询，无法捕捉生产条件（噪声文档+多维约束共存）。基准含 983 专家验证样本×6 域，系统模拟三种此前缺失的失败模式：检索噪声、知识缺口、事实冲突，叠加复杂指令。13 个 SOTA LLM 评测揭示严重的 instruction adherence collapse——高单约束满足率掩盖了低整体合规。知识缺口和事实冲突下，even reasoning-enhanced 模型也暴露深层障碍。
🔍 技术视角：EnterpriseRAG 的 57 点鸿沟是本周对企业 RAG 最硬的量化打击——它证明了单点能力不等于系统可靠。这与 VAKRA 的 multi-hop 衰减、Deployment Reliability 的 leaderboard 不可信形成三联证：企业 agent 的瓶颈不在模型单项能力，而在多约束联合满足的编排层。对用户课题的直接启示：你的业务 agent 查宽表 API 时，每个字段语义理解对了不等于整条查询结果可信——多维约束（字段语义+业务规则+权限+时效）的联合满足才是生产级可靠。reasoning-enhanced 模型在知识缺口/事实冲突下也崩塌，意味着堆更大模型无法解决编排鸿沟，必须建编排层。

Guided Table Retrieval：四阶段管道用确定性+LLM 分工规避端到端脆弱性

2026-08-14 · arXiv (cs.DB)
Guided Table Retrieval 提出四阶段管道解决结构化数据搜索中的表识别+join 问题：①确定性 hash-based 预测器 grounding；②join-graph 可达性的结构探索；③LLM 驱动的 source/target 消歧；④算法化合并为最小拓扑有序 join tree。通过把问题分解为确定性/覆盖/语义推理/连贯性四阶段，规避了端到端 LLM 方法的脆弱性，在 LLM 判断最有价值处利用 LLM。在 BIRD-DEV 达 94%、BEAVER（企业级）达 70% 精度。
🔍 技术视角：Guided Table Retrieval 的四阶段分工（确定性 grounding→结构探索→LLM 消歧→算法合并）是本周对 API/表选择最务实的架构范式。它与 MDB-Link（多库 schema linking）、Rosetta（值反推列语义）形成递进：Rosetta 解决字段语义、MDB-Link 解决跨库选库、Guided Table Retrieval 解决跨表 join 路径。对用户上百字段宽表 API 的启示：宽表 API 虽然字段多但通常单表，而四阶段可迁移为宽表字段子集选择——hash 确定性定位已知字段→结构探索发现字段间依赖→LLM 消歧语义模糊字段→算法合并为最小查询投影。

Deployment Decision Reliability：Agent leaderboard 排的是专精不是能力

2026-08-14 · arXiv (cs.AI)
论文用 Generalizability Theory 四 facet 方差分解证明：在三个开源 agent-trace benchmark（TheAgentCompany、τ²-bench、AppWorld）上，agent 主效应仅占 <3% 总方差，而 agent×task 交互占 7-23%——leaderboard 排的是专精不是能力。三种估计器（Henderson Method-I/REML via lme4/Bayesian binomial GLMM）一致到小数点后三位。最难任务 quartile 上 Eρ² 从 0.752→0.000（可靠性完全崩塌），训练 cell 可靠性与 held-out 可靠性负相关（r=-0.90）。
🔍 技术视角：这是本周对 agent 评测方法论最颠覆性的发现——它证明当前所有 agent leaderboard（包括 VAKRA/EnterpriseRAG 的排名）本质上排的是在某任务集上的专精而非通用能力。agent 主效应 <3% 意味着换 agent 对结果的影响远小于换任务。对用户课题的启示：你在选 agent 框架/模型时，不能信任通用 leaderboard 排名——必须在你的真实业务任务集上做 Generalizability Theory 方差分解，看 agent 主效应占比。最难任务 quartile Eρ²→0.000 意味着难任务上排名完全不可靠。

TDS：用 Google OKF 让 LLM 间共享预 tokenize 的 token array，TTFT 降 28-37%

ODI 的核心论点是开放 by design——跨引擎/catalog/BI/LLM 的可移植性。这与语义层的厂商中立诉求（Apache Ossie）共振。1/3 数据在用+半数黑暗是最硬的商业论据——它证明 AI 的瓶颈不在模型而在数据可达性。dbt 的战略是把合并后的 Fivetran（运动）+dbt（转换）+metadata+activation 打通为连续体，这直接对标用户业务知识库→业务语义理解→业务系统精确查询的三层需求。Iceberg 作为中性 substrate 让数据存一次到处可用，语义层则让业务语义定义一次到处可查——两者哲学同构。
