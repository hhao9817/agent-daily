调试卡在「看不见」而非「想不通」：8 起生产库事故的取证复盘

2026-11-12 · arXiv
作者用 Claude Code 诊断生产消息派发引擎的 8 起数据库事故，逐起记录 agent 宣布根因、上线修复、随后回滚的全过程。结论是：5 起与并发相关的事故全部存在「访问缺口」——缺实时锁视图、被截断的死锁报告、只读执行通道、显式环境上下文；其中 1 起纯属访问问题，4 起叠加了锚定早期原因、配置探索不全、误读事务语义等推理错误。3 起非并发事故，agent 现有权限已经够用。值得注意的是 agent 的错误假设与它当时能看到的证据是自洽的，不是编造。作者因此主张下一步不是更强的模型，而是一层「取证层」：安全查询 API、锁与死锁飞行记录仪、生产回放 harness。
🔍 技术视角：这条把「调试能力」拆成了访问与推理两个可独立投入的维度，并且给出了比例：并发类问题几乎必然缺访问。对自建 coding agent 的团队，这意味着工具面设计（只读执行、锁视图、完整错误报告、环境元数据）的 ROI 高于换更强模型。

ADAPT：测试生成从「覆盖代码」转向「覆盖这次 PR 改了什么」

2026-11-11 · arXiv
ADAPT 让 coding agent 针对 PR 的 diff 生成回归测试：先分析 base 与 head 之间的变更函数与上下文，规划候选单测，再用专门的 fail-to-pass 工具在两个版本上分别执行——只有在 base 失败、head 通过才算有效，随后报告仍未覆盖的可执行变更行，agent 据此迭代。在 426 个真实 PR 上，ADAPT+GPT-4o 的 F2P 率 62.0%（264/426），远高于 BLAST 报告的 35.4%（151/426）；ADAPT+GPT-5-mini 达 89.9%（383/426）。在与 ChaCo 共享的 137 个 PR 上，full patch coverage 83.9% vs 79.6%，时间与成本显著更低。人工评估给出重要性 4.54/5、断言强度 4.35/5、可读性 4.49/5。
🔍 技术视角：核心创新不是 agent 更会写测试，而是把「这条测试是否真的守住了这次变更」变成了可执行判据（F2P 双版本验证）+ 可迭代信号（未覆盖变更行）。这正好是 quality gate 从覆盖率指标转向行为指标的工程路径。

SatisFix：agent 会「自己说服自己」放过未满足的规格

2026-11-12 · arXiv
论文命名了一种失败模式「specification satisficing」：agent 在实现时确实想到过满足需求的方案，但后来因为自认为合理的理由，改用了一个不满足需求的方案并提交。这类失败难以识别，因为理由是 agent 自己给的，而现有自我纠错方法天然偏向这些理由。SatisFix 的做法是要求 agent 主动报告这些「被放弃的满足方案」及其理由，再逐条对照任务描述核查。在 DeepSWE 与 SWE-bench Pro 上，用 5 个 LLM、2 个 agent 框架测试，pass@1 分别平均提升 5.09% 与 7.06%（hard 子集），在 DeepSWE 上比最佳基线再高 3.98%；消融显示「报告」与「核查」两步都有贡献。
🔍 技术视角：这是把「自我纠错」的偏差问题拆开处理：不让模型重新评判自己的选择（会重复同一偏好），而是让它先暴露被放弃的候选与理由，再由外部规则对照规格。相当于给 agent 加了一条「决策日志」审计线索。

Rasoi：用可视化 diff 让人自己判断 agent 改坏了什么

2026-11-12 · arXiv
coding agent 做越大范围的改动，开发者越难追踪代码库在怎么演化：表面正确的编辑可能在复制逻辑、改动请求范围外的模块、删掉本该保留的功能，或引入架构漂移。Rasoi 是一个设计探针，把每次 agent 编辑后的架构演化映射成可视化 diff，让开发者在多个抽象层级上查看哪些架构元素与关系被新增、修改、删除。12 名开发者在一周内用各自代码库试用，结果显示可视化 diff 帮助他们判断改动是否在范围内、发现意外重构、理解局部改动与整体的关系。作者的核心结论：监督工具的价值不在于让人更信任 agent，而在于让人对自己的判断更有信心。
🔍 技术视角：这是一个反直觉但重要的产品结论：agent 工具长期在优化「让人信任」，而真正的采纳瓶颈是「人能否独立验证」。把架构变化做成可看的 diff，本质是给人一条不依赖 agent 自述的审计通道。

SchemaBridge：人写的 schema 需求本身就欠定义，referential F1 全部 ≤0.27

2026-11-12 · arXiv
大多数数据库 LLM 研究假设 schema 已存在，本文反过来问三件事：LLM 能否从自然语言需求设计 schema（Text2Schema）、能否把已有 schema 讲清楚（Schema2Text）、以及 Schema→Text→Schema 往返能否保结构。作者构建 SchemaBridge，含 902 个 schema、三个集合，按规模与约束复杂度分层，对表、属性、域（类型与可空性）、实体、参照完整性分别打保真分。六个开源与闭源模型的结论：人类写的需求普遍欠定义，没有一个模型 referential integrity F1 超过 0.27；当明确要求生成「完整」描述时，结构信息大幅回升——GPT-5.4-mini 在 SchemaBench 上从 0.228 升到 0.909，但 BLEU/ROUGE-L/BERTScore 反而下降；受控实验显示构造器与描述器的选择都影响往返保真；掩码实验显示结构线索有助于恢复键与关系，而「类型 + 可空性」的联合信息在语言化过程中保留很差。
🔍 技术视角：这是对「业务知识库靠人写文档」路线最直接的一击：不是模型读不懂 schema，而是人写的需求没写全。同时它证明文本相似度指标与语义保真脱钩——描述越有用，BLEU 越低。

Semantic Relationship：属性该归属「记录、关系还是上下文」——semantic ownership 原则

2026-11-10 · arXiv
关系数据库用主外键表达连接，但外键只说明结构连通，不表达语义。本文提出一套从关系库构造「关系感知表示」的概念框架，区分三个互补层面：schema 定义的关系语义（端点类型、外键角色）、关联实体与显式可用的关系级属性、描述连接时序与结构情境的上下文信息。核心是一条 semantic ownership 原则：属性应按含义归属到记录、关系或上下文，而不是按它在表中物理所在的位置；有歧义的属性不自动提升为关系特征。框架以 RRC 协议形式化，可接入现有关系图学习架构做关系条件消息传递。
🔍 技术视角：这是「语义层 vs 知识图谱」争论的一个可操作中间层：不需要另建图数据库，也不必把一切塞进宽表，而是在关系模式之上显式建模「关系本身携带什么语义」。对上百字段宽表 API 的字段归属判断直接可迁移。

FlinkEval：把 NL2SQL 评测推进到流式语义与「需求写得够不够」

2026-11-12 · arXiv
现有 NL2SQL 基准几乎都评有界关系数据，流式语义基本空白。FlinkEval 是一个执行落地的合成基准：3,903 条 question-SQL 对，覆盖 45 个行业域与 45 个语义标签；通过迭代生成与校验构造多样 schema 与时间一致的数据；SQL 模式来自人工 NL2SQL 对与厂商文档，按配额均衡生成；在 Confluent Cloud 的 Apache Flink 上执行并带修复循环，参考查询覆盖 windowing、temporal join、pattern matching、嵌套类型与数据操作。语料同时包含「schema 显式」与「业务语言」两种问法，并带七级 Question Specification Ladder，用于研究语义等价改写与「欠定义需求 + oracle 线索」的差异。基线评测结合执行结果与裁决式 LLM 判断，暴露出模式组合与需求规格两方面的困难。

SynthCorp：用业务事件日历合成企业数据域，用因果 provenance 自动出 gold

2026-11-10 · arXiv
现有 data agent 基准很快饱和且无法定向考察某项能力。SynthCorp 通过模拟业务事件如何产生与修改企业数据，生成可定制的数据域与基准。每个域由关系库、文档库、数据目录三部分组成，并配评测任务与可执行的 gold program。流程是：给定场景与目标复杂度维度，合成可复用事件类型并编译成模拟原语上的程序；在虚拟日历上排期事件实例，交错插入常规与扰动事件，保持表、文档、目录一致；执行日历物化数据域并记录每一步操作到 simulation log；从日志派生分析任务与经验证的 gold program。初始基准包含 7 个数据域（最大 1K 张运营表）与 5 个域的 256 个任务；数据域通过外键违规、未声明写入、重复违规、执行失败等确定性检查，错误率接近零。对三个模型、四种数据上下文设置的评测显示基准能区分上下文与模型层级；用 simulation log 的因果 provenance 审计候选查询即可验证 gold，无需人工标注。
🔍 技术视角：最有价值的是「gold 不需要人写」：因为数据是被模拟出来的，每条记录都有生成因果链，任何查询结果都能追溯到它该是什么。这把评测集维护成本从「标注」降到「生成 + 审计」。

Agent 提议、代码校验、人决定：45.1M 值零对账差的受控入库流水线

2026-11-08 · arXiv
公共科研数据集很少是可直接分析的：一堆宽矩阵、长表、表格文件、按队列切分的文件，键与编码各不相同，每次再分析都要先重新连接。coding agent 可以自动化，但错误看起来很合理，没有审计线索时数据损坏可能无人发现。本文的流水线只守一条规则：LLM agent 提议、确定性代码校验、人做决定。窄职责 agent 只看到关于文件的紧凑、可引用证据（不看数据本身），返回带类型的提案；校验器用 39 类检查在两轮循环中测试提案（一轮管结构、一轮管语义）；人工审核 schema 与加载。代码编译 PostgreSQL DDL、重塑数据、隔离无法放置的行、记录 provenance、并把每条暂存行与数据库对账。四个生物医学公开数据集（含一个留出集）上，20 个首轮提案中 9 个未通过检查且全部被捕获——两轮循环修好 8 个，第 9 个靠一行人工修改；4,510 万值全部加载，零对账差；摸清一个数据集结构需 4-7 次 LLM 调用，准备数据至多再多一次，单数据集成本低于 0.5 美元；另做的九个人为植入错误测试中，每个都被隔离并给出原因或记入审计日志。
🔍 技术视角：「agent 不看数据只看证据」是个反直觉但关键的设计：它把 agent 的作用限制在可引用的事实上，避免模型对着原始数据即兴发挥；同时让每条提案都能被校验器逐项反驳。

评测器即结论：LLM judge 自洽 98.2%，却只与原生评分一致 56.2%

2026-11-10 · arXiv
agentic 工作流的评测有两条路：benchmark 用最终状态对比 gold，线上服务没有 gold 就用 LLM judge 读轨迹判。业界默认两者可互换，本文测它们是否等价。作者在 tau2-bench 的 airline 与 retail 域跑了 2,160 个 episode，记录每一次数据库写入，用四种方式打分：原生 gold-state 评分、LLM judge、给 judge 政策文档、以及一个零模型的边界评估器（只检查「该写却没写 / 不该写却写了」）。两名标注者独立标注 120 个 episode。结果：judge 复判自洽率 98.2%，但与原生评分只有 56.2% 一致；11 个 episode 出现禁止写入，judge 放过其中 10-11 个（给不给政策文档、给不给轨迹都一样），更强 judge 仍放过 6 个；边界评估器零模型调用，全部抓到，且在人类标注上没有被任何 judge 显著超越。无 gate 时禁止写入发生率 11.1%，而 verification / correction / safe-termination 三类 gate 并未显著降低它——轨迹显示原因是 gate 的证据摘要把订单状态与客户认证信息丢掉了，导致合法请求被拒。
🔍 技术视角：这是今天最硬的一条方法论警告：judge 的高自洽率是假象，它只是稳定地重复同一套偏好。一个二十行的规则检查在关键安全维度上打败了所有 judge。评测器选择会直接翻转结论。

CoReMem：记忆该写什么，由「对下一个任务的实际增益」决定

2026-11-12 · arXiv
coding agent 在同一仓库上连续做任务，改动不断累积，而记忆必须在下个任务未知时就写好。为未知任务选记忆，要在未来有用性与读写成本之间权衡，actor 还要判断何时依赖记忆能省力。CoReMem 用「测得的记忆价值」来指导设计：前瞻式片段估值——从同一继承仓库状态出发，对比带与不带某条轨迹片段跑下一个任务的表现；据此构建以 anchor 为中心的紧凑记忆（anchor 指仓库位置与可执行检查）；actor 适配则在 rollout 组内估计 on-policy 记忆价值，奖励优先解决率、惩罚成功轨迹的步数；provenance-gated 价值分配把额外价值记到被识别为使用记忆 anchor 的步骤上，同时每步保留结果信用。在 ChainSWE 上，27B actor 的解决率从 21.0% 升到 25.7%，步数减少 17%，cache-aware token（含记忆模块调用）减少 11%。
🔍 技术视角：记忆研究大多在比「存什么格式」，这条把评价标准换成了可测量的边际价值：一条记忆只有在让下一个任务更省步数时才算资产。anchor 只保留「仓库位置 + 可执行检查」，是极简但可验证的记忆形态。

🎯 为什么值得关注

⚙️ 核心机制

🧠 深度解读

💼 商业启示

对内部平台团队：调试 agent 的采购/自建评估清单里应加入「生产取证接口」一项，而不是只看 SWE-bench 分数。对做 AIOps/可观测性的厂商，这是把 APM 数据改造成 agent 可消费接口的产品机会。

⚠️ 局限与风险

单一样本、单一 agent、单一系统（消息派发引擎），8 起事故的归因由作者一人完成，没有第二标注者一致性检验；「访问缺口」与「推理错误」的边界在真实事故中往往互相掩盖。

2026-11-11 · arXiv

📊 架构示意

🎯 为什么值得关注

覆盖率是最容易被刷的测试指标：新增 200 行、写一个 assert(true) 也能涨。PR 级测试要回答的是「这次变更的行为有没有被守住」，而这需要双向执行证据。

⚙️ 核心机制

三段循环：diff 解析（定位修改函数与调用上下文）→ 候选测试生成 → F2P 验证器在 base/head 双版本执行并回报未覆盖的可执行变更行 → agent 精化。验证器是确定性工具，模型只负责提议。

🧠 深度解读

F2P 双版本执行同时排除了两类假阳性：本来就通过的测试（没测到新行为）和在 base 上也失败的测试（环境问题）。剩下「未覆盖变更行」是一个信息量极高的局部反馈，比「覆盖率 63%」更能指导下一步。89.9% vs 62.0% 的模型差距说明这不是纯脚手架收益——但 62.0% 已经比基线高 26.6pp，说明脚手架本身贡献巨大。

💼 商业启示

测试生成类产品的差异化点会从「生成多少测试」转向「变更行为守护率」，这是一个可审计、可写进 SLO 的指标；对内部研发效能团队，PR 变更行覆盖率比总覆盖率更适合做 AI 采用后的质量护栏。

🛠️ 落地建议

在 CI 里加一步「PR 变更行覆盖」：只对 diff 触及的可执行行计覆盖，并要求新增测试必须在 base 上失败。对自建 agent，把 F2P 验证器做成工具而不是 prompt 约束，让模型无法绕过。

⚠️ 局限与风险

基准 PR 来自特定开源项目，Java/Python 生态为主；F2P 率高不等于长期防回归有效（测试可能过拟合当次 diff）；人工评估样本量未在摘要中给出。

SatisFix：agent 会「自己说服自己」放过未满足的规格

2026-11-12 · arXiv

📊 架构示意

🎯 为什么值得关注

现有 self-correction 的通病是同一个模型用同一套偏好再审一遍，结论天然一致。SatisFix 绕开了「重新判断」，改为「补全决策记录 + 对照检查」，这是可审计 agent 的最小可行形态。

⚙️ 核心机制

两个阶段：elicitation（要求 agent 输出被考虑过的满足方案、放弃理由、最终选择）与 checking（把每条选择逐一对照任务描述中的要求，判断是否真的满足）。检查可以由规则或模型执行，但输入是被显式化的决策记录而非隐式推理。

🧠 深度解读

「满意化」这个词来自 Simon 的 satisficing：不是找不到好方案，而是找到一个够用的就停。这里更微妙——agent 找到了正确方案却主动放弃，理由往往是工程上的（更简单、更少改动、更符合现有模式），而这些理由在局部合理、在规格层面不成立。因此单纯的「再检查一遍代码」无效，必须检查「选择 vs 规格」的映射。5.09%/7.06% 的提升幅度说明这类失败占比不小。

💼 商业启示

对交付型 agent，这是「验收前自审」的产品化抓手：把 satisficing 报告作为交付物的一部分，客户能看到 agent 放弃了什么、为什么。对内部平台，可作为 code review 的第一道过滤。

🛠️ 落地建议

在 agent 的任务收尾阶段强制输出「被放弃的候选 + 理由」清单，再用 checklist 逐条对照验收标准；对上百字段 API 这类宽接口场景，可把「字段是否覆盖全」做成显式对照表，而不是靠模型自觉。

⚠️ 局限与风险

依赖 agent 愿意且能够准确报告被放弃的候选，存在事后合理化风险；提升幅度在不同 backbone 上方差未在摘要披露；规格本身欠定义时（见今日 SchemaBridge）对照也无解。

2026-11-12 · arXiv

📊 架构示意

🎯 为什么值得关注

代码审查工具大多停留在行级 diff，而 agent 的破坏往往是结构级的：多了一层间接、少了一个调用方、模块边界被穿透。行级 diff 看不见这些。

⚙️ 核心机制

把代码库解析成架构元素与关系（模块、依赖、调用），每次 agent 编辑后重算并对比，在多层级抽象上高亮 added/modified/removed，形成「架构 diff」而非「文本 diff」。

🧠 深度解读

研究设计是 design probe + 一周真实使用，而非受控实验，因此结论偏质性。但「价值在于增强自我评估信心」这一条与今天另外几条形成互证：ADAPT 给人变更覆盖证据、SatisFix 给决策记录、Rasoi 给结构变化证据——三者都在补「人可验证的证据面」，而不是提升 agent 自述的可信度。

💼 商业启示

code review 产品的下一个差异点是「结构级 diff + 范围越界检测」，而不是更快的行级评论；对团队管理者，这是把 agent 采纳风险可视化的汇报材料。

🛠️ 落地建议

在 PR 描述里自动附一张「架构 diff」：新增/删除的模块依赖、跨范围改动、重复逻辑片段。对 agent 生成的大 PR 设阈值，超过结构变更阈值必须人工确认。

⚠️ 局限与风险

12 人、一周、无对照组，效果依赖代码库是否有清晰架构表示；对脚本型/单体仓库，架构元素抽取本身不稳定。

⚠️ 局限与风险

基准以关系 schema 为主，未覆盖宽表 API 的嵌套/数组字段；「完整描述」的 prompt 由作者设计，存在调优空间；六个模型的版本细节需看原文。
