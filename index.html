ERF-SQL: Beyond Benchmark Accuracy — Enterprise Deployment and Readiness Framework for Text-to-SQL

2026-08-27 · OpenAlex (IJARCCE 2026.15842)
论文指出企业试点 text-to-SQL 反复发现同一问题：Spider 85% 精度的模型仍被安全审查/审计/风控拒绝——生成的查询忽略行级访问策略、暴露脱敏列、schema 变更下静默崩溃、跑无界扫描、无证据链。作者论证问题是架构性非语言性：缺的不是更好的模型而是模型周围的系统，其中 vocabulary/policies/budgets 机器可读且强制确定性。ERF-SQL 系统：版本化语义契约成为 schema 与模型唯一接口；Policy-Aware Query Guard 在执行前重写每个候选查询的 AST；不确定答案路由到澄清或人工审查；行为按六就绪维度评分聚合为 gated Enterprise Readiness Index。EntSQL-450 评测套件含活角色策略+脱敏规则，四个生产 LLM 在 naive baseline 下相对 Spider 丢 19-23 精度点，实现 pipeline 恢复 13-16 点+执行前拦截 97% 不安全生成+漂移韧性 0.55→0.86，约 0.9s 延迟代价。
🔍 技术视角：这是用户"业务系统精确查询"课题的最直接论文。ERF-SQL 的'版本化语义契约= schema 与模型唯一接口'与用户的'通过业务 API 查数非直连 DB'约束完全同构——API schema/字段语义标注就是那个 versioned semantic contract。Policy-Aware Query Guard 的 AST 重写对应 API 调用参数的确定性强制（行级访问策略=字段级权限治理）。EntSQL-450 的'活角色策略+脱敏规则'评测设计为用户立项提供评测方法论模板——必须在真实权限/脱敏下测非裸 Spider benchmark。97% 拦截率+0.55→0.86 漂移韧性是部署就绪可工程化测量的硬数字。与 8/28 dbt context gap 四因（不可靠 SQL/捏造指标/无护栏/成本失控）精确映射：ERF-SQL 的语义契约管'捏造指标'+AST guard 管'不可靠 SQL'+Enterprise Readiness Index 管'无护栏'。

Meta-Books: Restructuring Organisational Knowledge for Agentic AI Reasoning

2026-08-25 · OpenAlex (ECKM 2026)
论文指出组织持有大量 AI 系统无法作为知识访问的知识资本——手册/入职文档/流程文档/积累的专业知识在结构上与 AI 推理不兼容：无可遍历的依赖结构、无角色分类可遵守、无关系上下文可浮现。Meta-Books 作为知识管理设计回应：把常规组织文档转换为 typed 依赖链接知识图谱。源内容分解为五类 typed 知识对象——concept/procedure/example/controversy/reflective insight——由 prerequisite-of/illustrates/contradicts/applies-to 等语义边连接。每节点带教学元数据：depth layer/role classification/engagement time/prerequisite links。区别于 RAG 的是 meta-books 重构源内容本身让 dependency/context/role 对 AI 在推理点可见，支持跨源整合让知识节点跨文档迁移。

2026-08-25 · OpenAlex (ECKM 2026)

Cube v1.7.30: 冷缓存双重竞态 + refresh key cache 三 bug 修复

2026-08-28 · GitHub (cube-js/cube)
Cube v1.7.30（8/28）修复 query-orchestrator 冷缓存续期路径双重竞态 #11674。同日 #11607 修复 refresh key cache 三个长期 bug：(1) PreAggregationLoadCache memo 100% miss 四年——refresh key 查询用 H2=md5([sql,params]) 存但用 H3=md5([sql,params,options]) 查，options 移入 tuple 时只更新 store 侧（#3061 回归），memo 从未命中；(2) scheduler/loader renewal key ping-pong——cube refreshKey 与 pre-agg invalidateKeyQuery 同 SQL 时双方用不同 renewalKey 写同一 entry 互相标 stale 无限循环；(3) 跨引擎/数据源条目碰撞——identity=[sql,params] 缺 external/dataSource 维度，prod/staging/Cube Store 同 SQL 共享一个 entry 谁先跑谁 serve 所有。修复给 refresh key 一个身份 [sql,params,!!external,dataSource||'default'] 一处计算（QueryCache.refreshKeyIdentity）一处应用（cacheRefreshKeyResult）。
🔍 技术视角：这是语义层引擎缓存基础设施的正确性修复，与 ERF-SQL'版本化语义契约为唯一接口'共振——Cube 的 refresh key cache identity 修复与 ERF-SQL 的 semantic contract versioning 都指向同一原则：缓存/契约的身份必须确定性可计算。'跨数据源/引擎共享 identity 是 bug 非特性'对用户上百字段宽表 API 场景直接相关：API 调用缓存的 identity 必须包含数据源/引擎维度，否则 prod/staging 共享缓存是安全隐患。'memo 100% miss 四年'警示：缓存正确性的回归可能长期潜伏——与 8/24 Deterministic Reproducible Wrong'自研评分器制造伪发现'共振：基础设施 bug 可能系统性制造伪结果。'ping-pong renewal'与 8/27 Cube v1.7.29 LRU 驱逐 orchestrator 释放 #11661 共振：两者都修缓存生命周期的竞态。

Why Your AI Pilot Stalled at the Context Gap (dbt Blog)

2026-08-28 · dbt Blog
dbt 指出 agentic AI 项目卡在 pilot 阶段的根因是 context gap——AI agent 被剥夺了做明智决策所需的治理上下文。四种常见失败：(1) 写不可靠 SQL——语法对但选错值；(2) 捏造或误读指标定义——无足够上下文用 stale/missing/fabricated metrics，缺 review 加剧；(3) 无护栏无审计链——无辅助过程检查 agent 工作，无记录可验证结论如何达成；(4) 计算成本因低效工作上升——agent 用更多计算完成任务吃掉利润。解法是机器可读计算式治理非大文档——'历史上数据消费者是人，现在变 AI agent'。dbt+Fivetran 合并交付 trusted Open Data Infrastructure for AI at scale。
🔍 技术视角：这是 ERF-SQL'问题架构性非语言性'的商业版本——dbt 用四种失败模式把'context gap'具象化。'不可靠 SQL 选错值非语法错'对用户上百字段宽表 API 场景直接相关：字段名相似的宽表 API 下 agent 选错字段比语法错更危险。'捏造指标定义'与 ERF-SQL'版本化语义契约为唯一接口'共振：指标定义必须版本化机器可读。'无护栏无审计'与 ERF-SQL'Policy-Aware Query Guard+Enterprise Readiness Index'共振。'计算成本失控'与 8/17 TDS Autoscaling'agentic traffic 打破两代 autoscaling'共振。'消费者从人变 agent 改变治理要求'与 8/14 Never the Number'消费者是 agent 非人时可靠性先于准确率'共振——三角共振指向同一范式转移。

Human-in-the-Loop Without Killing Throughput (TDS, 8/28)

2026-08-28 · Towards Data Science
作者分享真实 text-to-SQL agent 部署案例：三周后有人让 agent'clean up test rows in promotions table'，agent 理解'clean up'为 DELETE，因非 SELECT 已 gated HITL 被拦截。泛化'非 SELECT 走 HITL'gate 的失败模式是 rubber-stamp fatigue——中位审批等 15 分钟+审查者批量 skim 5-6 查询+第三周开始盲批。作者团队改为风险路由：四信号评分——(1) blast radius 真实行数非 EXPLAIN 估算（planner 估算在倾斜列/相关谓词下不可靠）；(2) table sensitivity 静态 allowlist（billing/auth/监管留存表有 floor risk score）；(3) semantic distance 与已批准查询 embedding 距离（与 50 条已批准相似 vs 语义新颖不同风险）；(4) resamples 一致性（非 token confidence，LLM 对自身不确定性校准差）。阈值下立即执行，阈值上走 ticket 模型非 hang。
🔍 技术视角：这是用户'业务数据可信度验证'方向最直接的工程实战。四信号风险路由对用户上百字段宽表 API 场景直接可迁移：blast radius 改为'API 返回行数+字段数'，table sensitivity 改为'业务域 allowlist'，semantic distance 改为'与历史已批准 API 调用 embedding 距离'，resamples 一致性改为'多次采样 API 参数一致性'。'rubber-stamp fatigue'是泛化 HITL gate 的必然失败模式——与 8/27 DEW'agent 与人走同一治理门'形成张力：DEW 要 agent 主动查询而非被动依赖检索触达，TDS 要风险路由非泛化 gate。'LLM 对自身不确定性校准差故不用 token confidence 用 resamples'与 8/21 TDS Bayesian Guardrails'point estimate 让模型显得比实际更确定'共振：两者都指出 LLM 自评 confidence 不可信。'EXPLAIN 估算不可靠改真实行数'对用户宽表 API 场景直接相关：API 字段基数估算在宽表下更不可靠。

Human-in-the-Loop Without Killing Throughput (TDS, 8/28)

2026-08-28 · Towards Data Science

📊 架构示意

🎯 为什么值得关注

真实 text-to-SQL 部署案例的风险路由工程实战，四信号设计可直接迁移到用户 API 查数场景。rubber-stamp fatigue 是泛化 HITL 的必然失败模式有警示价值。

⚙️ 核心机制

风险路由四信号：blast radius（真实行数非 EXPLAIN）+table sensitivity（静态 allowlist floor score）+semantic distance（与已批准 embedding 距离）+resamples 一致性（非 token confidence）。阈值下立即执行，阈值上走 ticket 模型。
