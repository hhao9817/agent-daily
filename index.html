SWE-Time：把"仓库演化"本身做成 benchmark，最强 coding agent 平均分仅 61.9

2026-11-09 · arXiv (cs.SE)
仓库级代码理解 benchmark 一路把推理范围从局部代码扩到整仓，却普遍把仓库当成静态快照。SWE-Time 把"演化"当作推理对象，设两个互补方向：回顾式（通过历史回归分析理解仓库怎么变成现在）与前向式（从变更前状态推断意图中的变更）。作者提出 RealWorld-to-Verifiable 构造框架，把真实开发者查询与历史证据转成可验证任务，在 65 个 GitHub 仓库、1,661 个用例上评测 15 个 coding agent。Claude Code 中 Claude Opus 4.8 取得最高 SWE-Time Avg. 61.9，作者称仍有大量提升空间；受控分析指向历史代码证据与开发者意图是主要增益来源，而跨仓库状态的一致推理仍很难。
🔍 技术视角：研发知识库如果只索引 HEAD，就只解决了空间维（文件→仓库），没解决时间维。SWE-Time 给出的信号很直接：模型缺的不是读代码的上下文窗口，而是"as-of 某一时刻的证据"——当时的 issue、当时的测试、当时的依赖版本。这正好是自建知识库相对 SaaS 的天然优势：你有完整 git/PR/CI 历史。架构上应把索引从"文件快照"升级为"变更事件流 + 可回放视图"，让检索支持 as-of 查询（某文件在某 tag/某 PR 前的状态）与回归证据（该行为曾被哪个测试覆盖、何时失效）。

Safe by Accident：LLM 写的数据库代码，54% 的"崩溃安全"是 sqlite3 借来的

2026-11-07 · arXiv (cs.SE)
现有对 LLM 生成代码的评测通常是"跑一次、在一个环境里、通过就算对"。作者在每次数据库、文件、邮件调用前注入崩溃并按运维方式重跑，同时在 Python sqlite3 的两种事务模式下判定结果：默认模式（库悄悄开事务）与 autocommit（不开事务）。在 10 个模型、24 个后端任务、9,100 份解法上，默认模式中"熬过全部崩溃"的数据库代码有 54% 在 autocommit 下留下半更新状态；这一现象跨所有模型存在，并藏在看起来像事务的 conn: 块里。告知模型连接处于 autocommit，对本地代码模型无效，对 API 模型可把不安全比例降 30 个百分点；明确要求崩溃安全对所有模型都有帮助，强模型几乎能全部改对，但常常"只有被要求时才写安全代码"。
🔍 技术视角：这条对 AI 测试自动化的杀伤力在于：它说明很多"通过率"度量的是环境属性而不是代码属性。只要被测代码依赖库的隐式行为（隐式事务、隐式重试、隐式回滚），换一个更严格的配置就会暴露。工程上应把"更严格配置下的第二遍测试"作为 AI 生成代码的准入条件，而不是可选项——这比再加 1,000 条单测更能抓住真实故障。

补丁正确性的五维证据框架：多写测试反而可能压低正确补丁保留率

2026-11-07 · arXiv (cs.SE)
自动程序修复（APR）与仓库级 coding agent 都以测试作为"补丁正确"的依据，但测试证据的强度差异巨大。作者提出五维证据画像与报告协议：测试来源与暴露度、行为范围、oracle 依据与依赖、执行完整性、标签裁定。审计数据集包含 39 份 benchmark/评测制品（32 项一手实证研究、1 份机构技术审计、6 个分类基线），对 33 项一手贡献按五维编码，核心区分是"修复搜索期可见的检查"与"留给最终评估的证据"。四组对照审计显示：改变候选集、oracle 规则或执行预算会改变报告的检出率；在固定预算下，追加测试既能暴露漏检 fault，也会误杀有效的替代补丁、降低正确修复产出。仓库级审计还把"问题复现"与"候选补丁区分"分开，把"自动差异检测"与"基于需求的裁定"分开。
🔍 技术视角：AI 代码审查/质量门禁最容易被忽略的一层是"oracle 是谁定的"。这份报告给了一套可直接抄的字段：这条测试是修复期就可见，还是最终评估才用？它检验的是行为范围还是仅复现 issue？执行是否被沙箱/超时/随机性污染？把这三问答清楚，比再堆一个模型更能提升结论可信度。

Let the Fixer Decide：按"fixer 需要读什么"训练代码定位器，少读 27.5% 代码

2026-11-09 · arXiv (cs.SE)
代码定位器通常被训练去预测"参考补丁改了哪些文件"，但 fixer 需要读的代码并不等于它最终改的代码。作者提出 Fixer-Guided Localization（FGL）：localizer 先给出若干个定位候选，用一个冻结的 fixer 为每个候选打"能产出可验证补丁的概率"，localizer 用这些分数做加权 SFT——不跑测试、不用强化学习。整条流水线构建在 Gemma 4 E4B 上，轨迹来自 1,629 条经测试验证的 Kimi K3 轨迹。FGL 目标让 fixer 找到 bug 的频率与教师定位持平，但少读 27.5% 的代码；开发集一轮 EM 后，更多任务产出补丁（53 vs 46）、更少卡在读取不存在的文件（43 vs 54）、解出更多任务（8 vs 6）；训练后 agent 探索量约为基模 3 倍、错误补丁显著减少，单 agent 最高解出 78 个任务中的 11 个（基模 8 个）。13 次评测分析指出 4B 模型在 8 分钟预算下的瓶颈是时间、重复循环与编辑质量。
🔍 技术视角：这条把"调试"重新定义成检索问题：agent 失败常常不是不会改，而是把预算烧在错误的文件上（54 次读取不存在的文件）。对自建 coding agent 的直接启示是——定位器的监督信号应该来自下游 fixer 的可解性，而不是上游 diff 的相似度；且"探索更多 + 错误补丁更少"说明好的定位目标能同时提升覆盖率与精度。

NIFT-SQL：用客户自己的问题训练表检索，complete@15 从 30.4% 提到 69.2%

2026-11-09 · arXiv (cs.DB / cs.CL)
企业 text-to-SQL 的第一步是找对表，而 schema 常跨多个库、包含数百张命名晦涩的表。论文问：只用表名、列名与声明的主外键，为每个客户单独训练模型，能否改善表检索？NIFT-SQL 把"在客户自有问题上微调的检索器"与"微调的 560M cross-encoder（逐表判断查询是否需要它）"做混合检索，再用 held-out 问题拟合 logistic 回归融合。在 BEAVER、LiveSQLBench、LiveSQLBench-Large（244-971 张表，四个 split、三次训练）上，complete@15 分别为 69.2%、89.5%、85.6%，混合检索基线为 30.4%、41.0%、21.8%，同样标签下微调检索器为 61.1%、81.7%、70.4%；用现成检索时未微调 cross-encoder 低 21 个点。零样本 8B reranker 无需标签，按库路由后在两个集合上与有监督方案无显著差异，把其分数作为两维融合特征可进入高精度模式（72.4%、92.5%、88.6%）。
🔍 技术视角：这是"每租户一个检索器"的实证背书，而且证据强度不低（三个 benchmark、四个 split、三次训练）。对自建业务的含义很明确：表级召回不该用通用 embedding 一次搞定，应该用该客户历史问题做轻量微调 + 逐表二分类，二者融合。更关键的是"500M 级 cross-encoder + 客户问题"这条路径成本极低，完全可以自建（对比之下，把宽表 API 的上百字段做成训练标签反而更难）。

SpecBridge：模型算得出两种口径，却只在 15-58% 的情况下都说出来

2026-11-03 · arXiv (cs.CL)
一个 text-to-SQL 答案可以跑通、返回一个看似合理的数字，却在算别的东西——当请求把计算口径留空（数行还是数去重实体），模型会自己悄悄选定一个。标准 benchmark 检测不到，因为每题只对照单一参考解释打分。SpecBridge 通过"只变口径"来测：对同一请求给三个版本（一个开放、两个各指定一种解释），用执行结果打分。数据库是真实的，口径选的是模型在现有 benchmark 上确实会失败的那些。204 条人工校验测试里，四个模型在被明确要求时通常都能算出每种解释，但面对开放请求只有 15-58% 会同时给出两种，且常常不提自己做了选择——差距在"报告"而非"计算"。benchmark 甚至会惩罚替代解释：BIRD 上口径改变答案的题里，被判错的答案超过五分之二在另一种解释下是对的。由于差距在报告层，不需要更强模型：先判定请求是否留下口径缺口，再分多次调用分别作答，在自有测试与 AMBROSIA 上把开放请求"全解释覆盖"提升 29-63 个百分点，且不降低清晰请求的精度，比追问澄清所需轮次更少。
🔍 技术视角：这条直接命中"业务数据可信度验证"：可信不是算得对，而是把不确定性显式交回。工程上可落成一个两阶段编排——先做歧义判定（是否留口径缺口），再对每种解释并行调用取数 API，最后在结果层做"多解并置 + 差异提示"。这比让模型输出置信度可靠得多，因为它把不确定性变成了可执行的分支。

GRIPS：grounding 错误是最大失败类别，且信息越多不一定越好

2026-11-02 · arXiv (cs.CL / cs.DB)
text-to-SQL 系统可能在生成 SQL 之前就失败：把问题中的 mention 链到了错误的表、列、值或关系，于是即使 SQL 合法也返回错答案。论文在 TempTabQA-C 与 BIRD 上审计 SQL Static 的失败，发现 grounding 错误在两边都是最大类别。作者提出 GRIPS（Grounding Representation and Input Processing for SQL generation），三阶段在生成前把结构化 pre-SQL 信息显式推导出来。在 GPT-5-nano 与 Llama-70B 上，GRIPS-Adaptive 在 20 个设置中 18 个优于 SQL Static，平均准确率 +11.8 个百分点，同时模型调用 token 减少 47.8%。受控分析显示：某些 grounding 信息确实能改善生成，但"增加更多 pre-SQL 信息"并不稳定增益；把"问题输入 grounding"与"SQL 生成"解耦后，系统更准、更省、更易诊断。
🔍 技术视角：这条对"宽表 API + 上百字段"的场景几乎是量身定制：字段语义标注的质量决定上限，而不是 SQL 写得好不好。更实用的结论是"解耦可诊断"——把 grounding 单独作为一步，失败时可以判定是"字段选错"还是"逻辑写错"，这与企业需要的可审计性直接对齐。

提议-验证-人决策：39 类检查兜住 agent 的"看起来很合理"的错

2026-11-08 · arXiv (cs.DB / cs.AI)
公开科学数据集很少是"可直接分析"的：它们以宽矩阵、长表、电子表格、按队列拆分的文件形式出现，键与编码各不相同。coding agent 可以自动化摄入，但其错误往往看起来合理，缺少审计线索时数据损坏可能无人发现。作者提出一条规则化的摄入流水线：LLM agent 提议、确定性代码验证、人类决策。窄 agent 只看关于文件的紧凑可引用证据、从不看数据本身，返回带类型的 proposal；验证器用 39 类检查在两个闭环（结构环与语义环）上验证，人类评审批准 schema 与加载。代码编译 PostgreSQL DDL、重塑数据、隔离无法归位的行、记录血缘，并把每条暂存行与数据库对账。在四份公开生物医学数据集（含一份开发期未见的留出集）上，20 个首版 proposal 有 9 个未通过检查且全部被捕获（闭环修复 8 个，评审一行修改修好第 9 个）；4,510 万个值全部加载、零对账差异；发现结构只需 4-7 次 LLM 调用，准备数据最多再加一次，单数据集成本低于 0.50 美元；另一组测试中 9 个植入错误全部被隔离并给出原因或写入审计日志。
🔍 技术视角：这是"企业级 agent 架构"的一个近乎教科书式的样板：agent 不碰原始数据（只碰可引用证据）、只输出有类型的结构化提议、验证器是确定性代码、人类只做批准与一行修正。它同时解决了三个用户关心的点——可审计性、构造性拒绝（隔离行 + 原因）、成本可控（4-7 次调用/$0.50）。对业务流程来说，这套模式可直接搬到单据/报表摄入。

Certified Hub：本体映射逐对认证不能组合，合并后才暴露 5 个类不可满足

2026-11-04 · arXiv (cs.AI / cs.LO)
国家级数字孪生被设想为通过映射连到共同基础的一群孪生，但路线图承诺"确认映射有效"却没说有效指什么。作者给出精确形式：合并本体的 coherence 与 conservativity（借自基于逻辑的对齐修复），并应用到 Information Exchange Standard（IES）——先逐对、再对整 hub。从 IES 到 7 个行业组 13 个本体的 crosswalk，以 BOT、Brick、SAREF4BLDG 为锚，经过匹配、人工评审、按两个类层次对每条 SKOS 对应做认证、再用 HermiT 推理。逐对看，各阶段抓不同失败：认证单独消除了原始 crosswalk 的全部 526 处 conservativity 违规（仅人工评审剩 73 处），二者合起来让 12 对中 11 对达一致且保守。但逐对认证不能组合：把三条已认证的建筑 crosswalk 合并成一个 hub 后，有 5 个 Brick 类变得不可满足，原因是 IES 与 Brick 对 floor 的同名不同义——只有 BOT 的 disjointness 公理能暴露这一点；删掉那一行即得一致且保守的 hub，并额外蕴含 290 条没人写过的跨本体链接。核心 hub 在加入任何 crosswalk 之前就已不一致，因为两份已发布标准（Open Energy Ontology 与 BFO 2020）互相矛盾；去掉任一份即一致且保守。结论：需要认证的单元是 hub，而不是 pair。
🔍 技术视角：这是"语义层 vs 企业知识图谱"路线之争里少见的一手证据：图谱路线的真实成本不在建模，而在合并后的逻辑一致性——而它只能在全量合并后才暴露。对自建业务知识库，实践含义是：不要把 crosswalk 当成两两对齐的体力活，必须建立"合并后推理检验"这一关卡（可满足性 + 保守性），并把它放进 CI。

MongoBench：能写出查询，不代表知道查询会做什么（自产题也错 10-31%）

2026-11-06 · arXiv (cs.DB / cs.CL)
LLM agent 越来越多直接操作数据库：自己写查询、自己执行。常见判定只有两条——查询是否合法、最终答案是否正确，但都不回答"agent 在执行前是否知道这条查询会做什么"。作者认为这种后果预测能力必须单独评测，于是构建 MongoBench：给定一组文档与一个 MongoDB find() 过滤条件，模型必须返回精确匹配的 _id 集合，ground truth 来自真实 mongod。300 道题每道组合三到四个有文档记载的匹配陷阱，并由三家厂商的模型对称出题，结果按出题来源分层。四个模型（三家前沿系统 + 一个开源权重推理模型）准确率在 70.1%-92.1%，跨度 22 个百分点；每个出题模型都会错自己写的题 10-31%，说明"能产出查询"不蕴含"能预测其效果"。失败模式分析显示，错误更好地由查询触及的语义陷阱（范围比较、null）预测，而不是文档数或规则组合数这类表层指标。预置一份已验证规则表帮助不均衡；把原始 filter 交给引擎执行能得到可靠匹配集，但委派必须校验：平均三次运行中，某个模型在 28% 的题目上执行的 filter 从未通过"与意图查询一致"的规范检查，并因此答错约 22 题，其余三个模型每题都通过。
🔍 技术视角：这是"宽表 API 精确查询"最容易踩的坑的镜像：Agent 能构造出合法调用，但对语义边界（null、范围、隐式类型转换）的预测能力远低于构造能力。工程上应把"执行前预测"作为一道独立关卡——尤其在写操作或高成本查询前，让 agent 先声明预期影响集/影响行数，再与真实执行比对，不一致就中止。
