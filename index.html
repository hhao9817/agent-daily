TMI：从计算机操作轨迹归纳符号化可审计任务模型

2026-08-20 · arXiv (2608.20319)
TMI（Task Model Induction）从被动录屏+键鼠的低级事件流，发现潜在任务并解耦并发活动（对受控人/agent 轨迹与真实标注 0.974 一致），再为每个潜在任务归纳一个任务模型：分层目标模型(递归 goal 分解)+过程模型(组织执行的控制流)。它重建 74.9% 观测执行步骤，远超最强 workflow induction 基线；导出的技能把 held-out 任务准确率提升 30.0%。作者强调这类符号化、可审计、可复用模型在 computer-use agent 进入真实工作时的价值——agent 需学任务实际如何执行，组织需审计并复用该知识。
🔍 技术视角：TMI 把"看人怎么做"变成"机器可读的任务模型"，是业务 Agent 从演示学习（learning from demonstration）的关键一环。对用户"让 AI 懂业务 API 调用"场景：可把业务人员操作宽表 API 系统的真实轨迹（点哪个字段、按什么顺序、填什么参数）录下来，TMI 归纳出"查这个业务指标的真实多步过程模型"——这比写文档更可信（来自实际执行而非人描述），且可审计（符号化可追溯）。30.0% 提升证明任务模型作为技能记忆比 step-level 摘要更强。与 8/22 MidTool（mid-training 学 tool-use）互补：MidTool 在训练层让模型懂 API 语义，TMI 在运行层从轨迹归纳任务过程，二者合起来覆盖"懂 API→懂业务任务过程"。

Pandora's Router：把异构 AI 路由建模为带成本检查的最优搜索

2026-08-20 · arXiv (2608.20316)
异构 AI 系统(多模型/架构/harness/推理设置)可路由查询给"最低成本最高效果"的专家以提质降本。但路由需估计每专家预期回报——廉价估计器(嵌入预测)快但噪，精确估计器(微调模型+检索/部分推理)贵但准。作者把它形式化为经典 Pandora's Box 问题（带成本检查的最优搜索），在高斯信号模型下给出闭式 value-of-information 表达式，决定"为某专家某输入是否值得花钱精化估计值"。Pandora's Router 匹配穷举估计的路由质量但远少调昂贵估计器；去中心化版 Pandora's Bidder 让专家独立决定是否投资自评再竞标接单。
🔍 技术视角：这是 Agent 调用业务 API/模型时"该用哪个专家"的理论最优解——不是简单按相似度路由，而是显式权衡"再查一步的边际信息价值 vs 其成本"。对用户"上百字段宽表 API"场景：不同业务查询可能需不同专家(简单聚合走小模型直查 API、复杂多跳走强模型+知识图谱)，Pandora's Router 给出"何时该为更准的估计付更多检索/推理成本"的量化判据。value-of-information 闭式表达意味着路由决策本身可审计可解释。

Break It Down：LLM Agent 跨任务技能迁移——子任务级+文本格式胜出

2026-08-20 · arXiv (2608.20274)
首次系统对照研究 LLM Agent 技能诱导方式如何影响跨任务迁移：沿现有方法差异的两轴——任务级 vs 子任务级诱导、文本 vs 代码技能格式。发现 task-level 技能多降低性能低于无记忆基线，subtask-level 平均提升；text 技能迁移优于 code。提出 skill utility score = specificity(技能与真实任务匹配度) × abstractness(相关性跨任务均匀度)，仅用技能与任务描述(无需执行)即可诊断技能记忆质量，subtask-level+text 技能得分更高。
🔍 技术视角：这是"业务 Agent 技能库该怎么建"的实证指南——按子任务粒度诱导、用文本格式存储，而非整任务级+代码。对用户业务知识库：把"查某业务指标"拆成子任务(选 API→填参数→校验结果→聚合)各自诱导技能，用文本描述而非硬编码，迁移更可靠。skill utility score 无需执行即可诊断技能质量，是技能库治理的实用工具——可在技能入库前预筛。

ClimbMix 投影：把 agentic 搜索评估迁到 400B-token 真实预训练语料

2026-08-20 · arXiv (2608.20317)
BrowseComp-Plus 用固定语料把 agentic 搜索评估从"不透明 web 搜索"解耦，但该语料仅约 10 万文档且按基准自身查询+硬负样本组装——证据和干扰都是按题配的。作者把问题迁移到 NVIDIA 400B-token/5.53 亿文档的 ClimbMix 预训练混合语料(不参照任何基准构建)。投影流水线：把每题分解为原子推理跳→在新语料逐跳落地→仅当自动验证+独立 agent+人工三重确认每跳有支撑才保留。830 题得 57 全锚定题。难度从答案层转到检索层(证据召回 84.3%→21.4%，搜索调用 +63%)。
🔍 技术视角：这是"业务 Agent 评估必须用真实分布语料而非为题配的语料"的方法学——为题配语料会高估检索能力。对用户：评估业务知识库 RAG 时，不能用"为测试题专门建的索引"，必须在真实业务文档分布上测。原子跳分解+三重确认的投影流水线可迁移为"业务知识库证据锚定"的治理流程——每条业务知识都应可分解为原子跳并在源文档落地验证。

8/22-23 三条独立来源同日指向业务 Agent 的三层正交能力：TMI(学术)从计算机操作轨迹归纳符号化可审计任务模型(学习层)+Pandora's Router(学术)把异构专家路由建模为带成本检查的 Pandora's Box 最优搜索(路由层)+SBproxy Cedar(工程)把治理决策从配置升级为可编译可审计的策略语言(治理层)。三层正交各司其职——学习层产任务模型、路由层按价值分配专家、治理层授权并审计每调用。与 8/19-22 已成型四层分工(记忆治理+约束建模+语义暴露+流量管控)精确映射。

TDS：无关 PDF 文件夹=一份带嵌套目录的长文档（Multi-Document RAG）

2026-08-22 · Towards Data Science (angela shi)
标准 RAG 多文档建议是"建索引：一文档一行、每可过滤字段一列、搜索前加 filter"。但该建议假设文档有共享字段。很多文件夹没有——如安全控制目录+零信任架构规格+AI 风险框架+31 篇 ML 论文+7 份商品市场报告，无客户/金额/生效日跨文档同义。无共享字段=无表可建。此时准备步骤塌缩为两件物：每文件一行摘要(写给路由器而非读者)+每文件自带目录表。两级路由(文件级→目录级)回答问题，嵌套大纲从不整块进 prompt。四种失效模式含"扁平文件列表不再扩展"。属 Enterprise Document Intelligence 系列第四部。
🔍 技术视角：这是用户业务知识库"上百字段宽表 API + 异构业务文档混存"的直接方法学。关键洞察"无共享字段=无需建索引"反直觉但正确——异构文档用嵌套目录+两级路由，而非强行建统一索引。每文件一行摘要"写给路由器而非读者"是关键设计原则：摘要要回答"这文件可能回答什么问题"而非"这文件讲什么"。两级路由避免把整个嵌套大纲塞进 prompt(噪音/上下文爆炸)。

⚙️ 核心机制

业务 Agent "任务建模→路由→治理"三件套同日成型

2026-08-23 · 综合研判（TMI + Pandora's Router + SBproxy Cedar）

📊 架构示意

🎯 为什么值得关注

业务 Agent 落地最缺的不是模型能力，而是运行时决策的可信链路——任务模型来源可靠吗、路由决策有量化依据吗、每次调用被授权且可审计吗。三件套分别回答这三个问题。

⚙️ 核心机制

学习层(TMI)：轨迹→任务模型→技能库(符号化可审计)；路由层(Pandora's Router)：查询→value-of-information 阈值→专家路由(闭式可审计)；治理层(SBproxy Cedar)：请求→Cedar 策略编译评估→allow/deny+审计日志(策略可编译可版本管理)。三者串联：任务模型触发查询→路由选专家→Cedar 授权→执行→全链审计。

🧠 深度解读

💼 商业启示

对业务 Agent 架构决策：三层正交意味着可分阶段独立投资——先建治理层(SBproxy Cedar，最低风险最高合规价值)→再建路由层(Pandora's Router，降本提质)→最后建学习层(TMI，知识资产化)。对投资：治理层是合规底线(必投)，路由层是成本优化(ROI 明确)，学习层是知识资产化(长期战略)。

🛠️ 落地建议

用户构建业务 Agent 运行时决策链：(1) 学习层——录业务人员操作宽表 API 轨迹，TMI 归纳任务模型作技能库种子，Break It Down 的 skill utility score 预筛入库；(2) 路由层——为每类业务查询定义候选专家(直查 API/小模型聚合/强模型多跳/知识图谱)，Pandora's Router 的 value-of-information 阈值决定何时升级估计；(3) 治理层——SBproxy Cedar 策略定义字段级授权+配额+护栏，编译验证后运行时审计每调用。三层串联构成"懂→选→治"闭环。

⚠️ 局限与风险

三层来自不同来源(学术+工程)，集成需自研胶水；TMI 受控轨迹验证非真实业务；Pandora 高斯信号模型假设可能不拟合；SBproxy Cedar 暂未接请求路径(独立单测)；三层均为 8/20-22 新发，生产成熟度待长周期验证。引用：TMI=0/infl0(已核实)，Pandora/Cedar 待核实(新发预期 0)。

SBproxy 8/22 八连发：Cedar 策略引擎 OSS 移植 + 九大 SOTA 网关子项

2026-08-22 · GitHub (soapbucket/sbproxy)

📊 架构示意

🎯 为什么值得关注

业务 Agent 调业务 API 必须有治理网关——否则任何 agent 可调任何 API 任何字段，无审计无配额无安全。Cedar 把治理从"配置"升级为"策略语言代码化"，治理规则可编译验证可版本管理可审计。

⚙️ 核心机制

Cedar 引擎：策略语言(类型化授权规则)→编译器(语法/类型/语义验证)→评估器(请求时按策略判定 allow/deny)→请求桥(把 HTTP/MCP 请求映射到 Cedar request 结构)→MCP hook(在 MCP 调用点拦截)。workspace override 合并+schema 演进检查支持策略灰度发布。九大网关子项：model groups(按模型分组路由)/deadlines(请求超时)/cache affinity(缓存亲和)/service tier(服务等级)/guardrail passthrough(护栏透传)/shadow eval(影子评估不阻断)/tenant key fallback(租户密钥兜底)。

🧠 深度解读

Cedar OSS 移植是治理代码化的关键一步——与 8/19 Policy Algebra 的"reliability as path property 9 维约束"共振：Policy Algebra 定义约束形式化，Cedar 是其可编译可执行的工程实现。shadow eval(影子评估)与 8/22 Pandora's Router 的"精确估计器"共振——影子评估是非阻断的精确估计，用于路由决策优化而不阻断主路径。bundle 候选不泄漏 live secret 与 MCP 配额上界是供应链安全与资源治理，与 8/16 SBproxy 历史版本 tool-call mutation refused 一脉相承。

💼 商业启示

对治理投资决策：Cedar 策略引擎把治理从"人审每次调用"升级为"策略编译期验证+运行时自动审计"，大幅降低治理人力成本且更可靠。对产品：治理网关是业务 Agent 平台的必备组件，SBproxy 的 OSS Cedar 是经济起点。shadow eval 提供"非阻断评估"能力，支持路由优化而不影响线上。

🛠️ 落地建议
